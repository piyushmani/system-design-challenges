Liam's Flash Sale Dilemma: Scaling Up vs. Sharding Out

Liam is a backend engineer at an online retailer. During flash sales the inventory service jumps from 200 to 10k requests per second, saturating the primary SQL database's I/O and CPU. This causes write latency spikes and intermittent overselling despite heavy index tuning. The current setup is a monolith with a single primary writer, several read replicas and a Redis cache for queries. He must choose an architecture that eliminates oversells, fixes backend latency and reliably absorbs sudden, massive traffic spikes.

A
Scale the primary database vertically (more CPU, memory and faster storage), raise connection pool limits and tune indexes further. Keep the single-writer architecture and rely on application-layer autoscaling.
✗ Not Best
B
Keep the single-writer database but add more read replicas and a larger Redis cache. Move reporting and read queries to replicas and cache, while writes still go synchronously to the primary.
✗ Not Best
C
Shard the inventory write domain horizontally by product ID and make the service partition-aware and stateless. Route writes to the right shard so app instances and shards scale horizontally. Keep strong consistency within each shard and use read replicas or async replication for read-heavy traffic per shard.
✓ Best Answer
D
Move to an eventually consistent, asynchronous write approach: process inventory decrements through a fast queue, apply the actual database updates with background workers and resolve conflicts later with compensating actions (CQRS and eventual consistency).
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — C: Shard Inventory Writes by Product ID

Option C is the best fit. The bottleneck is a single writer that every stock decrement must pass through. Sharding the write domain by product id gives each product exactly one authoritative owner, so a strongly consistent decrement stays simple and oversells can be prevented, while write capacity grows with the number of shards. Here's why it stands out:

  • Attacks the real bottleneck: indexes, replicas and caches all help reads, but the saturated resource is write I/O and CPU on one primary. Splitting writes across shards scales exactly that resource horizontally.
  • Overselling is prevented per product: all decrements for a product land on one shard leader, so a conditional update such as UPDATE inventory SET available = available - qty WHERE sku = ? AND available >= qty is atomic and can never go negative.
  • No distributed transaction on the hot path: a single-item reservation touches one shard, so strong consistency is local and there is no cross-node coordination cost.
  • Stateless, partition-aware service: app instances hold no stock state and can autoscale freely. A routing layer (hash or directory) maps each product to its shard.
  • Reads still scale: each shard can have its own replicas and cache for display data such as in-stock badges, while the authoritative decrement stays on the leader.
  • Failure isolation: a hot or failing shard affects only its own products, not the whole catalog.

Pair the sharded design with an atomic conditional decrement, reservations with expiry, an admission gate for hot SKUs and load tests that replay flash-sale traffic. Track the oversell count (target zero), per-shard write latency and lock wait time.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🏋️

A — Scale Up Vertically

A bigger primary buys headroom but has a hard ceiling and stays a single point of contention. A 10k RPS spike on a hot SKU can saturate even a very large node, and cost grows faster than capacity. It also does nothing about overselling if the decrement logic is racy. Caveat: as a short-term step before the next sale it is cheap and reversible, so it is a sensible stopgap, but not an architecture.

📚

B — More Replicas and a Bigger Cache

This helps reads, but the pain described is write saturation. Replicas lag, so stock decisions made from a replica or cache can be stale and make overselling worse during a spike. Cached counts that drift from the database become a second source of truth. Caveat: offloading reads is still good hygiene for browse and reporting traffic.

📬

D — Async Queue with Eventual Consistency

Acknowledging a decrement before the database applies it means the system can accept more orders than stock exists and then has to cancel or apologize through compensations. That directly contradicts the goal of eliminating oversells. Queues smooth write bursts well, but the authoritative stock check must happen before the customer is told yes. Caveat: a queue that serializes decrements per SKU and returns the real outcome to the caller can be strongly consistent, but that is not the fire-and-compensate design described. Businesses that accept occasional oversells and offer backorders may choose this on purpose.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Scale Up Vertically

A quick, reversible stopgap before the next event, or when growth is moderate and the bottleneck is raw CPU or I/O rather than lock contention.

📌

B — More Replicas and Cache

Read-dominated overload such as browsing, search and reporting. Not for write saturation or stock decisions.

📌

C — Shard by Product ID

Write saturation on a single primary where strong per-item consistency is required and the data partitions cleanly by product.

📌

D — Async Queue + Compensation

Stock is advisory or backorders are allowed, such as pre-orders or effectively unlimited digital goods, and absorbing peaks matters more than strict correctness.

⚠️ Common Mistakes to Avoid

  • Check-then-act on stock: reading the available quantity and then updating it lets concurrent requests all pass the check. Use a conditional update and check the affected row count.
  • Deciding from replica or cache stock: both can be stale during a spike. Only the authoritative store may say yes.
  • Sharding without addressing the hot SKU: one popular product still maps to one shard and one hot row.
  • Reservations without expiry: abandoned carts lock stock forever. Release automatically with a TTL.
  • Long transactions across payment calls: holding row locks while waiting for a payment provider serializes everything behind one slow call.
  • Never load-testing a realistic spike: the first real flash sale becomes the test.

🌍 Real-World Best Practice

In practice, teams fix correctness first, then control demand, and only then scale the write path. A typical sequence looks like this:

  • Step 0 — Fix correctness first: use an atomic conditional decrement, one unique reservation per order and SKU, and never trust a cache or replica for the final decision.
  • Step 1 — Reservation model: reserve with a TTL, confirm on payment and release on timeout. It is cheaper than rolling back confirmed orders.
  • Step 2 — Admission control: a waiting room, per-user and global rate limits, and an optional atomic counter gate in Redis. The database stays authoritative.
  • Step 3 — Shard by product id: partition-aware stateless services, a shard map and high availability per shard.
  • Step 4 — Hot-SKU strategy: bucketed stock or a per-SKU serialized processor for the few extreme items.
  • Step 5 — Reads: show stock from replicas and cache labeled as approximate, and re-check at checkout.
  • Step 6 — Load testing and autoscaling: replay a flash-sale traffic profile, alert on lock wait and p99 latency, and practice shard failover.

Scale out only after the decrement logic is provably safe, otherwise you will oversell faster on more hardware.

💡

Key Takeaway

Overselling is a consistency problem and latency spikes are a write-capacity problem. Give every product a single authoritative owner with an atomic conditional decrement, partition the write domain so capacity scales horizontally, and protect hot SKUs with admission control. Vertical scaling and read offloading only buy time, and fire-and-compensate trades correctness for throughput.
