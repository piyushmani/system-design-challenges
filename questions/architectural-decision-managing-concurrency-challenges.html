Architectural Decision: Managing Concurrency Challenges

Alex is building an application that must absorb a massive number of simultaneous user requests while preserving strict data consistency (no lost updates, no invalid states) and keeping throughput as high as possible. The data lives in a transactional datastore that supports atomic conditional writes, requests mostly touch many different records, and two requests rarely update the same record at the same moment (low to moderate contention). Operations are short, so retrying a rejected one is cheap. Alex must choose the concurrency strategy.

A
Use a locking synchronization approach to guarantee consistency, even if it creates bottlenecks.

✓ Best Answer
C

✗ Not Best

Answer & In-Depth Explanation

🏆 Best Answer — B: Version-Based Optimistic Concurrency

Optimistic concurrency control (OCC) with a version check is the best fit. Requests proceed in parallel without holding locks, and each write includes the version it read. The database applies the write only if the version is unchanged; if another request got there first, the write is rejected and retried. No update is ever silently lost, so consistency stays strict, while the common no-conflict case runs at full speed. Here's why it stands out:

  • Consistency is preserved: The conditional write (UPDATE ... WHERE id = ? AND version = ?) is atomic, so conflicting writers cannot both succeed. A losing writer must re-read and retry, which yields the same end state as running the two updates one after the other.
  • No blocking on the common path: Readers and writers do not wait for locks, so there are no lock queues, convoy effects or deadlocks on uncontended records, and throughput scales with the number of concurrent requests.
  • Cheap to implement and operate: A version column (or an ETag, or a conditional write in a key-value store) is enough. There is no lock service to run and no lock-expiry logic to get wrong.
  • Works across stateless instances: Because the check lives in the datastore, any application server can apply it, which fits horizontally scaled services.
  • Why not locking first? Locks guarantee consistency too, but they serialize access, hold resources while waiting and risk deadlocks. When conflicts are rare, that cost buys almost nothing.
  • Broad adoption: JPA and Hibernate @Version, HTTP ETag with If-Match, DynamoDB conditional writes and compare-and-swap loops in lock-free data structures all use the same idea.

A solid implementation uses an atomic conditional write, bounded retries with jittered backoff, side effects after commit, and a fallback to pessimistic locking or per-key serialization for hot records. Track the conflict rate and retry count: a rising conflict rate is the signal that contention has outgrown OCC.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🔒

A — Locking

Locks provide strong consistency, but threads or transactions wait in line, so throughput falls as concurrency rises, and lock-ordering mistakes lead to deadlocks. The requirement is maximum throughput, and locking everything uniformly makes that impossible. Caveat: pessimistic locks (for example SELECT ... FOR UPDATE) are the right tool for genuinely hot records where optimistic retries would thrash.

📨

C — Event-Driven Async Queues

Queues decouple producers from consumers and scale well, but this option explicitly trades away strict consistency: state is updated later, readers can see stale data, and the caller does not get an immediate, consistent answer. That conflicts with the stated requirement. Caveat: routing writes for one key through a partitioned queue (a single-writer-per-key design) can deliver consistency and throughput for hot keys, at the cost of latency and complexity.

🌐

D — Distributed Locking

A distributed lock (Redis, ZooKeeper, etcd) coordinates access across nodes but adds a network round trip to every operation, a new failure mode (lock service outage, expired leases) and subtle correctness hazards: a paused client can act after its lease expired, so safe use requires fencing tokens. It increases both latency and complexity compared with a conditional write in the datastore. Caveat: it is justified when the protected resource has no atomic conditional operation of its own, such as coordinating work across external systems.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Locking

Contention is high on specific records, critical sections are short, and the lock can be held in the same database (for example SELECT ... FOR UPDATE on account rows).

📌

B — Optimistic Concurrency

Many requests touch different records, conflicts are rare, and operations are short enough that a retry is cheap: typical CRUD, profile edits, document updates and cart updates.

📌

C — Async Queues

Work that tolerates delay and eventual consistency: notifications, analytics, fan-out, background processing, or per-key serialization for hot entities.

📌

D — Distributed Locking

Coordinating exclusive access to a resource that has no atomic conditional operation of its own (leader election, singleton scheduled jobs, external system access), with fencing tokens and short leases.

⚠️ Common Mistakes to Avoid

  • Check-then-write without atomicity: Reading the version in one step and updating in another allows a race. The version comparison must be part of the same atomic write (WHERE version = ?), and you must check the affected-row count.
  • Unbounded immediate retries: Under contention, tight retry loops amplify load. Cap attempts and add jittered backoff.
  • Using OCC on hot rows: A single counter updated by thousands of requests will mostly fail. Use atomic increments, row locks or sharded counters.
  • Side effects before commit: Sending notifications or charging payments inside the retry loop repeats them. Perform side effects after a successful commit (or via an outbox).
  • Ignoring write skew: Per-row versions do not protect rules that span multiple rows. Use serializable isolation or lock and verify the full set.
  • Swallowing conflicts: Dropping a failed update silently loses user intent. Surface a conflict (409 or 412) or merge deliberately.

🌍 Real-World Best Practice

In practice, systems pick the concurrency mechanism per workload and per record type rather than one mechanism for everything. A typical sequence looks like this:

  • Step 0 — Measure contention: Find which records are hot and how often two writers collide. The contention rate drives the choice.
  • Step 1 — Optimistic version checks by default: Add a version column or use conditional writes for ordinary entities (the best fit for this scenario).
  • Step 2 — Atomic operations where possible: Use UPDATE ... SET qty = qty - 1 WHERE qty > 0 or atomic increments instead of read-modify-write cycles.
  • Step 3 — Pessimistic locks or single-writer partitions for hot rows: Counters, the stock of a hot SKU, or balances under heavy contention.
  • Step 4 — Queues for work that tolerates delay: Offload non-critical, order-insensitive work to asynchronous processing, keeping the strongly consistent core small.
  • Step 5 — Distributed locks only when nothing else works: Use fencing tokens, short leases and a design that stays correct even if the lock is lost.

Default to the cheapest mechanism that preserves the invariant, and escalate only where measurements show conflicts.

💡

Key Takeaway

When you need strict consistency and maximum throughput and conflicts are uncommon, use version-based optimistic concurrency: parallel, lock-free execution with an atomic conflict check and retry. Escalate to pessimistic locks or per-key serialization for hot records, and treat queues and distributed locks as special-purpose tools rather than the default.
