Choosing a Change Data Capture (CDC) Strategy for Postgres at Tens of Thousands of Writes per Second

Maya, a backend developer, must keep downstream systems (an analytics warehouse, a search index, and several microservices) synchronized with a core Postgres database that takes tens of thousands of writes per second. The pipeline must preserve per-entity ordering, survive schema changes, expose lag and health metrics, and recover from broker or consumer crashes without losing or double-applying critical events. Adding query load to the primary, or modifying every write path in every application, is unacceptable. She needs the CDC architecture that best balances consistency, availability, latency, scalability, and operational overhead.

Synchronous distributed transactions: write to Postgres and the message broker in one two-phase commit (XA) transaction so downstream consumers see changes immediately.

B
Polling-based incremental queries: worker nodes poll tables by increasing ID or updated_at, compute row diffs, and emit events to a queue, with checkpoints for recovery.

Answer & In-Depth Explanation

🏆 Best Answer — C: Log-Based CDC to a Durable Broker

Reading the Postgres write-ahead log (WAL) through logical decoding captures every committed change in commit order, with no changes to application code and almost no extra query load on the primary. Streaming those events into a partitioned, durable log keyed by primary key gives per-entity ordering, independent consumer scaling, and replay. It is the only option that satisfies ordering, crash recovery, schema evolution, and low source impact at the same time. Here's why it stands out:

  • Ordering by construction: The WAL is already the database's serialized, commit-ordered history. Keying events by primary key sends all changes for one entity to one partition, so consumers see them in order.
  • Minimal load on the primary: Decoding reads the WAL stream instead of running repeated scans against hot tables. The cost is mostly one replication slot and some WAL retention, not extra queries.
  • Crash recovery and replay: The connector stores its position (LSN) in Kafka Connect offsets, and consumers track their own offsets. After a crash each side resumes from its last committed position, and the retained log supports backfills and rebuilding a search index or warehouse table.
  • Schema evolution: A schema registry (Avro, Protobuf, or JSON Schema) with compatibility rules lets producers and consumers evolve independently, and DDL changes arrive as schema updates instead of silently breaking a polling query.
  • Widely proven pattern: Debezium with Kafka Connect and Kafka is a common open-source CDC stack, and managed offerings (for example AWS DMS or Google Datastream) use the same log-based approach.

A production-grade design pairs Debezium (or equivalent) with the primary key as the event key, a schema registry with backward-compatible evolution, idempotent sinks, and monitoring of slot lag, connector status, and consumer lag. If you also need domain events rather than raw table changes, add a transactional outbox table and capture it with the same connector.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🔒

A — Synchronous Distributed Transactions (2PC/XA)

Two-phase commit couples the availability of Postgres and the broker: if either is slow or down, writes stall, and in-doubt transactions hold locks until a coordinator recovers. At tens of thousands of writes per second this caps throughput and adds latency to every request. It also forces changes in every writer, and most brokers, Kafka included, do not participate in XA transactions. Caveat: it only looks attractive in small systems that need atomic cross-resource writes and can accept the availability cost; the usual modern answer is an outbox instead.

🔁

B — Polling-Based Incremental Queries

Polling by updated_at or ID is simple, but it misses hard deletes, can skip rows when long-running transactions commit after the checkpoint has already moved past their timestamps, and adds repeated read load on the primary exactly at peak. Latency equals the polling interval, and computing diffs per table is expensive. Caveat: acceptable for low-volume, delete-free tables where minutes of lag are fine.

🪝

D — Database Triggers and Webhooks

Triggers run inside each write transaction, so they add latency and lock contention on the hot path, and synchronous HTTP calls from a trigger tie database availability to an external endpoint. Webhooks give no durable replay or ordering guarantee. An outbox table is a sound building block, but at this write rate it roughly doubles write volume and still needs a relay, which is effectively CDC. Caveat: an outbox captured through log-based CDC is great; triggers that call HTTP directly are not.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Distributed Transactions (2PC)

Small, low-throughput systems that need atomic writes across two transactional resources and can accept availability coupling. Most modern designs prefer an outbox instead.

📌

B — Polling

Low-volume, append-only or soft-delete tables where minutes of lag are fine, or where logical decoding is not available (some managed or legacy databases).

📌

C — Log-Based CDC

High-volume OLTP databases that feed several downstream systems and need ordering, replay, schema evolution, and minimal impact on the primary.

📌

D — Triggers / Webhooks

Small audit or notification needs on a few tables, or as the mechanism that writes an outbox table which is then captured by log-based CDC.

⚠️ Common Mistakes to Avoid

  • Ignoring replication-slot lag: An unattended slot retains WAL until the disk fills and takes the primary down. Alert on retained WAL and cap it with max_slot_wal_keep_size.
  • Assuming exactly-once end to end: Kafka transactions do not extend to your warehouse or search index. Make sinks idempotent with an upsert guarded by version or LSN.
  • Keying by the wrong field: Anything other than the entity's primary key breaks per-entity ordering, and changing partition counts later reshuffles keys.
  • Forgetting TOAST and replica identity: With default settings, updates may omit unchanged large columns or old row images, so consumers cannot rebuild full rows. Choose REPLICA IDENTITY deliberately and handle unchanged-TOAST placeholders.
  • Treating schema changes as an afterthought: Incompatible DDL breaks consumers. Use a schema registry with compatibility checks and coordinate migrations.
  • No plan for failover or re-snapshot: Depending on version and setup, a Postgres failover can lose slot state and force a resync. Know the procedure before you need it, and keep topic retention long enough to replay.

🌍 Real-World Best Practice

In practice, teams combine log-based CDC with a few supporting patterns, and they rehearse failure recovery before going live. A typical rollout looks like this:

  • Step 0 — Check prerequisites: Set wal_level=logical, size max_replication_slots, choose REPLICA IDENTITY per table, and confirm the slot behavior during a Postgres failover.
  • Step 1 — Snapshot, then stream: Take a consistent initial (or incremental) snapshot of existing data, then continue from the recorded LSN with no gap.
  • Step 2 — Key and partition correctly: Use the primary key as the Kafka key and pick a partition count for peak consumer parallelism, since it is hard to change later.
  • Step 3 — Govern schemas: Register schemas, enforce backward compatibility, and treat DDL as a reviewed change.
  • Step 4 — Make sinks idempotent: Upsert by key with a version or LSN guard, and route poison messages to a dead-letter topic.
  • Step 5 — Observe and rehearse: Alert on slot lag, connector failures, and consumer lag, and rehearse broker, connector, and consumer crashes plus a full replay.

Add the outbox pattern when you need domain events rather than raw table changes.

💡

Key Takeaway

For high-volume Postgres, read the transaction log instead of the tables. Log-based CDC into a durable, partitioned broker gives ordering, replay, and low source impact. Pair it with schema governance and idempotent sinks, and watch replication-slot lag so the pipeline never endangers the primary.
