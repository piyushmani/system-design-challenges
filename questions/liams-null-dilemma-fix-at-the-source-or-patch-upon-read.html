Liam's NULL Dilemma: Fix at the Source or Patch upon Read?

Liam, a backend engineer, owns an event-driven Orders service consumed by many downstream microservices. Older records have accumulated NULLs in columns such as promo_code, billing_country, and customer_tier. Some materialized views and reports use COALESCE(column, 'DEFAULT'), while other consumers apply their own defaults, so the same order can mean different things to different services. The stack is a sharded PostgreSQL OLTP database, Kafka for events, and Redis caching, handling thousands of writes per second. For the fields the business treats as required (every order has a billing country and a tier), the NULLs are a data-quality defect rather than a meaningful state. He must choose a long-term strategy for NULLs and defaults that balances consistency, latency, operational overhead, observability, availability, and scalability.

A
Keep the schema and producers unchanged and mandate COALESCE in every materialized view and read query as the standard normalization.
✗ Not Best
B
Normalize at the API boundary: add a stream processor or gateway that converts NULLs to defaults for all downstream clients, leaving producers and the database schema unmodified.
✗ Not Best
C
Make defaults first-class: add NOT NULL and DEFAULT constraints where appropriate, backfill historical rows in a coordinated background job, enforce producer-side validation (contract checks and a schema registry), and use COALESCE only as a temporary compatibility measure.
✓ Best Answer
D
Let each microservice default values locally, keep the schema nullable, and rely on service-specific logic plus asynchronous cleanup jobs to slowly backfill the data.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — C: Fix at the Source with Constraints and Contracts

NULLs here are a symptom of a missing contract. Every read-side workaround (COALESCE, gateway rewriting, per-service defaults) spreads the same decision across many places, and each copy can drift. Moving the rule into the schema, the event contract, and a one-time backfill makes it a single source of truth. Here's why it stands out:

  • One definition of 'missing': A database constraint plus a schema-registry contract means producers cannot emit NULL for required fields, so every consumer (current and future) sees the same data with no per-consumer logic.
  • Removes read-time cost and risk: No more wrapping columns in COALESCE in views, which is easy to forget in a new query and can prevent index use when the wrapped column is filtered or joined on.
  • Safe on a hot, sharded system when done in phases: Adding a DEFAULT is a metadata-only change, a CHECK ... NOT VALID constraint does not scan the table when added, VALIDATE CONSTRAINT does not block reads or writes, and the backfill runs in small throttled batches.
  • Observability improves: Producer-side validation turns bad data into a counted, alertable rejection at the source instead of a silent NULL discovered in a dashboard weeks later.
  • Backward-compatible rollout: COALESCE stays in place until the backfill is verified, so downstream consumers never break while the contract tightens (expand, migrate, contract).

A well-run migration follows expand → backfill → validate → enforce → contract: add defaults, deploy validating producers, backfill in batches, add a NOT VALID check, validate it, set NOT NULL, and only then remove COALESCE. Track NULL counts per column, producer rejection rate, and replica lag throughout.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🩹

A — COALESCE Everywhere

COALESCE is cheap per query, but the rule lives in every consumer, so each new view, report, or ad-hoc query is a chance to forget it or pick a different default. It can also defeat index usage when it wraps a filtered or joined column, and it never fixes the data. Caveat: it is exactly the right tool as a temporary compatibility layer during the migration, which is how the best answer uses it.

🚪

B — Normalize at the API Gateway or Stream Processor

A normalization tier centralizes the rule only for the clients that go through it. The database and Kafka topics still contain NULLs, so CDC consumers, analytics jobs, and admin tools that read them directly bypass it. It also adds a hop, another component to scale and monitor, and a new place where the contract can drift from the schema.

🧩

D — Per-Service Defaults + Slow Async Cleanup

Each team implements its own defaulting, so services can disagree about the same order (one treats a NULL tier as 'standard', another as 'unknown'). Eventual cleanup without a central contract has no completion criterion and no enforcement, so new NULLs keep arriving. This has the highest long-term operational and debugging cost.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — COALESCE Everywhere

Short-term compatibility while a migration is in flight, or read-only reporting on data you do not own and cannot fix.

📌

B — Gateway / Stream Normalization

A legacy estate where you cannot change producers or the schema yet and every consumer can be routed through one tier.

📌

C — Constraints + Contracts + Backfill

You own the service and schema, many consumers depend on the data, and required fields should be reliable everywhere (this scenario).

📌

D — Per-Service Defaults

Truly service-specific interpretations (a UI-only display default) where a wrong default has no cross-service impact.

⚠️ Common Mistakes to Avoid

  • Running ALTER TABLE ... SET NOT NULL directly on a big table: It holds a strong lock while it scans. Add a CHECK ... NOT VALID, validate it, then set NOT NULL (on PostgreSQL 12+ the validated check lets the scan be skipped).
  • One giant UPDATE for the backfill: It bloats the table, spikes WAL, lags replicas, and holds locks. Use small keyset-paginated batches with pauses tied to replica lag.
  • Tightening before producers and backfill are ready: A stricter schema fails writes in production, and a NOT VALID check is still enforced on updates, so touching an old row that still has a NULL fails. Deploy validating producers and backfill first, then add the constraint.
  • Replacing meaningful NULLs with magic strings: If NULL means 'not applicable', a sentinel like 'N/A' leaks into joins and reports. Model absence explicitly or keep the column nullable.
  • Breaking consumers with an incompatible schema change: Use registry compatibility rules (for example backward-compatible changes with defaults) and migrate consumers before removing old fields.
  • Forgetting derived stores: Redis caches, materialized views, and search indexes keep the old NULL-bearing shapes until refreshed. Include them in the cutover plan.

🌍 Real-World Best Practice

In practice, teams treat this as a staged data-contract migration, not a single change. A typical sequence:

  • Step 0 — Measure and define: Count NULLs per column and per producer, and decide with the business what each NULL means (missing, not applicable, or unknown).
  • Step 1 — Expand: Add DEFAULT values (metadata-only) and register the stricter schema in the registry, with required fields and defaults in a backward-compatible form.
  • Step 2 — Enforce at the source: Deploy producers that validate against the contract and emit metrics on rejections, so no new bad data arrives.
  • Step 3 — Backfill: Run throttled, idempotent, keyset-paginated updates per shard, pausing when replica lag rises.
  • Step 4 — Validate and tighten: Add the CHECK ... NOT VALID constraint, sweep stragglers, run VALIDATE CONSTRAINT, then SET NOT NULL. Rebuild or refresh materialized views and caches from clean data.
  • Step 5 — Contract: Remove COALESCE shims and per-service defaulting once metrics show zero NULLs for a full retention window.

Treat the data contract as the product: schema, registry, and constraints should all say the same thing.

💡

Key Takeaway

Handle missing values once, at the source: constraints in the database, validation at producers, a throttled backfill for history, and COALESCE only as a temporary bridge. Read-side patches spread the rule everywhere and never fix the data.
