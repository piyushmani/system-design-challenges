Challenge

Diego's CDC architecture: low-latency streaming feeds vs. database-level triggers

Diego must build a Change Data Capture pipeline for an e-commerce system whose customer profiles, inventory and orders live in PostgreSQL. Downstream consumers include a cache for faster reads, a search index that needs near-real-time updates, and analytics pipelines that need both live streams and historical replay. Changes must propagate in milliseconds to under a second, survive spikes of tens of thousands of writes per minute, keep ordering per aggregate (such as order id), support backfills and replays, accommodate schema changes and add minimal overhead to the primary database.

A
Use a log-based CDC tool (pg_logical or Debezium) to read the Write-Ahead Log and emit change events to a durable message bus such as Kafka, partitioned by primary key, with schemas in a registry. Downstream systems (Flink, Kafka Streams) handle idempotency, transformation and ingestion into cache, search and analytics, relying on Kafka consumer groups and durability for recovery and scaling.
✓ Best Answer
B
Use synchronous database triggers that call an RPC or HTTP microservice for every modified row. The service forwards the event to the cache, analytics and search targets so propagation is near-instant and downstream updates complete before the transaction's effects become visible.
✗ Not Best
C
Run periodic batch polling jobs that extract timestamp-based diffs or snapshots every few seconds to minutes, compute deltas and bulk-write to downstream services. Tune the polling interval to balance latency against database load and deduplicate during ingestion.
✗ Not Best
D
Deploy a dedicated logical read replica and run a custom process that tails its WAL, decodes the logical changes and streams them to consumers. Build custom logic for replica failover, offset tracking, schema change detection and replays.

Answer & In-Depth Explanation

🏆 Best Answer — A: Log-Based CDC to Kafka (Debezium)

Option A is the best fit. Log-based CDC reads committed changes from PostgreSQL's write-ahead log, so it adds almost no load to the primary, captures every insert, update and delete in commit order, and publishes them to a durable, partitioned log that any number of consumers can read, replay and scale independently. Here's why it stands out:

  • Minimal primary overhead: logical decoding reads the WAL that the database already writes. There are no triggers, no extra queries and no polling load on the tables.
  • Complete and ordered: every committed change, including hard deletes, appears in commit order. Keying Kafka messages by primary key (for example order_id) preserves per-aggregate order within a partition.
  • Sub-second propagation: events stream as the WAL is written, so typical lag is milliseconds to low seconds. Tens of thousands of writes per minute is only a few hundred per second, well within a single connector's capacity.
  • One stream, many consumers: the cache, search index and analytics each use their own consumer group and offsets. Kafka retention plus initial snapshots support replay and backfills by resetting offsets or re-snapshotting.
  • Schema evolution handled: a schema registry (Avro or Protobuf) with compatibility rules lets producers and consumers evolve independently, and Debezium tracks DDL changes in the stream.
  • Built-in recovery: the connector stores its WAL position in Kafka Connect offsets and uses a replication slot, so it resumes after a restart without loss. Snapshots bootstrap new consumers.
  • Proven components: Debezium and Kafka Connect already cover snapshotting, schema changes, heartbeats and failure handling that a custom tool would have to rebuild.

Use log-based CDC, key by primary key, a schema registry, idempotent consumers and alerts on replication-slot lag and connector status. Measure end-to-end lag from commit time to consumer apply time.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🪝

B — Synchronous Triggers Calling a Service

Triggers run inside the writing transaction, so every insert or update waits on a network call. A slow or failing service slows or aborts business transactions and holds locks longer, which puts the primary at risk during write spikes. It also cannot be atomic: if the transaction rolls back after the trigger called out, downstream systems have received a change that never happened, and a downstream failure leaves no replayable record. Ordering and backfill remain unsolved. Caveat: a trigger that only writes to a local outbox table in the same transaction is safe and is the basis of the outbox pattern.

⏱️

C — Periodic Batch Polling

Polling by timestamp or snapshot diff runs queries against the primary on every interval, and tightening the interval raises the load. It misses hard deletes unless rows are soft-deleted, and it can miss rows when a long transaction commits with an older timestamp than rows already polled. Latency is seconds to minutes, not sub-second. Caveat: polling is acceptable for low-frequency analytics refreshes that tolerate minutes of delay, or when WAL access is not available.

🛠️

D — Custom WAL Tailing on a Logical Replica

Moving decoding to a replica sounds protective, but decoding on the primary is lightweight and the real work is the plumbing: offset tracking, slot failover, schema change detection, snapshots and replay all become your code. Logical decoding directly on a physical standby only arrived in PostgreSQL 16, and replication-slot failover support in 17, so older versions are even more limited. You would be rebuilding Debezium with fewer features and more risk.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Log-Based CDC + Kafka

Several consumers, ordering per key, replay and backfill needs, schema evolution and sub-second lag targets with minimal load on the primary. This matches Diego's case.

📌

B — Synchronous Triggers

Only to write into a local outbox or audit table within the same transaction. Not for calling external services from inside the database.

📌

C — Batch Polling

Small, low-frequency syncs that tolerate minutes of delay, or sources where log access is unavailable, such as restricted managed databases or legacy systems.

📌

D — Custom WAL Tailing on Replica

Rare cases where existing tools cannot run and a team can own failover, offsets and schema handling. Prefer managed or off-the-shelf CDC first.

⚠️ Common Mistakes to Avoid

  • Ignoring replication slot growth: a stalled connector makes PostgreSQL keep WAL indefinitely until the disk fills. Alert on slot lag and cap retained WAL.
  • Non-idempotent consumers: at-least-once delivery means duplicates after restarts and rebalances. Upsert by version rather than blindly inserting.
  • Partitioning by anything other than the aggregate key: events for one order then land in different partitions and arrive out of order.
  • Assuming updates and deletes include old values: with the default replica identity, before-images contain only key columns. Set it deliberately.
  • Exposing raw table schemas as the public contract: every internal column rename becomes a breaking change for consumers.
  • No bootstrap plan: a new consumer needs a snapshot or a compacted topic, not just the stream from now on.
  • Treating CDC lag as zero: measure commit-to-apply lag and design consumers for brief staleness.

🌍 Real-World Best Practice

In practice, teams settle the ordering key, delete handling and replay horizon before touching the database. A typical sequence looks like this:

  • Step 0 — Capture requirements: lag target, ordering key, delete semantics, retention and replay horizon.
  • Step 1 — Prepare PostgreSQL: wal_level=logical, a publication for the needed tables, the right replica identity, slot monitoring and a WAL retention limit.
  • Step 2 — Deploy the connector: Debezium with an initial snapshot, heartbeats, one topic per table, messages keyed by primary key and Avro or Protobuf with a registry.
  • Step 3 — Partitioning and retention: size partitions for consumer parallelism, use compaction for current-state topics and long retention for history.
  • Step 4 — Idempotent consumers: upsert by version, handle deletes and tombstones, and send poison events to a DLQ.
  • Step 5 — Business events via outbox: when consumers need domain events instead of row changes, publish them through an outbox table.
  • Step 6 — Observability: end-to-end lag, slot lag, connector status and consumer lag, with runbooks for re-snapshot and replay.

Use CDC for state replication and the outbox pattern for business events.

💡

Key Takeaway

To feed many consumers with ordered, replayable changes at low latency, read the database's own log instead of adding work to transactions or polling tables. Log-based CDC into a durable partitioned log gives low overhead, ordering by key, replay and schema handling, but it must be operated carefully, especially replication slots and idempotent consumers.
