Enhancing Cache Performance in Scalable Systems

Sara, a software engineer at an expanding e-commerce business, is dealing with a cache that is losing effectiveness as the platform grows. The system relies heavily on Redis to cache frequently requested data, but the hit ratio keeps declining. Her investigation shows the Redis instances are running at their memory limit, the evicted_keys counter keeps climbing, and a large share of memory is held by long-lived entries that are rarely read again (old catalog variants, expired promotions, one-off lookups), while the truly hot set is still smaller than one node's memory. She must determine the most effective strategy to boost the cache hit rate.

A
Deploy a CDN to serve static assets, thereby lessening the burden on the Redis cache.
✗ Not Best
B
Implement a cache eviction policy to remove outdated information and free up space for fresh data.
✓ Best Answer
C
Apply a sharding approach to divide the cache and spread the data out among several Redis nodes.
✗ Not Best
D
Adopt a write-through caching model that instantly updates the cache whenever database modifications occur.
✗ Not Best

Answer & In-Depth Explanation

🏆 Best Answer — B: Cache Eviction Policy (with TTL Discipline)

A cache's hit ratio is determined by how well its limited memory is filled with data that will be read again. When memory is full, the eviction policy decides which entries are sacrificed, so a poor policy (or none) fills the cache with cold or stale data and pushes out hot data, which is exactly the symptom of a declining hit ratio. A frequency- or recency-aware eviction policy (in Redis, allkeys-lfu or allkeys-lru) combined with sensible TTLs makes the cache prune itself toward the hot set. Here's why it stands out:

  • Targets the cause: Hit ratio rises when hot items stay resident, and eviction decides residency. It acts on what is kept, whereas the other options address static assets, capacity or freshness.
  • Cheap, fast and reversible: It is a configuration change (maxmemory-policy) plus a TTL review, with no data migration, and can be rolled out and measured within hours.
  • LFU resists scan pollution: A burst of one-off keys (a crawler, a bulk job) can flush an LRU cache, while LFU keeps frequently used keys resident. Redis has supported allkeys-lfu since version 4.0.
  • The default deserves a deliberate choice: Open-source Redis defaults to noeviction (writes fail when memory is full), and managed offerings often default to volatile-lru, which ignores keys without a TTL. Neither is a considered cache policy.
  • Easy to measure: Hit ratio is keyspace_hits / (keyspace_hits + keyspace_misses), and evicted_keys and used_memory show whether the change worked.
  • Why not shard first? Sharding raises capacity, but if memory is full of cold data, more nodes just store more cold data, at the cost of operational complexity. Fix what you keep first, then scale out when the hot working set outgrows a node.

Pair the policy with explicit TTLs (with jitter), admission control so one-off keys are not cached, compact values, and a dashboard of hit ratio, evicted_keys and memory usage per key pattern. Re-measure after every change.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🌐

A — CDN for Static Assets

A CDN is excellent for user latency and origin offload of static content, and it frees Redis memory if large assets were cached there. But it does not improve the hit ratio of the data Redis actually serves; it removes traffic Redis should not be handling. Do it as an offload measure, not as the strategy that boosts Redis hit rate. Caveat: if static assets or large blobs consume a big share of Redis memory, moving them out is a legitimate memory-recovery step.

🧩

C — Sharding the Cache

Sharding (Redis Cluster or client-side partitioning) adds total memory and throughput, which raises the hit ratio when the hot working set no longer fits on one node. It also adds complexity: slot mapping, resharding, limits on multi-key operations (keys must share a slot), hot-key skew on one shard and more failure modes. It is the right next step once policy and TTLs are sound and hot keys are still being evicted.

✍️

D — Write-Through Caching

Write-through keeps cache and database in sync on writes, which improves freshness and read-after-write behavior, but it does not raise the read hit ratio. It can lower it: every write populates the cache, including data that is never read, consuming memory and evicting hot entries. It also adds write latency (two writes per update). Use it where read-after-write consistency matters, not as a hit-rate booster.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — CDN for Static Assets

Static assets (images, scripts, styles) and cacheable public responses, to cut origin load and user latency.

📌

B — Eviction Policy

The cache is at its memory limit with rising evictions and a falling hit ratio, and the hot set fits in memory. The first lever to pull.

📌

C — Sharding the Cache

The hot working set exceeds one node's memory, or throughput exceeds a node's capacity even after policy tuning.

📌

D — Write-Through

Data that is read immediately after being written and must be fresh (profiles, carts), where the added write latency is acceptable.

⚠️ Common Mistakes to Avoid

  • Tuning blind: Changing policy or adding nodes without per-pattern hit ratios and eviction counts. A single chatty low-value key pattern can mask a poor hit ratio on the hot path.
  • Using volatile-* policies with TTL-less keys: Keys without a TTL are never evicted, so memory fills and writes fail or the cache stops admitting new data.
  • One TTL for everything: Identical TTLs cause synchronized expiry and stampedes. Add jitter and use shorter TTLs only where freshness demands it.
  • Polluted cache keys: Timestamps, session ids or unordered query parameters in keys make near-identical requests miss. Normalize keys.
  • Caching one-hit wonders and giant values: They evict many small hot entries for no later benefit. Admit on second access and cap value size.
  • Confusing eviction with expiry: A low hit ratio with few evictions usually points to TTLs that are too short or to key design, not to memory.

🌍 Real-World Best Practice

A falling hit ratio is a diagnosis problem first. Teams usually proceed like this:

  • Step 0 — Measure: Track keyspace_hits, keyspace_misses, evicted_keys, expired_keys and used_memory against maxmemory, and break the hit ratio down per key pattern (sampling with redis-cli --bigkeys and MEMORY USAGE).
  • Step 1 — Eviction policy and TTLs: Switch to allkeys-lfu (or allkeys-lru), set TTLs with jitter and eliminate keys that have no TTL.
  • Step 2 — Fix what goes in: Add admission control, normalize cache keys (no timestamps or random parameters in keys), compress or shrink values and skip one-off or huge objects.
  • Step 3 — Offload what does not belong: Static assets to a CDN, large blobs to object storage.
  • Step 4 — Scale out: When the hot set exceeds one node's memory, use Redis Cluster or sharding with replicas, and watch for hot-key skew.
  • Step 5 — Layer caches: A small in-process L1 cache for the hottest keys, and write-through or refresh-ahead only where freshness requires it.

Fix what is cached before scaling how much you cache.

💡

Key Takeaway

A falling hit ratio means the cache holds the wrong data or too little of the right data. First make memory hold the hot set with a frequency-aware eviction policy, disciplined TTLs and admission control. If the hot working set still outgrows a node, then shard. Measure hit ratio and evictions at every step.
