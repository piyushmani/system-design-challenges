Jasper's Plan: Stopping Dashboards from Dragging Down the Production DB

Jasper, a backend engineer on a payment processing system, runs heavy business-dashboard SQL each morning directly on the primary transactional database. The reports cause CPU spikes, higher tail latency for customer requests, and intermittent replica lag. Tuning individual queries with EXPLAIN is possible, but the team wants a structural, long-term fix that balances observability, cost, consistency, and latency. Dashboards can tolerate data that is a few minutes old, but the numbers must reconcile with the ledger.

A
Keep everything on the primary and optimize: covering indexes, rewritten joins, pagination or batching, off-peak scheduling, and query throttling.
✗ Not Best
B
Add a cluster of synchronous read replicas and route all analytical queries to them for near-perfect read consistency, scaling the replicas horizontally behind a load balancer.
✗ Not Best
C
Move reporting to an isolated analytics pipeline: CDC/ETL feeding pre-aggregated tables or views in a dedicated OLAP or columnar store, with dashboards querying that store and refresh intervals set by business need.
✓ Best Answer
D
Add a federated query engine (for example Presto or Trino) over the existing data sources, relying on predicate and join pushdown so dashboards can query without ETL.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — C: Isolated Analytics Pipeline (CDC to OLAP)

The underlying issue is workload interference: long, scan-heavy analytical queries share CPU, I/O, buffer cache, and locks with short, latency-sensitive payment transactions. Tuning reduces the damage but not the sharing. Moving reporting to a separate system built for scans and aggregations removes the interference by design. Here's why it stands out:

  • True workload isolation: Dashboards no longer consume the primary's resources, so customer-facing p99 stays protected no matter how heavy or numerous the reports become.
  • Right engine for the job: Columnar OLAP stores scan and aggregate large datasets far faster than a row-oriented OLTP engine, and pre-aggregated tables let dashboards read thousands of rows instead of billions.
  • Minimal load on the primary: Log-based CDC reads the write-ahead log, which is far lighter than running analytical SQL against live tables. Each change is shipped once.
  • Predictable cost and freshness: Refresh intervals (or streaming latency) are an explicit, tunable choice that matches how fresh each dashboard needs to be, with a clear SLO such as 'under 5 minutes behind'.
  • Enables better modeling and compliance control: You can add dimensions, history, and joins to other sources without touching the transactional schema, and mask or exclude sensitive fields in the pipeline.

A strong pipeline has idempotent, ordered application of changes, pre-aggregated tables for the heaviest dashboards, a freshness SLO with alerting, and periodic reconciliation against the OLTP ledger. Track CDC lag, replication slot size, and primary p99 before and after the migration.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🔧

A — Optimize on the Primary

Query tuning is cheap, safe, and worth doing, but the reports still run on the primary, so growth in data volume or dashboard count brings the contention back. Off-peak scheduling helps only until someone needs a report at peak, and throttling slows reports instead of isolating them. Caveat: tuning is a good first-aid measure and remains valuable for the OLTP queries that stay on the primary.

🪞

B — Synchronous Read Replicas

Synchronous replication is the wrong lever: the primary waits for replica acknowledgment on commit, so more synchronous replicas can increase write latency and tie availability to them. Long analytical queries on a hot-standby replica also conflict with WAL replay, causing cancelled queries or growing replica lag (the symptom already seen). Replicas still use a row-oriented engine, so heavy scans remain expensive. Caveat: an asynchronous replica dedicated to reporting is a reasonable interim step, but not a long-term fix.

🧵

D — Federated Query Engine

Federation changes where the SQL is planned, not where the data lives. Pushdown still sends scans and aggregations to the source databases, so heavy dashboard queries can still hit the OLTP primary (now through a more complex stack). It helps for ad-hoc exploration across sources, not for protecting a latency-sensitive primary.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Optimize on Primary

Small data volumes, a few reports, and no real isolation problem yet, or as a first-aid step before a larger change.

📌

B — Synchronous Read Replicas

Rarely for analytics. Use asynchronous replicas to scale read-heavy application traffic where some lag is acceptable.

📌

C — CDC to OLAP

Heavy, growing analytical workloads that must not affect transactions (this scenario).

📌

D — Federated Query Engine

Ad-hoc exploration across several data sources or a data lake where each source can handle the load. Not for protecting a production primary.

⚠️ Common Mistakes to Avoid

  • Ignoring replication slot lag: A stalled consumer makes PostgreSQL retain WAL until the disk fills. Alert on slot lag and set retention limits.
  • Non-idempotent loads: CDC delivers at-least-once. Apply changes with upserts keyed by primary key and ordered by LSN or version, or payments will be double counted.
  • Dashboards without an 'as of' time: Users assume the numbers are live. Show data freshness and reconcile against the ledger.
  • Copying sensitive fields: Card data and PII in analytics extend compliance scope. Tokenize, mask, or drop them in the pipeline.
  • Querying raw tables in the OLAP store: Even columnar stores get slow and expensive if every dashboard scans raw events. Build rollups for the hot dashboards.
  • Forgetting schema evolution and backfills: A column added in OLTP can break the pipeline. Use a schema registry and a tested backfill procedure.

🌍 Real-World Best Practice

In practice, teams stabilize first, then isolate, then optimize the analytics path. A typical sequence:

  • Step 0 — Stop the bleeding: Move reports to an asynchronous replica (or a snapshot) with statement timeouts and a dedicated role with resource limits, so customer traffic is protected immediately.
  • Step 1 — Inventory the dashboards: Classify each by required freshness, data volume, and criticality.
  • Step 2 — Build the pipeline: Use log-based CDC into Kafka or a managed ingestion service, and load into a columnar store (ClickHouse, BigQuery, Snowflake, Redshift, or similar).
  • Step 3 — Pre-aggregate: Create rollups and materialized views for the top dashboards, and point BI tools at them.
  • Step 4 — Reconcile and monitor: Compare daily totals to the ledger, and alert on lag and drift.
  • Step 5 — Retire primary access: Revoke dashboard credentials on the primary and keep only the CDC connection.

Let the primary do transactions and the analytics store do scans.

💡

Key Takeaway

Query tuning helps, but the structural fix is workload isolation: stream changes out of the primary with CDC and serve dashboards from a store built for analytics, with a clear freshness SLO and reconciliation against the ledger.
