Challenge

Liam's upload pipeline: deciding how to track millions of objects

Liam is engineering a worldwide image-upload platform. Binary files live in object storage (such as S3 or Azure Blob), while clients need fast, consistent file listings and thumbnails. Traffic is high and bursty, with tens of thousands of simultaneous uploads. Thumbnails are generated after upload, and new files must appear in listings within seconds. He needs an architecture that favors high availability, scalability, low upload latency, practical listing consistency and good observability, while handling failures and retries gracefully.

A
Use pre-signed URLs: on upload initiation, write a 'pending' metadata record to a strongly consistent database and return a pre-signed URL. The client uploads directly to object storage, which emits object-created events to a queue; workers validate ETag and size, mark the record 'available' and trigger thumbnail creation. The database is the source of truth for listings, and a scheduled reconciliation job catches any dropped events.

B
Route all uploads through the central API servers: the client streams the file to the backend, which stores it in object storage and synchronously writes metadata to the database before acknowledging. Listings come from the database and thumbnail generation runs synchronously inside the same API request.
✗ Not Best
C
Drop the separate metadata database: use the object store's listing and user-defined prefixes as the source of truth. Clients upload directly, and the backend builds listing responses and triggers thumbnail generation by frequently polling the bucket for new files.
✗ Not Best
D
Let clients upload directly to the bucket and then call a separate metadata API to record the file as 'available' in the central database. The design relies on the client to report success, thumbnails are triggered by database inserts, and any state reconciliation is handled manually and ad hoc.

Answer & In-Depth Explanation

🏆 Best Answer — A: Pre-Signed Direct Upload with Event-Driven Finalization

The key insight is to separate the data plane from the control plane. File bytes should flow straight from clients to object storage (which is built for massive parallel throughput), while the application owns a small, strongly consistent metadata record that decides what exists, who owns it and when it becomes visible. Making the storage event, not the client's word, the trigger for 'available' keeps the system honest, and a reconciliation job closes the gap for lost events. Here's why it stands out:

  • Scales with the bursts: Tens of thousands of concurrent uploads hit the object store directly, so API servers handle only tiny JSON requests. Storage bandwidth, not application memory or sockets, becomes the limit, and storage scales horizontally.
  • Low upload latency and cost: Clients upload to the nearest storage endpoint (or an accelerated or regional endpoint) with multipart for large files, and no application server relays bytes.
  • Trustworthy state: The 'pending' to 'available' transition is driven by a storage-emitted event and validated (existence, ETag, size, content type), so a client crash or a malicious claim cannot create a phantom listing.
  • Fast, consistent listings: Listings are indexed queries on the metadata database (by user, status and created_at), not slow paginated bucket scans, and can add owner, ACLs, sorting and thumbnail URLs. Appearance within seconds is bounded by event delivery plus a quick worker.
  • Resilient to failure: The queue buffers bursts and retries failures, a dead-letter queue captures poison messages, and the reconciliation job repairs dropped or duplicated events, so the system self-heals instead of requiring manual cleanup.

A robust version includes server-generated keys, short-lived scoped pre-signed URLs, idempotent event handlers, a dead-letter queue, a reconciliation sweeper (HEAD pending objects older than N minutes and finalize or expire them), deterministic thumbnail keys and malware and content validation before 'available'. Monitor pending age, event lag, queue depth, DLQ size, reconciliation fixes and time-to-listing (p95); if time-to-listing exceeds the seconds target, scale workers or shorten sweeper intervals.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🚚

B — Proxy All Uploads Through the API

Relaying bytes through application servers makes them the bottleneck: each upload holds a connection, memory and bandwidth for its full duration, so tens of thousands of concurrent uploads require a very large, expensive fleet and amplify burst and slow-client risks. Synchronous thumbnailing also ties request latency and failure to image-processing time. It does give simple, immediate consistency, which is its only real advantage. Caveat: acceptable for small files at low volume, or for sensitive flows that must be scanned in-line.

🗂️

C — Object Store as the Only Source of Truth

Object-store listing is a prefix scan, not a query engine: it is paginated, comparatively slow and costly at millions of objects, offers no secondary indexes (by owner, status or time across prefixes) and has no place for ACLs or processing state. Strong list-after-write consistency on modern S3 and Azure Blob helps correctness, but polling the bucket for new files is wasteful, adds delay and does not scale with bursts. Caveat: viable for simple, prefix-organized data lakes with batch consumers, not for interactive user listings.

🙋

D — Client-Reported Completion

Relying on the client to say 'upload finished' means a crash, network drop or malicious client breaks the invariant: files can be orphaned in storage and never listed, or records can claim objects that do not exist. Nothing validates the object, and manual reconciliation does not scale or provide observability. Caveat: a client callback is fine as an optimization hint to speed up finalization, as long as the server verifies and event-driven reconciliation remains the source of truth.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Pre-Signed URL + Events

User-generated content at scale (images, videos, documents) with bursty uploads, a need for fast listings, post-processing such as thumbnails or scanning, and tolerance for seconds of finalization delay.

📌

B — Proxy Through API

Small files at low volume, or flows that must be inspected, transformed or scanned in-line before anything is stored, where simplicity matters more than scale.

📌

C — Storage Listing Only

Batch or data-lake style workloads organized by prefix and consumed by batch jobs, where interactive per-user listings and metadata queries are not required.

📌

D — Client-Reported Completion

Only as a hint layered on top of option A (clients tell the server to check sooner), or in prototypes where orphaned objects and manual cleanup are acceptable.

⚠️ Common Mistakes to Avoid

  • Trusting the client for completion: Clients crash and can lie. Finalize from a storage event or a server-side HEAD check.
  • Non-idempotent event handlers: At-least-once delivery means duplicates. Key updates and outputs deterministically so replays are safe.
  • No reconciliation: Events do get dropped. Without a sweeper, pending rows and orphan objects accumulate silently.
  • Client-chosen object keys: They allow overwriting other users' files and path tricks. Generate keys server-side and scope URLs to a single key.
  • Unbounded or unscoped pre-signed URLs: Long expiries and missing size or type limits invite abuse. Keep them short-lived and constrained, then validate after upload.
  • Forgetting multipart cleanup: Abandoned multipart uploads keep incurring storage charges. Add a lifecycle rule to abort incomplete uploads.

🌍 Real-World Best Practice

Production upload systems keep bytes and state separate and make every step idempotent. A typical sequence:

  • Step 0 — Define invariants: A record is 'available' only if the object exists, passed validation and belongs to its owner. Decide the freshness target (for example, visible within 5 seconds).
  • Step 1 — Direct upload: Issue scoped, short-lived pre-signed URLs (multipart for large files) after creating a 'pending' record.
  • Step 2 — Event-driven finalize: Consume storage events through a queue, verify the object, flip the record to 'available' and enqueue thumbnail work.
  • Step 3 — Idempotent processing: Use deterministic output keys and idempotent updates so retries and duplicates are harmless; send failures to a DLQ.
  • Step 4 — Reconcile: Run a sweeper that checks stale pending rows against storage and expires or finalizes them, plus lifecycle rules that abort stale multipart uploads.
  • Step 5 — Observe and serve: Track time-to-listing, event lag and DLQ depth; serve listings from the metadata store and thumbnails via a CDN.

Let storage move the bytes, let the database own the truth, and let events and reconciliation keep them aligned.

💡

Key Takeaway

Upload directly to object storage with pre-signed URLs, keep a strongly consistent metadata record as the source of truth for listings, and drive the 'available' transition from storage events with idempotent workers plus a reconciliation sweeper. This scales with bursts, keeps uploads fast and stays correct under failures.
