Challenge

Balancing Read and Write Throughput in a Dual-Traffic-Pattern Platform

Sarah, a software engineer at a fast-growing social media platform, is tackling a dual-traffic-pattern problem: during peak hours, the system is hammered with write-heavy traffic (posts, comments, reactions, stories) while off-peak periods are dominated by read-heavy traffic (timeline browsing, search, profile views). The current single-database architecture is buckling under both patterns, and Sarah needs to choose a scaling strategy that optimizes for both read and write throughput without over-engineering for one at the expense of the other.

A
Deploy a write-through cache layer to absorb write operations into memory while simultaneously serving cached data for faster reads.
✗ Not Best
B
Implement horizontal sharding to distribute write traffic across multiple independent database instances based on a partition key.
✗ Not Best
C
Introduce materialized views to precompute and persist the results of complex read queries, reducing query execution time for common access patterns.
✗ Not Best
D
Adopt a primary-replica (master-slave) database topology that routes all writes to a dedicated primary node while distributing read traffic across multiple read replicas.
✓ Best Answer
✅

Answer & In-Depth Explanation

🏆 Best Answer — D: Primary-Replica Topology

Adopting a primary-replica topology is the most effective single architectural decision for Sarah's dual-traffic-pattern workload. It directly addresses the core problem — read and write traffic competing for the same resources — by physically separating them into dedicated paths. Here's why it stands out:

  • **Direct separation of concerns:** The primary node is optimized exclusively for write throughput (indexes tuned for inserts/updates, write-ahead log configuration, minimal read contention). Read replicas are optimized for query performance (additional read-oriented indexes, query caching, connection pooling). Neither path degrades the other.
  • **Elastic read scaling:** During off-peak read-heavy periods, Sarah can spin up additional read replicas to absorb the load — this scales horizontally and independently of write capacity. During peak write hours, read replicas continue serving stale-but-recent data (typically seconds behind) while the primary absorbs the write surge without read contention.
  • **Minimal architectural disruption:** Primary-replica is natively supported by every major database (PostgreSQL streaming replication, MySQL replication, MongoDB replica sets). It requires no schema changes, no application-level sharding logic, and no data model restructuring. Sarah can deploy it incrementally — add one replica, route read traffic, measure, add more.
  • **Battle-tested at social media scale:** Twitter, Instagram, and LinkedIn all use primary-replica as the foundational layer of their database architecture. It's the first scaling step before more complex patterns (sharding, CQRS) become necessary, and it often buys 6–18 months of headroom before the next architecture evolution is needed.

Sarah should implement primary-replica with a connection-aware routing layer (e.g., ProxySQL, PgBouncer with read/write splitting, or application-level routing). Reads that tolerate slight staleness (timelines, profiles, search) go to replicas. Reads that require freshness (user's own just-posted content, notification counts) go to the primary with a read-your-writes consistency guarantee. This gives users the perception of strong consistency while distributing 80–90% of read traffic to replicas.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

💾

A — Write-Through Cache

Write-through caching writes data to both cache and database simultaneously. This adds latency to every write (two write operations instead of one) — exactly the wrong trade-off during peak write hours. It also doesn't reduce database write load at all; every write still hits the DB. The read benefits are real (cache hits are fast), but a write-through cache is optimized for read-after-write consistency, not write throughput. For Sarah's peak write surges, this makes the write path slower while only helping reads that hit cached keys.

🔪

B — Horizontal Sharding

Sharding distributes writes across multiple database instances, which does improve write throughput. But it introduces massive complexity: cross-shard queries (e.g., a user's timeline pulling posts from friends on different shards), shard rebalancing as data grows unevenly, application-level routing logic, and distributed transactions. Sharding is the right tool when a single node can't handle write volume — but Sarah's problem is read/write contention, not single-node write saturation. Sharding is a Layer 2 optimization after primary-replica has been exhausted.

📊

C — Materialized Views

Materialized views precompute expensive read queries, which dramatically speeds up specific read patterns (e.g., 'top posts this week', 'follower count'). But they only help reads — they do nothing for write throughput during peak hours. Worse, materialized views must be refreshed on write, which adds write overhead. They're also rigid: each view is tailored to one query pattern, so new read patterns require new views. Materialized views are a powerful tactical optimization for known hot queries, but they're not a scaling architecture — they're a query-level optimization layered on top of one.

⚡

D — Primary-Replica Topology ✓

Adopt a primary-replica (master-slave) database topology that routes all writes to a dedicated primary node while distributing read traffic across multiple read replicas.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Write-Through Cache

Read-after-write consistency is critical (e.g., user profile updates that must be immediately visible) and write volume is moderate. Best used as a complement to primary-replica, not as a standalone scaling strategy.

📌

B — Horizontal Sharding

Single-node write throughput is the proven bottleneck (>50K writes/sec), or the dataset is too large for a single node's storage. Natural fit when data partitions cleanly by a dimension (user ID, tenant, region) with minimal cross-shard queries.

📌

C — Materialized Views

Specific read queries are expensive (multi-table JOINs, aggregations, ranking algorithms) and their results can tolerate staleness. Ideal for dashboards, analytics, recommendation feeds, and trending content where precomputation is more efficient than real-time computation.

📌

D — Primary-Replica

Read and write traffic have different volumes or temporal patterns, and the database is struggling with contention between the two. The default first-step scaling architecture for any application that has outgrown a single database instance.

⚠️ Common Mistakes to Avoid

  • **Sending all reads to the primary** — After setting up replicas, engineers often forget to actually route read traffic. Use a connection proxy or application-level routing to ensure reads hit replicas by default. Monitor primary vs. replica query ratios.
  • **Ignoring replication lag** — Read replicas are asynchronously behind the primary. If a user posts content and immediately refreshes, they might not see their own post. Implement read-your-writes consistency by routing the authoring user's reads to the primary for a brief window after writes.
  • **Sharding prematurely** — Sharding is irreversible and dramatically increases operational complexity. Most platforms can serve 10–100M users on primary-replica + caching alone. Don't shard until you've proven that single-primary write throughput is the bottleneck via load testing.
  • **Caching writes instead of separating paths** — Write-through and write-behind caches don't reduce database write load — they just add another write target. If write throughput is the problem, you need write path optimization (batching, async processing, event sourcing), not caching.
  • **Over-indexing replicas** — Adding too many indexes to read replicas speeds up some queries but slows down replication (every replicated write must update all indexes). Profile actual slow queries before adding indexes, and consider different index configurations per replica if your DB supports it.
  • **Not monitoring replica drift during peak writes** — During write surges, replication lag can spike from milliseconds to seconds. If your application assumes near-real-time replica freshness, this creates subtle bugs. Set up alerts on replication lag and have a fallback strategy (route to primary) when lag exceeds thresholds.

🌍 Real-World Best Practice

In production social media platforms, senior engineers don't rely on a single scaling strategy. They layer complementary patterns to address different dimensions of the read/write scaling challenge:

  • **Layer 1 — Primary-replica separation:** Route writes to a primary, reads to replicas. This is the foundational layer that buys immediate headroom and is the biggest single architectural win.
  • **Layer 2 — Read-through caching (Redis/Memcached):** Cache hot read paths (timelines, trending content, user profiles) to intercept reads before they even reach replicas. This reduces replica load by 60–80% for typical social media access patterns.
  • **Layer 3 — Materialized views for analytics:** Precompute expensive aggregations (engagement metrics, trending algorithms, recommendation scores) as materialized views refreshed on a schedule. These never hit the primary or real-time replicas.
  • **Layer 4 — Sharding when single-primary saturates:** When write volume exceeds what a single primary can handle (typically >50K writes/sec for most RDBMS), shard by user ID or tenant. This is a last-resort architectural change that most platforms don't need until they're at massive scale.

Sarah's first move should be deploying read replicas because it directly addresses the read/write contention problem with minimal risk and maximum leverage. She can then layer caching for hot reads and materialized views for analytics before ever needing to consider sharding.

💡

Key Takeaway

When read and write traffic have different temporal patterns, the highest-ROI architectural decision is to physically separate the read and write paths. A primary-replica topology does this natively, scales reads horizontally, requires no schema changes, and is supported by every major database. Solve the contention problem first — optimize individual query paths later.
