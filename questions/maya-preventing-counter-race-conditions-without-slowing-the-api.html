Challenge

Maya Preventing Counter Race Conditions Without Slowing the API

Maya, a backend engineer on a payment API handling millions of requests per minute, must update a per-customer usage counter on every request (for throttling and billing) and return the remaining quota in under 10 ms. The service runs on many horizontally scaled, multi-threaded instances, so requests from the same customer can land on different instances at the same moment. Counters must be accurate, with no over-charging and no wrongful throttling, while the design stays fault tolerant, observable and scalable.

A
Keep counters in an in-process concurrent map protected by coarse-grained locks for read-modify-write, and flush them periodically to a central database.
✗ Not Best
B
Route all traffic for a customer to one instance with consistent hashing (sticky routing) and process that customer's counter in a single-threaded actor or event loop, relying on failover to move shards when an instance dies.
✗ Not Best
C
Offload counters to a dedicated external store such as Redis using atomic INCR/INCRBY, with a brief TTL-based local cache for fast reads (falling back to Redis when needed), Redis Cluster and replication for fault tolerance, and close monitoring of its availability and latency.
✓ Best Answer
D
Keep counters in the primary SQL database and use row-level locking (SELECT ... FOR UPDATE) or serializable transactions for every increment, with optimistic retries on conflict.
✗ Not Best

Answer & In-Depth Explanation

🏆 Best Answer — C: Atomic Redis Counters

Given the need for accurate, shared counters across many instances and a response in under 10 ms, the best approach is a dedicated in-memory store with atomic increment operations, such as Redis. Atomicity moves the race condition out of application threads and into a single-threaded command executor that serializes updates per key, so every request sees a correct post-increment value regardless of which instance handled it. Here's why it stands out:

  • Race-free by construction: INCR, INCRBY and Lua scripts execute atomically on the shard that owns the key. There is no read-modify-write window and no application lock to hold, so concurrent threads and instances cannot lose updates.
  • Latency fits the budget: A Redis round trip inside the same zone typically takes well under a millisecond to a couple of milliseconds, leaving headroom within a 10 ms budget. The command returns the new value, so the API gets the exact remaining quota in the same call.
  • Scales horizontally: Keys are spread across shards by hash slot, so customer counters distribute naturally. Capacity grows by adding shards, and a single shard can often handle on the order of 100k simple operations per second.
  • Check and update in one step: A short Lua script can deduct quota only if enough remains and return both the decision and the new value, which prevents overspending between a check and an update.
  • Operationally mature: Replication, clustering, failover and rich metrics (latency, memory, evictions, replication lag) are well understood and straightforward to monitor and alert on.

A solid design uses atomic INCRBY or a Lua script for check-and-deduct, idempotency keys, time-windowed keys with TTL for rate limits, a durable ledger for billing reconciliation, a defined fail-open or fail-closed policy when Redis is unavailable, and metrics for command latency, error rate, replication lag and hot keys.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🔒

A — In-Process Locked Map

Locks make a single process thread-safe, but they do nothing across many instances. Each instance holds its own partial view of the counter until the next flush, so the fleet can overspend a quota (every instance thinks there is room left) or throttle wrongly. Coarse locks also serialize all customers on one lock, and an instance crash loses everything not yet flushed. Caveat: local counters with periodic sync are a valid approximation for soft limits (such as coarse burst protection) where small overshoot is acceptable, but not for strict billing.

🎯

B — Sticky Routing with Single-Threaded Actors

This gives strong per-customer ordering without locks, and it is a legitimate pattern (actor and shard-per-key designs). But it adds operational complexity: consistent hashing, rebalancing, and a way to prevent two instances from owning the same customer during failover. A hot customer overloads a single instance, and an instance crash loses in-memory state unless it is persisted. Caveat: if you already run such a platform (Akka or Orleans style sharding) with durable state, it can meet the requirement; for a stateless API fleet it is more machinery than an atomic store.

🗄️

D — SQL Row Locks per Increment

Row-level locking and serializable transactions are correct but too slow at this scale. Every request becomes a write transaction, hot customers create lock queues, and p99 latency grows with contention. Serializable isolation adds aborts and retries that further inflate tail latency, and millions of writes per minute strain the primary and its WAL. Caveat: the database is the right home for the durable, reconciled record of usage (through batching or an event stream), just not for the per-request hot path.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — In-Process Locked Map

Soft limits and approximate metrics where small overshoot is acceptable, such as local burst protection layered in front of a global limiter.

📌

B — Sticky Routing with Actors

Systems already built around shard-per-key actors with durable state and strong per-entity ordering needs, such as stateful gaming or workflow engines.

📌

C — Redis Atomic Counters

Hard quotas and rate limits on a stateless, horizontally scaled API fleet that needs sub-10 ms responses and a cheap, atomic shared counter.

📌

D — SQL Row Locks

Low-volume systems where the database is the system of record and request rates are modest, or as the durable ledger behind a faster counter.

⚠️ Common Mistakes to Avoid

  • Read then write from application code: GET followed by SET is a race even with a single Redis. Use INCRBY or a Lua script so the read-modify-write is atomic.
  • Checking quota before incrementing: Two requests can both see one unit left and both proceed. Deduct first and compare the result, or use a script that deducts only if enough remains.
  • Returning cached quota values: A local TTL cache hides recent increments and shows more quota than actually remains. Return the atomic result for authoritative responses.
  • No idempotency on retries: Timeouts plus retries double charge customers. Deduplicate with a request ID inside the atomic operation.
  • Treating Redis as the only copy for billing: Asynchronous replication and restarts can drop increments. Keep a durable usage log and reconcile.
  • Undefined behavior on Redis failure: Without a decision between fail-open and fail-closed, an outage becomes either a billing leak or a full API outage. Decide per endpoint and test it.

🌍 Real-World Best Practice

In practice, high-traffic APIs separate the fast counter from the durable ledger. A typical sequence looks like this:

  • Step 0 — Define the accuracy contract: Decide which limits are hard (billing, quotas) and which are soft (burst protection). That decides whether a few lost increments are tolerable.
  • Step 1 — Use an atomic store for the hot path: Redis (or a similar store) with INCRBY or a Lua script returns the new value in the same round trip.
  • Step 2 — Make requests idempotent: Attach a request ID and deduplicate inside the same atomic operation so retries do not double count.
  • Step 3 — Persist a durable ledger: Emit each usage event to a log or queue and aggregate into the database asynchronously. Reconcile against the counters on a schedule.
  • Step 4 — Plan for failure: Choose fail-open (allow, log, reconcile later) or fail-closed (reject) per limit type, add timeouts, and keep a replica or cluster failover path.
  • Step 5 — Handle hot keys: For extremely hot customers, split a counter into sub-counters (sharded counters) or hand out quota leases to instances in batches.

Make the hot path atomic and cheap, and make the record of truth durable and reconcilable.

💡

Key Takeaway

Use an atomic, shared counter store to eliminate race conditions across threads and instances, return the post-increment value as the quota, and back it with a durable ledger for billing accuracy. Local locks do not cross instances, sticky actors add complexity, and SQL row locking cannot sustain the latency budget at this volume.
