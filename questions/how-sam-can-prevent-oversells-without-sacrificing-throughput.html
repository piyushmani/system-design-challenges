Inventory Management Throughput Concurrency
Challenge

How Sam can prevent oversells without sacrificing throughput

Sam, a backend engineer on a retail checkout application, runs several stateless servers that update a shared relational database's inventory table and rely on SELECT ... FOR UPDATE to avoid overselling. As traffic grows, row-lock contention on a small set of hot SKUs causes long tail latencies and regular transaction timeouts during flash sales. Sam needs a new design that never oversells, keeps throughput high and reads fast, and balances scalability, availability, latency, consistency, observability, and fault tolerance. He needs to choose the best architectural direction.

A
Keep the relational database as the single source of truth and apply pessimistic row-level locking (SELECT ... FOR UPDATE) for every inventory change. Scale the database vertically, add connection pooling, and set strict timeouts to shorten lock hold times.
✗ Not Best
B
Add a Redis-based distributed lock (Redlock) around inventory changes. Each checkout instance acquires a lock for the SKU, updates the database inventory, then releases the lock, leaving the rest of the architecture unchanged.
✗ Not Best
C
Move to optimistic concurrency control by adding a version or timestamp column and using compare-and-swap (UPDATE ... WHERE version = x). On conflict, retry with exponential backoff in the application, optionally adding a small in-memory queue per instance to absorb spikes.
✗ Not Best
D
Build a sharded, single-writer inventory service. Distribute SKUs across nodes and route every update to the owning shard, which applies changes sequentially through a local queue or a partitioned durable log (such as a Kafka partition), so each SKU is updated by one thread at a time. Serve reads from asynchronously replicated stores and caches, and make commands idempotent with built-in reconciliation for failures.

Answer & In-Depth Explanation

🏆 Best Answer — D: Sharded Single-Writer Inventory Service

Overselling is a per-SKU invariant (stock must never drop below zero), and the current design enforces it by making many servers queue on a database row lock while a transaction stays open across several network round trips. A sharded single-writer inventory service keeps the same correctness guarantee by serializing updates per SKU, but it does so in one thread next to the data instead of through lock waits. That takes lock-hold time off the critical path and lets throughput scale by adding shards. Here's why it stands out:

  • Serialization without lock waits: In the current design, per-SKU throughput is capped at roughly 1 / (lock hold time), and the hold time includes app-to-database round trips. A single writer checks available >= qty and decrements in memory, so the cap becomes CPU speed, which is typically orders of magnitude higher.
  • Throughput scales horizontally: SKUs hash to shards, so adding shards adds capacity. Writers can also batch several commands into one log append (group commit), which raises throughput further without weakening ordering.
  • Correctness stays local and simple: One writer per SKU means no race to reason about. The never-oversell rule is a single comparison executed in sequence, not a protocol spread across servers.
  • Reads are decoupled from the write path: Product pages and search read from asynchronously replicated stores and caches. They may be a little stale, which is fine for display, because the authoritative check happens at reservation time.
  • Fault tolerance through a durable log and idempotent commands: State is rebuilt by replaying the log from the last snapshot. Every command carries an idempotency key, so retries after a timeout or a failover are safe and a client never double-reserves.
  • Observability is natural: Per-shard queue depth, consumer lag, reject rate, and command latency show exactly where pressure is building, and a continuous invariant check (available stock never negative) catches bugs early.

A production-grade version uses reservations with a TTL (stock is held, then confirmed or released), idempotency keys on every command, epoch-based fencing on writer failover, and periodic reconciliation against the system of record. Track the reject rate, per-shard lag, and the number of times available stock would have gone negative (which should always be zero).

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🔒

A — Pessimistic Locking + Vertical Scaling

This is the design that is already failing. The lock is held for the whole transaction, and every extra millisecond of network or application time multiplies queueing on a hot row. Bigger hardware does not help, because contention on one row is serialization, not a resource shortage. Connection pooling and short timeouts reduce the damage but convert queueing into timeouts, so users still see failures. Caveat: for modest traffic with no hot rows, this is the simplest correct design, and it remains a fine fallback.

🗝️

B — Redis Distributed Lock (Redlock)

This moves the queue from the database to Redis and adds a network hop, yet the database row is still updated under contention. It also weakens safety: a lock can expire during a GC pause or network delay while its holder keeps going, and without fencing tokens two writers can proceed at once (Martin Kleppmann's well-known critique of Redlock). Distributed locks are reasonable for efficiency (avoiding duplicate work) but risky as the only guard for a correctness rule such as never overselling.

🔁

C — Optimistic Concurrency (CAS + Retries)

Optimistic control shines when conflicts are rare. On a flash-sale hot row, many writers collide on every attempt: one compare-and-swap wins per round and the rest retry, so wasted work grows with concurrency and backoff stretches tail latency. A per-instance in-memory queue does not coordinate across instances, so it cannot stop cross-instance collisions. Caveat: for ordinary, low-contention SKUs, OCC is cheap and correct, and a single atomic conditional UPDATE ... WHERE available >= qty is even simpler.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Pessimistic Locking + Vertical Scaling

Moderate traffic, evenly spread across many rows, where a single database can comfortably handle the load. The simplest correct approach, especially when transactions are short.

📌

B — Redis Redlock

Coordinating work for efficiency (avoiding duplicate jobs or thundering herds) where an occasional double execution is harmless. Not a sole guard for hard invariants.

📌

C — Optimistic CAS + Retries

Low-contention updates (many different rows, rare conflicts), or a single atomic conditional update on a moderately busy row. Poor fit for flash-sale hot keys.

📌

D — Sharded Single-Writer Service

Extreme write contention on a small set of keys, strict never-oversell requirement, and a team able to run a stateful, partitioned service with a durable log.

⚠️ Common Mistakes to Avoid

  • Acknowledging before the command is durable: If the writer replies success and then crashes before the log append reaches a quorum, the reservation is lost and the same stock can be sold twice. Ack only after a committed append.
  • Skipping idempotency keys: Clients retry on timeouts. Without a command id and a dedupe window, a retry decrements stock twice or double-reserves.
  • No fencing on failover: A paused or partitioned old leader can wake up and accept commands alongside the new one. Use epochs or fencing tokens so only the current owner can append.
  • Letting caches make the decision: Using a cached stock value to authorize a purchase reintroduces overselling. Caches are for display only.
  • Ignoring the single hot SKU: Sharding spreads SKUs, not one SKU's traffic. Plan stock bucketing or admission control for blockbuster items.
  • Reservations that never expire: Abandoned carts quietly hold stock forever. Give every reservation a TTL and run a release sweep.

🌍 Real-World Best Practice

In practice, teams escalate in stages and measure before each step. A typical sequence looks like this:

  • Step 0 — Measure: Look at lock-wait time, lock hold time, and per-SKU request distribution. Confirm that a handful of hot SKUs, not the whole table, cause the contention.
  • Step 1 — Shrink the critical section: Replace SELECT ... FOR UPDATE followed by UPDATE with one atomic statement such as UPDATE inventory SET available = available - :n WHERE sku = :sku AND available >= :n, check the affected row count, and keep the transaction free of other work. This often removes most lock-hold time cheaply.
  • Step 2 — Reserve, then confirm: Decrement stock via short-lived reservations with a TTL, and confirm or release them when payment completes. This keeps long-running checkout steps out of the stock transaction.
  • Step 3 — Single-writer inventory service: When one database row still cannot keep up, move hot SKUs behind sharded single writers with a durable log (the recommended answer).
  • Step 4 — Separate the read path: Serve product pages from caches or replicas fed from the log, and show approximate availability ('only a few left').
  • Step 5 — Handle extreme hot items: Split stock into buckets, add an admission queue or waiting room, and rate-limit at the edge during the sale.

Escalate only as far as the measurements justify, because each step adds operational cost.

💡

Key Takeaway

Overselling is prevented by serializing updates per SKU, but the serialization should happen in a single writer next to the data, not in lock waits spread across stateless servers. Shard SKUs, make commands idempotent, acknowledge only after a durable append, and let caches serve reads but never make the sell decision.
