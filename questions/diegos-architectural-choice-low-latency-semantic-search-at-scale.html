Semantic Search Scalability Architecture
Challenge

Diego's Architectural Choice: Low-latency semantic search at scale

Diego, a senior software engineer, is designing the search infrastructure for an international e-commerce platform with 200 million products and very high read volume. The goal is semantic search (a vector database plus embeddings) for related-product recommendations and natural-language queries. The requirements are a p99 search latency under 150 ms, multi-region availability with local read speeds, tens of thousands of catalog changes per hour, and clear paths for observability and disaster recovery. He must balance consistency, latency, availability, scalability, fault tolerance, and observability without excessive operational overhead.

A
A single strongly consistent managed vector DB in one primary region, updated synchronously together with the SQL metadata DB, with an active-passive DR region.
✗ Not Best
B
Partition the vector index by product ID across regions with asynchronous cross-region replication, search the local partition first, and fall back to remote partitions on local misses.
✗ Not Best
C
Hybrid retrieval: SQL for metadata, a lexical index for fast fresh candidates, async Kafka-fed embedding and ANN indexing, semantic re-ranking of the candidates, lexical-only fallback when vectors degrade, plus monitoring, idempotent consumers, and circuit breakers.
✓ Best Answer
D
No durable vector DB: embed at read time (or from a TTL cache) and search a lightweight in-memory ANN service per region that is periodically torn down and rebuilt.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — C: Hybrid Retrieval with Graceful Degradation

At 200 million products the biggest risks are availability and tail latency, not raw accuracy. A hybrid pipeline decouples catalog writes from vector indexing (async, idempotent), keeps a cheap lexical path that is always fresh and always available, and layers semantic ranking on top behind a circuit breaker. When the vector tier is slow or down, the product degrades from semantic to keyword search instead of failing. Here's why it stands out:

  • Graceful degradation: Search keeps answering when ANN, embedding, or replication has trouble. A circuit breaker and a hard time budget for the semantic stage (for example 40 to 60 ms) protect the p99.
  • Write path isolation: Tens of thousands of updates per hour (roughly 5 to 10 per second) flow through Kafka to embedding workers and idempotent upserts. No cross-store transaction is needed, so catalog writes never depend on vector infrastructure.
  • Always-fresh candidates: The lexical index updates in near real time, so new products are searchable immediately while their vectors catch up asynchronously.
  • Better relevance than either alone: Lexical handles exact matches (SKUs, brands, model numbers) where embeddings are weak, and vectors handle intent and synonyms where keywords fail. Re-ranking a bounded candidate set (hundreds, not millions) keeps the expensive step cheap.
  • Observability and DR by design: Stream backlog, per-stage p99, replication lag, and fallback rate are first-class signals, and the vector index is derived data that can be rebuilt from the event log and catalog.

Production-grade means per-stage latency budgets, circuit breakers with fast fallback, idempotent versioned consumers, regional index replicas fed from a replicated event stream, and relevance monitoring (fallback rate, zero-result rate, click-through). Track per-stage p99, lag, and fallback rate. If the fallback rate stays high, the vector tier is undersized.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🏢

A — Single Region, Synchronous Dual Write

There is no true 'unified transaction' across a SQL database and a vector DB (it would need two-phase commit or leaves a dual-write gap), and synchronous writes tie catalog availability to the vector tier. A single primary region also means users on other continents pay cross-region round trips (often 100 to 250 ms) on every search, which alone threatens the 150 ms target, and active-passive DR wastes capacity and fails over slowly. Caveat: it is the simplest to reason about for a single-market catalog with relaxed latency and a clear DR objective.

🌍

B — Product-ID Partitions per Region

ANN search finds nearest neighbors across the whole catalog, but partitioning by product ID scatters similar items across every partition. A local-first search always returns some local top-K, so the 'fallback on local miss' never triggers and recall silently drops, while correct recall would need scatter-gather across all regions, which destroys local latency. Asynchronous replication also leaves each region's subset stale in different ways. Caveat: sharding within a region is normal and necessary for 200M vectors, but each region should hold a full replica of the index.

🧊

D — Ephemeral In-Memory ANN

Embedding at read time puts model inference on every query's critical path, and rebuilding in-memory indexes of 200M vectors is slow and produces cold-start latency spikes and coverage gaps while it runs. Without a durable index, DR means rebuilding from scratch, and consistency is loose. Caveat: caching query embeddings is a valid optimization, and ephemeral ANN nodes are fine for experiments or very small catalogs.

⚡

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Single Region + Sync Dual Write

Single-market catalogs of small to mid size with relaxed latency targets, where strong consistency and simplicity outweigh global availability.

📌

B — Product-ID Partitions per Region

Data that is naturally partitioned by region or tenant and queried only within that partition (for example local inventory per country), not global similarity search.

📌

C — Hybrid Retrieval

Large global catalogs needing low-latency local reads, high availability, and continuous catalog updates, where search must degrade gracefully.

📌

D — Ephemeral In-Memory ANN

Prototypes, offline experimentation, or small short-lived datasets where the cost of a durable index is not justified.

⚠️ Common Mistakes to Avoid

  • Lexical-only candidate generation: The re-ranker can only reorder what lexical recall provides. Retrieve from both indexes and fuse.
  • No per-stage time budget: One slow ANN call can consume the whole 150 ms. Give each stage a deadline and cut off early.
  • Circuit breaker without fallback testing: Fallback code that never runs rots. Run game days that disable the vector tier.
  • Mixing score scales when fusing: BM25 and cosine scores are not comparable. Fuse by rank (RRF) or normalize carefully.
  • Memory sizing mistakes: Forgetting HNSW graph overhead and replicas. Plan with quantization and shard counts, and re-test recall after quantizing.
  • Unversioned async updates: Retries and out-of-order events can overwrite fresh vectors with stale ones. Use monotonic versions.

🌍 Real-World Best Practice

Large catalogs usually reach this design in stages, measuring relevance and resilience at each step:

  • Step 0 — Define SLOs: Set p99 latency per stage, freshness, recall@K against a labeled set, and availability. These drive every trade-off below.
  • Step 1 — Lexical baseline: A well-tuned inverted index (BM25, synonyms, filters) is fast, fresh, and the permanent fallback.
  • Step 2 — Async vector pipeline: Kafka to embedding workers to versioned idempotent ANN upserts, with a sharded, quantized index that fits in memory.
  • Step 3 — Hybrid retrieval: Retrieve from lexical and ANN in parallel, fuse by rank (RRF), then re-rank the top few hundred. Enforce time budgets and circuit breakers.
  • Step 4 — Multi-region: A full index replica per region fed from a replicated stream, geo-routing at the edge, and regularly tested regional failover.
  • Step 5 — Operate: Dashboards for stage p99, lag, and fallback rate, blue/green indexes for model upgrades, and periodic DR rebuild drills.

Ship the dependable lexical path first and add semantics behind a breaker.

💡

Key Takeaway

At global scale, resilience beats purity. Keep catalog writes decoupled from vector indexing, serve from a local index replica in each region, combine lexical and semantic retrieval, and make every semantic stage optional through budgets and circuit breakers. Prefer parallel lexical plus ANN retrieval over lexical-only candidate generation to protect recall.
