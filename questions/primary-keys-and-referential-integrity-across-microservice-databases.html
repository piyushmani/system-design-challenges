Challenge

Primary Keys and Referential Integrity Across Microservice Databases

Jordan, a seasoned backend developer, is designing the data model for an e-commerce platform split into Inventory, Customers and Orders services. Each is a bounded context with its own database. Under peak load the platform needs high write throughput, fast reads, independent deployments and regional failover. The business can tolerate a few seconds of staleness in cross-service lookups (for example a customer's display name shown on an order) but not lost or duplicated orders. The team must decide how to handle keys and referential integrity across services. Which strategy gives the best mix of scalability, performance, consistency, fault tolerance and observability?

A
Maintain a single, centralized relational database enforcing strict primary and foreign key constraints across all services. Ensure all cross-service writes employ synchronous transactions, relying entirely on the database to guarantee referential integrity and consistency.
✗ Not Best
B
Utilize isolated databases for each service, featuring UUID primary keys but omitting cross-database foreign key constraints. Denormalize parent information into child entities and manage referential integrity through application logic, potentially incorporating background reconciliation jobs to achieve eventual consistency.
✗ Not Best
C
Transition to a globally distributed, strongly consistent SQL database (like CockroachDB or Spanner), employing database-level foreign keys across nodes or shards. This enforces cross-service relationships simply for developers, albeit enforcing a single logical transactional consistency model.
✗ Not Best
D
Allow each service to control its own relational database, restricting foreign keys to its specific boundaries. Broadcast state changes through an outbox pattern or event stream to populate asynchronously updated, read-optimized materialized views (or local caches) within dependent services. Implement observability metrics and reconciliation processes to identify and resolve data drift, establishing hybrid eventual consistency.
✓ Best Answer
✅

Answer & In-Depth Explanation

🏆 Best Answer — D: Local Integrity + Outbox-Fed Read Models

Option D applies the rule enforce constraints inside a service boundary, reconcile across boundaries. Strict foreign keys remain where one database can enforce them cheaply, while cross-service references become explicit contracts: IDs plus event-fed local copies. Here's why it stands out:

  • Autonomy is preserved: services deploy, scale and fail over independently because no schema or transaction spans them.
  • The outbox pattern closes the dual-write gap: the state change and the event are committed in one local transaction, and a relay (or CDC) publishes the event, so downstream views never miss a committed change.
  • Reads are local and fast: each service queries its own materialized view or cache (for example customer name and status inside Orders) with no cross-service calls on the hot path.
  • Integrity is still taken seriously: local foreign keys protect the inside of each aggregate, and reconciliation jobs plus drift metrics catch what eventual consistency can miss.
  • Failure isolation: if Customers is down, Orders keeps accepting orders against its local replica of customer data.
  • Why not just Option B? It is close, but B leaves propagation to application logic. Without a transactional outbox, updating data and notifying others is a dual write that can silently diverge. Option D adds the reliable propagation and observability that make eventual consistency safe.

Aim for strong consistency inside, explicit eventual consistency outside. Track outbox lag, consumer lag, view freshness and reconciliation mismatch counts as first-class SLIs.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🏛️

A — Single Central Database

A shared database gives true foreign keys and ACID transactions, but it erases the independence the scenario demands. Services share a schema, so deployments and migrations must be coordinated, one noisy service can degrade all the others, and the database is a single failure domain and scaling ceiling. Synchronous cross-service transactions hold locks longer and reduce write throughput at peak. It is simple and appropriate for a modular monolith, but not for independently deployed services.

🧩

B — UUIDs, No Cross-DB FKs, App-Level Integrity

This is directionally right: no cross-database foreign keys, globally unique IDs, denormalized parent data and reconciliation. The weakness is that it leaves how changes propagate unspecified. If a service updates its data and then publishes an event as separate steps, a crash in between makes copies diverge, and application-level integrity checks tend to be inconsistent across teams. It also does not keep local FKs inside each service or build in observability. Caveat: add an outbox, idempotent consumers and drift metrics and it becomes Option D.

🌍

C — Globally Distributed SQL with Cross-Node FKs

CockroachDB or Spanner offer strong consistency and cross-node constraints, but cross-region transactions pay consensus round trips on commit, so write latency rises sharply at peak, and hot parent rows (such as popular inventory items) become contention points. More importantly, foreign keys across services couple their schemas: independent deployment and ownership are lost, and a migration in one domain can block another. It does simplify developer reasoning, which is a real benefit, but it trades away the service boundaries. Caveat: a good choice inside one service that needs global consistency.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Single Central Database

Early-stage products or modular monoliths owned by one team, where transactional simplicity matters more than independent scaling.

📌

B — UUIDs, No Cross-DB FKs

Smaller systems where occasional drift is tolerable and the team is disciplined, or as an incremental step toward event-driven integration.

📌

C — Global Distributed SQL

A single service that needs global strong consistency and cross-region transactions (ledgers, inventory of record), kept inside one bounded context.

📌

D — Local FKs + Outbox Read Models

Multi-team microservices that need independent deployment, regional resilience and fast local reads, with acceptable and monitored staleness.

⚠️ Common Mistakes to Avoid

  • Dual writes without an outbox: writing the database and publishing to the broker as separate steps will eventually diverge. Commit the event together with the state change.
  • Non-idempotent consumers: at-least-once delivery means duplicates. Upsert by ID and version, and ignore older versions.
  • Ignoring ordering: events for the same aggregate must be processed in order, so key the stream by aggregate ID.
  • No delete and anonymization story: orphaned references and privacy obligations (erasure requests, for example) need tombstone handling.
  • Treating events as internal: breaking an event schema breaks other teams. Version and validate with a registry.
  • No reconciliation: without comparison jobs and drift metrics, inconsistency is discovered by customers.

🌍 Real-World Best Practice

Teams running microservices at scale usually draw the consistency boundary around the aggregate and treat everything outside it as a contract. A typical sequence:

  • Step 0 — Draw boundaries: identify aggregates and decide which invariants must be strongly consistent (an order and its lines) and which can lag (the customer's display name).
  • Step 1 — Use stable IDs: UUIDv7 or ULID keys, generated by the owning service and never reused.
  • Step 2 — Enforce locally: foreign keys, unique constraints and transactions inside each service database.
  • Step 3 — Publish reliably: an outbox table plus a relay or CDC (for example Debezium) feeding an event stream.
  • Step 4 — Build read models: consumers upsert local views keyed by ID and version.
  • Step 5 — Coordinate with sagas: for multi-service workflows such as reserving stock and then placing the order, with compensations.
  • Step 6 — Observe and reconcile: measure lag and drift, run scheduled comparison jobs, and define repair procedures.

Synchronous cross-service validation is the exception, reserved for operations where staleness is unacceptable.

💡

Key Takeaway

Do not stretch database constraints across service boundaries. Keep foreign keys inside each service, connect services with IDs and reliable events, and make drift visible and repairable.
