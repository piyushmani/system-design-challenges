Maya's Metrics Dilemma: Selecting a Time-Series Storage Strategy

Maya, a backend architect, is building a multi-tenant telemetry platform that ingests 100k samples per second across 500 tenants. Raw data is kept for 90 days and aggregated data for one year. Queries range from sub-second real-time dashboards on recent data to large analytical scans that may run for minutes or hours. The SLOs are 99.95% read availability for dashboards, 99.9% write availability, and under 5 seconds for standard aggregates. Telemetry is append-only (samples are never updated), and dashboards that trail reality by a few seconds are acceptable. At this rate the raw tier alone holds about 778 billion samples (100k × 86,400 s × 90 days), so cost matters. She must choose the data model and storage architecture that best balances ingestion throughput, query latency, availability, consistency and cost.

A
Deploy a single managed relational database (like Postgres) utilizing time-based partitioning and indexes (partitioning by day, using B-tree for time and GIN for tags). Perform synchronous writes via a transactional API to maintain strong consistency, and depend on read replicas to scale query processing.
✗ Not Best
B
Implement a hybrid, append-only architecture: capture/accept samples locally, remote-write into a durable message queue (such as Kafka), then stream into a distributed, write-optimized TSDB (hot store) for recent data, alongside a columnar/cold store (like ClickHouse or object storage with an OLAP engine) for long-term queries. Partition by tenant/time, execute asynchronous downsampling and compaction, and prioritize eventual consistency to boost availability and throughput.
✓ Best Answer
C
Operate a CP-oriented distributed TSDB featuring synchronous replication for all writes (majority quorum) to ensure all nodes share a strongly consistent view. Maintain all data within this single distributed cluster, relying on its built-in compaction and retention policies.
✗ Not Best
D
Establish dedicated per-tenant clusters (one distinct TSDB instance for each tenant) on containerized VMs for strict data isolation. Scale the system by spinning up new tenant clusters and perform cross-cluster queries for aggregated analytics.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — B: Hybrid Queue + Hot/Cold Storage

Telemetry is append-only, write-heavy, time-ordered and tolerant of seconds of lag. The hybrid architecture is the only option that matches storage to that shape: a durable queue absorbs bursts and decouples ingestion from storage, a hot TSDB serves recent dashboards in sub-second time, and a compressed columnar/cold tier makes 90 days of raw data and a year of rollups affordable. Each layer is scaled and tuned for exactly one job. Here's why it stands out:

  • Ingestion throughput and burst absorption: 100k samples/s at roughly 100 bytes each is only about 10 MB/s, trivial for a replicated Kafka topic. Storage nodes can restart, rebalance or fall behind without dropping samples or pushing back on producers, and consumers write in the large batches that TSDBs and columnar engines are built for.
  • Query latency by tier: The last hours or days live in a small hot store, so dashboards stay sub-second. Wide scans go to the columnar tier, which uses compression and vectorized execution. Long analytics can no longer starve dashboards because the two workloads run on different hardware.
  • Cost control: At 50–100 bytes per row (including indexes), 778 billion samples would need roughly 40–80 TB in a row store. TSDB and columnar codecs (delta, Gorilla-style, ZSTD) commonly reach a few bytes per sample, so the same data fits in low single-digit TB depending on cardinality, with cold data on cheap object storage.
  • Availability: The write path depends only on the queue being up, and each read tier fails independently. Because samples are immutable, eventual consistency costs nothing, and avoiding synchronous cross-node coordination is what makes the 99.9% write and 99.95% read SLOs realistic.
  • Tenant fairness at 500 tenants: Per-tenant quotas at the gateway, per-tenant query limits, and partitioning by tenant/time keep one noisy tenant from degrading the others without paying for 500 separate clusters.

Make every stage idempotent (dedupe on tenant + series + timestamp) so queue replays are harmless, and track consumer lag, ingest-to-visible latency, per-tenant cardinality and hot-store query p99. If those stay healthy, the extra tiers are paying for themselves.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🐘

A — Single Relational Database (Postgres)

Time partitioning helps retention (drop a partition) and pruning, but synchronous per-sample transactional writes with a B-tree and a GIN index on tags make every insert expensive (GIN maintenance in particular). Row storage carries per-row overhead, so 90 days of raw data lands in the tens of TB and analytics scans are slow. Read replicas scale reads only: there is still one primary absorbing 100k writes/s, and replicas add lag. Strong consistency buys nothing for immutable samples. Caveat: at a few thousand samples/s with short retention, Postgres (or TimescaleDB) is an excellent, simple choice.

🔒

C — CP Distributed TSDB with Synchronous Quorum Writes

Linearizable writes protect against problems this workload does not have. Every write waits for a majority, which raises write latency, and a node in the minority during a partition rejects writes, directly threatening the 99.9% write SLO. Keeping all 90 days of raw data on the same replicated hot nodes is the most expensive layout, and heavy analytics compete with dashboards for the same CPU and disk. Caveat: CP stores are the right choice for state that needs linearizability (alert state, billing ledgers), not for bulk metrics.

🏢

D — Per-Tenant Clusters

Isolation is excellent, but the average tenant sends only ~200 samples/s (100k / 500). Giving each a highly available cluster (3+ nodes) means 1,500+ mostly idle nodes, and upgrades, monitoring, backups and capacity planning are multiplied by 500. Cross-cluster aggregate queries are slow and fragile, and skewed tenants still need their own scaling work. Caveat: dedicated clusters make sense as a premium tier for a handful of regulated or very large tenants, alongside a shared pool.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Single Postgres

Small scale (up to a few thousand samples/s), short retention, a team that already runs Postgres, and a need for relational joins with metadata. TimescaleDB-style extensions stretch this further.

📌

B — Hybrid Queue + Hot/Cold

Sustained high ingest, mixed real-time and analytical queries, long retention with cost pressure, and a need for burst tolerance and tenant fairness, as in this scenario.

📌

C — CP TSDB, Sync Quorum

Smaller volumes of data where linearizable reads and no acknowledged-write loss matter (alert state, billing events, configuration), not bulk metrics.

📌

D — Per-Tenant Clusters

A handful of tenants with regulatory, data-residency or extreme-scale requirements, offered as a premium tier next to a shared multi-tenant pool.

⚠️ Common Mistakes to Avoid

  • Unbounded label cardinality: Letting tenants use high-cardinality values (user IDs, request IDs) as labels creates millions of series and crushes indexes and memory. Enforce per-tenant active-series limits.
  • Non-idempotent consumers: Queues deliver at-least-once, so a replay can double count. Dedupe on (tenant, series, timestamp) or use insert deduplication tokens.
  • Tiny inserts into the columnar store: Columnar engines like ClickHouse want batches of thousands of rows. Many small inserts create too many parts and degrade merges and queries. Batch in the consumer.
  • Double counting at the hot/cold boundary: If both tiers hold the last day and the router queries both, sums are wrong. Define one authoritative store per time range.
  • Rollups that cannot be re-aggregated: An average of averages or a stored percentile is wrong at coarser levels. Store sum + count, min, max or mergeable sketches.
  • Partitioning only by tenant: The largest tenant becomes a hot partition. Partition by tenant + series hash + time bucket.

🌍 Real-World Best Practice

Large metrics platforms (Mimir/Cortex, Thanos, M3, VictoriaMetrics, ClickHouse-based observability stacks) converge on the same ideas: decouple ingestion from storage, keep recent data hot, push history to cheap columnar or object storage. A typical build-out looks like this:

  • Step 0 — Model the load: Samples/s, active series (cardinality), bytes per sample, query mix and retention math. Most capacity surprises come from cardinality, not rate.
  • Step 1 — Ingest gateway: Authenticate tenants, enforce rate and cardinality quotas, then produce to Kafka (acks=all, replication factor 3) keyed by tenant + series hash.
  • Step 2 — Hot store: Consumers write large idempotent batches to a TSDB or ClickHouse and keep only the last 1–3 days there for sub-second dashboards.
  • Step 3 — Cold store: Columnar tables or Parquet on object storage, partitioned by tenant and day. Raw 90-day retention is enforced by dropping partitions or TTL rules.
  • Step 4 — Downsampling: Asynchronous 1m / 5m / 1h rollups that store sum, count, min and max (or sketches) so they can be re-aggregated. A query router picks the resolution by time range.
  • Step 5 — Tenant tiers and DR: Quotas for everyone, dedicated partitions or clusters for outliers, and cross-zone or cross-region replication of the queue and object storage.

Start with the simplest tier layout that meets the SLOs and add stores only when measurements demand them.

💡

Key Takeaway

For append-only, write-heavy telemetry, spend consistency where it matters and buy availability and cost efficiency with eventual consistency: buffer in a durable queue, keep recent data hot, move history into compressed columnar storage and downsample asynchronously. Keep tenant isolation logical (quotas, partitions) unless a tenant truly needs dedicated infrastructure.
