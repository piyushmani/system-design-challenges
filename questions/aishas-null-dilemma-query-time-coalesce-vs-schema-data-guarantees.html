Aisha's NULL dilemma: query-time COALESCE vs schema data guarantees

Aisha, a backend engineer, owns the User Summary service behind a worldwide mobile and web app. It handles millions of reads per minute and must keep p95 read latency under 50 ms. The user profile schema has several optional columns (timezone, avatar_url, display_name) that are frequently NULL because of legacy creation flows. Product wants a single, simple API that always returns non-null defaults (such as Anonymous, UTC, or a standard avatar URL). Aisha must choose a solution that balances observability, consistency, latency, availability, and scalability, and that includes a viable production migration strategy for legacy records. Which architectural path is the best choice?

A
Retain the current schema and implement defaulting/COALESCE logic within all read queries (e.g., SELECT COALESCE(display_name, 'Anonymous') ...). Make no modifications to the write path, adopting COALESCE as the definitive method for supplying default values to clients.
✗ Not Best
B
Standardize defaults during write operations: update the service's write logic to consistently store non-null canonical values (applying defaults on updates and inserts), incorporate application-tier validation, and execute a gradual background backfill for historical data. Maintain straightforward read queries (without COALESCE) and introduce a NOT NULL constraint after the backfill finishes.
✓ Best Answer
C
Execute a single, blocking synchronous schema migration during a dedicated maintenance window to swap NULLs for default values and modify the columns to NOT NULL. Subsequently, adjust both read and write operations to depend on these NOT NULL columns.
✗ Not Best
D
Keep the database unmodified and manage NULLs at the application level through lazy fetching: if a NULL is encountered during a read, make a synchronous request to the primary profile/identity microservice to retrieve defaults or supplement the data, and then cache the outcome for subsequent read requests.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — B: Defaults on Write, Online Backfill, Then NOT NULL

Fix the data at its source: store canonical values on every insert and update, backfill legacy rows in small online batches, and then lock the guarantee in with a NOT NULL constraint. Reads become plain column projections with one source of truth, and the schema itself enforces the API contract. The migration follows the expand/contract pattern, so each step is incremental, observable, and reversible, with no downtime and no big bang. Here's why it stands out:

  • One source of truth: Default logic lives in one place (the write path plus a database DEFAULT) instead of being copied into every query, mapper, batch job, and downstream consumer. Exports, analytics, and other services see the same non-null values.
  • Simple, fast reads: Reads stay a plain projection. COALESCE itself is cheap per row, so the real win is not CPU: it is removing defaulting from every query path, which also keeps columns usable in filters, joins, and indexes without expression wrappers.
  • Zero-downtime migration: Keyset-paginated, throttled batches avoid long locks. In PostgreSQL, adding the constraint as NOT VALID and validating it later does not block writes, and SET NOT NULL on PostgreSQL 12+ skips the table scan when a validated CHECK already proves the column is non-null.
  • Schema-enforced guarantee: NOT NULL prevents regressions from new code paths, stale mobile clients, and ad-hoc scripts, so the API contract becomes something the database enforces, not something every developer must remember.
  • Measurable and reversible: Progress is a number (COUNT(*) of rows still NULL trending to zero), alongside backfill rate, replication lag, and p95 latency. Every phase can be paused or rolled back until the constraint is validated.

Run it as six phases: (1) write-path defaults plus DB DEFAULT, (2) a NOT VALID CHECK to block new NULLs, (3) throttled backfill, (4) verify zero NULLs, (5) VALIDATE then SET NOT NULL, (6) remove COALESCE. Track NULL counts, backfill throughput, replication lag, and p95 read latency throughout.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🧮

A — COALESCE in Every Read Query

It works immediately, carries almost no per-row cost, and is low risk, but it leaves the underlying data dirty. Defaults are re-implemented in every query, service, and report (and drift apart), NULLs still leak into exports, joins, and filters, nothing prevents new NULLs, and there is no plan for legacy records at all. Caveat: it is a good temporary bridge during the migration, not an end state.

⏱️

C — Single Blocking Migration in a Maintenance Window

A bulk UPDATE of every row followed by SET NOT NULL can hold heavy locks, generate huge WAL and replication lag, and bloat the table. A worldwide service has no quiet window, and shipping read and write changes in lockstep removes the ability to roll back safely. The same end state is reachable with phased, online steps and far less risk.

🔗

D — Lazy Fetch from the Identity Service

Putting a synchronous network call on the read path threatens the 50 ms p95 budget, adds failure coupling, risks thundering herds on cold caches, and can amplify into N+1 call patterns. The data stays dirty, and cached defaults can go stale or diverge from the database. This only makes sense when the missing data genuinely lives in another system.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — COALESCE on Reads

A quick fix or a temporary bridge during migration, or when you cannot modify the data (read-only replicas, third-party schemas). Acceptable when NULL semantics are limited to a single read path.

📌

B — Write Defaults + Backfill + NOT NULL

You own the schema, the data is large and live, and you want a durable guarantee with a zero-downtime path. The right default for production services with many readers.

📌

C — Blocking Migration Window

Small tables, internal tools, or systems with a genuine quiet period where a brief lock is harmless and the migration has been rehearsed on a production-sized copy.

📌

D — Lazy Fetch from Identity Service

The missing data legitimately belongs to another system of record and is rarely needed, with strict timeouts and caching. Not for latency-critical, high-volume read paths.

⚠️ Common Mistakes to Avoid

  • Adding NOT NULL directly on a large table: It scans the whole table under an exclusive lock and can stall every query. Add a NOT VALID CHECK first, validate it, then set NOT NULL, and set a lock_timeout so DDL never queues behind long transactions.
  • One giant UPDATE for the backfill: It creates a huge transaction, replication lag, table bloat, and lock waits. Use small keyset batches with pauses.
  • Backfilling before fixing the write path: The target keeps moving as old writers produce new NULLs. Fix writers and block new NULLs first.
  • Treating presentation text as data: Storing 'Anonymous' in every row makes later changes to that label costly and hides who never set a name. Separate invariants from display defaults.
  • Removing COALESCE before verifying zero NULLs: Clients then receive null values and crash. Verify, enforce the constraint, and only then delete the bridge.
  • Ignoring other writers and readers: ETL jobs, admin scripts, old mobile versions, and downstream consumers may rely on NULL meaning 'unset'. Inventory them before you change semantics.

🌍 Real-World Best Practice

In practice, teams treat this as an expand/contract migration and keep a temporary bridge in place while the data is repaired. A typical sequence looks like this:

  • Step 0 — Measure: Count NULLs per column, find every write source that produces them (legacy flows, ETL, old app versions), and classify each default as a data invariant or a presentation default.
  • Step 1 — Bridge: Keep COALESCE (or an API-layer mapper) in place so clients get stable output while the data is repaired.
  • Step 2 — Fix the write path: Add application-tier normalization and a database DEFAULT, deploy to all writers, and add a CHECK (col IS NOT NULL) NOT VALID constraint to block new NULLs.
  • Step 3 — Backfill online: Run a resumable, keyset-paginated job in small batches, throttled on replication lag and CPU, with a checkpoint so it can pause and resume safely.
  • Step 4 — Enforce: Verify zero NULLs, run VALIDATE CONSTRAINT, set NOT NULL, and drop the temporary CHECK.
  • Step 5 — Clean up: Remove COALESCE and defaulting code, update API contracts and docs, and add a CI lint that flags new nullable columns without a justification.

Treat the schema as the contract and repair data in small, observable steps.

💡

Key Takeaway

Don't paper over dirty data in every query. Enforce defaults on write, backfill history online, then make the database guarantee it with NOT NULL. COALESCE is a fine temporary bridge, but the durable fix is one source of truth in the schema, reached through a phased, zero-downtime migration.
