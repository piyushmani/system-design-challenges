Challenge

Elena's API gateway dilemma: choosing between central gateway, BFFs, GraphQL, or edge logic

Elena, lead backend engineer at a fast-growing e-commerce company, is designing the API layer in front of several microservices (user profiles, catalog, inventory, pricing, recommendations) whose response times differ widely. Clients are Android, iOS, and a SPA. She must keep latency low for mobile users, ship client-specific payloads, run per-client A/B tests quickly, enforce global rate limits and authentication, and keep fault isolation and observability strong at very large scale. Client teams release on different cadences, and the backend services should stay client-agnostic. She needs the API Gateway + Backend-for-Frontend (BFF) architecture with the best trade-off among latency, consistency, availability, scalability, and operational overhead.

A
Build a monolithic API Gateway that owns client-specific logic, transformation, aggregation, routing, and auth for every client, scaled vertically and horizontally, with feature flags and caching built in.
✗ Not Best
B
Use the API Gateway only for cross-cutting concerns (routing, rate limiting, edge caching, TLS, auth) and build a lightweight BFF per client type (web, Android, iOS) that handles aggregation, response shaping, client-specific caching, retries, and A/B tests, scaled independently.
✓ Best Answer
C
Put a single unified GraphQL gateway in front of the services so clients fetch exactly the fields they need, with field-level resolvers, global caching and rate limiting at the GraphQL tier, and schema directives for auth.
✗ Not Best
D
Move most caching and transformation to the edge/CDN using serverless functions (Lambda@Edge/Workers) as minimal BFFs, leaving the core backend services unchanged.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — B: Gateway + Per-Client BFFs

Elena's requirements split cleanly into two kinds of concerns: cross-cutting, client-agnostic ones (TLS, authentication, global rate limits, routing, coarse edge caching) and client-specific ones (payload shape, aggregation, A/B experiments, retries, caching). Option B is the only design that gives each kind its own home: a thin, stable gateway for the first and small, independently deployable BFFs for the second. That keeps the blast radius of any one client's change small, lets each BFF be tuned for its client's network profile, and avoids turning one tier into a bottleneck for every team. Here's why it stands out:

  • Mobile latency: The BFF calls profile, catalog, pricing, inventory, and recommendations in parallel inside the data center and returns one right-sized payload, so a phone makes one round trip instead of five. Per-call timeouts and fallbacks (for example, drop recommendations if they are slow) keep tail latency bounded by the slowest critical dependency rather than the slowest dependency overall.
  • Fault isolation: Separate BFF deployments mean a bad release, memory leak, or traffic spike in the web BFF does not take down the iOS or Android experience. Bulkheads and circuit breakers per downstream service live in the BFF, close to the code that knows what is optional.
  • Fast per-client experimentation: Each client team owns its BFF and can bucket users, ship a variant, and roll back without a coordinated gateway release or a change to the shared backend services.
  • Clean separation of cross-cutting policy: Authentication, global rate limits, WAF, and TLS stay centrally enforced at the gateway, so security and traffic policy are applied once and consistently regardless of which BFF serves the request.
  • Independent scaling and observability: Each BFF scales on its own traffic profile and emits per-client metrics, traces, and error budgets, which makes it obvious which client or dependency is hurting.
  • Proven pattern: The BFF pattern (documented by Sam Newman and used at companies such as SoundCloud) and Netflix's published API redesign away from a one-size-fits-all API toward device-specific adapters were driven by the same problem: different clients need different shapes, and a shared general-purpose API becomes a bottleneck for all of them.

A well-run BFF layer has per-dependency timeouts and circuit breakers, parallel fan-out with partial-response fallbacks, deterministic experiment bucketing, propagated trace IDs, and short client-specific caches for non-personalized data. Measure p95/p99 per client and per downstream call before and after rollout; if one BFF's latency is dominated by a single slow service, fix or cache that service rather than adding more tiers.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🏛️

A — Monolithic Gateway

A single gateway that carries every client's transformation, aggregation, and experiment logic becomes a shared bottleneck and a shared failure domain: one team's change or one noisy client can degrade every client, releases need cross-team coordination, and it tends to turn into a distributed monolith. Scaling the whole tier to satisfy the heaviest client is wasteful, and keeping three clients' experiments in one codebase raises the risk of cross-client regressions. Caveat: for a small team with one or two near-identical clients, a single gateway is the simplest thing that works and a reasonable starting point before the clients diverge.

🔗

C — Unified GraphQL Gateway

GraphQL solves over-fetching and under-fetching well, but making it the single global tier has real costs: HTTP caching is harder (usually POST to one endpoint, so CDN caching and per-URL rate limiting do not work out of the box), rate limiting must account for query cost and depth rather than request count, resolvers can create N+1 fan-out against slow services, and one gateway still concentrates failure and ownership. Per-client A/B tests and payload tuning still need client-aware logic somewhere. Caveat: GraphQL composes well inside a BFF (or as the BFF for the SPA); persisted queries, DataLoader-style batching, and cost limits mitigate most of its issues.

🌐

D — Edge/CDN Functions as BFFs

Edge functions are excellent for cacheable, low-compute shaping such as header-based variants and trimming static payloads, and they put logic close to users. But aggregating five microservices from the edge means many long-haul calls back to the origin region (often slower, not faster), edge runtimes have tight CPU, memory, and execution-time limits, local state and observability are harder, and logic is spread across a vendor's global fleet, which complicates debugging and rollouts. Caveat: use the edge as an accelerator (CDN caching of public catalog data, geo routing, simple A/B assignment), not as the primary orchestration layer.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Monolithic Gateway

A small team with one or two similar clients, early in the product's life, where simplicity matters more than isolation. Revisit when client needs or release cadences diverge.

📌

B — Gateway + BFFs

Several client types with different payload, caching, and experiment needs; multiple teams; a requirement for fault isolation and independent releases.

📌

C — GraphQL Gateway

Many clients with highly variable data needs, a strong schema-governance culture, and the capacity to invest in persisted queries, cost limiting, and resolver performance. Often best used inside or alongside BFFs.

📌

D — Edge Functions

Mostly cacheable, public, read-mostly content (catalog pages, images, static config), geo routing, and simple variant assignment close to users.

⚠️ Common Mistakes to Avoid

  • Letting business logic leak into BFFs: Pricing or eligibility rules copied into three BFFs drift apart. Keep decisions in domain services; BFFs only shape and orchestrate.
  • Sequential downstream calls: Calling profile, then catalog, then pricing in series adds up latencies. Fan out in parallel and set a per-call deadline.
  • All-or-nothing responses: Failing the whole screen because recommendations timed out. Mark dependencies as critical or optional and degrade gracefully.
  • No shared timeout budget: Each layer retrying independently multiplies load (gateway × BFF × client). Propagate a single deadline and retry at one layer only.
  • One shared BFF for all clients: That quietly rebuilds the monolithic gateway. Split by client family, not by team preference.
  • Inconsistent experiment bucketing: If each BFF buckets users differently, one user sees different variants on web and mobile. Use a shared deterministic assignment (hash of a stable user ID plus the experiment key).

🌍 Real-World Best Practice

In practice, teams evolve toward this architecture and keep each layer thin. A typical sequence looks like this:

  • Step 0 — Measure first: Trace the top user journeys (home, product page, checkout) and list the downstream calls each client makes, their payload sizes, and their p95/p99. This shows where aggregation and shaping will actually pay off.
  • Step 1 — Thin gateway: Centralize TLS, authN/Z, rate limiting, WAF, routing, and request IDs at the gateway. No business or client-specific logic.
  • Step 2 — BFF per client family: Start with the heaviest client (usually mobile), then split web if its needs diverge. Give each BFF to the client team that consumes it.
  • Step 3 — Resilience defaults: Add parallel fan-out, per-call timeouts, circuit breakers, and partial-response fallbacks to a shared BFF template.
  • Step 4 — Experimentation: Use a central experiment service for assignment and configuration; BFFs apply the variants and log exposure.
  • Step 5 — Edge and GraphQL as accelerators: Cache public catalog responses at the CDN, and adopt GraphQL inside a BFF (typically the SPA's) if over-fetching becomes the main pain.

Add layers in response to measured pain, not architectural fashion.

💡

Key Takeaway

Keep cross-cutting policy at the gateway and client-specific orchestration in small, client-owned BFFs. That gives mobile users one fast, right-sized round trip, keeps failures contained per client, and lets teams experiment independently. It costs more deployables and some duplication, so keep BFFs thin and share what is truly common. If you only have one client shape, a single gateway is enough.
