Delivering Real-Time Feature Flags Without Adding Request Latency

Aiden, a senior backend engineer, is rolling out a critical payment workflow across a large microservice architecture. He needs to (1) start at 5% of users with instant rollback, (2) add virtually zero per-request latency (under 5 ms), (3) keep high availability across global regions, (4) guarantee consistent user bucketing (a user always sees the same flag state), and (5) provide robust event history and observability for audits. Which feature flag evaluation and distribution architecture best balances these demands?

A
Evaluate feature flags synchronously by querying a central relational database on every incoming request. The management plane updates the database directly, ensuring services always retrieve the most current state during request processing.
✗ Not Best
B
Maintain feature flags in a versioned, in-memory cache within each service instance. The control plane broadcasts flag modifications via a durable pub/sub system (like Kafka). Service instances subscribe to these events to update their local caches, falling back to brief polling of the primary store if events are missed. Flag evaluation occurs server-side using deterministic hashing for user bucketing, with metrics linked to specific flag versions.
✓ Best Answer
C
Shift the responsibility of flag evaluation entirely to the client side: frontend applications poll the central feature flag service at regular intervals (e.g., every 10 seconds) to fetch updates made by the control plane. Implement client-side deterministic hashing to manage rollout bucketing.
✗ Not Best
D
Establish a persistent push connection (such as Server-Sent Events or WebSockets) directly from the control plane to every frontend client and service instance. The control plane immediately pushes all state changes, allowing clients to apply them in real-time, relying entirely on the stability of the push channels for accuracy.

Answer & In-Depth Explanation

🏆 Best Answer — B: Local Versioned Cache with Event-Driven Updates

The key design move is to separate the data plane from the control plane. Evaluating a flag should be an in-memory lookup plus a hash, which costs microseconds and does not depend on any remote system being healthy. Changes flow the other way: the control plane writes a new versioned flag state and publishes it through a durable pub/sub channel, so every instance converges within seconds, and a polling fallback repairs missed events. Deterministic hashing gives sticky bucketing without shared state, and tagging every evaluation with the flag version links metrics and audit to the exact configuration that produced them. Here's why it stands out:

  • Microsecond evaluation with no request-time dependency: A local lookup and hash is orders of magnitude below the 5 ms budget. A network round trip to a database costs at least a millisecond in-region and far more across regions, and it puts the flag store on every request's critical path.
  • Fast, safe rollback: A rollback is just a new flag version (for example rollout 0%) published to every instance, which applies it within seconds. The polling fallback bounds the worst-case delay if an event is missed or a consumer was briefly disconnected.
  • Sticky bucketing without shared state: A stable hash of the flag's salt and the user ID, taken modulo 10,000, always lands the same user in the same bucket on every instance and region. Raising the rollout from 5% to 25% only adds users, so nobody who already has the feature loses it.
  • Globally available by design: Each instance holds a last-known-good snapshot, so a control-plane, database or broker outage does not affect request handling. Regional topics or mirrored brokers keep propagation local to each region.
  • Auditable and observable: Each change is an immutable versioned record (who, what, when, diff), and every evaluation metric or log line carries the flag key and version. That makes it possible to correlate payment error rates and latency with the exact rollout state and to trigger or justify a rollback.

A well-designed flag system includes immutable snapshots swapped atomically, per-flag monotonic versions with gap detection, a durable event stream plus polling fallback, deterministic hashing with a fixed per-flag salt, safe defaults and a readiness gate, a kill switch per flag, and version-tagged metrics feeding automated guardrails. Track propagation delay (publish to applied), snapshot age, evaluation error rate and payment success rate by flag state. If propagation delay exceeds your rollback SLO, fix the delivery path before the next ramp-up.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🗃️

A — Database Lookup on Every Request

Always-fresh data is attractive, but it puts a network round trip and a query on the critical path of every request, turns a small hot table into a database bottleneck at high traffic, and ties every service's availability to that database. Adding a short-TTL cache to fix this is really option B with slower and less predictable propagation. Caveat: for low-traffic admin tools or batch jobs where a few milliseconds do not matter, this is simple and acceptable.

📡

C — Client-Side Polling Every 10 Seconds

Rollback takes at least the polling interval, and clients that are asleep or slow keep the old state longer. Polling load scales with the number of clients rather than services, and shipping targeting and bucketing logic to the client exposes the rules and lets users tamper with them, which is unacceptable for a payment workflow. It can be reasonable for non-sensitive UI toggles served from a CDN.

🔌

D — Persistent Push to Every Client and Instance

Streaming updates is a good idea for services, and many flag platforms do it. The problem is the scope and the absence of a fallback: holding millions of persistent frontend connections creates fan-out and reconnection-storm risk, silent staleness appears whenever a channel degrades, and clients are untrusted for payments. Option B uses push for services together with a polling safety net.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Database per Request

Small systems, internal admin tools or low-traffic back-office jobs where a few milliseconds do not matter and simplicity wins.

📌

B — Local Cache + Events

Latency-sensitive, high-throughput backends with safety-critical rollouts that need fast rollback, global availability and an audit trail.

📌

C — Client Polling

Non-sensitive UI toggles on static or CDN-served sites where updates that take 10 seconds or more are acceptable.

📌

D — Push to Every Client

Consumer or collaborative UIs that need instant updates for non-sensitive features, with a polling or resync fallback in place.

⚠️ Common Mistakes to Avoid

  • A network call per flag evaluation on the hot path: It adds latency and makes the flag store a dependency of every request. Evaluate from a local snapshot.
  • Random or non-deterministic bucketing: Users see the feature appear and disappear between requests. Use a stable hash of salt and user ID.
  • Changing the salt or bucketing key mid-rollout: This reshuffles users, so people who had the new payment flow lose it and others gain it unpredictably. Fix the salt for the life of the rollout.
  • No safe default or readiness gate: A cold-started instance that evaluates as 'on' (or crashes) when it has no snapshot is a production incident. Default risky flags to off and wait for the first snapshot.
  • Evaluating the same flag repeatedly inside one workflow: A flip mid-transaction produces inconsistent payment behavior. Evaluate once at the entry and propagate the decision.
  • No version tagging, ownership or expiry: Without versions you cannot attribute errors to a rollout step, and without owners and expiry dates flags accumulate as untested dead code.

🌍 Real-World Best Practice

Teams that roll out risky changes with flags decide how fast they must be able to roll back and then build delivery around that number:

  • Step 0 — Define requirements: The rollback SLO, criticality per flag, where evaluation happens (server, edge, client) and what the audit trail must contain.
  • Step 1 — Choose the evaluation model: Server-side local evaluation through an SDK backed by an in-memory snapshot. Buy or build (for example a commercial or open-source platform behind the OpenFeature API) with the same architecture.
  • Step 2 — Build the control plane: Versioned flags, role-based access, approvals for payment flags, an append-only audit log, kill switches, and propagation through a stream with polling fallback.
  • Step 3 — Ramp progressively with guardrails: For example 1% then 5%, 25%, 50% and 100%, with automated checks on error rate, p99 latency and payment success tied to the flag version, and automatic rollback when thresholds are crossed.
  • Step 4 — Keep decisions consistent across services: Evaluate once at the entry point, pass the decision in request context, and keep the bucketing salt fixed for the life of the rollout.
  • Step 5 — Maintain hygiene: Flag owners and expiry dates, tests for both code paths, and chaos drills that take down the broker or control plane to confirm last-known-good behavior.

Make evaluation local and boring, and make change distribution fast, versioned and auditable.

💡

Key Takeaway

Keep flag evaluation local and in memory, distribute changes as versioned events over a durable channel with a polling safety net, and use deterministic hashing so users stay in the same bucket. Evaluate once per workflow, set safe defaults, and tag metrics and audit records with flag versions so rollback decisions are fast and defensible. Avoid per-request remote lookups and avoid trusting clients with payment rollout logic.
