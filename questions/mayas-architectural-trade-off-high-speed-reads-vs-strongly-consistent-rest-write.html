Read Latency REST API Consistency
Challenge

Maya's architectural trade-off: high-speed reads vs. strongly consistent REST writes

Maya is architecting a RESTful API for a catalog service used by millions of end-users. Traffic is 90% reads, but writes occasionally surge when inventory or prices change in bulk. Users expect high availability, minimal read latency and standard REST behavior. Slight read staleness is fine for most users, but certain administrative clients need near-real-time consistency for their own changes. She must pick the architecture that best balances availability, latency, scalability, consistency and standard asynchronous REST patterns.

A
Execute synchronous writes to the primary SQL database, then synchronously invalidate and update every distributed cache. The API call blocks until caches and replicas match and returns 200 OK only when total system consistency is achieved.
✗ Not Best
B
Use a cache-aside approach: reads check the cache before the DB, writes commit to the DB, evict the relevant cache entries and return 200 OK once the DB commit succeeds. Use short TTLs and rigorous invalidation to limit staleness.
✗ Not Best
C
Use an asynchronous command pattern: the REST API returns 202 Accepted for writes, uses idempotency tokens for commands, emits events to an event bus and updates separate read models (CQRS) asynchronously. Provide webhooks or a status endpoint for admins who need real-time confirmation, and use resource versioning or ETags on read endpoints.
✓ Best Answer
D
Run every write through a distributed consensus mechanism (such as Raft or etcd) so all nodes agree before the request is acknowledged. Keep one strongly consistent source of truth and send reads straight to this store.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — C: Async Command (202 Accepted) + CQRS Read Models

Option C is the best fit. It treats a write during a surge for what it really is, a command that has been accepted but not yet applied, and uses the standard HTTP vocabulary for that: 202 Accepted plus a status resource. Reads come from independently scalable read models and HTTP caches, while admins get an explicit way to confirm or wait for their change. Here's why it stands out:

  • Honest HTTP semantics: RFC 9110 defines 202 Accepted as accepted for processing but not yet completed. The response carries a Location header that points to an operation (status) resource, which clients poll or learn about through a webhook. Option B returns 200 OK for a change that readers may not see yet, which overstates what has happened.
  • Writes cannot starve reads: a durable command log or queue absorbs price and inventory surges, and the read side scales on its own (CDN, caches, replicas or a search store). A write burst slows how fast the read model catches up, not how fast users get product pages.
  • Safe retries: an Idempotency-Key header on the command endpoint lets clients and gateways retry after a timeout without applying the same price change twice (POST is not idempotent by default).
  • Two consistency tiers, made explicit: public clients read the read model with Cache-Control and ETag (conditional GETs return 304) and accept seconds of staleness. Admins use the operation status endpoint or a webhook, and can pass a minimum-version token to get read-your-writes behavior.
  • Optimistic concurrency: If-Match with the resource ETag rejects stale edits with 412 Precondition Failed, so two admins editing the same price cannot silently overwrite each other.
  • Auditability and replay: the event log gives a full history of changes, lets read models be rebuilt, and makes projection lag a measurable metric.

Pair 202 Accepted with a status resource, idempotency keys, per-resource ordering and a projection-lag metric. Track p99 read latency, write-to-visible delay and the share of reads served from cache before and after rollout.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🔒

A — Fully Synchronous Writes

Blocking the response until the database, every cache and every replica match ties write latency and availability to the slowest component. If one cache node is down, the write either fails or returns an ambiguous result, and a surge turns into a pile of blocked requests. It also cannot make copies change at the same instant: you would need synchronous replication everywhere, which sacrifices exactly the availability the users demand. Caveat: synchronous confirmation is fine inside a single database transaction, just not across a fleet of caches and replicas.

🗄️

B — Cache-Aside with Eviction

This is a strong, simple and very common design, and the closest runner-up. It falls short here for three reasons. The write path is still synchronous to the primary, so a write surge hits the database directly. Eviction creates invalidation races (a slow reader can put an old row back after the writer evicts it) and stampedes on hot keys. And nothing in it gives clients a standard way to retry safely or to confirm an outcome. Caveat: for moderate write rates, cache-aside plus ETags and an admin bypass that reads from the primary is perfectly reasonable.

🗳️

D — Consensus on Every Write

Raft-based systems such as etcd are built for small, critical coordination data (configuration, leader election, locks), not for high-volume catalog data. Sending 90% of traffic from millions of users to one strongly consistent store creates a read bottleneck, adds cross-region quorum latency, and makes the system unavailable when a quorum is lost (a CP choice, opposite to the availability goal). REST does not require this level of consistency either.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Fully Synchronous Writes

A single database transaction or a small, co-located system where all copies can be updated atomically and write volume is low. Not suitable for fleets of caches and replicas.

📌

B — Cache-Aside

Read-heavy workloads with moderate write rates, where writes can safely hit the primary directly and some staleness is acceptable. Add an admin read-from-primary path for strict consistency.

📌

C — Async Command + CQRS

Read-dominated systems with write surges, different consistency needs per client type, and a need for safe retries, auditability and independent scaling of reads and writes.

📌

D — Consensus on Every Write

Small, critical coordination data such as configuration, leader election, locks or service discovery, where linearizability matters more than throughput.

⚠️ Common Mistakes to Avoid

  • Returning 202 before the command is durable: if the app crashes after replying, the write is lost. Persist the command and the outbox row in one transaction first.
  • Validating in the background: accepting invalid requests and failing later forces clients to poll for errors that could have been a synchronous 4xx.
  • No status resource or Location header: clients have no standard way to learn the outcome. Expose GET /operations/{id} with pending, succeeded and failed states.
  • Missing idempotency keys: retries after gateway timeouts apply the same change twice or create duplicates.
  • Ignoring ordering and versions: parallel consumers can apply an older update after a newer one. Partition by resource id and compare versions.
  • Invisible projection lag: without a lag metric or a version signal, support cannot tell a slow projector from a lost event.

🌍 Real-World Best Practice

In practice, teams classify endpoints by how much staleness each can tolerate before choosing a mechanism. A typical sequence looks like this:

  • Step 0 — Classify consistency needs: list which reads can be stale (browse, search) and which cannot (admin edits, checkout price), and set a numeric freshness target for each.
  • Step 1 — HTTP caching first: add Cache-Control, ETag and CDN caching to GET endpoints. It is cheap and removes most read load by itself.
  • Step 2 — Command endpoint: accept writes as commands with an Idempotency-Key, synchronous validation, and 202 Accepted with a Location header for the operation resource.
  • Step 3 — Outbox and event log: write the command and an outbox row in one transaction, then relay it to the bus so no accepted command is lost.
  • Step 4 — Read-model projections: build denormalized read stores per access pattern, apply events idempotently by version, and alert on projection lag.
  • Step 5 — Admin guarantees: offer operation polling, signed webhooks and a minimum-version read option, or a read-from-write-model path for the few endpoints that need it.
  • Step 6 — Backpressure: rate-limit command intake with 429 and Retry-After so surges degrade gracefully instead of flooding the bus.

Start with HTTP caching and add the command pipeline only where write surges or admin guarantees demand it.

💡

Key Takeaway

Treat reads and writes as different problems. Serve reads from cache-friendly read models, and accept writes as idempotent commands with 202 Accepted and a status resource. This keeps reads fast and available during write surges and gives admins an explicit way to confirm their changes, at the price of more moving parts. If write volume is modest, cache-aside with an admin read-from-primary path is a reasonable simpler alternative.
