Challenge

Enforcing Global Per-Key Rate Limits Without Sacrificing Latency or Availability

Maya, a senior backend developer, is designing the rate limiter for a public REST API served by stateless frontend nodes in many regions. Limits are enforced per API key (for example 100 requests/minute), aggregate traffic can burst to 100k requests per second, and the limiter may add at most 10 ms to a request. The API must keep serving through a region-wide outage, return accurate 429 responses with retry hints, and emit real-time telemetry. The business accepts small, bounded over-admission (a few percent beyond the quota, briefly) but not an unlimited bypass, and a small share of keys generates most of the traffic. She needs the architecture with the best overall trade-off.

A
A single authoritative Redis cluster enforced synchronously on every request (Lua script for atomic increment and expiry). Strictly consistent, but every request pays a network round trip to one place.
✗ Not Best
B
Fully decentralized local in-memory token buckets on each frontend node, with usage shipped asynchronously to a metrics pipeline for analytics only. No central dependency in the request path.
✗ Not Best
C
A managed global API gateway or CDN rate-limiting feature configured with per-key limits, relied on for enforcement, 429s, scaling, availability and monitoring.
✗ Not Best
D
A hybrid two-tier design: a fast approximate local token bucket on each frontend for normal traffic, consulting a centralized consistent store (e.g., Redis) only when a key approaches its quota. The central store is the authoritative ledger, and frontends fall back to conservative local limits if it is unreachable.

Answer & In-Depth Explanation

🏆 Best Answer — D: Hybrid Two-Tier Limiter

The constraints conflict if one mechanism has to satisfy all of them: strict global precision needs coordination, while a 10 ms budget and region-outage survival forbid a mandatory synchronous cross-region call. The hybrid two-tier limiter resolves this by making coordination rare and bounded: the common case is a local memory operation, and the central ledger is consulted only where precision matters (keys near their quota). Here's why it stands out:

  • Latency stays in microseconds for most requests: A local token-bucket check is a few memory operations, far inside the 10 ms budget. Only keys near their limit pay a Redis round trip, and that can be a same-region call.
  • Precision where it matters: Far from the quota, small local error is harmless. Near the quota, nodes switch to small leases (down to one token at a time) from the central ledger, so the global count is enforced tightly exactly when a 429 decision is imminent.
  • Graceful degradation: If Redis or a region is unreachable, nodes continue with a conservative local limit (for example the key's quota divided by the expected number of active nodes). The API stays up and over-admission is bounded instead of unlimited.
  • Scales with keys, not requests: Central traffic is proportional to lease refills and near-quota keys, not to the 100k rps aggregate, so the ledger can be sharded by API key and sized for a fraction of peak.
  • Observability is built in: Each node emits counters (allowed, denied, lease refills, fallback mode) asynchronously, giving real-time per-key telemetry without touching the request path. Responses carry Retry-After and X-RateLimit-* headers computed from local state plus the last lease.

A production implementation includes quota leasing with adaptive lease sizes, atomic Lua scripts in the central store, per-key sharding of that store, a circuit breaker with a conservative local fallback, and asynchronous telemetry. Measure over-admission directly (admitted requests vs configured quota per window) and tune lease size and safety margin against that number.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🗄️

A — Single Central Redis

Synchronous Lua-based counting gives exact counts, but every request now depends on one cluster. A cross-region round trip (often 50–150 ms) alone breaks the 10 ms budget for distant regions, a regional outage of that cluster takes the limiter (and the API, if fail-closed) down with it, and 100k rps against one logical store needs heavy sharding while still concentrating risk. Caveat: a regional deployment of this pattern is an excellent building block inside the hybrid design, as the authoritative ledger.

🧮

B — Pure Local Token Buckets

Highest availability and lowest latency, but there is no global view. With N nodes each enforcing the full quota, a key can be admitted up to N × limit, and a client that spreads requests across nodes bypasses the limit entirely; autoscaling silently loosens it further. The 429s are therefore imprecise, which contradicts the requirement. Caveat: it is the right model for coarse protection (per-node concurrency caps, DDoS shielding) and as the fallback mode of the hybrid.

🌐

C — Managed Global Gateway

Managed gateways remove operational toil and are a good first line of defense, but 'strict out of the box' is rarely true: some document their throttling as best-effort targets, counters are often per edge location or eventually synchronized, and you get limited control over dynamic per-key quotas, header semantics, lease behavior and telemetry granularity. You also inherit the vendor's failure modes. Caveat: for simple per-IP or coarse limits it can be sufficient, and it is often layered in front of a custom per-key limiter.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Central Redis

A single-region (or region-affine) API where nodes are close to the store, traffic is moderate and exact counting is contractually required (for example billing-grade quotas).

📌

B — Local Token Buckets

Per-node protection, concurrency caps or coarse abuse shielding; also the fallback mode when central coordination is unavailable.

📌

C — Managed Gateway

Simple per-IP or per-route limits, a quick launch, or an outer layer in front of a custom per-key limiter.

📌

D — Hybrid Two-Tier

Global, multi-region APIs with large aggregate traffic, tight latency budgets, per-key quotas and a need to survive region failures with bounded error.

⚠️ Common Mistakes to Avoid

  • Oversized leases: Handing each node a big slice of the quota makes over-admission roughly nodes × lease size. Size leases as a small fraction of the remaining quota and shrink them near the limit.
  • Stranded quota: Leases held by crashed or idle nodes silently reduce what clients can use. Give leases a short TTL and return unused tokens on graceful shutdown.
  • Non-atomic central updates: A read-then-write against the ledger races under concurrency. Use a single Lua script (or equivalent atomic primitive) that checks and decrements in one step.
  • Synchronous central calls with no timeout: A slow Redis then becomes a latency outage. Use tight timeouts (low single-digit milliseconds) and a circuit breaker that flips to local fallback.
  • Using wall-clock time for refills: Clock adjustments cause bursts or stalls. Use monotonic clocks locally and server-side time (or window IDs) centrally.
  • No telemetry on the limiter itself: Without counters for fallback mode, lease refills and measured over-admission, you cannot tell whether the limiter is protecting you or silently failing open.

🌍 Real-World Best Practice

In practice, large API platforms layer several mechanisms rather than choosing one, and they measure over-admission and added latency before tuning. A typical sequence looks like this:

  • Step 0 — Define the contract: Decide the acceptable error (for example up to 5% over-admission for a few seconds), the algorithm (token bucket for bursts, sliding window for fairness) and the fail-open or fail-closed policy per customer tier.
  • Step 1 — Coarse edge protection: Use the CDN or managed gateway for per-IP limits and volumetric abuse so garbage traffic never reaches your fleet.
  • Step 2 — Local token buckets: Add in-process buckets keyed by API key as the always-on first tier. They cost microseconds and protect each node.
  • Step 3 — Central ledger with leases: Add a sharded, regional Redis (or similar) holding authoritative counters. Nodes borrow token leases and report usage asynchronously.
  • Step 4 — Region failure handling: Reconcile ledgers across regions asynchronously, and test the fallback mode (kill Redis, partition a region) in game days.
  • Step 5 — Telemetry and tuning: Stream allowed, denied and fallback counters to dashboards and alerts, and tune lease size and safety margin from measured over-admission.

Add coordination only where measurements show local state is not precise enough.

💡

Key Takeaway

Don't coordinate every request, and don't coordinate none. Enforce locally, reconcile centrally, and tighten precision only near the quota. Accept a small, measured over-admission in exchange for single-digit-millisecond overhead and survival of regional failures, and choose the fail-open or fail-closed policy deliberately.
