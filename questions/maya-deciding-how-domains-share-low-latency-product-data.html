Domain Driven Design Data Sharing Low Latency
Challenge

Maya Deciding How Domains Share Low-Latency Product Data

Maya, a platform architect at a fast-growing e-commerce company, is moving to a Data Mesh. The Product, Inventory, Pricing and Checkout domains each have their own team and OLTP database. Checkout needs extremely low-latency reads of price and inventory to validate carts, and can tolerate sub-second to a few seconds of staleness on those reads (the final stock reservation is made authoritatively by the owning domain). Analytics pipelines need near-real-time updates and reporting teams need a governed, discoverable source. Every domain must own its data, and the platform must stay highly available, scalable, observable and affordable. She must choose a cross-domain data sharing architecture that balances cost, fault tolerance, consistency and latency.

A
Fully centralized: a central data team runs a master data warehouse, domains upload nightly ETL extracts, and all operational and analytical consumers query the warehouse.
✗ Not Best
B
Decentralized, event-driven data products: domains publish change events under strict contracts to a central streaming platform; consumers such as Checkout maintain local materialized views or stream processors for low-latency reads, while the platform provides SLAs, access control, monitoring and a schema registry.
✓ Best Answer
C
Synchronous API sharing: each domain exposes HTTP/gRPC APIs and consumers call them directly for real-time data, relying on each domain's latency and availability SLAs, with optional caller-side caching.
✗ Not Best
D
Hybrid lakehouse with CDC: replicate domain database changes into a shared lakehouse (Iceberg or Delta) and serve both analytics and near-real-time operational queries from it using streaming engines or materialized views.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — B: Event-Driven Data Products

Given these requirements (domain ownership, millisecond reads for Checkout, near-real-time analytics, governed discovery), decentralized, event-driven data products are the best fit. Data Mesh asks each domain to publish its data as a product with a contract, an owner and SLAs. Events on a streaming platform let every consumer build the read model it needs: Checkout gets local reads, analytics gets a continuous feed, and governance applies in one place without centralizing ownership. Here's why it stands out:

  • Domain ownership preserved: Each domain owns its event contract (schema, versioning, quality) as a published product. The central platform provides tooling (registry, access control, observability) but not the data semantics, which matches the Data Mesh principles of domain ownership, data as a product and federated governance.
  • Low-latency reads without runtime coupling: Checkout reads price and inventory from its own materialized view (in-memory cache or local store) in single-digit milliseconds. A slow or unavailable Inventory service does not break cart validation, which removes a synchronous dependency from the critical path.
  • One feed, many consumers: Analytics, reporting and search subscribe to the same ordered event streams. Adding a consumer puts no extra load on the domain's OLTP database and keeps the data consistent across consumers.
  • Governed and observable by design: A schema registry with compatibility rules, data contracts, consumer-lag metrics, dead-letter queues and lineage give the platform one place to enforce SLAs and make products discoverable.
  • Fault isolation and replay: A durable, partitioned log lets consumers fall behind, restart, or rebuild a view by replaying from an offset. Failures stay local to a consumer instead of cascading through synchronous call chains.

A solid implementation uses the transactional outbox for reliable publishing, keyed partitions for per-entity ordering, idempotent consumers, a schema registry with compatibility checks, freshness and lag SLOs per data product, and a synchronous authoritative API for the few operations that cannot tolerate staleness. Land the same streams in the lakehouse for analytics instead of making the lakehouse the serving layer.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🏢

A — Centralized Warehouse with Nightly ETL

A nightly batch cannot meet near-real-time analytics and is far too slow for Checkout's price and inventory validation (the data is up to a day old, and a warehouse is not an OLTP read path). It also moves ownership to a central team, which becomes a bottleneck for every schema change and contradicts Data Mesh principles. Caveat: a central warehouse is still a good consumer of data products for governed reporting; it is just not the sharing mechanism.

🔗

C — Synchronous API Sharing

Direct API calls give fresh data and strong semantics but create tight runtime coupling: Checkout's latency and availability become the product of its dependencies' latency and availability, and traffic spikes in Checkout propagate to Pricing and Inventory. Analytics and reporting would have to poll OLTP APIs, which does not scale. Caveat: synchronous APIs remain the right tool for authoritative operations (reserve stock, place an order) and for request-time reads that must be exactly current.

🏞️

D — Shared Lakehouse via CDC

CDC into a lakehouse is excellent for analytics, but as the serving layer for operational reads it falls short: table formats like Iceberg and Delta are optimized for scans and commits measured in seconds to minutes, not for point lookups in single-digit milliseconds. Raw CDC also exposes internal table schemas rather than a stable contract, and a centralized lakehouse tends to re-centralize ownership. Caveat: it works well as one of the consumers of option B's event streams, which is how most mesh implementations feed analytics.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Centralized Warehouse

Governed, batch-oriented reporting where hours of latency are acceptable and a central team curates a small set of conformed dimensions. Best as a consumer of data products.

📌

B — Event-Driven Data Products

Multi-team organizations where several consumers need the same domain data at different latencies, domains must own their contracts, and request-time reads must not depend on other services being up.

📌

C — Synchronous APIs

Authoritative operations and request-time reads that must be exactly current (reserve stock, charge a payment), or small systems where one or two consumers do not justify a streaming platform.

📌

D — Lakehouse via CDC

Analytics and ML workloads, historical queries and legacy sources that cannot publish events. Not for millisecond operational reads.

⚠️ Common Mistakes to Avoid

  • Publishing raw table changes as the contract: Consumers couple to internal schemas, and every refactor breaks someone. Publish domain events or a curated public model through an outbox.
  • Dual writes without an outbox: Writing to the database and then publishing to the broker in two steps loses events when one of them fails. Write the event in the same transaction and relay it.
  • Ignoring ordering and idempotency: Redeliveries and out-of-order events corrupt views. Key by entity ID, include a version or sequence number, and make updates idempotent (apply only if the version is newer).
  • Using stale views for authoritative decisions: Reserving the last unit of stock from a cached view oversells. Validate quickly from the view, then reserve through the owning domain.
  • No schema evolution rules: Without compatibility checks, a producer change breaks consumers in production. Enforce backward-compatible changes in the registry and version breaking changes.
  • No freshness SLO or lag alerting: A silent consumer lag means Checkout shows old prices for hours. Define a maximum staleness per data product and alert on lag and on event age.

🌍 Real-World Best Practice

In practice, mesh platforms combine several mechanisms and choose one per access pattern. A typical sequence looks like this:

  • Step 0 — Classify access patterns: Separate request-time reads (milliseconds), authoritative writes (strong consistency), near-real-time analytics (seconds) and reporting (minutes to hours). Each has a different best mechanism.
  • Step 1 — Publish domain events as products: Each domain emits events through the outbox pattern with a versioned schema, an owner, an SLA and documentation in a catalog.
  • Step 2 — Give serving consumers local read models: Checkout and similar services materialize the fields they need into a cache or local store, with a defined maximum staleness.
  • Step 3 — Keep an authoritative path: Use synchronous APIs or reservation workflows for operations that must be exactly right, such as stock reservation at order placement.
  • Step 4 — Land streams in the lakehouse: Feed analytics and reporting from the same events (or from CDC for legacy sources), with governed, discoverable tables.
  • Step 5 — Operate the platform: Monitor consumer lag, schema compatibility, data quality and cost, and enforce access policies centrally while ownership stays federated.

Choose the mechanism per access pattern, not one mechanism for everything.

💡

Key Takeaway

In a Data Mesh, domains publish events as contracted data products, consumers build local read models for low latency, and a central platform provides governance and tooling rather than ownership. Synchronous APIs remain for authoritative operations, and the lakehouse is an analytical consumer rather than the operational serving layer.
