Instant rollouts vs. low latency: Where should feature flags be evaluated?

Maya is the platform architect for a globally distributed SaaS application serving millions of users across regions. Customers expect API responses under 100 ms, while product teams need instant rollouts and emergency kill switches. Today every API request calls a central flag service, which inflates tail latency and is a single point of failure during outages. She must redesign flag evaluation to keep latency low at scale, enable near-real-time rollouts and rollbacks, stay highly available in every region, and provide observability into flag changes and their effects. Which architecture should she adopt?

A
Keep centralized synchronous evaluation: query the central flag service on every request, scale it horizontally and add caching layers in front, for immediate global consistency.
✗ Not Best
B
Local in-memory caching with periodic polling: services evaluate flags locally from a cache refreshed by polling the central datastore every few seconds, falling back to the last known values if the store is unavailable.
✗ Not Best
C
Push-based local evaluation with fallbacks: a central control plane stores flags and broadcasts changes through a global pub/sub system; each instance runs a local SDK that evaluates flags from an in-memory cache, receives changes over a persistent connection (gRPC or SSE), falls back to polling or last-known values if the connection drops, and emits change events for metrics and audit logs.
✓ Best Answer
D
Deployment-time flags: bake flags into deployment artifacts or environment variables, use canary deployments for gradual rollouts, and rely on rollbacks and redeploys to toggle features.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — C: Push-Based Local Evaluation

The core insight is to separate the control plane (where flags are authored, audited, and distributed) from the data plane (where flags are evaluated on the request path). Evaluating in-process from an in-memory ruleset takes microseconds and has no network dependency, which fixes both the tail latency and the single point of failure, while a push channel with a polling fallback keeps propagation in the sub-second to few-second range. Here's why it stands out:

  • Zero network hops on the hot path: Evaluation is an in-process function call over a locally cached ruleset (typically microseconds), so flag checks stop contributing to p99 and the 100 ms API budget is untouched.
  • Fast propagation: Changes streamed over SSE or gRPC typically reach instances in about a second or less (depending on fan-out topology), which is what makes kill switches useful during incidents. Polling alone (Option B) is bounded by the poll interval and adds load proportional to fleet size.
  • Survives outages (fail-static): If the control plane or the push channel fails, instances keep serving from the last known ruleset and reconnect with backoff, while a bootstrap snapshot or code-level defaults cover cold starts. A flag-service outage stops being an API outage.
  • Regional fan-out: Regional relay or proxy nodes (the pattern behind LaunchDarkly's relay proxy, Unleash Edge, and flagd/OpenFeature setups) hold the persistent connections to local instances, so the control plane does not carry tens of thousands of direct connections.
  • Observability built in: Control-plane audit logs record who changed what and when, and SDKs emit evaluation counts, ruleset versions, and propagation lag per instance, so a flag change can be correlated with error-rate or latency shifts.

A mature setup includes versioned, validated rulesets, push with polling fallback, a bootstrap snapshot shipped with the artifact, deterministic bucketing, flag lifecycle management (owners, expiry, cleanup), and metrics on propagation lag and stale instances. Test the failure path regularly by cutting the control plane and confirming the platform keeps serving.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🌐

A — Centralized Synchronous Evaluation

Scaling and caching the central service reduces load but not the architectural problem: every request still pays a network round trip, the flag service stays on the critical path, and a regional or global outage still takes the API down. Adding a cache in front also undermines the 'immediate global consistency' claim, since cached entries are stale by definition. Caveat: a central call can be acceptable for rarely evaluated, low-QPS back-office paths.

⏱️

B — Local Cache with Polling

A simple, widely used design and a valid fallback layer: local evaluation fixes latency and availability. The shortfall is propagation: a kill switch takes up to a full poll interval, and thousands of instances polling creates thundering-herd load unless you add jitter, ETags, or a CDN or relay in front. If a few seconds of delay is acceptable and you want the lowest operational cost, it is a legitimate choice, and it is exactly what Option C falls back to when the push connection drops.

🚢

D — Deployment-Time Flags

Deployment-time flags couple release speed to your CI/CD pipeline: a rollback takes minutes at best (build, canary, rollout), per-user or percentage targeting is impractical with environment variables, and an emergency kill switch would depend on the very deployment system that may be degraded during an incident. Flag state is also hard to audit across services. Caveat: deployment configuration is fine for permanent operational config (not true flags), and canaries complement flags for risky code releases.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Central Sync Evaluation

Low-QPS administrative or back-office paths where a network call is affordable and instant global consistency matters more than latency.

📌

B — Local Cache + Polling

Smaller systems or relaxed propagation needs (tens of seconds is fine), or as the fallback path inside a push-based design.

📌

C — Push-Based Local Evaluation

Latency-sensitive, multi-region services that need kill switches in seconds, audit trails, and resilience to control-plane outages.

📌

D — Deployment-Time Flags

Static configuration that rarely changes (not true feature flags), or gating that should be tied to a specific build.

⚠️ Common Mistakes to Avoid

  • Evaluating flags with a remote call per request: Even a fast service adds tail latency and puts a dependency in the critical path.
  • No safe defaults: If the SDK cannot load rules at cold start and the code has no default, you get exceptions or the wrong behavior. Every flag needs a default and every service a bootstrap.
  • Push without a polling fallback: Long-lived connections drop silently behind proxies and load balancers. Without heartbeats and a poll fallback, instances can run on stale rules for hours.
  • Thundering herd on reconnect: After an outage, every instance reconnects and refetches at once. Use jittered backoff and regional relays that serve cached rulesets.
  • Non-deterministic bucketing: Random numbers instead of a stable hash flip users between variants and corrupt experiments.
  • Flag debt: Flags that are never removed create combinatorial test states and dead code paths. Give each flag an owner and an expiry.

🌍 Real-World Best Practice

Mature teams layer these approaches and keep the evaluation path free of network calls:

  • Step 0 — Classify flags: Release flags, ops flags and kill switches, experiments, and permission flags have different latency, audit, and lifetime needs. Kill switches get the strictest propagation and safety rules.
  • Step 1 — Local evaluation: Ship an SDK that evaluates from an in-memory ruleset; this alone removes the latency and single-point-of-failure problems.
  • Step 2 — Streaming updates: Add SSE or gRPC push through regional relays, with polling (jitter plus ETag) as the fallback.
  • Step 3 — Bootstrap and defaults: Include a ruleset snapshot in the artifact or fetch it at startup from regional storage, and define a safe code-level default for every flag.
  • Step 4 — Observability and governance: Audit logs, per-instance version metrics, propagation SLOs, flag ownership, and expiry dates.
  • Step 5 — Combine with canaries: Use progressive delivery for code changes and flags for behavior changes, so a bad release can be switched off without a rollback.

Set propagation targets (for example, 99% of instances within 5 seconds) from the business need for kill switches, not from the technology.

💡

Key Takeaway

Move evaluation into the request path's own process and keep the central service as a control plane only. Push for speed, poll for safety, and fail static with defined staleness limits. A flag decision should never need a network call on the hot path.
