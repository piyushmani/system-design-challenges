Mitigating Hot Keys in a Read-Heavy, Cache-Fronted User-Profile Service

Ava runs a read-heavy (95% reads) user-profile service that feeds a product feed with a p95 target under 50 ms and tolerates a few seconds of staleness. One profile recently went viral and became a hot key: the single memcached node that owns it (consistent hashing maps a key to exactly one node) is saturated, and whenever the entry expires, a surge of concurrent requests misses together and overloads the database. The stack is a primary SQL database with a basic memcached cluster using consistent hashing. She needs a design that prevents single-key hotspots from hurting availability and latency while keeping cost and operational complexity manageable.

A
Global lock per key: on a miss, a request takes a distributed lock and refreshes the cache from the database while all others wait, ensuring a single updater and strict consistency.
✗ Not Best
B
Write-through caching with synchronous database updates and all reads through a much larger cache tier, keeping the same consistent-hashing layout and relying on bigger instances to absorb spikes.
✗ Not Best
C
Dedicated hot-key management: detect hot keys with metrics, replicate them across multiple cache nodes or a separate tier, coalesce concurrent misses into one database query, and use controlled TTLs (or async write-behind) to allow bounded staleness.
✓ Best Answer
D
Aggressive caching: long TTLs, client-side caching, and stale-while-revalidate, serving slightly stale data while background jobs refresh it, with clients retrying if needed.
✗ Not Best

Answer & In-Depth Explanation

🏆 Best Answer — C: Dedicated Hot-Key Management

A hot key is a concentration problem: one key's traffic lands on one cache node, and when the entry expires, all concurrent misses stampede the database. The fix must therefore both spread read load for that key and collapse duplicate refreshes. Dedicated hot-key handling does both, inside the staleness budget the product already allows. Here's why it stands out:

  • Spreads the read load: Replicating a hot key across several cache nodes, or serving it from an in-process L1 cache with a 1 to 2 second TTL, means no single node answers every request. This removes the node-level hotspot that scaling up or locking leaves in place.
  • Prevents stampedes: Request coalescing (single-flight) collapses thousands of concurrent misses into one database read per instance, and a short lease across instances reduces that to roughly one read per refresh.
  • Fits the staleness budget: Because a few seconds of staleness is acceptable, jittered TTLs, soft expiry, and stale-while-revalidate keep p95 low without heavy consistency machinery.
  • Targeted cost: Only the small set of keys detected as hot (for example via top-k or count-min-sketch counters) gets extra replicas, so the rest of the cluster stays simple and cheap.
  • Adapts to the next viral key: Automatic detection means the system responds without manual intervention.

A practical stack is L1 in-process cache (1 to 2 s) → replicated hot-key tier → memcached or Redis → database, with single-flight, TTL jitter, stale-while-revalidate, and a rate-limited database fallback. Watch per-key QPS, per-node CPU and network, hit rate, and database QPS.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🔐

A — Centralized Global Lock per Key

Locks prevent duplicate refreshes but do nothing for the hit path: the node that owns the hot key still serves every read. Waiters queue behind the lock holder, so tail latency can exceed 50 ms, a slow or failed lock holder blocks everyone until its lease expires, and the lock service becomes another dependency on the critical path. Caveat: a short, non-blocking lease (one request refreshes while others serve stale data) is a useful component of option C, but blocking waiters is not.

📈

B — Write-Through + Bigger Cache Tier

Write-through keeps the cache fresh after writes, but this workload is 95% reads and the problem is read concentration on one key. Consistent hashing still maps that key to one node, so larger instances only raise the ceiling slightly while raising cost for the whole cluster, and synchronous database updates add write latency. Caveat: useful if the pain were write-to-read staleness or cold caches, not hot keys.

⏳

D — Long TTLs + Client-Side Caching + Stale-While-Revalidate

This is a valuable and complementary tactic: serving stale data while refreshing in the background and caching in clients removes much of the load. On its own it leaves gaps: long TTLs can stretch staleness beyond the few seconds allowed, the first miss after a cold start or eviction still stampedes without coalescing, client caches are hard to invalidate, and nothing spreads load across cache nodes for the hot key. Caveat: as a layer inside option C it is excellent; as the entire strategy it trades correctness bounds for simplicity.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Global Lock per Key

Rare, expensive recomputations on keys with moderate read traffic where duplicate refreshes are the only problem. Prefer non-blocking leases.

📌

B — Write-Through + Bigger Cache

Workloads where write-to-read freshness matters most and traffic is spread evenly across many keys, so total cache tier capacity is the limit.

📌

C — Hot-Key Management

Skewed, read-heavy traffic with viral or celebrity keys, strict tail latency, and a staleness budget of seconds.

📌

D — Long TTL + SWR + Client Cache

Content that tolerates minutes of staleness, mostly public data, or as one layer inside a hot-key strategy.

⚠️ Common Mistakes to Avoid

  • Treating a hot key as a capacity problem: Bigger nodes do not help because consistent hashing keeps the key on one node. Spread the key, not the cluster.
  • Synchronized expiry: Identical TTLs make popular keys expire together. Add jitter and refresh early with a soft TTL.
  • Blocking waiters on a lock: Queues form and p95 blows up. Let waiters serve stale data or a short-lived fallback instead of waiting.
  • Replicating without coordinated invalidation: Copies diverge. Use versioned values and invalidate or update all replicas together.
  • Unprotected database fallback: If every instance falls back at once, the database still melts. Add single-flight, rate limits, and a circuit breaker.
  • Detecting hot keys too slowly: Aggregating metrics over minutes misses the first spike. Use local counters with a window of seconds.

🌍 Real-World Best Practice

Large-scale systems handle hot keys with layers, each cheap and each removing a different failure mode. A typical order:

  • Step 0 — Confirm the failure mode: Check per-key QPS and per-node CPU and network, and see whether database spikes line up with cache expirations.
  • Step 1 — Coalesce misses: Add single-flight in each app instance and a short cross-instance lease so only one refresh per key reaches the database.
  • Step 2 — Soften expiry: Use TTL jitter and stale-while-revalidate so expiry never makes every request miss together.
  • Step 3 — Add a local L1 cache: A 1 to 2 second in-process cache for the hottest keys removes most network hops.
  • Step 4 — Replicate hot keys: Detect them and spread copies across nodes (for example key suffixes #0..#N-1 with random reads), invalidating all copies together.
  • Step 5 — Protect the database: Rate-limit and circuit-break fallback reads, and load-test with a simulated viral key.

Detect early, spread the load, and collapse duplicate work.

💡

Key Takeaway

A hot key breaks both the cache node that owns it and the database behind it. Combine replication or local caching to spread reads with request coalescing and soft expiry to prevent stampedes, using the staleness budget the product already allows.
