Preventing Double Charges in a Distributed Billing Pipeline

Elena is building a horizontally scalable billing system that pulls charge tasks from a distributed queue at tens of thousands of tasks per second. A task charges a user's account, and a duplicate charge is the worst possible failure. The queue delivers at least once, any worker may pick up a given user's task, workers can crash after calling the payment provider but before acknowledging the message, and network partitions occur. Each task carries a stable charge ID assigned when the charge was created, the payment provider accepts idempotency keys, and the primary store is a transactional database with unique constraints. She must choose the design that balances correctness, speed, availability and scale.

A
Distributed locking (such as Redis Redlock): a worker acquires a per-account lock before charging and releases it afterwards, giving mutual exclusion across the fleet.
✗ Not Best
B
Consistent-hash partitioning of the event stream by customer ID into consumer queues, so every event for a customer reaches the same worker shard and no cross-worker locks are needed.
✗ Not Best
C
Optimistic concurrency with idempotent workers: read account state and commit the charge using a database unique constraint or compare-and-swap version; on conflict, the idempotent worker retries, relying on transactions instead of global locks.
✓ Best Answer
D
A single centralized leader service that processes all billing transactions sequentially, giving absolute consistency while reads and auxiliary services scale out.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — C: Idempotent Optimistic Concurrency

Duplicate charges are not mainly a concurrency problem, they are a retry problem: at-least-once delivery, crashes and timeouts guarantee that the same task will sometimes run twice. The only mechanism that stays correct under crashes, partitions and rebalances is to make the charge idempotent and let the database arbitrate with a unique constraint or compare-and-swap. Here's why it stands out:

  • Correct under every failure mode: If a worker crashes mid-charge, the redelivered task hits the same charge ID, finds the existing record, and resumes or returns the stored result instead of charging again.
  • The database is the arbiter: A unique constraint on the charge ID (or a version check) is enforced atomically by the store, so no clock, lease or network assumption can be violated.
  • Scales horizontally: Any worker can process any task, and conflicts are rare and cheap (one failed insert or a zero-row update). Throughput scales with workers and database capacity, with no lock service in the hot path.
  • Extends to the provider call: Pass the same charge ID as the payment provider's idempotency key, so a retried API call returns the original result instead of charging twice.
  • Simple to observe: Count unique-violation conflicts, retries and re-driven pending charges; a spike signals redelivery storms or a stuck dependency.

A robust design uses a charges table with a unique charge ID, a PENDING → CAPTURED/FAILED state machine updated with compare-and-swap, provider-side idempotency keys, bounded retries with backoff, a sweeper for stale PENDING rows, and a periodic ledger-vs-provider reconciliation. Alert on any charge ID with more than one captured payment, which should be impossible.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🔒

A — Distributed Lock (Redlock)

A lock prevents two workers from running at the same time, but it does nothing about sequential duplicates (redelivery after a crash). It is also unsafe as a correctness guard: a worker that pauses (GC, network stall) can keep acting after its lease expires, and without fencing tokens the store cannot reject it. Locks also add latency and a new failure domain at tens of thousands of tasks per second. Caveat: locks are acceptable as an efficiency optimization (avoid wasted duplicate work) when correctness is guaranteed elsewhere.

🧭

B — Consistent-Hash Partitioning

Routing a customer's tasks to one shard removes most contention and preserves per-customer order, and it is an excellent scalability tool. But it does not guarantee exactly-once: consumer rebalances can briefly give two workers the same shard, crashed workers cause redelivery, and hot customers skew load. Caveat: use it together with idempotency, not instead of it.

🚦

D — Single Central Leader

Sequential processing makes ordering trivial, but one service becomes a throughput ceiling at tens of thousands of tasks per second and a single point of failure. Even a perfectly sequential processor still needs idempotency, because it can crash after charging and before recording the result. Caveat: acceptable for low-volume, high-value flows (periodic settlement for a few accounts).

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Distributed Lock

Efficiency-only guards (avoid redundant expensive work) where a rare duplicate is harmless, or locks with fencing tokens validated by the resource.

📌

B — Consistent-Hash Partitioning

High-volume pipelines needing per-key ordering and reduced contention, combined with idempotent processing.

📌

C — Idempotent Optimistic Concurrency

Any payment or ledger flow with at-least-once delivery, many workers and a transactional store: the default choice.

📌

D — Single Central Leader

Low-volume, high-value sequential workflows (periodic settlement for few accounts) where simplicity beats throughput.

⚠️ Common Mistakes to Avoid

  • Generating a new idempotency key per attempt: A retry then looks like a different charge. Create the key once, at charge creation.
  • Calling the provider before recording intent: A crash after the call leaves no trace to resume from. Insert the PENDING row first.
  • Check-then-insert without a unique constraint: Two workers both see 'not found' and both charge. Let the database enforce uniqueness.
  • Swallowing unique-violation errors blindly: A conflict may mean 'done' or 'in flight'. Read the existing row's status and act accordingly.
  • Unbounded retries: Retrying forever against a failing provider creates retry storms. Use capped exponential backoff with jitter and a dead-letter queue.
  • No reconciliation: Edge cases (provider timeouts, manual refunds) still occur. Reconcile the ledger against provider reports and alert on anomalies.

🌍 Real-World Best Practice

In practice, payment teams assume every message will be delivered more than once and design so that repeats are harmless. A typical sequence looks like this:

  • Step 0 — Mint an idempotency key at creation time: Create the charge ID when the order or invoice is created and carry it through every hop.
  • Step 1 — Record intent before acting: Insert a charges row (unique on charge ID, status PENDING) in the same transaction as the business event, often via an outbox.
  • Step 2 — Call the provider idempotently: Send the charge ID as the provider's idempotency key so retries return the original outcome.
  • Step 3 — Finalize with compare-and-swap: Update status from PENDING to CAPTURED only if it is still PENDING, and write the ledger entry in the same transaction.
  • Step 4 — Partition for efficiency: Key the queue by customer ID to cut contention and preserve per-customer order, without relying on it for correctness.
  • Step 5 — Sweep and reconcile: Re-drive stale PENDING charges and reconcile your ledger against provider settlement reports.

Make duplicates harmless instead of trying to make them impossible.

💡

Key Takeaway

Exactly-once effects come from idempotency plus an atomic arbiter (unique constraint or CAS), not from locks or routing. Partitioning by customer is a useful performance optimization, while a central leader or a distributed lock adds cost and risk without solving the redelivery problem.
