Aisha's Near-Real-Time Dashboard: How to Efficiently Maintain the Materialized View?

Aisha, a backend engineer, is building a near-real-time metrics endpoint for an analytics dashboard that aggregates orders, payments, and refunds across several microservices, each owning its own database. The endpoint must hold a p99 read latency under 100 ms during heavy concurrent dashboard usage, while the source services keep high write throughput. The system must tolerate partial outages, and both staleness and update failures must be observable. Staleness of a few seconds is acceptable. She needs to choose how the materialized view(s) behind the endpoint are maintained.

A
Modify the materialized view synchronously within the source database transaction (e.g., using a DB trigger or in-transaction write to the MV table) to guarantee strongly consistent reads.
✗ Not Best
B
Produce change events from the source databases and employ a CDC + stream-processing pipeline (e.g., Debezium -> Kafka -> Kafka Streams/Flink) for incremental updates to read-optimized materialized view stores (e.g., a dedicated Postgres/ClickHouse/Elasticsearch table), while exposing metrics and offsets for monitoring.
✓ Best Answer
C
Maintain a read-through/write-through Redis caching layer preceding the canonical queries: during writes, invalidate or refresh cache entries through a pub/sub channel; on cache misses, reads revert to the DB and populate the cache to ensure low latency.
✗ Not Best
D
Refrain from maintaining a persistent MV: calculate aggregations on the fly at query time utilizing highly optimized distributed SQL queries and sharded partial aggregates, potentially supplementing with background batch recomputes every few minutes for less critical paths.
✗ Not Best

Answer & In-Depth Explanation

🏆 Best Answer — B: CDC + Stream Processing into a Read-Optimized MV Store

Every requirement in the scenario points at decoupling the read path from the write path: sub-100 ms p99 under heavy dashboard concurrency, no slowdown for write-heavy source services, survival of partial outages, observable staleness, and a freshness budget of seconds (not milliseconds). A CDC + stream-processing pipeline that incrementally maintains a purpose-built MV store is the only option that satisfies all of them at once. The dashboard reads pre-aggregated rows from a store tuned for reads, the source databases only pay the cost of writing their own transaction log, and Kafka acts as a durable buffer between the two. Here's why it stands out:

  • Read isolation: Dashboard queries hit a store holding pre-aggregated rows (keyed by tenant, metric, time bucket). Read latency no longer depends on source-database load, so a single-partition lookup comfortably fits a 100 ms p99 budget even with many concurrent dashboards.
  • Near-zero write-path impact: CDC tails the database log (WAL/binlog) or a transactional outbox table, so no extra locks, triggers, or cross-service calls land on the order, payment, or refund write transactions. Source throughput is untouched.
  • Failure isolation and replay: Kafka durably buffers events. If Flink or the MV store is down, writes continue, the dashboard serves the last known data (stale but available), and the pipeline catches up from committed offsets. The same log lets you rebuild a view from scratch.
  • Observability by construction: Consumer lag, end-to-end freshness (now minus the watermark of the data materialized), dead-letter counts, and checkpoint age are first-class metrics. The API can return an as_of timestamp so clients and alerts see staleness directly.
  • Correct incremental aggregation: Keyed state plus idempotent upserts of absolute bucket totals gives effectively-once results even when events are redelivered. Refunds become negative deltas applied to the original order's bucket instead of ad hoc recomputation.

A production-grade version includes a transactional outbox or CDC per service, keyed incremental aggregation with event-time watermarks, idempotent upserts into the MV store, a freshness SLO with alerting, and a periodic reconciliation job that compares the view against the source of truth to catch drift.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🔒

A — Synchronous In-Transaction MV Update

Strong consistency is attractive, but it couples every write to the view. Aggregate rows (daily revenue, refund counts) become hot rows that serialize concurrent writers through lock contention, which directly hurts the high write throughput requirement. A slow or failed MV update fails the business transaction, so a view problem becomes an outage. Worse, orders, payments, and refunds live in different microservices and databases, so one local transaction cannot cover them without 2PC. Caveat: for a single database with modest write volume and a hard need for read-your-writes (for example, a ledger balance), this is simple and correct.

⚡

C — Redis Read-Through / Write-Through Cache

A cache is an optimization in front of a query, not a way to maintain an aggregate. Each write invalidates or refreshes aggregate entries, so hot dashboard keys churn constantly, and every miss falls back to an expensive aggregation over the source databases, exactly when concurrency is highest (cache stampede, p99 spikes). Redis pub/sub is fire-and-forget, so a missed message silently leaves stale data with no lag metric to alert on. Aggregation across several services still has to be computed somewhere. Caveat: a small Redis or in-process cache with a 1-2 second TTL is a good complement in front of the MV store for the hottest tiles.

🧮

D — Compute on the Fly at Query Time

With no persisted view, query cost scales with data volume and with the number of concurrent dashboards, so holding p99 under 100 ms at peak is hard, and analytical reads compete with transactional writes for the same resources. The batch recompute 'every few minutes' for non-critical paths also contradicts the few-seconds staleness target. Failures in any shard or source directly degrade reads. Caveat: this works for low-concurrency, ad hoc exploration, or when a columnar engine ingests events directly, which is essentially option B with a different sink.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Synchronous MV in Transaction

A single database, modest write volume, and a hard requirement that reads reflect the latest write (for example, an account balance or a stock counter updated in the same transaction).

📌

B — CDC + Stream Processing

Multiple services or databases feed one read model, writes are heavy, reads must be fast under load, and seconds of staleness are acceptable. Needs a team able to operate the streaming stack.

📌

C — Redis Cache with Invalidation

Repeated reads of the same query result with a clear invalidation key, where a miss is cheap enough to absorb. Best as a layer in front of another store.

📌

D — Compute at Query Time

Low-concurrency or ad hoc analytics, small data volumes, or an OLAP engine that already ingests the raw events and can scan fast enough.

⚠️ Common Mistakes to Avoid

  • Treating at-least-once as exactly-once: Redelivered events double-count revenue. Keep per-entity version state and write idempotent upserts of absolute totals, not blind increments.
  • Ignoring out-of-order and late events: A refund can arrive before the order event is processed. Use event-time buckets, watermarks, allowed lateness, and a DLQ with a repair path.
  • Exposing raw table CDC as a public contract: Any schema change upstream breaks the pipeline. Use an outbox or domain events with schema-registry compatibility rules.
  • No freshness metric: Consumer lag alone is not enough (an idle topic has zero lag). Measure end-to-end freshness from event time to materialization and return as_of in the API.
  • Committing offsets before the sink acknowledges: A crash then loses data silently. Commit offsets (or checkpoints) only after the MV store write succeeds.
  • No rebuild path: Bugs in aggregation logic need reprocessing. Keep retention or snapshots long enough to replay, and rehearse the rebuild.

🌍 Real-World Best Practice

In practice, teams treat the materialized view as a product with an explicit freshness SLO and build it in layers. A typical rollout looks like this:

  • Step 0 — Define the contract: Agree on metric definitions, the freshness SLO (for example, p99 end-to-end lag under 5 s), and what the dashboard shows when data is stale.
  • Step 1 — Emit reliable change events: Use a transactional outbox or Debezium per service, with versioned schemas in a registry and a stable event key (entity id).
  • Step 2 — Incremental aggregation: Flink or Kafka Streams keeps keyed state, applies deltas (refunds as negative amounts), assigns event-time buckets, and handles late events with watermarks.
  • Step 3 — Serve from a read-optimized store: Idempotent upserts into ClickHouse, Postgres, or Elasticsearch, partitioned by tenant and time, behind a thin metrics API that returns as_of.
  • Step 4 — Observe and degrade gracefully: Alert on consumer lag, freshness, DLQ growth, and checkpoint failures. Serve last-known data with a staleness banner instead of failing.
  • Step 5 — Reconcile and rebuild: A periodic batch job compares the view with source-of-truth counts, and the log or snapshots allow a full rebuild with no downtime.

Add micro-caching only after the MV store is in place and measurements show a need.

💡

Key Takeaway

When many readers and heavy writers share the same data, move aggregation off both the write path and the read path. CDC plus stream processing keeps views incrementally fresh within seconds, isolates failures, and makes lag measurable. Pair it with idempotent updates, event-time handling, and a reconciliation job, and accept bounded eventual consistency in exchange for scale and availability.
