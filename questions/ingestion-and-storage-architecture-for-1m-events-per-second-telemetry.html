Ingestion and Storage Architecture for 1M Events per Second Telemetry

Lucas, an engineering lead, is designing a telemetry backend for many microservices and a large IoT fleet. It must ingest about 1 million time-series events per second (peaks near 3 million) from clients worldwide, retain raw events for 90 days, support ad-hoc queries, and power dashboards with a 2-second query SLO for the last week of data. It must also be highly available across two regions and provide downsampling and rollups for long-term storage. Which ingestion, storage and query design best balances scalability, resilience, speed, consistency, monitoring and cost?

A
Deploy a single horizontally scalable cluster of TimescaleDB (a PostgreSQL extension) equipped with synchronous cross-region replication to guarantee strong consistency. Scale by upgrading node capacities and manually sharding data based on device IDs, while leveraging native hypertables, continuous aggregates for summarization, and WAL-based replicas to ensure high availability.
✗ Not Best
B
Utilize durable, log-based ingestion systems (such as Kafka or Kinesis) in each region, paired with stream processing applications (like Flink or Beam) to generate real-time data rollups. The processors should output to two destinations: a columnar OLAP database tailored for time-series analytics (e.g., ClickHouse or Druid) to power high-speed dashboards, and cost-effective cold object storage (like S3) for archiving raw events. Employ cross-region Kafka replication and asynchronous OLAP replication, directing dashboard queries to the OLAP store and in-depth historical analysis queries to S3.
✓ Best Answer
C
Adopt a write-heavy approach using a wide-column database (such as Cassandra or ScyllaDB) configured with time-based partitioning and TTLs. Execute server-side compactions and manage pre-aggregated partitions (hourly or daily) using scheduled batch processing. Fulfill query requests directly from Cassandra by utilizing secondary indexes and merging range query results on the client side.
✗ Not Best
D
Shift the bulk of aggregation duties to the edge by programming device agents or edge gateways to pre-aggregate data and periodically transmit summaries. The central backend will store these summaries within a standard relational database and process on-demand raw event uploads. Rely on eventual consistency and opportunistic retry mechanisms to ensure data reliability, while making raw-event retention an optional feature to keep costs in check.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — B: Durable Log + Stream Rollups + OLAP Hot Tier + Object Storage Cold Tier

This workload has three different access patterns that no single store serves well: bursty high-volume ingest, low-latency dashboards over recent data, and cheap long-term retention with ad-hoc analysis. Option B assigns each pattern to the right component: a durable log absorbs bursts, stream processing computes rollups once, a columnar OLAP engine serves the 2-second dashboards, and object storage holds the 90-day raw archive. Here's why it stands out:

  • Ingest that absorbs bursts: Kafka or Kinesis scales horizontally by partition and buffers 3M events per second peaks durably. Producers write to the nearest region, and slow consumers never push back on devices. As an illustrative sizing, at about 200 bytes per event, 1M events per second is roughly 200 MB/s (about 17 TB/day raw), and 90 days is on the order of 1.5 PB uncompressed. That is why storage tiering matters.
  • Right engine per access pattern: ClickHouse or Druid (columnar, compressed, time-partitioned, with pre-aggregation and materialized views) can serve dashboard queries over a week of data within the 2-second SLO. Raw data older than that lives in Parquet on object storage at a fraction of the cost, queried ad hoc with Trino or Athena.
  • Rollups computed once: Flink or Beam produces 1-minute, 5-minute and 1-hour aggregates (using mergeable sketches for percentiles). Dashboards read small rollup tables instead of scanning raw events, and long-term retention keeps the downsampled data.
  • No dual-write trap: Both sinks consume from the log independently, so each can fail, lag or be rebuilt by replaying the log without affecting the other.
  • Availability and DR fit the workload: Cross-region log replication (MirrorMaker 2 or equivalent) and asynchronous OLAP replication give an RPO measured in seconds. Telemetry does not need synchronous cross-region commits, so you avoid paying WAN latency on every write.
  • Cost control by design: Keep only about 7 days on fast storage, push the remaining 83 days to object storage with lifecycle policies, and avoid querying raw data for dashboards.

Validate with a load test at 3M events per second plus a replay test: kill a sink for an hour, restart, and confirm it catches up without data loss or duplicates. Track end-to-end freshness (event time to queryable) as a first-class SLO.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🐘

A — Single TimescaleDB Cluster with Synchronous Cross-Region Replication

PostgreSQL's write path is fundamentally single-writer per primary, and 1 to 3 million inserts per second sustained is at or beyond what a single primary handles even with batching. Synchronous cross-region replication adds WAN round-trip latency to every commit, hurting throughput and availability. Manual sharding by device ID reintroduces the complexity the option claims to avoid, and Timescale's multi-node mode has been deprecated upstream. Strong consistency is also unnecessary for telemetry. Caveat: for roughly 100K rows per second or less in a single region, TimescaleDB is simple and excellent.

🧱

C — Cassandra/ScyllaDB with Secondary Indexes

Wide-column stores handle write-heavy ingest well, but they are weak for analytics: secondary indexes on high-cardinality columns are an anti-pattern, range queries become scatter-gather with client-side merging, and wide-range dashboard queries won't reliably meet a 2-second SLO. Batch pre-aggregation adds lag, and compaction at this scale is operationally heavy. Caveat: Cassandra is a good fit for key-based lookups such as the latest values per device, not ad-hoc time-series analytics.

📉

D — Edge Pre-Aggregation with Optional Raw Retention

It contradicts the stated requirements: raw events must be kept for 90 days and ad-hoc queries must work. Once raw data is aggregated away, you can't re-aggregate, drill down or compute correct percentiles from averages. 'Opportunistic retries' on constrained devices mean silent data loss, and a standard relational database as the summary store is a poor fit for bursts. Caveat: edge filtering, batching and compression are great complements for reducing volume where raw detail is truly not required.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Timescale + Sync Replication

Moderate volumes (up to roughly 100K inserts per second), a single region, a need for full SQL and joins with relational data, and a small team that values simplicity.

📌

B — Log + Stream + OLAP + S3

Very high ingest, multi-region deployments, mixed real-time dashboards and long retention, and ad-hoc analytics at controlled cost.

📌

C — Cassandra + Secondary Indexes

Key-based access patterns such as latest state per device or time-bucketed reads by device, with massive write throughput and simple read shapes.

📌

D — Edge Aggregation + RDBMS

Bandwidth- or battery-constrained devices where summaries are sufficient and raw data is not needed. Best used as a complement to a raw-capable backend.

⚠️ Common Mistakes to Avoid

  • Dual-writing from one job to two sinks without failure handling: A partial failure leaves the stores inconsistent. Use independent consumers or sink connectors that checkpoint separately.
  • Hot partitions from a poor key: Keying by device type or customer concentrates load on a few partitions. Use a high-cardinality, evenly distributed key.
  • Ignoring series cardinality: Unbounded labels or high-cardinality dimensions in sort keys inflate storage and slow queries.
  • No schema registry or evolution rules: One producer change can break every consumer.
  • Querying raw data for dashboards: Dashboards should read rollups. Raw scans are for drill-down.
  • Small files and no compaction on object storage: Query engines slow down dramatically with millions of tiny objects.

🌍 Real-World Best Practice

Telemetry platforms are built log first, with storage tiers added around the log:

  • Step 0 — Quantify: Event size, series cardinality, query shapes and retention per tier. Capacity plans without these numbers are guesses.
  • Step 1 — Schema and contracts: Protobuf or Avro with a schema registry and an explicit event ID for deduplication.
  • Step 2 — Regional durable log: Partition by a high-cardinality key (device ID hash), provision for peaks, and replicate across regions.
  • Step 3 — Stream rollups: Event-time windows with watermarks, mergeable sketches, and a late-data side output.
  • Step 4 — Two independent sinks: OLAP for the hot 7 days plus rollups, and Parquet or Iceberg on object storage for raw 90 days.
  • Step 5 — Query routing and cost control: Dashboards to OLAP, ad-hoc history to Trino or Athena, lifecycle policies and compaction.
  • Step 6 — DR drills: Region failover and sink replay tests on a schedule.

Keep the log as the source of truth and everything downstream rebuildable.

💡

Key Takeaway

At millions of events per second, don't force one database to do everything. Land events in a durable log, compute rollups in the stream, serve dashboards from a columnar OLAP store, and keep raw history cheap in object storage. You trade simplicity for scalability, resilience and cost, and you must design for at-least-once delivery and eventual cross-region consistency.
