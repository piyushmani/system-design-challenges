Maya's Consensus Decision: Selecting Paxos vs. Raft for a Global Config Store

Maya, a backend engineer, is building a global service-discovery and configuration store for her organization's microservices. It requires linearizable reads and writes for the service registry and feature flags, 10,000 reads per second and 100 writes per second, write latency under 100 ms, high availability across three regions, and strong observability of commit latency and leader elections. She must choose the consensus protocol (Raft or Paxos) together with the scaling and placement strategy for the consensus groups. Which architecture best satisfies these demands, and why?

A
Partition the keyspace across several independent Raft groups containing 3 to 5 nodes, locating replicas in every region with a per-shard leader. Direct reads and writes for specific keys to the corresponding shard leader to ensure linearizability, while permitting read-through caches and strictly managed follower reads for non-essential low-latency requests. Utilize an established Raft library like Consul or etcd, track commit, term, and leader metrics, and achieve scale by introducing additional shards.
✓ Best Answer
B
Operate one unified global Multi-Paxos instance covering all data, utilizing numerous nodes across all regions to optimize fault tolerance. Adjust the learner and acceptor roles to enhance throughput, and aim to horizontally scale this singular consensus group by integrating more servers and splitting logical logs rather than sharding the actual data.
✗ Not Best
C
Adopt a leaderless, Dynamo-style quorum architecture employing N/R/W configurations along with CRDT-based or last-write-wins conflict resolution. Embrace eventual consistency for the majority of actions to ensure high availability during network partitions and low-latency reads, applying a strong-consistency mode exclusively to a restricted subset of critical keys.
✗ Not Best
D
Implement Raft but place a centralized proxy layer in front of it to manage all client traffic. This proxy directs write operations to the active leader and handles read requests using a meticulously updated cache or by querying the leader for linearizable reads. Horizontally scale the proxy layer and depend on it to manage retries and track the current leader.

Answer & In-Depth Explanation

🏆 Best Answer — A: Raft Groups with Cross-Region Quorums

The workload needs CP behavior (consistency over availability during partitions), a quorum that spans regions, and tooling that exposes commit latency and elections. Raft and Multi-Paxos offer equivalent safety guarantees; the practical difference is maturity of implementations and operability. Raft has a clear specification, including membership changes, and production-grade stores (etcd, Consul) expose the metrics Maya wants. Option A uses Raft and provides a scale-out path through independent groups. Here's why it stands out:

  • Linearizability by construction: Writes commit through the leader once a majority acknowledges, and linearizable reads use the leader or a ReadIndex/lease protocol, so a registry or flag read never returns a stale value.
  • Quorum placement controls latency: With five voters spread 2-2-1 across three regions, a write needs three acknowledgements, so commit time is roughly the round trip to the nearest other region plus disk fsync. That is what makes sub-100 ms writes achievable when regions are within tens of milliseconds, and it keeps working if an entire region fails.
  • A scale-out path exists: Independent Raft groups each have their own leader and log, so write throughput and data size scale by adding groups. This is how Spanner (Paxos groups), CockroachDB, and TiKV (Raft ranges) scale consensus.
  • Reads scale without giving up correctness: The 10,000 reads per second can be spread out: linearizable reads through ReadIndex from followers, explicit opt-in serializable or bounded-stale reads, and client-side caches kept fresh by watch streams for non-critical lookups.
  • Operational maturity and observability: etcd and Consul expose commit latency, pending proposals, leader changes, term, apply lag, and disk fsync latency. Debuggable consensus matters more than theoretical elegance.
  • Raft versus Paxos in one line: Same safety, but Raft's strong leader, log-matching property, and built-in membership change are easier to implement and operate correctly than the hand-rolled Multi-Paxos most teams end up with.

Operationally: use odd-sized voter sets, pin leaders near writers (leader priority or leases), enable pre-vote and check-quorum to avoid disruptive elections, snapshot and compact regularly, and alert on commit-latency percentiles, leader changes per hour, proposal failures, and disk fsync latency. Rehearse region-failure drills.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🏛️

B — One Global Multi-Paxos Group

Paxos is just as safe as Raft, but adding nodes to one consensus group does not add throughput: every write still passes through one leader and one log and needs a larger quorum, which increases latency and failure surface across regions. Splitting logs without sharding the data does not change that. Multi-Paxos also has no single canonical specification, so implementations vary and operational tooling is thinner. Caveat: Paxos variants (Flexible Paxos, EPaxos) can reduce WAN latency in specialized designs, but they are harder to build and operate.

🕸️

C — Leaderless Dynamo-Style Quorums

Eventual consistency with last-write-wins or CRDTs violates the stated linearizability requirement. Even with R + W > N, sloppy quorums, concurrent writes, and clock skew can return stale values or lose updates, which is unacceptable for feature flags and registries where inconsistency causes outages. A strong mode for a subset of keys means running two systems. Caveat: for non-critical, high-volume data such as telemetry or caches, leaderless designs are a good fit.

🔀

D — Raft Behind a Central Proxy

A proxy does not scale consensus; writes still go to one leader, and the proxy adds a hop and a new failure domain that must itself be highly available. Serving reads from a proxy cache is not linearizable, and proxy-based leader tracking duplicates what client libraries already do. Caveat: a thin, stateless routing layer (or a smart client) in front of shards is reasonable; a stateful caching proxy that claims linearizability is not.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Sharded Raft Groups

Linearizable metadata (registry, flags, locks, leader election) across regions with modest write rates, strong tooling needs, and a future scale-out path.

📌

B — Global Multi-Paxos

Specialized systems with deep consensus expertise or an existing Multi-Paxos platform; not recommended as a greenfield choice here.

📌

C — Leaderless Quorums

High-volume, availability-first data that tolerates staleness (shopping carts, telemetry, session caches).

📌

D — Raft + Central Proxy

As a thin stateless router or client-side library that hides leader discovery; not as a place to cache or to claim consistency.

⚠️ Common Mistakes to Avoid

  • Even-sized or oversized clusters: Four nodes tolerate the same failures as three, and seven or nine voters raise commit latency. Use three or five.
  • All voters in one region: A regional outage loses quorum. Spread voters so no single region holds a majority.
  • 'Linearizable' reads from followers without ReadIndex or leases: A stale follower can return old data after a leader change.
  • Ignoring disk and clock behavior: Slow fsync or clock jumps cause missed heartbeats and election storms. Use SSDs, monitor fsync latency, and tune election timeouts to the WAN RTT.
  • Large values or hot keys in the consensus log: Config stores are for small metadata. Large blobs slow replication and snapshots.
  • Never testing region failure and membership change: Failure handling that has not been rehearsed will not work during an incident.

🌍 Real-World Best Practice

Teams that run consensus-backed control planes keep the consensus group small, the data small, and the critical path short. A typical sequence looks like this:

  • Step 0 — Quantify: Measure inter-region RTT, key count and size, read/write mix, and the staleness each consumer can actually tolerate.
  • Step 1 — Start with one group: Five voters (2-2-1 across three regions) on SSDs, with the write-ahead log on a dedicated disk.
  • Step 2 — Cache and watch: Clients cache reads and use watch streams, so most reads never reach the leader.
  • Step 3 — Tiered reads: Linearizable by default, with explicit opt-in serializable reads for hot, non-critical paths.
  • Step 4 — Shard when needed: Split by key range or domain when size or write rate demands it, and keep atomic units inside one shard (the answer to this question).
  • Step 5 — Operate: Dashboards and alerts for leader changes and fsync latency, game days for region loss, and tested backup and restore.

Consensus is expensive per write; reserve it for the data that truly needs it.

💡

Key Takeaway

For linearizable configuration and service discovery, choose a mature Raft implementation (etcd or Consul style), place a majority quorum across regions, and scale by adding independent groups rather than adding nodes to one group. Raft versus Paxos is a choice about operability, not safety, and neither bigger quorums nor proxies buy throughput.
