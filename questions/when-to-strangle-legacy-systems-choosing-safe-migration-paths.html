When to Strangle Legacy Systems: Choosing Safe Migration Paths

Mateo, a senior backend engineer at an e-commerce company, is migrating a monolithic order management service to a new microservice using the Strangler Fig pattern. The legacy system handles about 5,000 writes per second plus low-latency reads. The business demands near-zero data loss, read-after-write consistency for critical operations, strong observability, and fast rollback. He wants to migrate customer segment by segment, minimize user-facing errors, and avoid long-lived dual-write inconsistencies and data drift.

A
Big-bang migration: migrate the schema and data during a maintenance window, then switch all routing to the new microservice at once.
✗ Not Best
B
Proxy with synchronous dual-writes: route by URL path, write to both legacy and new services synchronously (using 2PC or distributed transactions), then read from the new service.
✗ Not Best
C
Event-driven strangulation: keep legacy as the source of truth, use CDC to build the new service's state asynchronously, gradually route reads to the new service with eventual consistency, and reconcile drift with background jobs and compensating transactions.
✗ Not Best
D
Incremental strangulation with a transactional outbox and traffic mirroring: an API gateway with canary and feature flags, shadow traffic for validation, an outbox in the legacy write path feeding the new system, gradual per-segment migration, deep observability, and simple rollback.

Answer & In-Depth Explanation

🏆 Best Answer — D: Outbox, Shadow Traffic and Per-Segment Cutover

The hard problem in a strangler migration is not routing. It is moving state without ever having two writers for the same entity. The outbox makes the legacy write and its event atomic, the gateway moves ownership one segment at a time, and shadowing proves the new service is correct before it owns anything. Here's why it stands out:

  • No dual-write bug by construction: The order row and the outbox event commit in the same local transaction in the legacy database. A relay (polling, or CDC on the outbox table) publishes events reliably, so the new service's state follows without a distributed transaction.
  • Near-zero data loss: The outbox row is durable together with the business write. If the relay or Kafka is down, events wait in the table and are delivered later, in order per order ID.
  • Safe validation before cutover: Shadow (mirrored) traffic exercises the new service with real request shapes, and comparing its responses and resulting state to legacy finds defects while users are still served by legacy.
  • Controlled blast radius and fast rollback: Feature flags and canary routing move one customer segment at a time. Rolling back is a flag flip, provided writes made by the new service for that segment also flow back to legacy (a reverse outbox).
  • Read-after-write where it matters: Each segment has exactly one owner at a time, and its reads and writes go to the same system, so a customer never reads from a copy that has not yet seen their write.

Keep a per-segment ownership flag as the single source of truth for routing, measure outbox lag, event processing errors, shadow-diff rate, and error budget per segment, and keep the reverse sync running until a segment has been stable long enough to decommission its legacy path.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

💥

A — Big-Bang Migration

A single cutover concentrates all risk in one window: any defect in the new service hits every customer, migrating live order data must finish inside the window at 5k writes per second, and rollback after the new system has accepted writes means losing or reconciling those writes. It also gives no gradual validation. Caveat: big-bang is only reasonable for small systems that can tolerate downtime, which this one cannot.

🔀

B — Proxy with Synchronous Dual-Writes and 2PC

Dual-writes reintroduce exactly the failure the scenario wants to avoid: if one write succeeds and the other fails or times out, the systems diverge, and distributed transactions across a legacy database and a new service are rarely supported or performant. Latency and availability become the product of both systems, and the proxy becomes a correctness-critical component.

📡

C — CDC-Only with Eventually Consistent Reads

CDC from the legacy database is a good building block and avoids dual-writes, but this option routes reads to a copy that lags legacy writes, which violates the read-after-write requirement for critical operations. Row-level CDC also couples the new service to the legacy schema, and relying on background reconciliation and compensating transactions to fix drift treats drift as an expected condition instead of preventing it. Caveat: CDC on the outbox table is a good way to implement the relay in the best answer.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Big-Bang

A small, low-traffic system with a safe downtime window and a simple data model.

📌

B — Sync Dual-Writes + 2PC

Rarely recommended. Only for short transitional periods with a strong reconciliation process and very low write volume.

📌

C — CDC-Only, Eventual Reads

Read-heavy migrations where stale reads are acceptable (catalog, search, analytics), or as a read-model building block.

📌

D — Outbox + Mirroring + Segments

High-volume transactional workloads that need near-zero data loss, per-segment rollout, and fast rollback (this scenario).

⚠️ Common Mistakes to Avoid

  • Two writers for the same entity: If both systems accept writes for an order, conflicts are unavoidable. Enforce a single owner per segment and fence in-flight writes at cutover.
  • Publishing to Kafka directly after the DB commit: A crash between the two loses the event. Write the event to an outbox table in the same transaction and relay it.
  • No reverse sync, so no real rollback: Once the new service has accepted writes, flipping routing back loses them unless they also reach legacy.
  • Non-idempotent consumers: At-least-once delivery produces duplicates. Deduplicate by event ID or aggregate version.
  • Shadow writes with real side effects: Mirrored traffic that triggers payments or emails is a production incident. Make shadow paths side-effect free.
  • Migrating by URL path only: Path-based routing cannot express 'this customer segment owns writes in the new service'. Route by entity or segment ownership, not only by path.

🌍 Real-World Best Practice

In practice, strangler migrations proceed slice by slice, with measurable gates. A typical path:

  • Step 0 — Put a facade in front: Introduce the API gateway with routing rules and flags while all traffic still goes to legacy. Add tracing and per-route metrics.
  • Step 1 — Add the outbox and build the new read model: Emit order events from the legacy transaction, consume them in the new service, and verify state parity with automated comparisons.
  • Step 2 — Shadow traffic: Mirror reads (and side-effect-free writes) to the new service and drive the diff rate to zero.
  • Step 3 — Canary a small segment: Flip ownership for internal users or a low-risk segment, with reverse sync to legacy enabled and rollback rehearsed.
  • Step 4 — Expand segment by segment: Increase coverage while watching error rate, latency, outbox lag, and reconciliation mismatches.
  • Step 5 — Decommission: After a stable period at 100%, remove reverse sync, retire the legacy write path, and archive legacy data.

Move ownership in small, reversible steps, and keep data flowing in both directions until you are certain.

💡

Key Takeaway

Avoid both big-bang risk and dual-write drift: make the legacy write and its event atomic with an outbox, validate with shadow traffic, and migrate one segment at a time with a single owner and a rollback path.
