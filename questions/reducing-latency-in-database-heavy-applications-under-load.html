Challenge

Reducing Latency in Database-Heavy Applications Under Load

Priya, a senior backend developer, is investigating performance bottlenecks in a production system that serves millions of requests daily. During peak traffic windows, database query response times degrade significantly, leading to timeouts and a poor end-user experience. She needs to choose the most effective strategy to enhance query throughput and minimize response latency.

A
Create composite (multi-column) indexes tailored to the most common query patterns.
✗ Not Best
B
Introduce a caching layer (e.g., Redis or Memcached) to serve repeated query results from memory.
✓ Best Answer
C
Apply table partitioning to spread data across multiple nodes and balance the read/write workload.
✗ Not Best
D
Denormalize selected tables to eliminate expensive join operations and speed up read-heavy queries.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — B: Caching Layer

Introducing a caching layer (such as Redis or Memcached) is the most impactful single strategy for a system already suffering latency spikes under peak load. Here's why it stands out:

  • **Immediate latency reduction:** Cache hits return data in sub-millisecond time versus tens or hundreds of milliseconds for a database query. For hot data paths, this can reduce p99 latency by 10×–100×.
  • **Load shedding:** By intercepting repeated reads before they reach the database, caching dramatically reduces the number of queries hitting the DB during peak hours — exactly when the system struggles.
  • **Non-invasive:** Unlike schema changes (denormalization) or infrastructure changes (partitioning), a cache can be layered on top of the existing architecture with minimal refactoring.
  • **Battle-tested at scale:** Companies like Twitter, Instagram, and GitHub use read-through and write-behind caching as a cornerstone of their high-traffic architectures.

A well-designed caching strategy includes TTL-based expiry, cache invalidation on writes, and a cache-aside or read-through pattern to keep data fresh while absorbing the majority of read traffic.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

📇

A — Composite Indexes

Indexes speed up individual query execution, but they don't reduce the volume of queries hitting the database. Under peak load with millions of identical reads, every request still round-trips to the DB. Indexes also add write overhead (every INSERT/UPDATE must maintain the index B-tree).

🧩

C — Table Partitioning

Partitioning helps when a single table is too large to scan efficiently or when you need to shard writes across nodes. But it introduces significant operational complexity (cross-partition queries, rebalancing, migration) and doesn't help if the bottleneck is repeated reads of the same data.

📋

D — Denormalization

Removing JOINs speeds up reads, but it duplicates data, complicates writes, and risks inconsistency. It's a permanent schema change that's hard to reverse. For Priya's scenario (peak-hour spikes on a working system), this is a heavy-handed structural change when a simpler layer can solve the problem.

⚡

B — Caching Layer ✓

Introduce a caching layer (e.g., Redis or Memcached) to serve repeated query results from memory.

🌍 Real-World Best Practice

In practice, senior engineers rarely pick just one strategy. The optimal production setup layers multiple techniques together:

  • **Layer 1 — Caching:** Intercept hot reads with Redis/Memcached (biggest immediate win).
  • **Layer 2 — Indexing:** Ensure all remaining DB queries are well-indexed (steady-state performance).
  • **Layer 3 — Partitioning:** Shard only when single-node DB storage or write throughput becomes the bottleneck.
  • **Layer 4 — Denormalization:** Apply surgically to specific read-heavy paths where JOINs are proven bottlenecks via query profiling.

Priya's first move should be caching because it yields the highest impact with the lowest risk. She can then layer in other optimizations based on profiling data.

💡

Key Takeaway

When facing latency spikes under peak traffic, reduce demand on the database first — don't just make the database faster. A caching layer absorbs the thundering herd, buys time, and is the highest-ROI first step in any database performance toolkit.
