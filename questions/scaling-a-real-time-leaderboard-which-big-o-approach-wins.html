Challenge

Scaling a real-time leaderboard: which Big-O approach wins?

Maya, a backend engineer, is building a global gaming leaderboard. Players submit score updates at a massive rate (millions per day, with large bursts), and reads are even heavier: clients request the top 100 per region with a tail latency under 50 ms. Re-sorting all users on every update is O(N log N) and collapses at this scale. She needs a design that keeps update cost and read cost both feasible while balancing write throughput, availability, and consistency.

A
A single centralized in-memory sorted structure (such as one Redis Sorted Set) storing scores for every player. Each update requires O(log N) processing on the central server; read operations take O(1) to retrieve the top-100.
✗ Not Best
B
Partition players across multiple nodes based on user ID. Each partition keeps its own local sorted structure and top-100 list. For a global read, fetch the top-100 from all partitions and merge them during query execution to form the overall top-100 (merging k sorted lists).
✗ Not Best
C
Employ an approximate streaming or heavy-hitter data structure (like Count-Min sketch or frequent-items sketch) to monitor top players. Updates execute in O(1) time using minimal memory, though results are estimations and might misorder scores near the cutoff.
✗ Not Best
D
Send all score updates to a durable message log (such as Kafka) and utilize a stream processor to incrementally update a materialized global and regional top-100 (acting as a background aggregator). Read queries access the cached materialized view in O(1) time, while updates are processed asynchronously and amortized in batches.
✓ Best Answer
✅

Answer & In-Depth Explanation

🏆 Best Answer — D: Stream-Updated Materialized Top-100

The workload is write-heavy and read-heavier, but the read is always the same tiny result: the current top 100 per region. That is a textbook case for precomputing the answer. A durable log absorbs write bursts, partitioned stream processors keep a small top-K per partition (O(log K) per update, with K = 100), and a regional merger combines k tiny lists into a cached result. Reads become a single cache lookup, independent of player count and score update volume. Here is why it fits:

  • Read cost is O(1) and independent of write load: Clients read one cached value per region, so tail latency does not depend on how many scores arrive. Heavy read traffic never touches the ranking machinery.
  • Write cost is small and parallel: Each partition owns a disjoint set of players. An update is a hash lookup plus an O(log 100) heap operation, and partitions scale horizontally with no cross-partition coordination.
  • Merge happens once, not per read: The k-way merge of k lists of 100 entries is performed by the aggregator when a partition's top-K changes, not on every client request. Fan-out cost is paid once per change instead of once per read.
  • Burst absorption and replay: The log buffers spikes, lets consumers lag temporarily, and allows rebuilding the leaderboard (new season, bug fix) by replaying events.
  • Availability: Reads are served from a cache even if the stream processor is behind or restarting. The worst case is slightly stale rankings, not an outage.

Partition the stream by player ID, keep per-partition top-K, merge per region, and publish to a cache or CDN. Track processing lag, publish-to-read freshness, merge time, and cache hit rate, and alert when freshness exceeds the product's tolerance.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🏆

A — Single Redis Sorted Set

Simple and exact: ZADD is O(log N) and a top-100 read (ZREVRANGE) is O(log N + 100), not strictly O(1). The real limits are operational: one node's throughput and memory, a single failure domain, and cross-region read latency for global players. Heavy read traffic also competes with writes on the same node. It is a good first version and a reasonable building block (a sorted set per region inside the aggregator), but not the final answer for this load profile.

🧩

B — Partitioned with Query-Time Merge

Partitioning solves write scaling, but doing the merge on every read multiplies the cost of the heaviest traffic by the partition count k. Read latency becomes the maximum of k parallel calls, so tail latency worsens as k grows, and one slow partition slows every leaderboard read. The fix is to cache the merged result and recompute it when partitions change, which is exactly option D.

🎲

C — Count-Min / Heavy-Hitter Sketch

Sketches estimate frequencies of items in a stream (and Count-Min only overestimates). A leaderboard ranks arbitrary score values and needs exact order, including replacement of a player's previous score. Misordering near the cutoff is unacceptable when rank carries rewards or competitive meaning, and the memory saving is irrelevant when only 100 entries per region need to be stored exactly.

⚡

D — Stream-Updated Materialized Top-100 ✓

Send all score updates to a durable message log (such as Kafka) and utilize a stream processor to incrementally update a materialized global and regional top-100 (acting as a background aggregator). R

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Single Sorted Set

A moderate scale (up to tens of thousands of updates per second), exact ranks and instant freshness needed, and a single region or a board per region fitting on one node.

📌

B — Partition + Merge on Read

Occasional global queries over partitioned data where read volume is low, or as an internal step whose merged result is then cached.

📌

C — Sketch

Approximate popularity or trending detection (most frequent items, hot keys), where small errors near the cutoff do not matter.

📌

D — Stream + Materialized Top-100

Very high write rates, very high read fan-out for the same top-N result, many boards (global, regional, seasonal), and seconds of staleness acceptable.

⚠️ Common Mistakes to Avoid

  • Assuming scores only increase: A bounded top-100 heap breaks when scores can drop or players are removed, because the next-best candidate was discarded. Retain more state or an ordered store.
  • Non-idempotent updates: At-least-once delivery will replay events. Without event IDs or versions, replays and out-of-order arrivals corrupt rankings.
  • Partitioning by region or score instead of player ID: Updates for one player must reach the same owner, or the per-player best score is wrong. Hot regions also create hot partitions.
  • Re-merging on every event: Publishing and merging on every single update creates needless churn. Batch or debounce merges (for example every 100 to 500 ms).
  • Cache stampede on leaderboard expiry: A simultaneous expiry of popular regional boards sends reads to the backend. Use versioned keys, stale-while-revalidate, and TTL jitter.
  • Ignoring tie-breaking: Equal scores need a deterministic order (for example earliest achiever first), or the board will flicker between merges.

🌍 Real-World Best Practice

Large leaderboards (game platforms, social feeds, trading boards) typically combine these ideas rather than choosing one:

  • Step 0 — Clarify semantics: Best score or latest score, can scores decrease, what freshness is acceptable, how many boards (global, region, friends, weekly).
  • Step 1 — Start simple: One sorted set per region and board covers many products up to tens of thousands of updates per second.
  • Step 2 — Decouple writes with a log: Put Kafka (or similar) in front, partitioned by player ID, to absorb bursts and enable replay.
  • Step 3 — Hierarchical top-K: Per-partition top-K, regional merge, global merge of regional results.
  • Step 4 — Serve from cache: Publish the materialized top-100 to Redis and a CDN, with short TTLs and versioned keys.
  • Step 5 — Add personal rank: Maintain an order-statistics structure for 'my rank and neighbours' queries.

Precompute what everyone reads, and compute lazily what only one person asks for.

💡

Key Takeaway

When millions of reads ask for the same small answer, compute it once on the write path and serve it from cache. Use a durable log for burst absorption, per-partition top-K with a hierarchical merge for exactness, and accept seconds of staleness. Reach for it only when a single sorted set stops being enough.
