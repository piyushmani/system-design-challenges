Scaling a Monolithic Profile Service: Vertical Scale-Up vs. End-to-End Horizontal Scale-Out

Liam, a backend engineer at a social networking app, runs the profile service as a monolithic JVM process backed by one large database. Traffic arrives in bursts, profile and photo updates create a high write load, and users far from the primary region see slow reads. Profiling shows that the primary's write throughput and storage growth, not a missing index, are the limiting factors, and every vertical resize causes downtime and is becoming cost-prohibitive. Reads must be fast and profile changes should become visible quickly, but cross-region linearizability is not required, and availability during spikes matters most. He must choose the architecture that scales the platform while balancing cost, operational complexity, availability, and latency.

A
Keep the single database and scale up: a bigger instance with faster storage and a larger application host. Minimal code change and few components, but everything depends on one machine.
✗ Not Best
B
Make the application tier stateless and scale it horizontally, keep a single unsharded primary, and add a few read replicas plus a shared cache for hot objects.
✗ Not Best
C
Scale out end to end: stateless services, shard the primary by user or tenant ID, add read replicas and a regional cache per shard, automate partition management and health checks, and keep cross-shard operations rare.
✓ Best Answer
D
Move to asynchronous writes with a durable event log and CQRS: append writes to the log, build read models asynchronously, and accept eventual consistency on reads.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — C: End-to-End Horizontal Scale-Out

Liam's bottlenecks sit in three different places: bursty compute, a single-writer database that cannot absorb growing write volume, and the distance between users and their data. Only an end-to-end scale-out addresses all three: stateless services scale with load, sharding by user ID spreads writes and storage across nodes, and replicas plus regional caches bring reads close to users. Because the product accepts bounded cross-region staleness, the design avoids the cost and complexity of global strong consistency. Here's why it stands out:

  • Removes the single-writer ceiling: Sharding by user ID splits write throughput and storage across several primaries, so growth means adding shards instead of buying a bigger machine. Replicas and caches alone (option B) never raise the write limit.
  • Natural partition key: Profile access is overwhelmingly by user ID, so most requests touch exactly one shard and need no cross-shard joins or transactions.
  • Low regional read latency: Read replicas and per-region caches serve most reads locally, which matches the requirement for fast reads with seconds of tolerated lag.
  • Availability and burst handling: Stateless instances autoscale behind a load balancer, a failing shard affects only its slice of users, and capacity changes no longer require downtime.
  • Strong consistency where it matters: Writes and read-your-writes reads go to the shard's primary, so a single user's profile stays consistent while other regions may lag slightly.

Treat this as a staged migration, not a big bang: make services stateless, move photos to object storage plus a CDN, add caching and replicas, then introduce sharding behind a routing layer with logical shards so rebalancing does not require re-keying. Track per-shard write rate, replica lag, cache hit rate, and p99 latency by region.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

⬆️

A — Vertical Scale-Up

Bigger machines are the fastest change, but they hit a hard ceiling, cost grows faster than capacity at the high end, and resizing often means downtime. The single instance also remains a single point of failure for every user and does nothing for users far from the region. Caveat: it is a sensible stopgap while load is modest or while a real migration is being prepared.

🧱

B — Stateless App + Replicas + Cache (Single Primary)

This is the right first stage: it fixes bursty compute and absorbs reads. But all writes (profile and photo metadata) still funnel into one primary, so the write ceiling and storage growth remain, and replicas in distant regions still pay replication lag. Caveat: if profiling shows the system is read-bound, this may be enough and far cheaper than sharding.

📜

D — Async Writes with CQRS and an Event Log

CQRS with an event log scales read models independently and tolerates bursts, but it is a major redesign: event schemas, projection rebuilds, idempotent consumers, and tooling for reasoning about eventual consistency. Users also expect to see their own edit immediately, which CQRS complicates. The write side still needs a scalable, partitioned store, so it does not remove the need to partition data. Caveat: a strong fit when you need an audit trail, many independent read models, or complex downstream fan-out.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Vertical Scale-Up

Early-stage or modest traffic, a need to buy time, or a database that is not yet near its limits and can tolerate a short maintenance window.

📌

B — Stateless App + Replicas + Cache

Read-heavy workloads where compute bursts and reads dominate, writes fit comfortably on one primary, and one or a few regions are acceptable.

📌

C — Full Scale-Out

Write throughput or dataset size exceeds what one node can handle, access is keyed by user or tenant, users are globally distributed, and the team can run a partitioned system.

📌

D — CQRS + Event Log

Audit and replay requirements, several independent read models, or complex downstream fan-out, with teams ready for eventual consistency and projection management.

⚠️ Common Mistakes to Avoid

  • Sharding before measuring: If the system is read-bound, caching and replicas deliver most of the benefit at a fraction of the complexity.
  • Choosing a poor shard key: A key that does not match access patterns causes cross-shard fan-out, and a skewed key (a region or a very large tenant) creates hot shards.
  • Mapping keys directly to physical nodes: Without logical shards or a directory, adding a node forces a mass data migration. Use many logical shards mapped onto fewer nodes.
  • Ignoring read-your-writes with replicas: Users who edit a profile and still see the old version file bugs. Pin post-write reads to the primary or use version tokens.
  • Leaving photos in the database: Large blobs inflate storage and replication. Use object storage plus a CDN and keep only references in the database.
  • Running stateful instances behind autoscaling: Local caches of mutable state or sticky sessions break scale-out and rolling deploys.

🌍 Real-World Best Practice

Teams rarely jump straight to sharding. They remove the cheapest bottlenecks first and shard once write throughput or storage proves to be the limit. A typical sequence:

  • Step 0 — Measure: Break down p99 latency by region and record write rate, storage growth, and the share of reads that could be cached.
  • Step 1 — Make the service stateless: Move sessions and local state out, add autoscaling and health checks (this also removes downtime during deploys).
  • Step 2 — Offload media: Store photos in object storage behind a CDN so only metadata reaches the database.
  • Step 3 — Cache and replicate reads: Add a regional cache and read replicas, with read-your-writes handling after profile edits.
  • Step 4 — Shard by user ID: Introduce a routing layer with many logical shards and migrate gradually using CDC or dual writes with verification.
  • Step 5 — Add event-driven read models selectively: Use asynchronous pipelines for search, feeds, and analytics rather than for the primary profile path.

Scale the layer that is actually saturated, and keep the number of moving parts proportional to the problem.

💡

Key Takeaway

When the write path and storage reach the limit of a single machine, bigger boxes only delay the problem. Scale out every tier: stateless compute, a partitioned database keyed by user, and replicas plus caches near users, while limiting cross-shard operations and handling read-your-writes explicitly.
