Idempotency Payments Double Charges
Challenge

Maya must prevent duplicate charges — how can she achieve request idempotency?

Maya is developing a globally distributed payment gateway API that handles high-frequency retries triggered by transient network failures, client SDK exponential backoff loops, and webhook delivery replays. To prevent duplicate billing (guaranteeing strict exactly-once processing for charge creation), the infrastructure must absorb traffic bursts of up to 10,000 transactions per second (TPS), maintain sub-10ms tail latencies across multiple geographic regions, and minimize operational maintenance overhead. Every logical payment request carries a client-supplied Idempotency-Key header. Maya needs an idempotency architecture that provides the optimal compromise between financial correctness, horizontal scalability, global latency, and operational burden.

A
A) Rely on the primary relational database to guarantee idempotency by applying a unique constraint on the combination of `client_id` and `idempotency_key` within the payments table, using an `INSERT ... ON CONFLICT` approach so the initial insert processes the charge while any later retries simply retrieve the existing record.
✗ Not Best
B
B) Construct a dedicated idempotency microservice supported by a Redis cluster. This service would use atomic check-and-set operations (through Lua scripts or CAS), save the standard response, and provide a REST endpoint that other services consult prior to executing a payment. Keys would be asynchronously backed up to object storage for auditing purposes.
✗ Not Best
C
C) Leverage a distributed, highly consistent key-value database (such as DynamoDB or Bigtable) to execute a conditional write (put-if-absent) for every idempotency key. Save the outcome alongside a Time-To-Live (TTL). If the write is successful, move forward with the charge; if it fails, return the previously saved outcome. Utilize global replication features to support reads across different regions.
✓ Best Answer
D
D) Forego dedicated idempotency tracking and instead ensure the payment process itself is logically idempotent by structuring payments as upserts on an aggregate, or by depending on reconciliation processes and compensating transactions to resolve any duplicate charges post-facto.

Answer & In-Depth Explanation

🏆 Best Answer — C: Distributed Key-Value Store with Atomic Conditional Writes & Native TTL

In high-volume, mission-critical financial applications, idempotency cannot simply be an afterthought or an in-memory cache; it must function as an atomic, durable, distributed gatekeeper. Using a managed distributed key-value store (such as Amazon DynamoDB Global Tables or Google Cloud Bigtable) with conditional writes (put-if-absent) is the industry standard for payment architectures (e.g., Stripe, Adyen, AWS). This strategy delivers an optimal balance across all required architectural dimensions:

  • Atomic Check-and-Mutate Primitive: The database engine executes the conditional write (e.g., attribute_not_exists(idempotency_key)) atomically at the storage layer in a single network round-trip. If two duplicate requests arrive simultaneously within milliseconds, the storage partition guarantees that exactly one succeeds and proceeds to charge the customer, while the other receives an immediate condition check error and transitions to polling or returning the cached result.
  • Predictable Burst Scalability (10,000+ TPS): Distributed key-value stores automatically partition data across storage nodes using a consistent hash of the partition key. Unlike relational databases that suffer from lock manager contention, B-tree latching, and connection exhaustion during 10k TPS traffic spikes, partitioned key-value databases scale write throughput horizontally and linearly without cross-shard bottlenecks.
  • Multi-Region Low-Latency Distribution: Modern managed KV stores support multi-active or globally replicated tables with single-digit millisecond read and write latencies. Regional API edge services in the Americas, Europe, and Asia-Pacific read and mutate local replicas without paying transatlantic latency penalties (150–250ms), keeping payment checkout flows responsive.
  • Zero-Maintenance Storage Lifecycle (TTL): Idempotency records only need to be retained for a finite contract window (e.g., 24 to 72 hours per IETF specifications). Native Time-To-Live (TTL) automatically purges expired records in the background without consuming provisioned throughput, running expensive table scans, or incurring the dead-tuple vacuuming bloat characteristic of RDBMS solutions.
  • Minimal Operational Overhead: Fully managed cloud KV stores eliminate the heavy operational toil of provisioning database clusters, managing read replicas, tuning WAL flush rates, performing Redis sentinel failovers, or maintaining custom pruning cron jobs.

By combining atomic conditional writes for lockless reservation, native TTL for automated lifecycle management, and managed multi-region partitioning, Maya achieves rock-solid financial exactly-once semantics without introducing operational friction or database bottlenecks.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🏛️

A — Relational Database Unique Constraint (INSERT ... ON CONFLICT)

Using an RDBMS with INSERT ... ON CONFLICT (client_id, idempotency_key) works well in low-scale monoliths, but collapses under global distributed scale. Directing global writes to a single primary database forces intercontinental network hops (150–250ms), violating low-latency requirements. Furthermore, handling sudden 10,000 TPS bursts on an indexed table causes intense row-level lock contention, buffer pool churn, and connection pool exhaustion. Caveat: Relational tables lack native TTL; without complex scheduled partitioning or table maintenance scripts, historical idempotency records cause massive table bloat and performance degradation.

⚡

B — Dedicated Redis Microservice with Object Storage Backup

While Redis delivers microsecond latency and atomic Lua scripts, relying on it as the source of truth for payment idempotency introduces critical durability hazards. Redis asynchronous replication means an ungraceful failover or cluster partition can lose recently acknowledged keys, allowing duplicate charges to pass through during failovers. Additionally, introducing a dedicated idempotency microservice adds extra network hops and significant operational overhead to patch, cluster, and monitor. Caveat: Asynchronously syncing keys to object storage leaves an audit gap during crashes and cannot provide synchronous consistency for real-time charge prevention.

🛑

D — Eventual Reconciliation & Compensating Transactions

Relying on reconciliation or treating payment creation as an upsert is catastrophic for payment systems. Payment processors and card networks (Visa, Mastercard) immediately charge the cardholder's financial institution; duplicate API calls trigger real duplicate money transfers. Resolving duplicate charges post-facto via compensating transactions (refunds) alienates customers, causes overdrafts, damages merchant reputation, and incurs non-refundable processing fees and chargeback penalties. Caveat: Exactly-once processing must be enforced prior to dispatching downstream credit card authorizations, never resolved retroactively.

📌

High-throughput, non-financial operations (e.g., notification deduplication, rate limiting, clickstream processing) where microsecond latency is critical and rare key loss during failover is harmless.

⚠️ Common Mistakes to Avoid

  • Ignoring Payload Mutation: Storing the idempotency key without verifying the payload hash. A client bug could send an identical key with a $1,000 charge instead of a $10 charge, resulting in returning the previous $10 receipt without executing the new charge.
  • Lack of In-Flight State Handling: Assuming an idempotency record is either missing or completed. If a retry arrives while the first call is still awaiting a payment gateway response, treating it as completed or throwing an unhandled exception results in dropped transactions.
  • Zombie Locks on Process Crashes: Marking a key as STARTED without an automatic in-flight timeout. If the worker process crashes before contacting the payment processor, subsequent retries will be blocked indefinitely by the stranded lock unless a lease timeout is enforced.

🌍 Real-World Best Practice

In production architectures at scale (such as Stripe's idempotency layer and modern fintech platforms), idempotency is implemented as an atomic state machine across three distinct phases: Reservation, Execution, and Finalization.

  • Step 1 — Ingress Hashing: The API Gateway receives Idempotency-Key in the HTTP headers. It computes a cryptographic SHA-256 hash of the request method, route, and canonical JSON body to detect payload tampering or accidental key reuse across distinct payments.
  • Step 2 — Atomic Reservation (Put-if-Absent): The service initiates a conditional write to the KV store (e.g., DynamoDB PutItem with attribute_not_exists(idempotency_key)). The item is written with status STARTED, payload hash, and an expiration timestamp (e.g., ttl = current_time + 86400).
  • Step 3 — Collision Resolution: If the write succeeds, the service holds the execution lock. If a ConditionalCheckFailedException occurs, the service performs a strongly consistent read. If the existing record is COMPLETED, it immediately returns the saved HTTP status and response payload. If it is STARTED, the service polls with backoff until completion or returns HTTP 409 Conflict.
  • Step 4 — Acquirer Invocation: With the reservation confirmed, the worker securely calls the upstream payment processor (e.g., Visa Direct, Stripe, or Chase Paymentech) passing the idempotency key as the merchant reference ID to ensure multi-tier idempotency.
  • Step 5 — Atomic Finalization: Upon receiving the processor's result, the service updates the KV record to COMPLETED, storing the sanitized HTTP status code and response body. Subsequent retries from the client will now immediately fetch this cached outcome without contacting the processor.

This distributed multi-tier reservation pattern ensures that even in the face of sudden process crashes, network timeouts, or repeated webhook retries, a customer's payment card is charged exactly once.

💡

Key Takeaway

To prevent duplicate billing across global environments, enforce request idempotency using a distributed key-value store with atomic conditional writes (put-if-absent) and native TTL. It provides atomic reservation, horizontally scales past 10,000 TPS, avoids database lock contention, and eliminates manual storage pruning.
