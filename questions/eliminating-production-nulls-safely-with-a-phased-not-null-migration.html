Eliminating Production NULLs Safely with a Phased NOT NULL Migration

Liam runs a user profile service that feeds analytics pipelines and several product-facing microservices. Over time the optional columns preferred_name, marketing_consent, and timezone in user_profiles accumulated many NULLs. Each consumer now applies its own COALESCE(...) with its own default, which recently caused wrong aggregations, an inconsistent user experience, and a CPU spike on a high-volume read path (where COALESCE inside filters and groupings can prevent index use). The table is live and large, so any fix must avoid long locks, keep read latency low, and be observable and reversible. He also has to decide, column by column, whether NULL ever meant something real, such as consent that was never asked. Which approach should he adopt?

A
Retain the nullable columns but consolidate the COALESCE logic into a shared database view or materialized view. This allows all services to query a unified canonical projection that applies the necessary defaults during read time. This represents a low-risk, rapid solution that circumvents the need for schema modifications.
✗ Not Best
B
Execute an online, phased schema migration to enforce NOT NULL constraints with explicit defaults on the columns. Add the defaults (or new columns), perform a batched background backfill, and employ triggers or write-side guards for incoming data during the backfill process. After verifying the data via metrics and audits, alter the columns to NOT NULL and eliminate the legacy COALESCE logic, managing the rollout with feature flags and robust monitoring.
✓ Best Answer
C
Restructure the optional fields by moving them into a separate sparse table (e.g., user_profile_optional), which contains a row for a user only when a value is present, and join this table during read operations. This approach minimizes NULL storage in the primary table and explicitly indicates value presence, keeping the main profile table streamlined to enhance the performance of wide-table scans.
✗ Not Best
D
Maintain the current database schema and handle defaulting within the application or caching tier. Each service (or a shared library) will apply the default logic and store the result in a Redis cache or CDN, ensuring rapid read responses with the defaulted values. Utilize background workers to proactively warm the caches and asynchronously rectify glaring NULL values.

Answer & In-Depth Explanation

🏆 Best Answer — B: Phased Online Migration to NOT NULL

NULLs here are a data-contract problem, not a query problem: every consumer invents its own meaning for 'missing'. The durable fix is to make the database enforce one explicit default so every reader, report, and downstream pipeline sees the same value, and to get there through an expand, backfill, validate, contract sequence that never takes a long lock. Here's why it stands out:

  • Single source of truth: One default defined in the schema replaces N private COALESCE rules, so aggregations, UIs, and CDC feeds agree by construction.
  • Removes read-path cost: Once values are real, queries filter and group on the column directly (sargable and index-friendly) instead of wrapping it in COALESCE for every row.
  • Safe on a live table: Setting a constant default is a metadata-only change on modern PostgreSQL (11+ for added columns with defaults) and online DDL on MySQL 8. The backfill runs in small batches, and the constraint is validated before it is enforced.
  • Prevents regression: Write-side guards stop new NULLs entering during the transition, and once NOT NULL is in place they cannot come back.
  • Observable and reversible: Track remaining NULL counts, batch progress, and error rates. Roll out consumer changes behind feature flags, and every phase can be paused or rolled back before the final constraint.

A sound rollout has an explicit default per column, write guards, a batched and throttled backfill, validation and audit queries, feature-flagged consumer cleanup, and finally NOT NULL enforcement. Remove the COALESCE logic only after the NULL count has stayed at zero for a full release cycle and downstream pipelines (CDC, warehouse) have picked up the new schema.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🪟

A — Shared View with COALESCE

A canonical view centralizes the default logic, which beats N copies, but the data stays dirty: the base table, CDC streams, exports, and anyone who bypasses the view still see NULLs. The view adds a layer under a hot read path, and a materialized view trades CPU for staleness and refresh cost. Filtering on a COALESCE expression inside the view remains non-sargable. It is a reasonable temporary stopgap while the migration runs.

🧱

C — Sparse Optional-Fields Table

Moving optional fields into a side table does not remove the ambiguity: 'no row' becomes the new NULL and every consumer still decides its own default. In PostgreSQL a NULL costs roughly one bit in the row's null bitmap, so the storage saving is negligible, while every read now needs a join, which hurts latency on the hot path. Sparse side tables make sense for genuinely rare, wide attributes, not for three fields every profile should have.

🧰

D — Defaults in the App or Cache Tier

Defaulting in a shared library or a Redis/CDN layer duplicates logic, risks version skew between services, and leaves the source of truth unchanged, so analytics and any direct database consumer still produce wrong results. It also adds cache invalidation and warm-up complexity to a problem that a schema constraint solves permanently. Caches are for speed, not for data correctness.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Shared COALESCE View

A fast, short-lived mitigation while the real migration is prepared, or reporting views that deliberately present a different shape than the stored data.

📌

B — Phased NOT NULL Migration

Production tables with a shared data contract, many consumers, and a need for correctness and read performance. The default choice for removing semantic ambiguity from a column.

📌

C — Sparse Optional Table

Genuinely sparse, rarely populated attributes (for example vendor-specific fields) where most rows have no value and the attribute is not part of the core contract.

📌

D — App / Cache Defaults

Presentation-level fallbacks (such as a UI placeholder) that are not business data, or an emergency patch when the database cannot be changed immediately.

⚠️ Common Mistakes to Avoid

  • One giant UPDATE: A single statement over the whole table holds locks, bloats the table, and lags replicas. Backfill in small keyed batches with pauses.
  • Adding the NOT NULL constraint first: SET NOT NULL on a big table can block writes while it scans. Validate a CHECK constraint first and set a lock_timeout.
  • Forgetting write guards: Rows inserted during the backfill (or by old service versions) reintroduce NULLs and the migration never converges.
  • Wrong default semantics: Defaulting consent to true, or treating 'unknown' as 'no' without recording it, creates legal and analytical errors. Decide per column.
  • Dropping COALESCE too early: Removing it from consumers before the constraint is enforced exposes them to NULLs. Flip consumers only after the NULL count is zero.
  • Not telling downstream teams: CDC consumers, warehouse models, and BI dashboards need the schema and semantics change communicated, or their own defaults will drift.

🌍 Real-World Best Practice

Large-table schema changes follow the expand and contract pattern, one safe step at a time:

  • Step 0 — Inventory and decide semantics: Count NULLs per column, find every reader and writer (services, ETL, BI), and decide per column whether NULL carries meaning and what the explicit default is.
  • Step 1 — Expand: Set the column default (metadata-only) and add write-side guards (a BEFORE trigger or application validation) so new rows and updates stop producing NULLs.
  • Step 2 — Backfill: Update existing rows in small, throttled batches (for example a few thousand rows) by primary-key range, watching replication lag, locks, and vacuum.
  • Step 3 — Validate: Add a CHECK (col IS NOT NULL) constraint as NOT VALID, VALIDATE it (which does not block writes), and confirm with audit queries and metrics.
  • Step 4 — Contract: SET NOT NULL, drop the temporary check and trigger, then remove COALESCE from services behind feature flags, one consumer at a time.
  • Step 5 — Inform downstream: Update schema registries, warehouse models, and data contracts so analytics sees the new non-null definition.

Make the invariant explicit in the schema, then delete the workarounds.

💡

Key Takeaway

Fix the data contract at the source. A phased, online migration to explicit defaults and NOT NULL constraints removes duplicated COALESCE logic, restores index-friendly queries, and keeps aggregations correct, while views and caches only mask the problem. Decide what NULL meant for each column before you overwrite it, especially for consent.
