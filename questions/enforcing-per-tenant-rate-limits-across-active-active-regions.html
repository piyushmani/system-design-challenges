Enforcing Per-Tenant Rate Limits Across Active-Active Regions

Sofia is building a globally available REST API that handles 100,000 requests per second at peak, running active-active in three regions. It must enforce strict per-tenant limits (requests per minute) with under 10 ms of added p95 latency, and the limiter must stay highly available even when a region is cut off from the central control plane. Cross-region round trips typically cost tens of milliseconds or more. She needs the design that best balances operational simplicity, availability, low latency, and accurate enforcement.

A
Use one centralized, strongly consistent datastore: a single Redis cluster in one region (Lua scripts for atomic token-bucket operations) as the global source of truth, with every API server validating and decrementing synchronously on each request and relying on multi-AZ failover and cross-region networking for availability.
✗ Not Best
B
Enforce limits locally with token buckets at the edge (API gateway or Envoy sidecar), synchronized with a central service: the central service is the source of truth and periodically hands out token quotas or refills to the edges; on cache misses or large bursts the edge falls back to querying the central service synchronously, using short TTLs, leases, and background reconciliation for long-term accuracy.
✓ Best Answer
C
Use client-side signed allowances: hand clients cryptographically signed tokens that state their remaining allowance and expiry, and have API servers verify the signature statelessly and act on the embedded claims with no synchronous central call.
✗ Not Best
D
Use asynchronous, eventual enforcement: accept every request immediately, log per-tenant usage to an event stream, and have a background worker compute totals and apply retroactive penalties, rejections, or billing adjustments if limits were exceeded.
✗ Not Best

Answer & In-Depth Explanation

🏆 Best Answer — B: Local Token Buckets With Central Quota Leasing

This is a CAP-style tradeoff in disguise: a limit that is perfectly accurate across three regions requires coordination on every request, and cross-region coordination costs tens of milliseconds and fails during a partition. The requirements (under 10 ms p95, available during partitions) rule out per-request global coordination, so the right design makes the hot path local and the coordination asynchronous and bounded: each region enforces from an in-memory token bucket filled by quota leases from a central allocator, with a conservative fallback when the center is unreachable. The result is enforcement that is exact while connected and has a known, configurable error bound when it is not. Here's why it stands out:

  • The hot path is local: An in-memory token-bucket check takes microseconds, so the 10 ms p95 budget is easily met at 100,000 requests per second, with no network call for the vast majority of requests.
  • Accuracy is controlled by leases: The central service gives each region only the tokens it may spend now, with a short expiry. While it is reachable, the sum of outstanding grants never exceeds the tenant's limit, so over-admission is bounded by lease size and sync interval rather than unbounded.
  • Partitions degrade gracefully: A disconnected region keeps serving from its last lease and then from a pre-agreed conservative share (a fraction of the limit), so the API stays up and any overshoot has a hard ceiling.
  • Demand-aware rebalancing: The central allocator can shift quota toward the regions where a tenant's traffic actually is, instead of splitting the limit statically three ways, which would waste capacity for regionally concentrated tenants.
  • An operationally proven pattern: Local enforcement in the proxy plus a global rate-limit service is a standard approach (for example Envoy's local and global rate limiting), and it separates the data plane (fast, local) from the control plane (slow, shared).

A production design includes token buckets with burst capacity, lease TTLs, fail-static fallback shares, idempotent refill messages, 429 responses with Retry-After, and metrics for rejections, lease utilization, and measured overshoot. Track the overshoot ratio against the agreed error bound, central call rate, and per-region rejection skew; if overshoot exceeds the bound, shorten leases or lower the fallback share.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🏛️

A — Single Central Redis, Synchronous Per Request

This is the most accurate design on paper and the worst fit for the constraints. Requests from the other two regions pay a cross-region round trip (tens of milliseconds or more) on every call, which blows the 10 ms p95 budget, and a single-region Redis is both a bottleneck for 100,000 requests per second and a single point of failure. A disconnected region must either reject all traffic or fail open and stop limiting. Caveat: for a single-region deployment where limits must be exact and the latency budget is relaxed, a central Redis with Lua token buckets is an excellent choice.

✍️

C — Client-Side Signed Allowances

A signature proves who issued a token, not how much has been spent. A stateless server cannot decrement a counter it does not store, so the same signed allowance can be replayed across regions, shared across clients, or reused concurrently until it expires. Per-tenant limits across many clients also need an aggregate view that signed tokens cannot provide, and revocation requires state anyway. Caveat: signed tokens are useful for carrying entitlements (the limit and tier) that the edge then enforces locally, which fits inside Option B.

⏳

D — Asynchronous Eventual Enforcement

Accept-first, penalize-later is a metering and billing model, not rate limiting. Rate limits protect the backend during a burst, and this design admits the entire burst before any counter is consulted, so one tenant can saturate capacity before the first penalty lands. Retroactive rejection is also meaningless, because the work has already been done. Caveat: for soft quotas and billing (monthly usage, plan overage), asynchronous accounting is the right tool, and it complements Option B.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Central Redis, Synchronous

Single-region systems or low-throughput APIs where limits must be exact and a few extra milliseconds are acceptable, with a bounded set of API servers.

📌

B — Local Buckets + Central Leases

Multi-region, high-throughput APIs where latency and availability matter more than perfect precision and a bounded error is acceptable.

📌

C — Client-Side Signed Allowances

As a carrier for entitlements (limit, tier, expiry) that servers then enforce locally; not as the enforcement mechanism itself.

📌

D — Async Eventual Enforcement

Usage-based billing, plan quotas over long windows, and abuse analytics where eventual accuracy is acceptable and no real-time protection is needed.

⚠️ Common Mistakes to Avoid

  • Synchronous global calls on the hot path: A call to another region for every request adds tens of milliseconds and a new failure mode. Keep the hot path local.
  • Fixed-window counters with boundary bursts: A tenant can send double the limit across a window boundary. Use token buckets or sliding-window counters.
  • Static equal splits across regions: Dividing the limit by three wastes capacity for tenants whose traffic is concentrated and causes spurious 429s. Allocate by observed demand.
  • No defined fail-open or fail-static behavior: If the control plane is down and the limiter fails open, there is no protection; if it fails closed, it causes an outage. Decide explicitly, usually fail-static with a conservative share.
  • Unbounded lease sizes or long TTLs: Big leases improve latency but increase overshoot and strand tokens in idle regions. Size leases to rate multiplied by the sync interval.
  • Clock skew between regions: Window boundaries based on wall clocks drift. Use monotonic local clocks with server-side refill rates, and avoid cross-region time comparisons.
  • Not telling clients how to behave: Without 429 plus Retry-After and rate-limit headers, clients retry immediately and amplify load. Return clear headers and encourage backoff with jitter.
  • Never testing partitions: The failure behavior you designed is only real if you test it with injected network cuts.

🌍 Real-World Best Practice

In practice, teams build rate limiting as layers with different consistency budgets:

  • Step 0 — Classify the limits: Separate protective limits (must be fast and always on), contractual quotas (must be accurate over longer windows), and billing counters (must be exact eventually).
  • Step 1 — Local enforcement: Put token buckets in the gateway or proxy, keyed by tenant, with burst capacity and a clear response contract (429 plus Retry-After and rate-limit headers).
  • Step 2 — Regional counter: If instances are many or load balancing is uneven, add a regional Redis for exact intra-region counts, which stays within a millisecond or two.
  • Step 3 — Global allocator: Add a control-plane service that leases quota to regions based on observed demand and tenant limits, replicated for availability.
  • Step 4 — Define failure behavior: Decide the fail-static share per region and the maximum acceptable overshoot, and test partitions explicitly with injected network cuts.
  • Step 5 — Observe and audit: Export accepted, rejected, lease-utilization, and overshoot metrics, and reconcile with asynchronous usage events for billing.

Accept an explicit error bound instead of pretending to have perfect global accuracy.

💡

Key Takeaway

Strict global limits and sub-10 ms latency cannot both be met by per-request coordination across regions. Enforce locally, coordinate asynchronously, and bound the error: token buckets at the edge, short-lived quota leases from a central allocator, and a conservative fail-static fallback during partitions. Use asynchronous accounting for billing, not for protection.
