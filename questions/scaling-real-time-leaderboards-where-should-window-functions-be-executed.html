Scaling Real-Time Leaderboards: Where should window functions be executed?

Lena, a systems engineer, is building a feature that shows running totals, dense rankings, and 7-day rolling statistics for millions of users. Events arrive at roughly 100k per second into a primary OLTP Postgres database. Users expect near-real-time updates (under about 5 seconds of staleness) and query responses under 300 ms. The heavy window-function work (sliding windows, running sums, row_number() aggregations) must not degrade the OLTP database, and the design must stay fault tolerant and observable. She needs the architecture with the best trade-off between operational complexity, latency, availability, and scalability.

A
Run the window functions directly on the primary Postgres OLTP database, adding read replicas, indexes, and vertical scaling as needed.
✗ Not Best
B
Compute everything in an overnight batch job into a read-only table and serve queries from it, accepting up to 24 hours of staleness.
✗ Not Best
C
Stream changes with CDC into a read-optimized analytical store (ClickHouse, Druid, Snowflake), run the window functions there, and accept eventual consistency with lag monitoring and backfills.
✓ Best Answer
D
Build continuous aggregates or materialized views inside the Postgres cluster (or a read replica), refreshed every 1-5 seconds, and serve queries from them.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — C: CDC + Analytical Store

Window functions over millions of users are scan-and-sort heavy work, and the primary is already absorbing 100k writes per second. The winning move is to take the computation off the OLTP path: capture changes with CDC, stream them into a columnar analytical engine built for aggregation and ranking, and serve the leaderboard from there. This isolates the transactional workload, meets the seconds-level freshness target, and lets the read tier scale independently. Here's why it stands out:

  • OLTP isolation: CDC reads the write-ahead log, so it adds little load to the primary, and heavy ranking queries never compete with transactional writes for CPU, buffer cache, or locks.
  • Engine fit: Columnar stores such as ClickHouse, Druid, or Pinot ingest streams continuously and aggregate huge row counts per second per node. Running totals and 7-day windows, especially via incremental rollups, fit comfortably inside a 300 ms budget.
  • Freshness is tunable and measurable: End-to-end lag (WAL, Debezium, Kafka, ingest) is typically sub-second to a few seconds, within the 5-second target, and the lag itself is a metric you can alert on.
  • Independent scaling and availability: The analytics cluster scales horizontally with replicas for read QPS. If it fails, OLTP keeps working and the leaderboard degrades to stale data instead of taking the product down.
  • Why not a bigger primary or more replicas? Replicas replay the same WAL, so they do not reduce per-query cost, and long window queries on a replica can be cancelled by replication conflicts or make it fall behind. More hardware raises cost without changing the shape of the problem.

A solid implementation has log-based CDC (for example Debezium), idempotent, deduplicated ingestion, incremental rollups, freshness and lag SLO alerts, and a replay and backfill procedure. Measure end-to-end staleness (event time versus the time it appears on the leaderboard) and p99 query latency. If lag regularly exceeds 5 seconds, tune batching or move the hot path to a stream processor (such as Flink) that maintains scores continuously.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🔥

A — Window Functions on the Primary

At 100k writes per second the primary is already busy. Window functions must scan and sort large row sets (a global dense rank over millions of users touches every user's total), which consumes CPU, memory, and I/O and competes with transactional work, causing latency spikes and vacuum pressure. Read replicas help with isolation but not with per-query cost. Caveat: at much smaller scale (thousands of users, modest write rate) a replica with good indexes is perfectly fine and the simplest option.

🌙

B — Nightly Batch

Operationally simple and cheap, but it violates the core requirement: up to 24 hours of staleness against a 5-second target. Caveat: batch is still valuable as a reconciliation layer, where a nightly job recomputes totals from the source of truth to correct drift in the streaming path.

🧱

D — Materialized Views in Postgres

Native Postgres materialized views are refreshed by recomputing the whole query, so refreshing a millions-of-users ranking every 1-5 seconds is not feasible and adds exactly the load you are trying to avoid. A replica cannot refresh them at all because it is read-only. Incremental options (TimescaleDB continuous aggregates, pg_ivm) work for sums and counts over time buckets, but rank-style window functions cannot be maintained incrementally, and everything still shares the same cluster's resources and write ingest. Caveat: continuous aggregates are a good fit for per-user rolling sums at moderate ingest rates, as a stepping stone.

⚡

C — CDC + Analytical Store ✓

Stream changes with CDC into a read-optimized analytical store (ClickHouse, Druid, Snowflake), run the window functions there, and accept eventual consistency with lag monitoring and backfills.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Window Functions on Primary

A small user base or modest write rate where an indexed query on a replica meets the SLA and operational simplicity matters most.

📌

B — Nightly Batch

Daily or weekly reports, billing summaries, or leaderboards where hours of staleness are acceptable (for example, season-end standings).

📌

C — CDC + Analytical Store

High write rates and large user bases that need second-level freshness and sub-second queries while the OLTP database must be protected.

📌

D — Postgres Materialized Views

Moderate scale, a requirement to stay inside Postgres, and aggregations that can be maintained incrementally (sums or counts per time bucket), for example with TimescaleDB continuous aggregates.

⚠️ Common Mistakes to Avoid

  • Ignoring replication slot lag: A stuck consumer makes Postgres retain WAL until the disk fills. Set max_slot_wal_keep_size and alert on slot lag.
  • Applying CDC events non-idempotently: Redelivery after a consumer restart double-counts points. Deduplicate on source LSN or event ID, or use engine-level dedup for mutable rows.
  • Recomputing rank from raw events per request: Even a fast columnar engine wastes budget. Use incremental rollups and cache the top pages.
  • Choosing a warehouse for serving: Pick the engine by query concurrency and latency needs, not just by the word 'analytics'.
  • Fuzzy rolling-window edges: Hourly buckets make '7 days' bucket-aligned. Decide whether that approximation is acceptable or use finer buckets with exact edge handling.
  • No backfill or reconciliation plan: Schema changes, bugs, and outages create drift. Keep a replay path and a nightly reconciliation job.

🌍 Real-World Best Practice

Senior engineers usually build this as a pipeline with precomputation at every stage rather than as one big query:

  • Step 0 — Define the metrics: Decide which values must be exact (total score, 7-day sums) and which can lag by seconds (rank).
  • Step 1 — Capture: Log-based CDC (Debezium on a logical replication slot) with a bounded-lag alert, or emit events to Kafka through an outbox.
  • Step 2 — Incremental rollups: Maintain per-user hourly or per-minute sums with materialized views. The 7-day window becomes a sum over the latest buckets, not a scan of raw events.
  • Step 3 — Serve ranking from a purpose-built structure: Top-N from the analytical store behind a short-TTL cache, or a Redis sorted set (ZADD, ZREVRANGE) for the global board. An individual's rank comes from counting users with a higher score.
  • Step 4 — Observe and recover: Dashboards for ingest lag, rows behind, and query p99. Replay from Kafka or backfill from a Postgres snapshot after incidents.
  • Step 5 — Reconcile: A nightly job compares aggregates with the source of truth and repairs drift.

Move the work to where it is cheap, and precompute whatever you can.

💡

Key Takeaway

Heavy window-function workloads do not belong on the OLTP primary. Stream changes out with CDC and compute rankings in an engine built for aggregation, ideally from incremental rollups. You trade a few seconds of eventual consistency for isolation, scale, and predictable latency, provided you monitor replication-slot and pipeline lag.
