Challenge

Fast Order Creation Without Double Charges or Overselling

Maya is building the POST /orders endpoint for a high-traffic e-commerce system made of Orders, Payment, and Inventory microservices plus a message broker. Mobile clients need a 200-500 ms response, yet the system must never double charge a customer and must never oversell stock across replicas. The payment provider's API commonly takes hundreds of milliseconds to a few seconds, and mobile networks cause client timeouts and retries. She needs an API and processing design that balances scalability, availability, latency, consistency, fault tolerance, and observability. Which approach should she implement?

A
A fully synchronous end-to-end HTTP request process: the Orders API validates the incoming request, invokes the Payment service to process the charge, and calls the Inventory service to reduce stock, all encapsulated within a distributed transaction (2PC) or a strict coordination protocol. It returns a 200 success status only if every step completes successfully.
✗ Not Best
B
A semi-synchronous hybrid model: the Orders API executes the payment charge synchronously and issues a success response once the payment is confirmed. The inventory reduction is handled asynchronously through a background process. If there is insufficient inventory, the system automatically triggers a compensating refund.
✗ Not Best
C
A completely asynchronous, event-driven architecture: the Orders API validates the request, stores a tentative order requiring an idempotency key, returns a 202 Accepted status with the order ID, and emits an OrderCreated event to the message broker. Dedicated workers for payment and inventory consume these events, utilizing idempotent operations and either optimistic concurrency or a reservation system to process payments and update stock. Order status is provided via a read model (using polling or webhooks), supported by dead-letter queues, retries, and distributed tracing for full observability.
✓ Best Answer
D
A centralized order processing system: direct all incoming order requests to a solitary, stateful Order Processor service. This service executes both payment and inventory steps synchronously internally, relying on a central inventory database with strict locking mechanisms to guarantee no overselling occurs. This service would be scaled vertically and placed behind a load balancer configured with sticky sessions to maintain application state.
✗ Not Best

Answer & In-Depth Explanation

🏆 Best Answer — C: Async Order Acceptance with an Idempotent Saga

The latency target and the correctness rules only conflict if you try to finish everything inside the request. The way out is to separate acceptance from completion: durably record the order and an idempotency key in a few milliseconds, answer 202 Accepted, and complete reserve, pay, and confirm asynchronously with idempotent steps and compensations. Correctness comes from atomic reservations and idempotent payment calls, not from holding the client connection open. Here's why it stands out:

  • Latency is decoupled from slow dependencies: The API only validates, writes the order (plus an outbox event) in one local transaction, and returns the order ID. That fits comfortably in 200-500 ms even if the payment provider takes two seconds.
  • Double charges are prevented by idempotency: A unique constraint on the client's idempotency key makes retried requests return the same order, and an order-derived key forwarded to the payment provider means a repeated charge call cannot create a second charge.
  • Overselling is prevented by atomic reservation: Inventory is decremented with a conditional update or a reservation with a TTL, so two replicas can never both take the last unit, regardless of how many workers run.
  • Scales and survives failures: Workers scale horizontally, the broker absorbs bursts, dead-letter queues capture poison messages, and retries are safe because every step is idempotent.
  • Observable by design: Order status is an explicit state machine exposed through a read model (polling, push, or webhook), and a correlation ID flows through traces from the API to every worker.

A complete design includes an idempotency-key table with a unique constraint, a transactional outbox, reserve-then-authorize ordering, idempotent provider calls, compensations (release the reservation, void the authorization), dead-letter queues, and an order state machine with timeouts. Alert on orders stuck in PENDING beyond the SLA.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🧵

A — Fully Synchronous with 2PC

Holding the client request open across Payment and Inventory makes response time the sum of every dependency's tail latency, and a provider taking one to two seconds breaks the 200-500 ms target. External payment processors cannot participate in 2PC, so the distributed transaction either does not truly exist or blocks resources while waiting, and availability is the product of all services' availability. Timeouts also leave the client unsure whether it was charged. Caveat: a synchronous call is acceptable when all dependencies are fast, internal, and reliable, which is not the case here.

💳

B — Charge Synchronously, Reserve Stock Asynchronously

This ordering puts the slowest, least reliable call (payment) on the critical path and then discovers stock-outs after taking the customer's money. Compensating refunds cost fees, can take days to appear on statements, trigger support contacts and chargebacks, and mean overselling has already happened from the customer's point of view. Reversing the order (reserve first, then pay) and finishing asynchronously avoids this.

🏢

D — Central Stateful Order Processor

A single stateful processor with sticky sessions and vertical scaling is a scalability ceiling and a single point of failure: a crash loses in-memory state, deployments disrupt sessions, and strict locks on a central inventory table create contention hot spots. It also keeps the slow payment call on the request path, so latency stays hostage to the provider. It simplifies reasoning at small scale but conflicts with the high-traffic and availability requirements.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Fully Sync + 2PC

Internal, low-volume workflows where all dependencies are fast, reliable, and under your control, and an instant final answer is required.

📌

B — Charge Sync, Reserve Async

Digital goods or services with effectively unlimited inventory, where the payment result is the main gate and stock-outs are very rare.

📌

C — Async Accept + Idempotent Saga

High-traffic checkout with scarce inventory, slow external payment providers, flaky mobile clients, and strict correctness requirements.

📌

D — Central Stateful Processor

Small systems or prototypes with one instance and moderate traffic where simplicity beats resilience.

⚠️ Common Mistakes to Avoid

  • No idempotency key (or no unique constraint): Check-then-insert races let two retries create two orders. Enforce uniqueness in the database.
  • Not forwarding the key to the payment provider: Your own dedupe does not help if the provider call is retried after a timeout. Pass an idempotency key to the provider too.
  • Dual write of order and event: Saving the order and then publishing to the broker separately can lose accepted orders. Use an outbox.
  • Charging before reserving: Refund-after-stock-out is a poor experience and costs money. Reserve first, then authorize.
  • Reservations without a TTL: Failed or abandoned orders hold stock forever. Expire and release them, and make release idempotent.
  • Unbounded retries without a DLQ or state timeouts: Orders get stuck invisibly. Cap retries, route failures to a DLQ, and alert on PENDING age.

🌍 Real-World Best Practice

High-traffic checkout systems typically follow reserve, authorize, confirm and make every step safe to repeat:

  • Step 0 — Accept fast: Validate input, check the idempotency key, insert the order as PENDING and an outbox row in one transaction, and return 202 with the order ID.
  • Step 1 — Reserve inventory: An atomic conditional decrement (or a reservation with a TTL) per SKU. On failure, mark the order REJECTED_OUT_OF_STOCK.
  • Step 2 — Authorize payment: Call the provider with an idempotency key derived from the order, authorizing first and capturing on confirmation when the provider supports it.
  • Step 3 — Confirm or compensate: On success mark CONFIRMED and capture. On failure release the reservation and void the authorization.
  • Step 4 — Tell the client: Push notification, webhook, or polling on a read model, with an optional short long-poll for the fast path.
  • Step 5 — Reconcile: A periodic job compares orders, reservations, and provider records to catch stuck or orphaned states.

Accept quickly, finish reliably, and make every step safe to repeat.

💡

Key Takeaway

Separate acceptance from completion. Returning 202 after a durable, idempotent write meets the latency target, while atomic reservations and idempotent provider calls deliver the no-oversell and no-double-charge guarantees. Synchronous 2PC, charge-then-refund, and a single stateful processor each sacrifice latency, customer experience, or availability.
