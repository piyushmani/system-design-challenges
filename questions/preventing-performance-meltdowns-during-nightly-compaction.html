Challenge

Preventing Performance Meltdowns During Nightly Compaction

Aisha manages the backend of a high-volume time-series data platform whose nodes use an LSM-tree storage engine. Data is append-mostly, expires through TTLs or retention rules, and most queries touch recent data. Operators currently run nightly full compactions or VACUUM jobs, which cause CPU and IO bursts, extended tail latencies and brief outages, while tombstones from deleted or expired data pile up between runs and make storage grow quickly. The platform spans many nodes and shards and the team wants minimal operational intervention. She must choose a compaction and space-reclamation strategy that keeps read and write latency predictable and scales with the cluster.

A
Run synchronous compaction in the write path: delay or block writes until the relevant SSTables are compacted and tombstones are purged.
✗ Not Best
B
Use a central compaction coordinator that schedules full-table compactions across all nodes during defined maintenance windows.
✗ Not Best
C
Run continuous, incremental, IO/CPU-adaptive background compaction independently on every shard, with time-windowed and tombstone-aware logic for older data, tiered storage for cold segments, and backpressure and monitoring to throttle ingestion if compaction falls behind.
✓ Best Answer
D
Rely on weekly, operator-initiated full VACUUM or compaction during low-traffic periods, backed by strict retention policies and snapshot cleanup.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — C: Decentralized Incremental Compaction

Given this workload (time-series, append-mostly, TTL-driven deletes, many shards, strict latency targets), a decentralized, incremental background compaction model per shard is the right design. The nightly pain comes from letting compaction debt (SSTable count, tombstones, read amplification) pile up and then paying it all at once. LSM engines are built to pay that cost continuously and in small pieces. The goal is to match the pace of compaction to the pace of ingestion, with every node bounding its own IO and CPU use. Here's why it stands out:

  • No big-bang IO bursts: Small, continuous compactions use a bounded IO budget (a rate limiter or token bucket), so the cost is spread across the day instead of landing in a nightly spike. Tail latency stays flat because there is never a large batch of work competing with foreground reads and writes.
  • Time-windowed layout fits time-series data: Grouping SSTables by time window (like Cassandra's TimeWindowCompactionStrategy) means old windows stop being rewritten once sealed, and whole expired windows can be dropped as files with almost no IO instead of being rewritten to purge tombstones.
  • Tombstone-aware scheduling reclaims space early: Prioritizing SSTables with a high tombstone or expired-data ratio, and compacting them as soon as it is safe, keeps space amplification and tombstone scanning on the read path under control without a full rewrite.
  • Scales linearly with shards: Each shard decides locally using its own metrics (pending compaction bytes, L0 file count, disk headroom). There is no global scheduler to become a bottleneck or single point of failure, and adding nodes adds compaction capacity.
  • Self-protecting through backpressure: If compaction falls behind, the engine slows or stalls ingestion gradually (as RocksDB write stalls do) instead of letting read amplification run away, and monitoring shows the debt before it becomes an outage.

A mature setup combines time-window or leveled compaction tuned to retention, a per-node IO and CPU budget, tombstone-ratio triggers, whole-window expiry for TTL data, backpressure, and dashboards for pending compaction bytes, SSTables per read, tombstones scanned per query and disk headroom. Alert on the trend of compaction debt, not only on disk usage.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

⛔

A — Synchronous Write-Path Compaction

Making writes wait for compaction ties write latency directly to compaction cost, the opposite of what the platform needs. One large compaction would stall ingestion for the whole shard, and a slow disk or a large SSTable set turns into client timeouts. LSM trees exist so that writes are cheap appends to a memtable and WAL, with heavy work deferred to the background. Caveat: a bounded form of this idea is valid, namely slowing writes when compaction debt crosses a threshold, but that is backpressure on a background process, not compaction in the write path.

🎛️

B — Central Compaction Coordinator

A central scheduler adds a single point of failure and a scaling bottleneck, and it needs a fresh view of every shard to make good decisions. It also keeps the problem that hurts today, namely full-table compactions in a window, so the IO and CPU bursts remain. Compaction is an inherently local decision (it depends on each node's own SSTables, disk and load), so there is little for a global controller to optimize. Caveat: a lightweight global policy layer (for example staggering heavy work so not all replicas of a shard compact at once) is useful, but execution should stay local.

🗓️

D — Weekly Operator-Run Full Compaction

This is today's approach with a longer interval. Tombstones and SSTables accumulate for a week, so reads slow down as the week goes on, storage balloons, and the eventual full compaction is bigger and riskier than the nightly one. It also relies on manual operations, which do not scale across many nodes and shards. In size-tiered setups, a major compaction can leave one huge SSTable that rarely gets compacted again, which makes later maintenance harder. Caveat: strict retention policies and snapshot cleanup are good hygiene and belong in any design, but they are not sufficient on their own.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Synchronous Write-Path Compaction

Almost never as a general design. Narrowly justified as backpressure when compaction debt crosses a hard limit and continuing to accept writes would make the node unrecoverable.

📌

B — Central Coordinator

Cluster-wide policy and visibility, for example staggering heavy work across replicas, capping concurrent compactions per rack, or pausing compaction during a maintenance event. Not for executing compaction itself.

📌

C — Decentralized Incremental

Large, multi-node LSM-tree deployments with time-series or TTL-driven data, strict latency targets and a need for low operational effort. The default for production systems.

📌

D — Weekly Manual Full Compaction

Small or dev-scale clusters, rarely written archival data, or a one-off repair after a bad bulk delete. Always rate-limited and one node at a time.

⚠️ Common Mistakes to Avoid

  • Running a major compaction to fix tombstones: A full compaction rewrites everything, creates a long IO burst, and in size-tiered setups leaves one giant SSTable that rarely compacts again. Prefer targeted, tombstone-triggered compaction.
  • Leaving compaction throughput unlimited: Without a rate limit, compaction competes with foreground IO on the same disks. Set an explicit IO budget and a bounded number of concurrent compactions.
  • Dropping tombstones before replicas are repaired: If a tombstone is purged before every replica has seen it, deleted data can come back. Keep the grace period longer than the repair interval.
  • Mismatched TTLs and compaction windows: If data in one window expires at different times (mixed TTLs, late out-of-order writes), whole-file expiry never triggers and tombstone-heavy files linger.
  • No headroom for compaction itself: Compaction temporarily needs extra disk space for input and output files, and size-tiered strategies can need close to the size of the data being compacted. Running disks near full leads to stuck compactions and emergency stalls.
  • Ignoring write stalls as a signal: Stalls are the engine telling you compaction debt is too high. Raising the stall thresholds only delays the failure. Fix the throughput budget or the ingestion rate instead.

🌍 Real-World Best Practice

In practice, teams measure compaction debt before changing strategy and then tune continuously. A typical sequence looks like this:

  • Step 0 — Measure first: Track pending compaction bytes, SSTables per read, tombstones scanned per query, write stalls and disk headroom. Know whether the pain comes from too many L0 files, too many tombstones, or too little IO budget.
  • Step 1 — Fit the strategy to the data: Time-window compaction for TTL'd time-series, leveled for read-heavy updatable data, size-tiered for write-heavy data with few overwrites.
  • Step 2 — Cap the cost: Add compaction rate limits and IO priorities so background work cannot starve foreground traffic, and limit concurrent compactions per node.
  • Step 3 — Align retention with layout: Make TTLs and window sizes line up so whole files expire together, which turns space reclamation into a cheap file delete.
  • Step 4 — Add backpressure and alerting: Throttle ingestion or shed load gracefully when debt grows, and alert on the growth rate of pending compaction rather than on absolute disk usage.
  • Step 5 — Tier cold data: Offload sealed old windows to cheaper storage once the hot path is stable, and keep a manual full compaction only as a rare, rate-limited repair tool.

Fix the shape of the workload first; the compaction schedule follows from it.

💡

Key Takeaway

Pay compaction cost continuously and locally instead of in nightly bursts. Time-windowed, tombstone-aware, rate-limited background compaction on each shard keeps latency flat and space under control, and backpressure protects the system when it falls behind. Full compactions and central schedulers concentrate risk, and synchronous compaction puts that risk on the write path.
