Challenge

How Can Arjun Safely Extract the Profile Service from the Monolith?

Arjun, an engineering lead, owns a large monolith that handles user profiles, settings, and session customization for 20 million monthly active users. The workload is read-heavy (about 10 reads per write), with a p95 profile read SLA under 50 ms and a 99.9% availability target. The monolith's database has become the bottleneck for scaling and deployment safety: schema changes are slow and releases are tightly coupled. The team wants to use the Strangler Fig pattern to extract the Profile domain with negligible user impact. Most attributes (personalization) can be eventually consistent, but a small set of legal-compliance fields at checkout needs strong consistency. Which migration architecture best balances scalability, availability, latency, consistency, observability, and fault tolerance?

A
Separate out a Profile microservice while continuing to read and write directly to the current monolith database in a shared DB setup. The new service functions as a lightweight API wrapper, sending any requests that alter the schema back to the monolith. Direct traffic via an API gateway that incrementally routes to the new service, with both applications sharing the underlying database.
✗ Not Best
B
Make the new Profile service handle only the write operations by setting up application-level dual writes, synchronizing data to both the monolith database and the new service's database. Read operations are directed to the active service, utilizing distributed tracing and periodic reconciliation jobs to resolve any data inconsistencies caused by write failures.
✗ Not Best
C
Provide the new Profile service with a dedicated database and establish an anti-corruption layer. Employ change-data-capture (CDC) or an event stream from the monolith to asynchronously update the new database, allowing eventual consistency for personalization data while maintaining synchronous interactions or a strong-consistency proxy for the few critical checkout fields. Shift read traffic incrementally using an API gateway and traffic-splitting, leveraging feature flags, monitoring, and retries to identify and manage data divergence.
✓ Best Answer
D
Maintain the monolith as the primary source of truth, but introduce a sidecar or cache layer on each host that provides a Profile interface. Rely on central materialized views (such as read replicas or materialized tables) refreshed by scheduled batch processes to ensure fast reads. The new microservice acts merely as a facade with the bulk of the write operations remaining in the monolith, while the sidecar manages cache invalidation and local data retrieval.
✗ Not Best

Answer & In-Depth Explanation

🏆 Best Answer — C: Dedicated DB + Anti-Corruption Layer + CDC with Incremental Cutover

The Strangler Fig pattern puts a routing facade in front of the monolith and moves capabilities out one slice at a time. For that to deliver autonomy, the new service must own its data; otherwise it is just a renamed module. Option C does exactly that: Profile gets its own datastore, an anti-corruption layer keeps the legacy model from leaking in, change-data-capture (CDC) replaces fragile application-level dual writes, and traffic shifts gradually behind flags with a rollback path. Here's why it stands out:

  • Removes the real bottleneck: A dedicated database lets Profile scale reads independently (replicas, cache, read-optimized schema) and change its schema without coordinating with monolith releases. A shared database (option A) keeps both problems.
  • CDC avoids the dual-write problem: Reading the monolith's transaction log (or an outbox table) yields an ordered, durable stream of changes that commits atomically with the source write. Two independent writes (option B) can fail halfway and diverge with no atomic way to repair them.
  • Fits mixed consistency needs: Personalization attributes tolerate seconds of lag, so asynchronous replication is fine. The few checkout-critical fields take a strongly consistent path (read from the current system of record, or a synchronous call), so legal-compliance reads are never stale.
  • Meets the latency SLA: Reads are served from the Profile service's own store, usually fronted by a cache, with no cross-service hop to the monolith. A p95 under 50 ms is realistic for key-based reads on a purpose-built store.
  • Safe, reversible rollout: The gateway splits traffic by percentage or cohort, shadow reads compare old and new responses, feature flags allow instant rollback, and metrics (mismatch rate, CDC lag, error rate, p95) gate each step.
  • Fault isolation: If the new service degrades, the gateway can fall back to the monolith, which still holds a correct copy during the migration. That protects the 99.9% availability target.

Plan the migration as phases with clear exit criteria: backfill, CDC lag under a threshold, shadow-read mismatch near zero, incremental traffic shifts (for example 1%, 10%, 50%, 100%), write-ownership cutover, then retirement of monolith code. Track CDC lag, mismatch rate, p95/p99 latency, and error-budget burn, and keep the rollback switch until the monolith path is deleted.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🪞

A — Shared Database Facade

Two services reading and writing the same tables form a distributed monolith: the schema is still coupled, migrations still need cross-team coordination, and the database bottleneck is unchanged. Sending schema-changing requests back to the monolith means the new service cannot evolve on its own. Caveat: a shared database is a defensible, short-lived first step to prove routing and API contracts, as long as there is a concrete plan to split the data.

✌️

B — Application-Level Dual Writes

Writing to two databases from application code is not atomic: one write can succeed while the other fails, or concurrent requests can interleave differently in each store, causing silent divergence. Reconciliation jobs detect drift after the fact but cannot always tell which side is right, and checkout-critical fields cannot tolerate that. Caveat: dual writes driven by a transactional outbox or log are fine; naive dual writes are the problem.

🧊

D — Sidecar + Cache Facade

Sidecar caches and materialized views speed up reads, but the monolith database remains the source of truth and the write bottleneck, so deployment coupling and slow schema changes remain. Batch refresh makes staleness unpredictable, and per-host cache invalidation across a large fleet is error-prone. It is an optimization, not a decomposition.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Shared DB Facade

A very short-lived first step to validate routing and API contracts, never as the final state.

📌

B — Dual Writes

Only with a transactional outbox or log-based mechanism; avoid naive dual writes for anything that needs correctness.

📌

C — Own DB + ACL + CDC

Extracting a data-owning, read-heavy domain from a monolith where autonomy, scalability, and gradual rollout all matter.

📌

D — Sidecar + Cache

Quick read-latency relief on a monolith that will remain the system of record; not a decomposition strategy.

⚠️ Common Mistakes to Avoid

  • Big-bang cutover: Moving reads, writes, and data at once. Slice by capability and field, and keep each step reversible.
  • Skipping the snapshot-to-stream handoff: Starting CDC without a recorded log position leaves gaps or duplicates. Snapshot at a known position, then stream from it.
  • Two writers for the same field: Concurrent writers across old and new systems cause lost updates. Assign a single owner per field and enforce it.
  • Letting the monolith's model leak: Without an anti-corruption layer, legacy naming and semantics spread into the new service and re-couple it.
  • No observability on divergence: Without shadow comparison, mismatch metrics, and CDC lag alerts, customers find the drift before you do.
  • Ignoring read-your-writes: Users who just saved a change expect to see it. Plan for it explicitly.

🌍 Real-World Best Practice

Teams that extract data-owning services successfully treat it as a sequence of low-risk, reversible steps:

  • Step 0 — Define the seam: Inventory profile tables, consumers, and access patterns; classify each field as eventually or strongly consistent; publish an API contract and put the gateway in front of the monolith.
  • Step 1 — Build and backfill: Stand up the Profile service and its store, snapshot existing data, then start CDC from the log position recorded at snapshot time so nothing is missed.
  • Step 2 — Shadow reads: Keep serving from the monolith while comparing against the new service in the background; fix mapping bugs in the anti-corruption layer.
  • Step 3 — Shift reads incrementally: Percentage and cohort rollouts through the gateway, with automatic rollback when an SLO is breached.
  • Step 4 — Move write ownership: Flip per field group, reverse the sync direction, keep the old path as a fallback, and handle critical fields last with extra reconciliation.
  • Step 5 — Decommission: Remove monolith code and tables only after a clean soak period and a verified final reconciliation.

Never move reads, writes, and data in the same step; separate them so any failure is easy to attribute and undo.

💡

Key Takeaway

A strangler migration succeeds when the new service owns its data and the cutover is incremental and reversible. Use CDC (not dual writes) to keep stores aligned, treat strongly consistent fields as a separate explicit path, and let metrics, not the calendar, decide when to shift more traffic.
