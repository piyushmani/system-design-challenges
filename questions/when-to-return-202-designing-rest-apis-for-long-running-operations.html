When to return 202: designing REST APIs for long-running operations

Lena, a backend engineer at a fast-growing e-commerce company, is designing the REST API for a create order endpoint. Placing an order triggers inventory reservation, fraud evaluation, payment processing, and downstream fulfillment. Several of these steps are unstable or slow and can take seconds to minutes. Product needs transparent tracking of the final success or failure of each order, while users expect immediate feedback in the UI. Lena must choose a RESTful strategy that optimizes observability, fault tolerance, consistency, availability, and latency while avoiding excessive coupling among microservices. Which architectural design should she select?

A
Design the /orders POST to be synchronous: manage all downstream requests sequentially and return a 200 OK only once every single downstream service reports success. Should any step fail, send a 4xx or 5xx error back to the client.
✗ Not Best
B
Implement distributed two-phase commit (2PC) encompassing the necessary services, causing the /orders POST request to block until a system-wide commit is achieved, thereby guaranteeing strict consistency across all services prior to returning a response.
✗ Not Best
C
Receive the order request and instantly respond with a 202 Accepted, including a Location header that references an /orders/{id}/status endpoint. Place the task onto a durable message queue to be handled by idempotent consumers, provide an optional webhook for callbacks, and allow clients to periodically check the status resource. Integrate metrics and distributed tracing to ensure observability.
✓ Best Answer
D
Reply with a 200 OK straight away once the initial request is saved, without offering idempotency guarantees or a dedicated status endpoint; instead, depend on eventual consistency across services and background reconciliation processes.
✗ Not Best

Answer & In-Depth Explanation

🏆 Best Answer — C: 202 Accepted with a Status Resource and Durable Queue

When work takes seconds to minutes and depends on flaky services, holding the HTTP request open ties the user's experience and your availability to the slowest dependency. The REST-native answer is to durably accept the order, return 202 Accepted immediately with a Location header pointing at a status resource, and finish the work asynchronously through a queue with idempotent consumers. The client gets instant feedback and a reliable way (polling or webhook) to learn the final outcome. Here's why it stands out:

  • Fast, predictable latency: The response time is just validation plus one durable write, typically tens of milliseconds, regardless of how slow fraud checks, payment, or fulfillment are.
  • Fault tolerance and availability: The queue buffers spikes and downstream outages, consumers retry with backoff, and poison messages go to a dead-letter queue. A slow payment provider no longer shows up as 5xx errors and timeouts at the edge.
  • Loose coupling: The order service does not call every downstream system synchronously. Steps run as an orchestrated or choreographed saga, so new steps can be added without changing the client-facing contract.
  • Transparent outcomes: A status resource backed by an explicit state machine (PENDING to CONFIRMED or FAILED), optional signed webhooks, and a Retry-After hint give clients a clear, honest way to track progress.
  • Strong observability: The order id and trace context (W3C traceparent) flow from the request into the messages. Queue depth and age, time-to-confirm, failure reasons by step, and DLQ counts become direct SLIs.

A solid contract has durable acceptance, an Idempotency-Key, a Location header to the status resource, idempotent consumers with dead-lettering, compensating actions for failure, and trace propagation across the async boundary. Add a sweeper that flags orders stuck in PENDING beyond their SLA.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

⏳

A — Fully Synchronous Orchestration

Simple to reason about, but total latency is the sum of every step and availability is the product of every dependency's availability. A timeout leaves the outcome ambiguous (did the payment go through?), clients retry and create duplicates, threads and connections stay tied up, and a single HTTP status cannot express partial progress. Caveat: it is fine for fast, reliable, few-step flows, and cheap validation should stay synchronous even in the async design.

🔐

B — Distributed Two-Phase Commit

2PC blocks the request while locks are held across inventory, payment, and fulfillment, the coordinator becomes a single point of failure, and throughput falls as participants are added. External providers such as payment gateways and fraud APIs do not take part in XA transactions at all. The standard alternative for cross-service workflows is a saga with compensating actions.

🙈

D — Immediate 200 OK, No Idempotency, No Status Endpoint

It looks fast but fails the explicit requirement for transparent tracking: 200 OK claims the work is done when it is not, clients have no way to learn the outcome, and retries create duplicate orders. Relying on background reconciliation as the primary mechanism turns failures into silent, delayed surprises.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Fully Synchronous

A short, reliable chain of fast operations (typically under a second in total) where the client genuinely needs the final result in the same response.

📌

B — Distributed 2PC

Rare cases with a small number of cooperating XA-capable resources in one trust domain and a hard requirement for atomic commit. Almost never for microservices or third-party providers.

📌

C — 202 + Status + Queue

Multi-step workflows with slow or unreliable dependencies, durations from seconds to minutes, and a need for transparent tracking and resilience, as in orders, payments, exports, and provisioning.

📌

D — Immediate 200, No Status

Fire-and-forget, low-stakes notifications such as best-effort analytics events, where losing or repeating an item is acceptable.

⚠️ Common Mistakes to Avoid

  • Returning 202 before the work is durable: If the process crashes after the response but before persistence or enqueue, the order silently vanishes. Commit the order and the outbox row first.
  • No Idempotency-Key on POST: Mobile networks retry. Without a key, one tap can create several orders or charges.
  • No status resource or Location header: The client cannot learn the outcome, so support tickets become the monitoring system.
  • Non-idempotent consumers and no DLQ: At-least-once delivery replays messages. Without dedupe, steps run twice, and without a DLQ, one poison message blocks the queue.
  • Unbounded polling: Clients that poll every 100 ms create load that rivals the original problem. Send Retry-After, support ETag/304, and offer webhooks or SSE.
  • No compensation or stuck-order detection: A failure in the last step must release stock and void the payment, and orders stuck in PENDING need an alert and a timeout path.

🌍 Real-World Best Practice

In practice, teams decide which checks must be synchronous, then make everything else asynchronous with a clear status contract. A typical sequence looks like this:

  • Step 0 — Define the contract: Keep only cheap, must-fail-fast checks synchronous (authentication, schema validation, idempotency lookup, perhaps a quick stock pre-check). Everything else becomes asynchronous.
  • Step 1 — Accept durably: Insert the order as PENDING plus an outbox row in one transaction, then return 202 Accepted with Location and Retry-After, honoring the Idempotency-Key.
  • Step 2 — Orchestrate with a saga: Run inventory, fraud, payment, and fulfillment as idempotent steps with compensations. Choose orchestration (a workflow engine) for complex flows or choreography for simple ones.
  • Step 3 — Expose status: Offer GET /orders/{id}/status (or a status field on the order) with timestamps and a failure reason, use ETags for cheap polling, and optionally redirect with 303 See Other to the final resource when done.
  • Step 4 — Push where it helps: Provide signed webhooks with retries and replay, or SSE/WebSocket for live UIs, keeping polling as the fallback.
  • Step 5 — Instrument: Propagate trace context through messages, track time-to-confirm and queue age, alert on DLQ growth, and run a stuck-order sweeper.

Keep the synchronous part tiny and the status contract explicit.

💡

Key Takeaway

For multi-step, failure-prone workflows, accept fast, process asynchronously, and make the outcome observable. Return 202 with a status resource, protect retries with idempotency, process through a durable queue, and compensate on failure. You trade immediate finality for resilience, low latency, and honest tracking.
