Maya's API Versioning Crossroads: Launching v2 Without Breaking Existing Clients

Maya is a senior backend engineer on a payments platform handling hundreds of millions of requests daily. The public REST API /v1/ is used by many third-party merchants. The team must ship v2 with breaking changes (new resource structures and a different authentication header) while keeping v1 fully operational for a 12-month migration window. Tail latency directly affects checkout success. They want to minimize duplicated business logic, keep operations manageable, ensure strong observability, and run a phased migration with rollback.

A
Deploy distinct services for each major API version and employ path-based versioning (/v1/, /v2/) alongside independent deployments and separate databases if required. Each major version operates in isolation to reduce interference; both codebases are maintained and run concurrently until the older version is deprecated.
✗ Not Best
B
Implement header-based versioning where a single service binary processes requests for both v1 and v2. Incorporate branching logic at the application layer to deliver different request and response structures depending on the version header, utilizing feature flags to switch behavior for specific clients.
✗ Not Best
C
Eschew explicit API versioning in favor of backward-compatible, additive modifications, combined with feature flags and semantic versioning for internal libraries. Notify partners of breaking changes well in advance, relying on the assumption that most consumers will upgrade without needing parallel version support.
✗ Not Best
D
Deploy an API gateway that routes and, if necessary, executes request and response transformations between client-facing versions and a unified set of backend services. Maintain core business logic within a single codebase, utilizing the gateway for translation and routing, while managing the migration process through per-client feature flags and contract testing.
✓ Best Answer
✅

Answer & In-Depth Explanation

🏆 Best Answer — D: API Gateway Translation Layer over a Single Core

The hardest requirements to satisfy together are no duplicated business logic and a long, reversible, per-client migration. Option D addresses both: the core payments logic exists once (speaking the latest contract, v2), while the gateway owns everything that is genuinely version-specific, namely routing, authentication header mapping, and request/response translation for v1. Because version is resolved at the edge, migration becomes a routing decision per merchant, which is easy to observe, ramp, and roll back. Here's why it stands out:

  • One source of truth for money logic: A bug fix or compliance change in payment processing ships once and applies to v1 and v2 clients alike. In a payments platform, divergent behavior between two codebases is itself a risk.
  • Isolated, testable translation: v1 handling reduces to pure functions: v1 request -> v2 request and v2 response -> v1 response. They are small, deterministic, and verifiable with golden files and contract tests, and they can be deleted wholesale when v1 sunsets.
  • Phased migration with instant rollback: Per-merchant flags (allowlists, percentages, pinned versions) route traffic. Moving a merchant to v2 or back is a configuration change, not a deploy.
  • Observability per version and per client: The gateway sees every call, so it can report v1 usage by merchant and endpoint, error rates by version, and latency of the translation step. That data drives the deprecation plan, Sunset headers, and outreach.
  • Controlled latency: Translation is in-memory work on already-parsed payloads, typically adding a small overhead. Implemented as a gateway plugin or in-process adapter, it avoids an extra network hop on the checkout path.

Pair the gateway with consumer-driven contract tests, shadow replay of recorded v1 traffic against the adapter to prove equivalence, per-merchant version pinning, Sunset and deprecation headers, and a published timeline with brownout tests (short planned v1 disablements) to flush out silent dependents before final shutdown.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🪞

A — Separate Services per Major Version

Strong isolation, but it duplicates core business logic: every fix, compliance rule, or fraud check must be implemented and tested twice, and behavior can drift between versions. Separate databases make things worse for payments, because consistency between v1 and v2 views of the same transactions becomes a data-sync problem. It doubles operational overhead during the 12-month window. Caveat: reasonable when v2 is a ground-up rewrite with a different domain model, or when regulatory isolation is required.

🌿

B — Header-Based Versioning with In-App Branching

Header versioning is a legitimate choice, but scattering if version == 1 branches through business logic couples the versions inside the core, makes behavior hard to reason about, and is painful to remove later. Versioning in a header is also less visible in logs, caches, and quick debugging than a path, unless you add Vary and tooling. A defect in a branch can affect all traffic. Caveat: fine for small differences if all translation lives in a clean adapter layer, which is effectively option D implemented in-process.

🙏

C — No Versioning, Additive Changes Only

Additive evolution is the best default for non-breaking changes, but this scenario includes breaking changes by definition (restructured resources and a different auth header), and the business requirement is that v1 keeps working for 12 months. Hoping partners will upgrade on notice is not a migration strategy for third-party merchants and risks failed payments. Caveat: prefer expand/contract and additive fields whenever a change can be made compatible, which reduces how often a new major version is needed.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Separate Services per Version

v2 is a complete rewrite with a different domain model, or isolation between versions is required for compliance or risk reasons.

📌

B — Header Versioning + In-App Branching

Small differences between versions, a small client base you control, and a team that confines all version logic to a single adapter layer.

📌

C — No Versioning

Changes are purely additive and compatible, or the clients are internal and can be upgraded in lockstep.

📌

D — Gateway Translation + Single Core

Many external clients, long migration windows, mostly structural breaking changes, and a need for per-client rollout, rollback, and visibility.

⚠️ Common Mistakes to Avoid

  • Putting business rules in the gateway: Adapters should reshape data, not decide outcomes. Rules in two places recreate the duplication you were avoiding.
  • Assuming every change is translatable: A semantic change (new state machine, different error taxonomy) cannot be faked by renaming fields. Handle it in the core and document the v1 behavior.
  • Skipping equivalence testing: Without shadow replay and contract tests, subtle serialization or rounding differences reach merchants as failed payments.
  • Forgetting webhooks and async payloads: Merchants consume events too, and those need version-aware formatting and per-merchant pinning.
  • No version telemetry: Without per-merchant v1 usage data you cannot target outreach or know when it is safe to sunset.
  • Open-ended deprecation: Without a published timeline, Sunset headers, and brownouts, v1 lives forever and the adapters become permanent.

🌍 Real-World Best Practice

Companies with long-lived public APIs (payments especially) treat compatibility as a product feature. A common pattern is one canonical core plus version translation at the boundary:

  • Step 0 — Inventory and classify breaking changes: Separate mechanical transformations (rename, nest, reshape, header swap) from semantic differences that need core support.
  • Step 1 — Make v2 the canonical contract: Implement core logic against the new model only, so there is a single behavior to test and secure.
  • Step 2 — Build v1 adapters: Pure request and response translators plus an auth bridge that accepts the legacy header and produces the new credential, with golden-file tests.
  • Step 3 — Route per merchant: The gateway resolves the version from the path and the merchant's pinned version, with feature flags for ramping and rollback.
  • Step 4 — Prove equivalence: Run consumer-driven contract tests and shadow-replay recorded v1 traffic through the adapter and compare responses.
  • Step 5 — Drive the migration: Dashboards of v1 usage by merchant, Sunset headers, outreach, brownouts, and finally removal of adapters after the window closes.

Design every adapter so that deleting it on sunset day is a non-event.

💡

Key Takeaway

Version at the boundary, not in the core. Keep one implementation of business logic, translate old contracts in a thin, testable gateway layer, and let per-client routing and telemetry steer a measured, reversible migration. Use additive changes whenever possible and reserve new major versions for truly breaking changes.
