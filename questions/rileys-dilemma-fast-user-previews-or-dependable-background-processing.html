Challenge

Riley's dilemma: fast user previews or dependable background processing?

Riley, a backend developer, is designing a serverless image-processing system. Clients upload images through an API and expect an immediate preview (under 500 ms) in the UI. The real processing (face detection, multi-resolution resizing, metadata extraction) is CPU-intensive and can take up to several minutes. The organization wants a serverless design that keeps the UI responsive, scales through sudden traffic spikes, provides clear observability and error handling, and limits user-facing failures when downstream tasks error out. Riley must pick the design that best balances latency, scalability, fault tolerance, and operational transparency.

A
Execute a single synchronous Lambda function triggered by API Gateway to handle both preview creation and intensive processing. Only return the preview once all tasks are done (hoping most executions complete before the API Gateway times out).
✗ Not Best
B
Implement a dual-path process: use a lightweight synchronous Lambda (API Gateway -> Lambda) to quickly generate and return the preview along with saving metadata. Then, send a message to SQS (or EventBridge) to trigger distinct asynchronous Lambda workers for the intensive tasks, incorporating visibility timeouts, retries, and a Dead Letter Queue for failed jobs.
✓ Best Answer
C
Save upload metadata to DynamoDB directly from the API Lambda and leverage DynamoDB Streams to invoke worker Lambdas for the heavy processing. Depend on the at-least-once delivery and per-shard ordering of Streams for the workflow.
✗ Not Best
D
Utilize Step Functions to manage the entire process: the API Lambda initiates a Step Functions workflow that executes coordinated steps (like a parallel Map for resizing and retries for individual stages), while the API awaits a brief callback or actively polls the workflow for completion.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — B: Dual-Path: Sync Preview + Async Queue Workers

The core requirement is to decouple what the user waits for (a preview in under 500 ms) from what the system needs time for (minutes of CPU work). Option B does exactly that: a thin synchronous path returns the preview and persists job metadata, while a durable queue hands the heavy work to independently scaling workers with retries and a dead-letter queue. Here's why it stands out:

  • Latency isolation: The request path does only bounded work (validate, create a small preview, write the job record, enqueue). Its p99 no longer depends on how long face detection or resizing takes.
  • Elastic buffering: SQS absorbs sudden spikes, and the Lambda event-source mapping scales workers with queue depth. A maximum-concurrency cap on the mapping protects downstream resources (models, databases, third-party APIs).
  • Built-in fault tolerance: Visibility timeouts, retries, and a DLQ mean a failing job never becomes an API error. The user already has a preview; the job simply moves to RETRYING or FAILED, and poison messages are parked for inspection and redrive.
  • Operational transparency: A job record (status per stage) in DynamoDB, queue metrics (depth, age of oldest message, DLQ depth), and trace context propagated through message attributes give on-call engineers a clear picture of where each job is.
  • Why not Step Functions alone? It is excellent for orchestration and per-step visibility, but as described in option D the API waits on or polls the workflow, which ties request latency to a long-running process. Step Functions is better used behind the queue than in front of the user.

Model the job as a small state machine (RECEIVED → PREVIEW_READY → PROCESSING → COMPLETE | FAILED), persist it, expose a status endpoint (or push via WebSocket/SSE), and alarm on queue age and DLQ depth. If stage-level orchestration grows complex, let the queue trigger a Step Functions workflow for fan-out resizing and per-stage retries.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

⏳

A — Single Synchronous Lambda

This couples the user-visible response to the slowest work. API Gateway's default integration timeout is about 29 seconds while the work can take minutes, so 'hoping most executions finish in time' guarantees timeouts, client retries that duplicate work, and wasted compute. A spike multiplies long-running concurrent executions, and there is no fault isolation: a failure in face detection also fails the preview. It violates the sub-500 ms preview goal outright.

🌊

C — DynamoDB Streams as the Job Trigger

Workable, but the wrong tool for a job queue. It ties workflow triggering to table writes, and Streams processing is shard-based: one poison record can stall its shard until retries are exhausted (you must configure bisect-on-error, a retry limit, and an on-failure destination). Records are retained for only 24 hours. The per-shard ordering it advertises is something this workload does not need, and it is the very property that makes a single failure block later records. SQS gives per-message retries, visibility timeouts, a DLQ, and redrive. Use Streams for CDC and derived views, not as a work queue.

🔀

D — Step Functions with API Awaiting Completion

Great orchestration and observability (execution history, per-step retry and catch, Map state for parallel resizing), but the design has the API await a callback or poll the workflow. That re-couples request latency to a long process, and synchronous Express workflows are capped at five minutes. Standard workflows are billed per state transition, which can be costly for very high volumes of small jobs. Best placed behind the queue as the engine of the heavy path, not as the front door.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Single Sync Lambda

Tiny, bounded jobs that reliably finish in about a second or two (for example a single thumbnail), where simplicity matters more than resilience.

📌

B — Sync Preview + SQS Workers

A user-visible fast response plus heavy background work that must survive spikes and failures. The default pattern for upload-then-process systems.

📌

C — DynamoDB Streams

Change-data-capture needs: audit trails, derived views, or per-key ordered reactions to table changes. Not for general job queues.

📌

D — Step Functions in Front

Multi-stage workflows with branching, parallel fan-out, long waits, or human approval, especially when a visual execution history is valuable. Often combined with option B.

⚠️ Common Mistakes to Avoid

  • Non-idempotent workers: At-least-once delivery means duplicates will happen. Guard each stage with conditional writes and write outputs to deterministic keys.
  • Visibility timeout shorter than processing time: The message reappears while the first worker is still running, causing duplicate processing and wasted CPU.
  • Unmonitored DLQ: A DLQ nobody watches is a silent failure channel. Alarm on depth, and keep a tested redrive procedure.
  • Gap between 'save job' and 'enqueue': A crash between the two leaves an orphaned job. Write the job as RECEIVED first and run a sweeper that re-enqueues old RECEIVED jobs.
  • Unbounded worker concurrency: A spike can overwhelm a downstream model endpoint or database. Set maximum concurrency on the event-source mapping.
  • Scope creep in the preview path: Adding 'just a little' face detection to the synchronous Lambda quietly breaks the 500 ms SLO.

🌍 Real-World Best Practice

In practice, teams keep the user-facing contract tiny and make everything expensive retryable and observable. A typical sequence looks like this:

  • Step 0 — Define SLOs: Preview p99 under 500 ms, and a job-completion target (for example 95% within two minutes) with an error budget.
  • Step 1 — Keep the API payload small: Use presigned S3 uploads for large images and generate the preview from the stored object or a bounded in-request thumbnail.
  • Step 2 — Fast path: Validate, produce the preview, write the job record, enqueue with an idempotency key, and return 202 with a job ID.
  • Step 3 — Async path: SQS to Lambda workers (or a Step Functions workflow per job for fan-out), idempotent stages, partial batch responses, DLQ with a documented redrive runbook.
  • Step 4 — Status delivery: Polling endpoint, WebSocket/SSE push, or webhook so the UI can show progress without blocking.
  • Step 5 — Protect and observe: Reserved or maximum concurrency, separate queues per priority or tenant, tracing across the message hop, and alarms on queue age and DLQ depth.

Return a fast preview, persist the job, and let queue-driven workers do the rest.

💡

Key Takeaway

Never make the user wait for work that can be made durable and asynchronous. Return a preview in the synchronous path, persist a job, and let queue-driven workers run the heavy tasks with retries, a DLQ, and visible status. An orchestrator such as Step Functions is a good upgrade behind the queue, not a reason to block the request.
