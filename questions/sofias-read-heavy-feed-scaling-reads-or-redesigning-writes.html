Sofia's read-heavy feed: scaling reads or redesigning writes?

Sofia is a backend systems architect responsible for scaling an expanding social media platform. The platform faces an intensely skewed read-heavy traffic distribution (90% reads, 10% writes), peaking at 20,000 reads/sec and 2,000 writes/sec. Users expect their timeline feeds to render in under 150ms (p95), though product requirements permit feeds to be eventually consistent by a few seconds. The write profile is dominated by append operations—such as publishing new posts, liking items, and establishing follow links—with minimal in-place record updates. The existing single-primary relational SQL database is experiencing catastrophic saturation: multi-table joins are choking read latencies, read replicas exhibit severe replication lag during spikes, and cache-aside invalidation schemes are collapsing under stampeding cache misses.

A
Maintain the single SQL primary database, upgrade its hardware (vertical scaling), and introduce a robust Redis read-through cache that invalidates synchronously upon writes.
✗ Not Best
B
Implement a primary-write, read-replica SQL setup using asynchronous replication. Direct the majority of reads to the replicas while sending crucial reads to the primary.
✗ Not Best
C
Embrace CQRS: utilize a streamlined write model (such as a single primary or append-only events), broadcast write events through an asynchronous pipeline, and construct denormalized read models optimized for querying to serve clients. Tolerate eventual consistency while establishing protocols for data reconciliation and replays.
✓ Best Answer
D
Migrate to a multi-master, synchronous distributed SQL database deployed across multiple datacenters or zones, allowing any node to process both reads and writes with strict consistency.
✗ Not Best

Answer & In-Depth Explanation

🏆 Best Answer — C: CQRS with Asynchronous Materialized Feed Projections

In social media platforms, relational normalized schemas fail at scale because assembling a dynamic timeline requires multi-way joins across users, followers, posts, likes, and media. Executing these joins at 20,000 QPS overwhelms database CPU and memory bandwidth. Command Query Responsibility Segregation (CQRS) fundamentally decouples the write ingestion path from the read query path. The write path accepts appends into a high-throughput, append-only store or streamlined relational table and immediately emits domain events (e.g., PostCreated, UserFollowed) to an event stream like Kafka. Asynchronous stream consumers (fan-out workers) project these events into pre-aggregated, denormalized read models—such as Redis Sorted Sets or wide-column stores (Cassandra/ScyllaDB)—where each user's feed is a pre-materialized list of post IDs. Reads become simple $O(1)$ or $O(K)$ range slices requiring zero runtime joins, effortlessly serving 20,000 QPS within single-digit milliseconds while honoring the acceptable eventual consistency SLA.

  • Eliminates runtime relational joins: Read queries fetch pre-materialized, denormalized timeline structures, reducing complex multi-table joins to simple single-key range queries (e.g., Redis ZREVRANGE).
  • High-throughput append-only writes: Stripping relational constraints and indexes from the write path allows the command engine to process 2,000 writes/sec without locking or contention.
  • Isolated scaling vectors: Read-serving infrastructure (cache clusters, document stores) can be scaled horizontally and independently from the event ingestion and persistence pipeline.
  • Resilient replayability: Storing immutable events in an event log enables background workers to rebuild, backfill, or modify read projection schemas at any time without downtime.
  • Natural alignment with business SLAs: Sub-150ms read latency is guaranteed through pre-computed timelines, while the tolerated 2-3 second propagation delay provides adequate headroom for stream fan-out.

At scale, relational normalization is the enemy of sub-100ms read latencies. Decoupling reads from writes via CQRS and asynchronously pre-computing timeline projections converts an unscalable join problem into an effortless, linearly scalable range-scan operation.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🛑

A — Vertical Scaling + Synchronous Cache Invalidation

Vertical hardware scaling hits a hard technical and financial ceiling. Furthermore, invalidating cache entries synchronously on every write at 2,000 writes/sec causes write amplification and massive cache stampedes (thundering herds). Evicting the feeds of thousands of followers on every new post forces subsequent read requests to hit the overloaded primary database, rapidly triggering connection exhaustion and total outage.

⚠️

B — Primary-Write with Asynchronous Read Replicas

Adding read replicas distributes query volume but does not fix the fundamental algorithmic bottleneck: executing expensive, un-indexed multi-table relational joins across millions of rows at 20,000 queries per second. Replicas still replicate every write via WAL logs, consuming CPU and disk I/O, while asynchronous replication lag causes stale reads and replica desynchronization under load.

🔒

D — Synchronous Multi-Master Distributed SQL

Multi-master distributed SQL databases (e.g., CockroachDB, Spanner) enforce strict ACID transactional consistency across distributed nodes via consensus protocols (Raft/Paxos) and two-phase commit. This adds significant network coordination latency to every write and still requires expensive distributed joins across shards for timeline assembly, completely over-engineering consistency where eventual consistency was explicitly acceptable.

⚡

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Vertical Scaling + Synchronous Cache

Early-stage startups with simple relational schemas and modest QPS (<500 reads/sec) where developer velocity and operational simplicity outweigh scaling limits.

📌

B — Primary-Replica SQL Cluster

Enterprise reporting and business intelligence systems where reads consist of periodic analytical queries across normalized tables that don't need real-time user-facing latency.

📌

C — CQRS with Materialized Read Models

High-scale, read-intensive consumer applications (news feeds, activity streams, e-commerce storefronts) where read QPS is massive and latency must remain sub-150ms.

📌

D — Synchronous Distributed SQL

Global financial ledgering, payment gateways, and banking core engines requiring strict multi-region serializability and zero data loss.

⚠️ Common Mistakes to Avoid

  • Pure fan-out on write for mega-influencers: Attempting to insert a post into 20 million follower timelines simultaneously, locking up Kafka queues and exhausting Redis memory.
  • Full object payload duplication: Storing the entire post, author profile, and comments inside every follower's timeline list rather than storing lightweight post_id references.
  • Lack of backpressure and dead-letter queues: Allowing projection worker failures to halt the event consumption pipeline, causing feed updates to stall indefinitely.
  • Failing to support out-of-order event delivery: Ingesting events without monotonic logical timestamps or version tags, causing edited or deleted posts to be overwritten by delayed create events.

🌍 Real-World Best Practice

Every major social platform (Twitter/X, Facebook, LinkedIn, Instagram) migrated away from monolithic relational joins toward fan-out CQRS architectures early in their growth curves. Materializing feeds into user-centric timelines is the proven blueprint for handling tens of thousands of feed reads per second.

  • Hybrid Push/Pull fan-out: Push new posts into the timeline mailboxes of followers for regular users (fan-out on write), but pull celebrity posts at query time (fan-out on read) to prevent write explosions when accounts with millions of followers publish.
  • Two-tier materialized caching: Store only the most recent 800 post IDs in Redis sorted sets per active user; fetch full post contents (hydrated payload) in a single batched multi-get query.
  • Active vs. Inactive user pruning: Only materialize feeds for users who have logged in within the past 14 days. If an inactive user returns, compute their feed on-demand and cache it.
  • CDC with Debezium: If preserving an existing SQL write model, use Change Data Capture (Debezium/Kafka Connect) to stream commit logs into Kafka topics without modifying application write code.
  • Read-your-own-writes handling: When an author posts, immediately append the post to the local client state or prepend it directly to the author's own timeline cache so they perceive instantaneous consistency.

Architectural maturity means recognizing that read models and write models have fundamentally conflicting optimization targets. CQRS allows each side to achieve maximum performance without compromise.

💡

Key Takeaway

When joins choke read performance at scale, stop joining at read time; use CQRS to pre-materialize denormalized feeds asynchronously.
