Reducing Latency in Database-Heavy Applications Under Load

Priya, a senior backend developer, is investigating performance bottlenecks in a production system that serves millions of requests daily. During peak traffic windows, database query response times degrade significantly, leading to timeouts and a poor end-user experience. Profiling shows that the slow queries already use appropriate indexes with healthy query plans, the workload is read-heavy, and a small set of hot rows (such as popular user profiles and product pages) accounts for most reads. The product can tolerate bounded staleness (seconds to a few minutes) on this data. She needs to choose the most effective first strategy to improve throughput and reduce response latency.

A
Create composite (multi-column) indexes tailored to the most common query patterns.
✗ Not Best
B
Introduce a caching layer (e.g., Redis or Memcached) to serve repeated query results from memory.
✓ Best Answer
C
Partition or shard large tables to spread data across multiple nodes and balance the read/write workload.
✗ Not Best
D
Denormalize selected tables to eliminate expensive join operations and speed up read-heavy queries.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — B: Caching Layer

Given this workload (read-heavy, repetitive, already-indexed queries, staleness-tolerant), introducing a caching layer (such as Redis or Memcached) is the most impactful first step for a system whose profiling already shows healthy query plans and high read repetition on a small set of hot rows. Because profiling has already ruled out query-plan inefficiencies and the workload has high temporal locality, reducing demand on the database is the right next step — not further query optimization. Here's why it stands out:

  • Immediate latency reduction: A cache hit is typically served in around a millisecond or less, versus tens or hundreds of milliseconds for a loaded database query. For hot data paths the improvement is often an order of magnitude or more, depending on hit rate and query cost.
  • Read offloading: By intercepting repeated reads before they reach the database, caching sharply reduces the number of queries (and connections held) during peak hours, which is exactly when the system struggles.
  • Relatively non-invasive: Unlike schema changes (denormalization) or data-layout changes (partitioning/sharding), a cache can be layered onto the existing architecture with limited refactoring: reads go through a cache-aside helper, and writes add an invalidation step.
  • Why not read replicas first? Replicas also offload reads, but each one still executes the query, so latency per request stays the same, you pay for more database capacity, and replication lag adds its own consistency issues. A cache removes the work entirely for repeated reads.
  • Proven at scale: Facebook's published memcache architecture (Nishtala et al., NSDI 2013) is a well-known example of look-aside caching absorbing most read traffic in front of MySQL.

A well-designed caching strategy includes TTL-based expiry, invalidation on writes, stampede protection, and a cache-aside or read-through pattern. Track the hit rate and the database query rate before and after rollout; if the hit rate stays low, caching is not the right fix for this workload.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

📇

A — Composite Indexes

Indexes lower the cost of each query, which raises how many queries the database can handle, but they don't reduce the volume of queries hitting it. In this scenario profiling already shows the slow queries use appropriate indexes, so adding more yields little, and each extra index adds write overhead (inserts, deletes, and updates to indexed columns must maintain it). Caveat: if profiling had shown sequential scans or poor query plans, indexing would be the right first move: it's cheap, low-risk, and easy to reverse.

🧩

C — Table Partitioning / Sharding

Partitioning divides a table into segments on the SAME server (helps the planner skip irrelevant segments). Sharding distributes data across MULTIPLE nodes (scales writes and storage). Both are heavy changes that introduce significant operational complexity (cross-partition queries, rebalancing, migration), and neither helps much if the bottleneck is repeated reads of the same hot rows, since a hot row still lives on one shard.

📋

D — Denormalization

Removing JOINs speeds up reads, but it duplicates data, complicates writes, and risks inconsistency. It's a schema change that is hard to reverse. For Priya's scenario (peak-hour spikes on a working system, with no evidence that JOINs are the dominant cost), this is a heavy-handed structural change when a simpler layer can absorb the load.

⚡

B — Caching Layer ✓

Introduce a caching layer (e.g., Redis or Memcached) to serve repeated query results from memory.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Composite Indexes

Slow query logs show sequential scans or poor plans, or queries are diverse (not repeated identical reads) and the database itself is the bottleneck. Usually the cheapest, safest fix when profiling points to missing index coverage.

✅

B — Caching

Read-heavy workload with high temporal locality: the same data is requested thousands of times between changes, queries are already well-indexed, and some staleness is acceptable. Not effective if requests are mostly unique.

📌

C — Table Partitioning / Sharding

A table has grown to billions of rows and queries naturally split by a dimension (date, tenant, region), or write throughput or storage on a single node is the limiting factor.

📌

D — Denormalization

Analytics or reporting paths that run complex multi-table JOINs and can tolerate slight staleness, applied after profiling proves JOINs are the dominant cost.

⚠️ Common Mistakes to Avoid

  • Skipping profiling: Picking a fix before you know where time is going. A cache can hide a bad query instead of fixing it, and the problem returns when the cache is cold. Use slow query logs and EXPLAIN ANALYZE first.
  • Caching everything blindly: Without analyzing access patterns, you end up with a bloated cache full of cold keys and a low hit rate. Cache hot paths identified through profiling, and monitor the hit rate.
  • Ignoring cache invalidation: Serving stale data after writes is a common caching bug. Pair every cached read with an invalidation strategy (explicit eviction on write, or write-through), and keep a TTL as a backstop.
  • Missing the invalidation race: A reader fetches an old row, a writer updates the DB and deletes the key, and the reader then writes the old row back into the cache. Mitigations, from most to least robust: leases (as in the Facebook paper), versioned values, short TTLs, and a delayed second delete as a heuristic.
  • Cache stampede on expiry: When a popular key expires, hundreds of concurrent requests hit the DB at once. Use request coalescing (singleflight), probabilistic early expiry, TTL jitter, or lock-based refresh with a stale fallback.
  • No plan for cache failure or cold start: If Redis restarts or is flushed at peak, the full load lands on the database at once. Plan for warm-up, rate limiting, and graceful degradation.

🌍 Real-World Best Practice

In practice, senior engineers rarely pick just one strategy, and they measure before choosing. A typical sequence looks like this:

  • Step 0 — Profile first: Use slow query logs, EXPLAIN ANALYZE, and p99 breakdowns (queueing vs. execution time) to find what is actually slow. If profiling shows full scans or bad plans, start with indexing instead.
  • Step 1 — Caching: Intercept hot, repeated reads with Redis/Memcached (the biggest win for this scenario).
  • Step 2 — Connection pooling and read replicas: Timeouts under load are often caused by connection exhaustion or queueing. Pool connections sensibly, set sane timeouts, and offload remaining reads to replicas (accepting some replication lag).
  • Step 3 — Indexing: Make sure all remaining database queries are well-indexed for steady-state performance.
  • Step 4 — Partitioning/sharding: Only when single-node storage or write throughput becomes the bottleneck.
  • Step 5 — Denormalization: Apply surgically to specific read-heavy paths where JOINs are proven bottlenecks.

Layer these in based on profiling data, not habit.

💡

Key Takeaway

Measure first, then reduce demand on the database when reads are repetitive. A caching layer absorbs repeated read traffic and buys time, but it only works if the workload has repeated reads and tolerates some staleness, and it must be paired with invalidation and stampede protection. If profiling instead shows slow query plans, fix those first.
