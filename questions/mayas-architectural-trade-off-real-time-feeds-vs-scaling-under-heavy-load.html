Challenge

Maya's architectural trade-off: real-time feeds vs scaling under heavy load

Maya is building an activity feed service for a rapidly growing social networking app. It must sustain millions of write events per minute, store events durably, serve feed queries at p95 under 200 ms, and tolerate several seconds of data staleness for most users. The architecture must also stay highly available across multiple regions with strong observability (error rates, processing delays, latency). She needs an architecture that trades off throughput and latency effectively, avoids extreme operational complexity, and carries no risk of data loss. What is the best architectural strategy?

A
Execute synchronous writes to a highly consistent, multi-region transactional database (such as Spanner or a system using synchronous cross-region Paxos) for each event, and process read requests straight from this primary or replicated database to ensure absolute freshness.
✗ Not Best
B
Separate the read and write workflows: rapidly accept incoming events by adding them to a distributed, durable log (like Kafka), confirm receipt to the client, and asynchronously construct highly optimized read models (materialized views) to be delivered via caches and specialized read data stores. Employ dead-letter queues for errors, track processing lag, and utilize idempotent consumers.
✓ Best Answer
C
Implement an in-memory write-through cache at the API boundary: log events in the cache initially (to minimize client latency) and flush them to the database asynchronously (using a write-behind pattern). Fulfill read requests directly from the cache while the background persistence is finalized.
✗ Not Best
D
Bundle incoming events at the API gateway into distinct batches (based on size or time windows) and write these batches to the main database to elevate throughput and lessen the write load on the backend. Adjust the batch parameters to balance latency against throughput.
✗ Not Best

Answer & In-Depth Explanation

🏆 Best Answer — B: CQRS with a Durable Log and Asynchronous Read Models

Writes and reads have very different shapes here. Writes are huge, append-only, and must never be lost. Reads are latency-sensitive, repetitive, and can tolerate seconds of lag. Separate them: acknowledge each event as soon as it is durably appended to a replicated log, then asynchronously build read-optimized feed views (per-user timelines in a cache or wide-column store) that the read API serves in milliseconds. The staleness the product tolerates is exactly what buys this decoupling. Here's why it stands out:

  • Durable, fast writes: With acks=all, a minimum in-sync replica count, and idempotent producers, an event is acknowledged after a replicated sequential append, typically in a few milliseconds. A modest Kafka cluster handles tens of thousands of events per second (millions per minute) with ease.
  • Read latency by design: Feeds are precomputed into Redis, Cassandra, or DynamoDB, so a feed read is one key lookup plus a small merge. That keeps p95 well under 200 ms without ever touching the write path.
  • Independent scaling and failure isolation: Partitions scale writes, consumers scale on lag, and caches and replicas scale reads. A slow or failing consumer builds lag instead of failing writes, because the log is a buffer.
  • Replayable and evolvable: Read models can be rebuilt or reshaped (new ranking, bug fixes) by replaying the log, and new consumers such as notifications and analytics can be added without touching ingestion.
  • Observability and multi-region fit: Consumer lag, end-to-end freshness (event time to visible), error rates, and DLQ depth are direct SLIs. The log can be replicated across regions (MirrorMaker 2, Cluster Linking) or run regionally with regional read models.

Run the log with acks=all and replicated partitions, build read models with idempotent consumers, bound every timeline, send failures to a dead-letter topic with a replay procedure, and publish a freshness SLO (for example, 95% of events visible within 5 seconds) with alerts on lag.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🌍

A — Synchronous Multi-Region Strongly Consistent Database

It gives absolute freshness and no data loss, but every write pays cross-region consensus (tens to hundreds of milliseconds), cost climbs steeply at millions of events per minute, and assembling a feed still requires joins or fan-in that are slow at read time. It buys linearizability the product explicitly does not need. Caveat: it is the right tool for balances, inventory, and ledgers, not activity feeds.

💾

C — In-Memory Write-Through / Write-Behind Cache

The terms conflict: write-through persists synchronously, while write-behind acknowledges before persisting. Anything acknowledged but not yet flushed is lost on a crash, eviction, or restart, which violates the durability requirement and makes the cache the de facto system of record. Flush backlogs, ordering problems, and unbounded memory growth make this fragile at this scale.

📦

D — Batching at the API Gateway into the Main Database

Batching is a useful technique (consumers in option B should batch too), but holding events in gateway memory risks loss on a crash and adds up to a full batch window of latency. It does nothing for read latency, and the primary database remains both the write bottleneck and the read source.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Sync Multi-Region Strong DB

Data that must be globally consistent and never stale, such as balances, inventory, entitlements, or ledgers, and where the write rate is modest relative to the budget.

📌

B — Durable Log + Read Models

Very high write volume, durable events, read-optimized and staleness-tolerant views, and a need for replay and independent consumers, as in feeds, notifications, timelines, and analytics.

📌

C — Write-Behind Cache

Data that can be recomputed or safely lost (counters, ephemeral presence, rate-limit state), where the cache is explicitly not the system of record.

📌

D — Gateway Batching into DB

Moderate write loads where small batching windows relieve the database and some added latency is fine, ideally as a technique inside a durable pipeline rather than the whole design.

⚠️ Common Mistakes to Avoid

  • Pure push fan-out for celebrity accounts: One post from an account with millions of followers becomes millions of writes and a lag spike. Use a hybrid with read-time merge for large accounts.
  • Poor partition keys: Keys with low cardinality or a few dominant values create hot partitions. Choose a key with high cardinality (actor id) and monitor skew.
  • Acknowledging before replication: Using acks=1 can lose events when a leader fails. Use acks=all with a minimum in-sync replica count and idempotent producers.
  • Non-idempotent consumers: Redelivery produces duplicate feed items. Use set-like writes (same member and score) or dedupe by event id.
  • Unbounded timelines: Storing every item forever bloats memory and slows reads. Cap each timeline and archive the rest.
  • No freshness SLO, lag alerts, or replay procedure: Without them, a stalled consumer looks like 'the feed is slow' and a DLQ becomes a graveyard. Define SLOs, alert on lag, and rehearse replay.

🌍 Real-World Best Practice

In practice, teams characterize the workload first and then split ingestion from serving. A typical sequence looks like this:

  • Step 0 — Characterize the workload: Measure the read-to-write ratio, the follower-count distribution (to find hot accounts), the freshness SLO, and the tolerance for loss (which should be zero).
  • Step 1 — Durable ingest: Validate the request, assign an event id, append to a partitioned log (key by actor), and acknowledge after replication.
  • Step 2 — Build read models: Stream processors fan events out to per-user timelines (hybrid push and pull), write idempotently, and cap each timeline at the latest N items.
  • Step 3 — Serve reads: The feed API reads from the cache and feed store, merges celebrity posts at read time, and paginates with cursors.
  • Step 4 — Make it resilient: Add dead-letter topics with replay, backpressure, lag-based autoscaling, regional failover drills, and load tests that include hot-key scenarios.
  • Step 5 — Observe: Track freshness (event time to visible), consumer lag, error budgets, and p95 and p99 latency per endpoint.

Spend consistency only where the product needs it, and buy throughput with decoupling everywhere else.

💡

Key Takeaway

When writes are huge and reads tolerate seconds of staleness, separate the paths: durably append events to a replicated log, then build fast, disposable read models from it. You trade instant consistency for scalability, resilience, and replayability, and you manage the new risks (lag, fan-out, read-your-writes) with explicit SLOs and design.
