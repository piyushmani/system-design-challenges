Challenge

Selecting the fastest, safest way to roll out flags at 100k RPS

Leah, a backend engineer, is building a feature-flag system for a microservice architecture handling roughly 100,000 requests per second across many services and regions. Flag evaluation should be sub-millisecond, flags must be changeable for instant rollback, the system must survive regional outages, and engineers need audit logs and observability for every flag change. She must pick the architecture that gives minimal latency, high availability, fast propagation, and easy recovery.

A
Require every request to synchronously query a centralized flag service (via HTTP/gRPC) backed by a strongly consistent database. If the service fails, requests stall until a timeout or failover occurs. This ensures the most recent flag state is used for every request.
✗ Not Best
B
Implement a basic local in-memory cache within each service using a fixed Time-To-Live (e.g., 30 seconds). Services periodically poll the central database to update flags. Decisions are made locally using the cached data; if the cache is empty, a safe default is applied.
✗ Not Best
C
Deploy a lightweight SDK that determines flags locally from an in-memory cache, and distribute updates from a central flag management service to all microservices via a streaming pub/sub mechanism (such as gRPC streams, Kafka, or a managed push service). Incorporate safety features like local fallback defaults, versioned flag data, and audit trails for modifications. Supply metrics and change events to ensure observability.
✓ Best Answer
D
Store feature flags in the primary relational database and utilize database triggers combined with Change Data Capture (CDC) to broadcast changes to a message broker. Each service subscribes to the broker to refresh its local cache. Services resolve flags locally via the cache, falling back to database queries if the data is missing.

Answer & In-Depth Explanation

🏆 Best Answer — C: Local SDK Evaluation with Streaming Push

At 100k RPS the flag decision must be a local memory read: any network call per request is both a latency cost and a new failure dependency on the hottest path. The control plane (changing flags) and the data plane (evaluating flags) should therefore be separated. An SDK that evaluates locally from an in-memory snapshot, fed by a push stream for fast propagation, with versioned data, safe defaults, and an audit trail, gives microsecond evaluation, rollback in seconds, and independence from the flag service during outages. This is the model used by mature flag platforms:

  • Sub-millisecond evaluation: A flag decision is a hash-map lookup plus a rule evaluation, typically microseconds, with zero network I/O and zero added failure modes per request.
  • Fast, safe rollback: A change is pushed to all connected SDKs within seconds, so a kill switch does not wait for a TTL. Versioning guarantees updates are applied in order and stale messages are ignored.
  • Resilient to outages: If the flag service or a region is down, SDKs keep serving the last known good snapshot, and can start from a persisted local copy or compiled-in defaults.
  • Auditable control plane: Every change is written with actor, before and after, and version in an append-only audit log, and a change event is published for dashboards and correlation with incidents.
  • Observable: SDKs report evaluation counts (sampled), snapshot version, and last-update age, so you can detect services running stale flags.

Treat flag changes like deployments: versioned, audited, staged (percentage rollouts by region or cohort), and monitored. Alert on snapshot age, stream disconnect rate, and the gap between the published version and the versions running in services.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

☎️

A — Synchronous Central Flag Service

Always the freshest value, but it adds a network hop and a failure dependency to every request. At 100k RPS the flag service becomes a critical, hot, tail-latency-sensitive dependency, and its outage stalls or fails user traffic. This is the wrong trade: instant freshness for each request is not required, while sub-millisecond evaluation and availability are.

⏱️

B — Local Cache with 30s TTL and DB Polling

Local evaluation is correct, but 30 seconds of propagation delay breaks 'instant rollback': a bad release keeps running for up to half a minute per service, and lowering the TTL shifts load onto the database. Polling from every instance multiplies read load and, without versioning, offers no ordering guarantee or audit linkage. It is a decent baseline, not a safe rollout mechanism.

🔀

D — Primary DB + Triggers + CDC

Pushing changes through CDC works, but it couples flag config to the primary application database and adds trigger and replication-slot overhead for a tiny, low-write data set. The stated fallback to database queries on a cache miss is dangerous at 100k RPS: a cold or evicted cache turns into a stampede on the primary. It also lacks first-class versioning, defaults, and SDK semantics unless you build them.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Synchronous Central Service

Low-traffic internal tools where a per-request network call is cheap and absolute freshness matters more than latency.

📌

B — Local Cache + TTL Poll

Small systems or non-critical flags where a delay of tens of seconds is acceptable and simplicity matters most.

📌

C — SDK + Streaming Push

High-throughput, multi-region systems that need fast kill switches, resilience to flag-service outages, and a full audit trail.

📌

D — DB + CDC + Cache

Organizations already running CDC infrastructure that want flags co-located with existing data and can protect the database from cache-miss storms.

⚠️ Common Mistakes to Avoid

  • Starting with an empty cache: If an SDK has no snapshot and no defaults, flags evaluate to undefined. Always bootstrap from a persisted snapshot or compiled-in defaults.
  • No versioning: Without a monotonic version, out-of-order or duplicate stream messages can roll a flag back to an older value.
  • Relying on push alone: Streams drop silently. Add periodic snapshot polling and alert on snapshot age.
  • Unjittered reconnects and polls: Thousands of instances reconnecting simultaneously overload the flag service. Add jitter and a cacheable snapshot endpoint.
  • Unsafe defaults: Defaulting a risky new feature to on when the flag system is unavailable turns an outage of the flag service into a production incident.
  • Inconsistent evaluation in one request chain: Different services seeing different flag states mid-request causes confusing partial behavior. Propagate the decision when consistency matters.

🌍 Real-World Best Practice

Platforms such as LaunchDarkly, Unleash, and Flagsmith, and in-house systems at large companies, share a common architecture:

  • Step 0 — Separate planes: Control plane (admin UI, API, audit) and data plane (SDK evaluation) are distinct systems with distinct SLOs.
  • Step 1 — Versioned snapshot store: Flags live in a small store with a monotonically increasing version per environment, plus an append-only audit log.
  • Step 2 — Streaming and polling: SDKs bootstrap from a snapshot, subscribe to a stream for deltas, and poll periodically as a fallback.
  • Step 3 — Local resilience: SDKs persist the last known good snapshot locally and ship with compiled-in defaults.
  • Step 4 — Staged rollout: Percentage and cohort rollouts use deterministic hashing so the same user gets a stable result, with fast kill switches.
  • Step 5 — Observability and hygiene: Track snapshot age, evaluation sampling, and flag change events, and remove stale flags regularly.

The flag service should be able to go completely down without a single user-visible request failing.

💡

Key Takeaway

Keep evaluation local and distribution asynchronous: in-memory SDK reads for speed, a push stream plus polling for freshness, versioning and defaults for safety, and an audit log for accountability. Never put a network call on the per-request path for something that changes a few times a day.
