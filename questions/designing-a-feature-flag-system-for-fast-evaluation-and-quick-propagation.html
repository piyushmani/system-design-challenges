Challenge

Designing a Feature Flag System for Fast Evaluation and Quick Propagation

Kavya, a platform engineer, is building the feature flag infrastructure for a large web application that runs on hundreds of service instances. Flags are checked on almost every request, often several times per request, so evaluating them must add almost no latency. Product teams also want flag changes (gradual rollouts, kill switches) to take effect within seconds. Which architecture balances these needs best?

A
Run a central flag service that every application instance queries, using long-polling to receive flag changes as they happen.
✗ Not Best
B
Let each service own its flags and notify dependent services of changes through webhooks.
✗ Not Best
C
Keep flag rules in a local in-memory cache inside each application instance, refreshed every few seconds from a central flag store.
✓ Best Answer
D
Connect application instances in a peer-to-peer mesh that gossips flag changes directly between them.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — C: Local In-Memory Cache with Periodic Refresh

Evaluating flags against a local in-memory copy that syncs from a central source of truth is the core design of mature flag platforms (LaunchDarkly, Unleash, Flagsmith, OpenFeature providers). It addresses Kavya's specific bottleneck profile by moving the network completely out of the read path:

  • Near-zero evaluation latency: A flag check becomes an in-process hash-map lookup plus rule evaluation, taking microseconds instead of a network round trip. With several checks per request, it's the only option that doesn't multiply latency.
  • Resilience by default: If the central store goes down, instances keep serving the last-known flag values. The flag system can never cause an outage on the request path.
  • Bounded, predictable staleness: A 2–10 second refresh interval comfortably meets the "within seconds" propagation requirement. Conditional requests (ETag / version number) keep each poll cheap when nothing has changed.
  • Simple to run and scale: Read load on the central store depends on instance count divided by refresh interval, not on request traffic. Hundreds of instances polling every few seconds is trivial load, and a CDN or read replica can serve the flag payload.

Mature flag platforms like LaunchDarkly default to streaming (SSE) rather than polling for update propagation, with the periodic poll kept as a reliability fallback. This hybrid gives sub-second propagation with polling as a safety net. Shipping a bootstrap snapshot with each deploy means instances always start with valid flags.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

📡

A — Centralized Long-Polling Service

Long-polling solves update propagation. But if each evaluation calls the central service, every request pays network latency and the flag service becomes a critical dependency on the hot path: if it goes down, the whole app degrades. It also means holding hundreds of open connections. The only way to make it fast is to cache locally, which turns it into option C.

🔗

B — Decentralized with Webhooks

Spreading flag ownership across services leaves no single source of truth for auditing, targeting rules, or kill switches. Webhooks are fire-and-forget: a missed or failed delivery leaves an instance silently out of sync, and every service has to build its own retries, ordering, and security for incoming callbacks.

🕸️

D — Peer-to-Peer Mesh

Gossip protocols are eventually consistent, with unpredictable convergence time, and they're hard to debug ('why does instance 47 still have the old value?'). In autoscaled environments instances constantly join and leave, and there's no clean audit trail of who changed what. That's a lot of complexity for a problem a central store solves simply.

⚡

C — Local In-Memory Cache with Periodic Refresh ✓

Keep flag rules in a local in-memory cache inside each application instance, refreshed every few seconds from a central flag store.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Centralized Long-Polling

Client-side or edge apps with few instances, where one long-lived connection is cheap. Also works as the update channel that feeds a local cache, but never as the per-evaluation path.

📌

B — Decentralized Webhooks

Small systems where each team fully owns its flags and there are no cross-service rollouts, or for notifying external systems (CI/CD, Slack) about flag changes.

📌

C — Local Cache + Refresh

The default for server-side applications at any scale. Flags are read far more often than they change, and a few seconds of staleness is acceptable.

📌

D — Peer-to-Peer Mesh

Rarely appropriate. Only for disconnected or edge environments (e.g., offline-capable devices) that can't reach a central store.

⚠️ Common Mistakes to Avoid

  • Calling the flag service on every evaluation: This turns a config lookup into a network dependency, and one slow flag API call can cascade into request timeouts.
  • No safe default when the cache is empty: On cold start or SDK failure, code must fall back to a defined default value instead of throwing.
  • Synchronized refresh across the fleet: If every instance polls on the same second, the store gets load spikes. Add jitter to the refresh interval.
  • Treating flags as permanent config: Old release flags pile up as tech debt and dead code paths. Give them expiry dates and remove them after rollout.
  • Inconsistent bucketing: Using random numbers instead of a stable hash of the user ID makes users flip between variants from one request to the next.
  • Putting secrets or large payloads in flags: Every instance fetches and caches flag payloads in memory, so keep them small and non-sensitive.
  • Flag skew across services during a request: A single user request may fan out to multiple services, each with its own flag cache refreshed at different times. During a rollout, service A may see the new flag value while service B still has the old one. For flags that affect cross-service behavior, use a request-scoped flag snapshot passed in headers or context, or accept the brief inconsistency window.
  • Deploying a broken flag payload to the fleet: A malformed or semantically invalid flag update (e.g., rollout percentage of 200%, a missing targeting rule) can affect every instance simultaneously. Validate flag payloads at the admin/API layer before publishing, and have the SDK validate the schema before swapping the snapshot. Consider a canary deployment model for flag changes to critical paths.

🌍 Real-World Best Practice

Production flag systems combine several mechanisms instead of relying on just one:

  • Source of truth — Central flag store: Versioned flag definitions with an audit log, RBAC, and approval workflows.
  • Evaluation — Local SDK cache: Every flag check runs in-process against an in-memory ruleset.
  • Fast propagation — Streaming push: SSE or a pub/sub channel tells SDKs about changes in under a second.
  • Safety net — Periodic poll + bootstrap file: Recovers from missed push events and lets instances cold-start when the flag service is unreachable.

Kavya should start with local cache + periodic refresh as the foundation. Streaming push is an excellent addition, particularly when sub-second propagation is vital.

💡

Key Takeaway

When high read volumes dictate design, prioritize moving data to the reader. Feature flags sit on the hot path, so evaluate locally and sync in the background. Avoid networking on the evaluation path, and separate read latency from update propagation.
