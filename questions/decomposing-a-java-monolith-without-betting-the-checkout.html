Decomposing a Java Monolith Without Betting the Checkout

Alex is a backend engineer at a mid-sized e-commerce company running a single Java monolith that contains the catalog, search, user profiles, cart, checkout, and payments. During promotions the app shows high CPU usage and long garbage-collection pauses, and the team wants faster, more independent deployments. Checkout and payments must stay correct (no double charges) and low-latency. The operations team is small and cannot absorb a sudden jump in operational surface area (dozens of services, a service mesh, per-service pipelines and on-call rotations). Alex needs a safe, incremental migration path that improves scalability and delivery speed without betting the business on a big-bang rewrite. Which approach fits best?

A
Immediately decompose the monolith into independent microservices: assign one service per domain, each with its own database. Utilize event-driven asynchronous communication for the majority of flows, accepting eventual consistency between services. Deploy these services independently within containers and integrate a service mesh for traffic management and observability.
✗ Not Best
B
Retain the monolithic architecture and scale it both vertically and horizontally: provision additional CPU and memory, increase replica counts, route high-traffic paths through caches and read-replicas, and optimize JVM/GC settings to minimize pauses. Postpone the extraction of microservices until the engineering team expands.
✗ Not Best
C
Isolate only the checkout and payment functionalities into distinct services, but continue sharing the existing monolith database to maintain simplicity. Employ synchronous REST API calls from the monolith to these newly extracted services to ensure straightforward transactions and strong data consistency.
✗ Not Best
D
Currently refactor the application into a modular monolith: establish distinct modules based on bounded contexts with clear interfaces. Implement asynchronous message queues between modules where eventual consistency is tolerable, while strictly isolating the checkout/payment module internally to enforce strong consistency. Later, apply the strangler fig pattern to gradually transition modules into standalone microservices as the development and operations teams mature.
✓ Best Answer
✅

Answer & In-Depth Explanation

🏆 Best Answer — D: Modular Monolith, Then Strangler Fig

The real problem is twofold: unclear boundaries inside the code (which slows teams and makes extraction risky) and resource hot spots (CPU and GC under promotional load). A modular monolith attacks the first without adding network failure modes or operational load, and it creates the seams that make a later, evidence-driven extraction cheap. Strong consistency for checkout and payments stays inside one process and one transaction boundary. Here's why it stands out:

  • Boundaries first, network later: Modules aligned to bounded contexts (catalog, search, profile, cart, checkout, payments) with explicit public interfaces and no cross-module table access make the code understandable and the dependency graph enforceable, for example with Spring Modulith, ArchUnit, or separate Gradle or Maven modules.
  • Keeps the money path simple: Checkout and payments remain in-process, so local ACID transactions plus an idempotency key on charge requests deliver exactly-once effects without distributed sagas or 2PC.
  • Fits the team: One deployable, one pipeline, one runtime to observe. There is no service mesh, no per-service database estate, and no distributed-tracing prerequisite just to get started.
  • Async where it is safe: Domain events between modules (an in-process event bus, backed by an outbox) decouple flows such as catalog-to-search or order-to-notification where eventual consistency is acceptable, and prepare them for a real broker later.
  • Reversible, evidence-driven extraction: The strangler fig pattern routes traffic for one capability at a time to a new service behind a facade, with rollback by flipping a route. Extract what hurts first (often search or catalog reads), using the module boundary as the contract.

A good execution plan has module boundaries enforced in CI, one schema owner per module, idempotent payment calls, in-process events with an outbox for async flows, and a strangler facade with percentage-based routing for each extraction. Track deploy frequency, change failure rate, GC pause p99, and per-module latency to prove each step paid off.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

💥

A — Big-Bang Microservices

Splitting everything at once converts every in-process call into a network call, multiplies failure modes, and forces eventual consistency into flows (cart, checkout, payment) that need correctness. A small operations team would suddenly own many services, databases, pipelines, a service mesh, and distributed debugging, all before the domain boundaries have been proven. Caveat: a full microservice estate can be right for large organizations with platform teams, clear domains, and independent scaling needs.

🏋️

B — Scale the Monolith Only

Vertical and horizontal scaling, caching, read replicas, and GC tuning are worthwhile and cheap, so do them anyway. As the whole strategy, though, it leaves the root cause (tangled code and a single deployment unit) untouched: feature velocity stays slow and the codebase gets harder to split later. Deferring structural work until the team grows usually makes the eventual migration more expensive.

🔗

C — Extract Checkout/Payments with a Shared Database

Sharing the monolith's database turns the new services into a distributed monolith: schema changes still need coordinated releases, two codebases can write the same tables, and synchronous REST calls make checkout availability depend on a network hop. A timeout on the charge call also creates the classic double-charge ambiguity (did it succeed or not?) that the monolith's local transaction used to hide. Extracting the most correctness-sensitive path first is the riskiest possible starting point.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Big-Bang Microservices

Large organizations with a platform team, well-understood domains, independent scaling needs, and the tooling (CI/CD, observability, on-call) to run many services.

📌

B — Scale the Monolith

Short-term stabilization during a promotion window, or when the monolith is fundamentally healthy and only needs capacity headroom.

📌

C — Extract Checkout, Shared DB

Rarely. Possibly as a very short-lived transitional step while data is being split, with a dated plan to give the service its own store.

📌

D — Modular Monolith + Strangler Fig

Mid-sized teams with a tangled monolith, a small ops team, and critical consistency requirements who need an incremental, reversible path to selective extraction.

⚠️ Common Mistakes to Avoid

  • Modules in name only: Packages that freely import each other's internals. Enforce boundaries with architecture tests and visibility rules, and fail the build on violations.
  • Shared tables across modules: Cross-module joins and writes recreate the coupling you are trying to remove and block later extraction. Give each module owned data and expose it through an API or events.
  • Skipping quick wins: Leaving hot queries, missing caches, and GC settings unfixed, then blaming the architecture for the CPU spikes.
  • Extracting without a facade or rollback: A hard cutover has no escape hatch. Route through a gateway or adapter with a feature flag so you can shift 1 percent, 10 percent, 100 percent and go back.
  • Event-izing everything: Using async events for flows that need an immediate, consistent answer (such as a stock check at checkout) creates new correctness bugs. Keep synchronous in-process calls where consistency matters.
  • No idempotency on payments: When payments are eventually extracted, retries and timeouts will otherwise cause double charges. Use idempotency keys from the start.

🌍 Real-World Best Practice

Teams that migrate successfully earn each extraction with data instead of starting from a target diagram:

  • Step 0 — Baseline and quick wins: Profile CPU and GC under load, add caching and read replicas for hot read paths, and tune the JVM. Measure again before restructuring anything.
  • Step 1 — Find the seams: Use domain modelling (for example event storming) and dependency analysis to define bounded contexts, and map who calls whom and which tables each area touches.
  • Step 2 — Modularize in place: Introduce module interfaces, forbid cross-module table access, enforce with architecture tests, and give each module its own schema or table prefix.
  • Step 3 — Decouple with events: Replace direct calls with in-process domain events where eventual consistency is fine, using an outbox so events survive crashes.
  • Step 4 — Strangle the first candidate: Pick a module that is read-heavy or resource-hungry and loosely coupled (often search or catalog), put a facade in front, shift traffic gradually, and compare metrics.
  • Step 5 — Extract payments last, deliberately: Only when there is a clear need (compliance isolation, independent scaling), and with idempotency keys, a saga or orchestrator, and reconciliation in place.

Move the boundaries first, the processes later, and the money last.

💡

Key Takeaway

Structure before distribution. A modular monolith gives most of the organizational benefit of microservices at a fraction of the operational cost, keeps checkout and payments strongly consistent, and creates the seams for a reversible strangler-fig migration. Distribute only the parts that have proven they need it.
