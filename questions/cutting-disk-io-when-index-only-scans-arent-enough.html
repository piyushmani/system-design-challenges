Challenge

Cutting Disk I/O When Index-Only Scans Aren't Enough

Arjun, a software engineer, is tuning a PostgreSQL-backed analytics dashboard whose queries aggregate millions of rows from a wide orders table. He hoped index-only scans would fix it, but the queries need too many columns to fit in an index, so the planner keeps fetching table (heap) pages from disk and reads stay slow. Users apply many different filter combinations, and data that is a few minutes old is acceptable. Which architectural change should Arjun make?

A
Put an in-memory cache (e.g., Redis) in front of the database to hold frequently requested query results.
✗ Not Best
B
Shard the database across multiple nodes to spread out the disk I/O.
✗ Not Best
C
Move the workload to a column-oriented database so scans read only the columns they need.
✗ Not Best
D
Create a materialized view that precomputes and stores the aggregated results, with its own indexes.
✓ Best Answer
✅

Answer & In-Depth Explanation

🏆 Best Answer — D: Materialized View

A materialized view tackles the problem at its source: instead of reading millions of wide rows on every request, queries read a small, precomputed table. Given Arjun's constraints, it's the most effective change:

  • Far less I/O: Pre-aggregating millions of order rows into something like daily totals per region and category can cut the data scanned by 100× or more. A relation that small stays in the buffer cache, so most reads never touch disk.
  • Zero-I/O reads: A plain REFRESH rebuilds the relation from scratch, producing a clean visibility map. When using REFRESH CONCURRENTLY (which is recommended to avoid blocking readers), schedule VACUUM on the view afterward to maintain the visibility map for index-only scans.
  • Flexible within its dimensions: Unlike a key-value cache, the view is a SQL table that supports any combination of filters on its grouped columns (day, region, category). This covers the dashboard's primary access patterns. However, filters on dimensions not included in the view's GROUP BY require querying the base table or creating additional views.
  • Fits the freshness budget: Running REFRESH MATERIALIZED VIEW CONCURRENTLY every few minutes stays within the stated staleness tolerance without blocking readers, and it needs no new infrastructure.

Arjun should match the refresh interval to the freshness requirement, add a unique index (required for concurrent refresh), and monitor how long refreshes take. If they get too slow, he can switch to incremental aggregation: summary tables updated by triggers or CDC, or something like TimescaleDB continuous aggregates.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

⚡

A — In-Memory Cache

A result cache works well for repeated identical queries. With many filter combinations, each unique query is its own cache key, so hit rates stay low and every miss still pays for the full disk-heavy scan. Correctly invalidating aggregated results as orders change is also hard.

🧩

B — Sharding

Sharding spreads data and I/O across nodes, but each query still scans the same total volume of wide rows, now with scatter-gather overhead for aggregations. It's a major operational project (rebalancing, cross-shard queries, resharding) that addresses storage and write scale, not inefficient read patterns.

🏛️

C — Columnar Database

Columnar stores (ClickHouse, DuckDB, Redshift, BigQuery) are purpose-built for exactly this workload and would eliminate the I/O problem at its root. They read only the columns each query needs, compress aggressively, and handle ad-hoc filter combinations that a pre-aggregated view cannot support. The trade-off is operational: a new data store, a sync pipeline (CDC or batch ETL), and a separate query interface. If the dashboard's filter requirements outgrow the materialized view's grouped dimensions, or if non-additive aggregates are needed, a columnar store becomes the right next step. For Arjun's current needs — known aggregate patterns with bounded staleness — the materialized view is a lower-cost starting point inside the existing database.

⚡

D — Materialized View ✓

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — In-Memory Cache

Hot, repeated, identical queries (e.g., homepage stats, top-N lists) with a small set of keys and tolerance for brief staleness.

📌

B — Sharding

Data volume or write throughput is more than a single primary can handle, and queries naturally go to one shard by tenant or region.

📌

C — Columnar Database

Large-scale, ad-hoc analytics over billions of rows, where precomputation can't anticipate the queries.

📌

D — Materialized View

Repeated aggregate or reporting queries over large tables, where results can be minutes old and the query patterns are known.

⚠️ Common Mistakes to Avoid

  • Blocking refreshes: A plain REFRESH MATERIALIZED VIEW locks out readers. Use CONCURRENTLY, which requires a unique index on the view.
  • Refreshing too often: If a refresh takes longer than the interval, refreshes overlap and hammer the database. Measure refresh time and schedule around it.
  • Forgetting to index the view: A materialized view is just a table, and without indexes queries against it still do full scans.
  • Neglecting VACUUM: Index-only scans depend on an up-to-date visibility map. Bloated tables with stale visibility maps fall back to heap fetches.
  • Over-wide covering indexes: Stuffing every column into INCLUDE bloats the index until it costs as much to read as the table.
  • Sharding to fix a query-shape problem: Spreading inefficient scans across more machines multiplies cost without fixing the root cause.

🌍 Real-World Best Practice

Teams usually escalate read optimizations in stages, matching the effort to the size of the problem:

  • Stage 1 — Covering indexes: Use INCLUDE columns and keep VACUUM healthy so true index-only scans work for narrow queries.
  • Stage 2 — Materialized views / summary tables: Precompute aggregates for dashboards that can tolerate a few minutes of staleness.
  • Stage 3 — Result caching: Add Redis on top of the views for the handful of hottest, identical queries.
  • Stage 4 — Columnar analytics store: Move heavy ad-hoc analytics to ClickHouse/BigQuery through CDC once the OLTP database can't keep up.

For Arjun's dashboard, a materialized view delivers most of the gain inside the existing database. Caching and columnar storage are the next steps if the workload keeps growing. If the materialized view approach proves too limiting (too many dimensions, non-additive aggregates, ad-hoc queries), migrating to a columnar store is the natural escalation.

💡

Key Takeaway

When disk I/O dominates read latency, the fastest read is the one that touches less data. Precompute what the queries need into a small, indexable table before reaching for caches, shards, or a new database engine.
