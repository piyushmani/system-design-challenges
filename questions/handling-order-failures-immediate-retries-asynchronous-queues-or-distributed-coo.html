Challenge

Handling order failures: immediate retries, asynchronous queues, or distributed coordination?

Maya manages a high-volume order-processing backend with peaks of 5k requests per second, a 99.9% availability SLA and a user-facing API that must average under 200 ms write latency. Downstream dependencies (shipping, payment and inventory) occasionally slow down or fail. She needs an error-handling strategy that keeps the API responsive, prevents data loss, allows safe retries and gives operators clear failure diagnostics.

A
Keep everything synchronous: the API gateway calls the order service, which calls the downstream dependencies. Handle transient errors with client-side retries and exponential backoff (up to a limit) before returning an error, and add a circuit breaker to prevent cascading failures.
✗ Not Best
B
Decouple with durable asynchronous messaging: accept the order synchronously, publish a reliable message to a processing queue and return success promptly. Workers consume with at-least-once delivery, idempotent handlers, exponential backoff and a dead-letter queue for problem messages, with strong metrics and tracing.
✓ Best Answer
C
Use fire-and-forget: receive the request, emit a non-durable event to a lightweight stream and reply with success immediately. If downstream processing fails, rely on compensating transactions or periodic batch reconciliation, with minimal retry logic.
✗ Not Best
D
Use distributed transactions (2PC or XA) across all involved services for strict consistency. If any participant fails or is unreachable, the coordinator aborts and immediately tells the client, using locks or leases to keep state correct.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — B: Durable Queue with Idempotent Workers and DLQ

Option B is the best fit. The API's only job becomes durably accepting the order. Everything that can be slow or flaky moves behind a durable queue, where retries, backoff and dead-lettering are normal operations rather than user-facing errors. Here's why it stands out:

  • Availability is decoupled from dependencies: in a synchronous chain, three dependencies at 99.9% each, called in series, cap the order path near 99.7% before your own failures, which already misses a 99.9% SLA. With a queue, the API depends only on its own database and the broker.
  • Latency stays flat: accepting an order is one local commit plus a publish (typically single-digit milliseconds), so the 200 ms average holds even when shipping takes seconds.
  • No data loss: the order and an outbox row commit in one transaction, and the broker stores messages with replication. A crash at any point leaves either nothing or a durable record.
  • Safe retries: at-least-once delivery plus idempotent handlers (deduplicate by message id, use idempotency keys on downstream calls) means a retry can never double-charge or double-ship.
  • Failure becomes a managed state: exponential backoff with jitter absorbs transient slowdowns, and messages that keep failing land in a dead-letter queue with the error, attempt count and trace id for review and replay.
  • Operator-friendly diagnostics: queue depth, oldest-message age, retry rate and DLQ size give an immediate health picture, and trace ids carried in the message connect the API request to every worker attempt.
  • Absorbs the 5k RPS peaks: the queue is a buffer, so a slow downstream grows a visible, bounded backlog instead of timing out user requests.

Combine outbox publishing, idempotent consumers, backoff with jitter, circuit breakers inside the workers and a DLQ with redrive tooling. Watch queue age, retry rate and DLQ depth, not just error rates.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🔁

A — Synchronous Calls with Retries and Circuit Breaker

Retries with backoff add seconds of latency exactly when dependencies are slow, and each retry adds load to a struggling service. Availability is the product of every dependency in the call chain. A circuit breaker prevents cascades but, once open, it fails user requests instead of preserving them, and nothing durable records an order that was never completed. Caveat: synchronous calls with breakers are right for reads that must return fresh data inline, and breakers remain useful inside the workers of Option B.

🔥

C — Fire-and-Forget with Non-Durable Events

Replying success before the event is durable breaks the requirement to prevent data loss: a broker restart or crash silently drops orders. Reconciliation batches can detect discrepancies, but they find them hours later, which makes them a safety net, not a primary design. With minimal retry logic, transient failures become permanent ones. Caveat: this style is acceptable for loss-tolerant events such as click tracking or telemetry.

🔗

D — Distributed Transactions (2PC / XA)

Blocking coordination across payment, shipping and inventory makes the API as slow and as unavailable as the weakest participant, and holding locks across network calls at 5k RPS does not scale. External providers usually cannot join XA, and a coordinator failure strands transactions. It also pushes failures straight to the client instead of absorbing them.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Sync + Retries + Circuit Breaker

Reads or queries where the caller needs the result inline, with idempotent dependencies and low volume. Circuit breakers are still valuable inside async workers.

📌

B — Durable Queue + Idempotent Workers

Write workflows with unreliable dependencies, strict loss and availability requirements, and traffic peaks that exceed what downstream systems can absorb in real time.

📌

C — Fire-and-Forget

Low-value, loss-tolerant events such as telemetry, click tracking or best-effort notifications.

📌

D — Distributed Transactions

Tightly coupled resources inside one trust boundary with short transactions and modest throughput, where atomic commit is mandatory.

⚠️ Common Mistakes to Avoid

  • Dual write without an outbox: saving to the DB and publishing in two steps can lose the message if the process dies in between.
  • Non-idempotent consumers: at-least-once delivery guarantees duplicates, so handlers that are not idempotent double-charge or double-ship.
  • Unbounded immediate retries: without backoff and jitter, retries create thundering herds that keep a recovering dependency down.
  • One shared queue for all dependencies: a slow shipping provider then blocks payment and inventory work. Isolate per dependency.
  • A DLQ nobody watches: without alerts and a redrive process, the DLQ is just a graveyard for lost orders.
  • Poison messages blocking the queue head: cap attempts and move bad messages aside so healthy ones keep flowing.
  • Telling users the order is complete when it is only accepted: show a pending state and update it when processing finishes.

🌍 Real-World Best Practice

In practice, teams define what accepted means and how long retries may run before they build anything. A typical sequence looks like this:

  • Step 0 — Set SLOs and a failure budget: define what accepted means, the retry window and the maximum acceptable backlog age.
  • Step 1 — Intake: validate, persist the order and an outbox row in one transaction, and return 202 with a status link.
  • Step 2 — Queue topology: separate queues or topics per dependency, partitioned by order id where sequence matters.
  • Step 3 — Idempotent workers: a deduplication table, idempotency keys on downstream calls and a timeout on every call.
  • Step 4 — Retry tiers: immediate retry for blips, delayed retry queues with exponential backoff and jitter, then a DLQ after the maximum attempts. Add circuit breakers and bulkheads inside workers.
  • Step 5 — Operations: DLQ alerts, redrive tooling, runbooks, dashboards for queue age and retry rate, and distributed tracing across API and workers.
  • Step 6 — Safety net: a periodic reconciliation job that compares order states with downstream systems.

Treat the queue as the system of record for in-flight work, and design every consumer for duplicates.

💡

Key Takeaway

When downstream dependencies are unreliable, do not make the user wait for them. Accept work durably, process it asynchronously with idempotent, retryable handlers, and make failures visible through dead-letter queues, metrics and traces. The price is eventual completion and extra infrastructure, which is far cheaper than lost orders or a broken SLA.
