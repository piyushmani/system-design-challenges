Challenge

Priya's real-time aggregation dilemma: balancing accuracy against scale

Priya, a backend software engineer, is building an analytics platform for a heavily used web application. It ingests about 200k events per second from several global regions and must serve near-real-time aggregations (per-minute distinct counts, sums, averages, and counts) with dashboard reads under 500 ms. Requirements also include strong availability, the ability to reprocess historical data after bug fixes, and correct handling of events that arrive late or out of order. Per-minute numbers should be accurate once a window closes, with small, bounded revisions for stragglers. She needs the architecture that best balances scalability, latency, consistency, availability, fault tolerance, and observability.

A
A centralized aggregation service: all sources send synchronous RPCs to a single stateful aggregator that keeps aggregates in memory, checkpoints to a relational database, and uses leader election for availability.
✗ Not Best
B
Decentralized CRDT aggregation: each application instance keeps local CRDT counters and periodically gossips or replicates state to peers and a read store, with dashboards merging CRDTs at read time for eventually consistent results.
✗ Not Best
C
Stateful partitioned stream processing: ingest into a partitioned log such as Kafka, run keyed, windowed aggregations in a stream engine such as Flink or Kafka Streams with checkpointed state, write through idempotent or exactly-once sinks, and serve reads from materialized views.
✓ Best Answer
D
Scheduled batch aggregation: land raw events in object storage, run Flink or Spark batch jobs every 5 to 60 minutes, and load the results into a database for dashboards.
✗ Not Best

Answer & In-Depth Explanation

🏆 Best Answer — C: Stateful Partitioned Stream Processing

These requirements describe the textbook case for event-time stream processing over a durable log: high throughput that must be partitioned, windowed aggregates that tolerate late and out-of-order data, fault tolerance without losing state, and replay for bug fixes. A partitioned log plus a stateful stream engine provides all of these natively. Here's why it stands out:

  • Scales horizontally by key: Kafka partitions and Flink keyed state spread 200k events per second across many workers. Adding partitions and parallelism scales both throughput and state size.
  • Correct time semantics: Event-time windows with watermarks and allowed lateness handle out-of-order and late events deterministically, and very late events can go to a side output for reconciliation instead of silently corrupting results.
  • Fault tolerance with exactly-once effects: Periodic checkpoints (state in RocksDB plus Kafka offsets) allow recovery without losing or double-counting. Idempotent upserts keyed by window and dimension make sinks safe under replays and late updates.
  • Reprocessing is built in: Because the log (plus an object-store archive) retains raw events, a bug fix can be deployed and the job replayed from an earlier offset into a new versioned output, then swapped in without special tooling.
  • Low-latency reads: Results are written to a serving store (an OLAP or key-value store, or a materialized view) so dashboards read pre-aggregated per-minute rows in tens of milliseconds, independent of ingest load.

A production setup includes event-time watermarks and allowed lateness, incremental checkpoints, idempotent upserts, sketches for uniques, replay and backfill tooling, and alerts on consumer lag, watermark lag, checkpoint failures, and backpressure.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🏢

A — Centralized Aggregator

A single stateful service receiving synchronous RPCs from every source is a scaling bottleneck and a single point of failure. At 200k events per second from global regions, producers pay cross-region RPC latency, backpressure flows into the application, and in-memory state since the last checkpoint is lost on failover (leader election does not fix that). It also offers no natural replay mechanism for reprocessing.

🔀

B — CRDT Aggregation

CRDTs merge counters and sketches nicely and tolerate partitions, but they have no notion of event-time windows or lateness (late events simply merge into current state). Averages need paired sum and count state, exact distinct counts are not a simple CRDT, there is no raw event history to reprocess after a bug fix, and read-time merging across many replicas threatens the 500 ms dashboard target. They suit approximate global counters, not windowed, replayable analytics.

🗓️

D — Scheduled Batch

Batch is simple, cost-efficient, and excellent for reprocessing, but a 5 to 60 minute cadence misses the near-real-time requirement. It works best as a complement, a backfill and correction path, rather than as the main architecture.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Centralized Aggregator

Low-volume, single-region counters where one node is enough, and simplicity matters more than horizontal scale.

📌

B — CRDT Aggregation

Globally replicated counters, presence, or approximate metrics where replicas must stay writable during partitions, with no need for event-time windows or replay.

📌

C — Stream Processing

High-volume event streams that need windowed aggregates, late-data handling, fault-tolerant state, and the ability to replay after fixes.

📌

D — Scheduled Batch

Hourly or daily reports, large historical recomputation, or a backfill path that complements a streaming system.

⚠️ Common Mistakes to Avoid

  • Using processing time instead of event time: Results then depend on network delays and outages, and replays produce different numbers. Window on the event timestamp.
  • Mis-sizing watermarks and lateness: Too tight drops legitimate late events, too loose delays results and bloats state. Measure real delay distributions per region.
  • Non-idempotent sinks: Appending window results duplicates rows when windows re-fire or jobs restart. Upsert by window and key.
  • Ignoring hot-key skew: A few popular keys can overload single partitions. Pre-aggregate locally or salt keys.
  • Unbounded state growth: Windows or keys that never expire eventually exhaust state storage. Set state TTLs and use incremental checkpoints.
  • Averaging averages: Averages do not combine. Store sum and count, and compute the average at read time.

🌍 Real-World Best Practice

In practice, teams treat streaming as the main path and batch as the correction path. A typical sequence looks like this:

  • Step 0 — Define the contract: Windows, lateness tolerance, accuracy per metric (exact vs. sketch), freshness SLO, and dimensions.
  • Step 1 — Ingest: Partition Kafka by a well-distributed key, use a schema registry, size retention for replay, and archive raw events to object storage.
  • Step 2 — Stream jobs: Event-time windows, watermarks, and allowed lateness, with RocksDB state, incremental checkpoints, and a side output for very late data.
  • Step 3 — Serve: Idempotent upserts into a serving store, pre-aggregated at minute grain with rollups for longer ranges.
  • Step 4 — Reprocess: Replay from offsets, or run the same code in batch mode over the archive, into a versioned table. Validate, then swap.
  • Step 5 — Operate: Dashboards for lag, watermark, checkpoint duration, backpressure, and data quality (late-event rate, reconciliation against batch).

Treat the stream as the fast path and replay as the safety net.

💡

Key Takeaway

For high-volume, windowed analytics with late data and replay needs, use a durable partitioned log plus stateful event-time stream processing, with checkpointed state, idempotent sinks, and a pre-aggregated serving layer. Use sketches where exact distinct counts are too costly, aggregate regionally when needed, and keep batch as a backfill path rather than the primary design.
