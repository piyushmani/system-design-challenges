How can Nadia avoid overselling across microservices?

Nadia, a software engineer, is building an e-commerce backend where an order spans three microservices: Orders, Payments, and Inventory, deployed across multiple regions to reduce latency. A strict business rule says inventory must never be oversold. Today, Orders asks Inventory to reserve stock and then asks Payments to bill the customer. As traffic grows, Nadia sees rising latency and sporadic inconsistencies: stock reserved with no matching payment, and duplicate reservations under concurrent or retried requests. She must choose a strategy that preserves the inventory rule while optimizing scalability, availability, latency, observability, and operational overhead.

A
Use distributed transactions (two-phase commit or XA) across all three microservices, so Orders reserves inventory and processes payment inside one globally serializable transaction.
✗ Not Best
B
Make Inventory the sole authoritative owner of stock state, managing all reservations and commits through local database transactions with serializable or repeatable-read isolation. Other services call Inventory synchronously, and Inventory scales by sharding products and adding read replicas for non-critical queries.
✗ Not Best
C
Use the Saga pattern: the Orders service acts as an orchestrator, first sending a reserve command to Inventory and then a charge command to Payments. If a later step fails, run compensating transactions to undo earlier steps. Use version checks or optimistic concurrency in Inventory to reduce conflicts.
✓ Best Answer
D
Move all microservices onto a globally consistent distributed SQL database (such as CockroachDB or Spanner) so every service transacts against one system that provides global serializable isolation and external consistency.
✗ Not Best

Answer & In-Depth Explanation

🏆 Best Answer — C: Saga with Inventory-Owned Reservations

Nadia has two separate problems. The never-oversell invariant belongs to a single service, so it should be enforced by Inventory with a local atomic update. The cross-service workflow (reserve, pay, confirm) cannot be a single ACID transaction, because Payments usually talks to an external gateway and the services span regions. A saga handles that second problem by running each step as a local transaction and undoing earlier steps with compensations when a later step fails. Together, these remove both symptoms: stock reserved without payment (compensation and TTL release it) and duplicate reservations (idempotency keys). Here's why it stands out:

  • The invariant stays local: Inventory is the only writer of stock, and an atomic conditional update (or version check) guarantees stock cannot go negative regardless of how many callers race.
  • No cross-region locking: Every step is a short local transaction. Nothing holds locks across services or regions, so latency is the sum of the calls, not multiple coordinated round trips with locks held.
  • Reserve first, then charge: Stock is the scarce resource, so reserving first with a TTL means a customer is never charged for something that cannot be fulfilled. If payment fails, a release compensation returns the stock.
  • Duplicates are handled by design: Each command carries an idempotency key (for example the order id). A retried reserve or charge returns the previous result instead of acting twice.
  • Failures degrade gracefully: A persisted saga state machine can resume after a crash, retry compensations until acknowledged, and surface stuck orders instead of leaving silent inconsistencies.
  • Observability is built in: Each order has an explicit state (STARTED, RESERVED, AUTHORIZED, COMPLETED, COMPENSATED), so dashboards, alerts, and traces can follow a correlation id end to end.

A production-grade saga uses idempotency keys on every command, a transactional outbox for reliable messaging, TTL-based reservations as a safety net, authorize-then-capture payments, and a reconciliation job that finds orders stuck in intermediate states. Track saga age by state, compensation rate, and reservation expirations.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🔐

A — Two-Phase Commit / XA

2PC makes participants hold locks while waiting for the coordinator, which stretches latency over cross-region round trips and blocks everyone if the coordinator or a participant fails mid-protocol. It also assumes every participant can join the protocol, but external payment providers generally cannot take part in XA. Throughput and availability drop sharply as services and regions are added. Caveat: 2PC is acceptable inside a single trusted datacenter with a small number of XA-capable databases.

🏬

B — Inventory as Sole Owner with Local Transactions

This is the right half of the answer: one owner for stock with serializable local transactions does protect the never-oversell rule. But on its own it does not solve the cross-service failures Nadia sees. If Payments fails after Inventory reserved, nothing releases the stock, and synchronous calls couple Orders' availability to Inventory's latency. Serializable isolation also aborts transactions under contention, which needs retries. Caveat: this is the correct core inside option C, and it is enough on its own when Orders and Inventory share one database and there is no external payment step.

🌍

D — Globally Consistent Distributed SQL

Distributed SQL gives genuine global transactions, but multi-region commits carry cross-region latency on the critical path, and migrating three services onto one shared database couples them tightly and gives up independent ownership. More importantly, the payment gateway call is outside the database, so a database transaction cannot make 'charge the card' atomic with 'reserve stock'. A saga or similar workflow is still needed. Caveat: distributed SQL is a strong choice for the Inventory service's own storage when you need geo-distributed, strongly consistent stock.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Two-Phase Commit / XA

A small number of XA-capable databases in one datacenter, short transactions, and tolerance for coordinator blocking.

📌

B — Inventory Sole Owner, Sync Calls

A simple flow where Orders and Inventory share a boundary and no external step can fail after reservation. Also the core of any saga-based design.

📌

C — Saga + Inventory-Owned Reservations

Multi-service, multi-region workflows involving external systems, where availability and latency matter and temporary intermediate states are acceptable.

📌

D — Global Distributed SQL

Geo-distributed, strongly consistent state owned by one service (such as stock) where the team accepts cross-region commit latency and the migration cost.

⚠️ Common Mistakes to Avoid

  • Charging before reserving: Taking money first means refunds whenever stock is gone. Reserve the scarce resource first.
  • No idempotency keys: Retries after timeouts create duplicate reservations or double charges. Every command needs a stable key.
  • Compensating on an ambiguous timeout: Releasing stock because a payment call timed out, when the payment actually succeeded, creates a paid order with no stock. Check the payment status by key first.
  • Reservations with no expiry: A crashed orchestrator can strand stock forever. Give every reservation a TTL and a sweep.
  • Losing messages between state change and publish: Updating the database and sending a message separately can drop one of them. Use a transactional outbox.
  • Non-idempotent compensations: Compensations are retried, so releasing the same reservation twice must not add stock twice.

🌍 Real-World Best Practice

In practice, teams separate who owns the invariant from how the workflow recovers. A typical sequence looks like this:

  • Step 0 — Map the failure modes: List what can fail between reserve, authorize, and capture, and what each failure should do. Add correlation ids to every call.
  • Step 1 — Make Inventory the sole owner: Enforce stock with an atomic conditional update and store reservations with a TTL inside the same local transaction.
  • Step 2 — Add idempotency keys: Use them on reserve, release, confirm, authorize, and capture so retries never double-act.
  • Step 3 — Orchestrate with a persisted saga: Orders drives the steps, stores state after each one, and retries compensations until acknowledged. Use a transactional outbox for messages.
  • Step 4 — Authorize, then capture: Hold funds early, capture only after stock is confirmed, so the irreversible action is last.
  • Step 5 — Reconcile: Run a periodic job comparing orders, reservations, and payments, and alert on sagas stuck beyond a threshold.

Keep the invariant local to one owner, and make the workflow around it retryable and observable.

💡

Key Takeaway

Don't try to make the whole checkout one transaction. Let Inventory own and atomically enforce stock, then coordinate Orders, Inventory, and Payments with a saga that uses idempotency keys, TTL reservations, and compensations. This preserves the never-oversell rule while avoiding cross-region locks and blocking protocols.
