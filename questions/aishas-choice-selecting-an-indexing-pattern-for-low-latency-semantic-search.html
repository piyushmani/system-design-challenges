Aisha's Choice: Selecting an indexing pattern for low-latency semantic search

Aisha, a software engineer, is designing a semantic search backend for an e-commerce catalog with tens of millions of products. The system handles up to 10k writes or updates per minute (about 170 per second), hundreds of search queries per second with occasional spikes, and must keep end-to-end search latency under 100 ms. New or updated items must be searchable within about one minute. The deployment spans two regions for high availability and must be easy to observe, scale, and recover. She must choose the best strategy for generating vector embeddings and updating the vector database without excessive operational burden.

A
Synchronous write-through: compute the embedding and upsert it into the vector DB inside the write request before responding.
✗ Not Best
B
Asynchronous streaming pipeline: persist metadata, publish an event to a durable broker (Kafka), and let independent consumers embed and idempotently upsert into the vector DB.
✓ Best Answer
C
Hybrid: a synchronous fast path for critical items (such as promotions) and an asynchronous stream for everything else, selected by an item-level flag.
✗ Not Best
D
Query-time merge: save metadata immediately, embed only unindexed items at query time and merge their scores with the main index, and rebuild the index in offline batches.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — B: Asynchronous Streaming Pipeline

The requirements only conflict if indexing sits in the request path. At roughly 170 updates per second and a one-minute freshness budget, indexing does not need to be synchronous at all. A durable event stream between the write path and the vector index lets the API return in milliseconds, absorbs spikes, and gives each stage its own scaling and failure handling, while freshness becomes a measurable lag metric that fits comfortably inside the one-minute target. Here's why it stands out:

  • Write latency stays low: The API commits metadata plus an event (via a transactional outbox or CDC) and returns. Embedding model inference, which takes tens to hundreds of milliseconds and can queue on GPUs, never blocks the client.
  • Freshness matches the SLO: End-to-end lag (event, embedding, upsert, searchable) is typically seconds, well inside one minute, and it can be observed per partition and alerted on.
  • Spike absorption and independent scaling: Kafka buffers bursts such as bulk catalog imports, consumers scale horizontally on lag, and the embedding service can batch requests for GPU efficiency.
  • Availability decoupling: A vector DB or embedding outage does not stop catalog writes. Events accumulate and drain on recovery, and replay also gives you disaster recovery and a path to re-embed with new models.
  • Idempotent, versioned upserts make it safe: Keyed by product ID with a monotonic version, consumers can retry and tolerate duplicates or out-of-order events, so at-least-once delivery is sufficient.

A production setup has a transactional outbox or CDC to avoid dual writes, content-hash checks so only embedding-relevant changes are re-embedded, versioned idempotent upserts, a dead-letter queue, and per-region consumers reading a replicated stream. Track indexing lag p99, consumer lag, upsert error rate, and search p99. If lag approaches the freshness budget, scale consumers before changing the architecture.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🔗

A — Synchronous Write-Through

Embedding generation in the request path adds model inference latency to every write, and the write now fails or slows whenever the embedding service or vector DB is degraded, so availability is coupled to the weakest dependency. The promised 'immediate consistency' is also weaker than it looks: many vector indexes expose new vectors only after a refresh or segment flush, and a dual write to two stores is still not atomic. Caveat: for small catalogs, admin tools, or prototypes with low write rates, where simplicity beats resilience, it works.

🔀

C — Hybrid Fast Path

It solves a problem the SLO does not have, because one-minute freshness is already met by the async path. The cost is real: two indexing paths to test and monitor, flag management, and races where the sync and async paths write different versions of the same item (which demands strict versioning). Caveat: it is reasonable only if a small subset truly needs sub-second visibility, and even then it is often simpler to speed up the async path with a priority topic.

🧮

D — Query-Time Merge

This pushes cost onto the read path, exactly where the 100 ms budget is tightest: extra embedding calls, a second search, and score merging on every query (cross-source score normalization is hard). During ingestion spikes the unindexed set grows, so query latency grows with write volume, and caching becomes difficult because results depend on that set. Caveat: a small, bounded 'delta index' of very recent items (not query-time embedding) is a legitimate optimization on top of the async pipeline.

⚡

B — Asynchronous Streaming Pipeline ✓

Asynchronous streaming pipeline: persist metadata, publish an event to a durable broker (Kafka), and let independent consumers embed and idempotently upsert into the vector DB.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Synchronous Write-Through

Small catalogs, low write rates, admin-driven updates, or prototypes where immediate visibility matters and the embedding and vector services are highly available.

📌

B — Async Streaming Pipeline

Medium to large catalogs with continuous updates, minute-level freshness, multi-region requirements, and a need to isolate failures and absorb spikes.

📌

C — Hybrid Fast Path

A small, well-defined subset (flash promotions, compliance takedowns) needs seconds-level visibility and the team can afford two paths with strict versioning.

📌

D — Query-Time Merge

Short-lived delta windows (items added in the last few minutes) kept as a small bounded side index, or very low query volume where the extra read cost is acceptable.

🧑‍💻 Idempotent Embedding Consumer

A batch consumer that applies deletes, skips stale events and unchanged content, embeds in batches, performs version-guarded upserts, and dead-letters poison messages:

⚠️ Common Mistakes to Avoid

  • Dual write without an outbox: Writing to the DB and publishing to Kafka as separate steps can lose or duplicate events on a crash. Use a transactional outbox or CDC.
  • Unversioned or non-idempotent upserts: Out-of-order or retried events can overwrite a newer vector with an older one. Carry a monotonic version and apply only if newer.
  • Re-embedding on every update: Price or stock changes do not alter semantics. Hash the embedding inputs and skip unchanged content, treating price and stock as filterable metadata updates rather than new vectors.
  • Ignoring deletes: Delisted products must be removed with tombstone events, or they keep appearing in results.
  • Mixing embedding model versions in one index: Vectors from different models are not comparable. Version the index and migrate with an alias swap.
  • No lag alert or DLQ: Silent consumer stalls turn a one-minute SLO into hours. Alert on the age of the oldest unindexed event and route poison messages to a dead-letter queue.

🌍 Real-World Best Practice

Teams building semantic search usually treat embeddings as a derived data store fed from the source of truth, and evolve in this order:

  • Step 0 — Define SLOs: Set targets for freshness (p99 time to searchable), query p99, and recall. 10k per minute is modest, but size for bulk-reindex peaks too.
  • Step 1 — Reliable event capture: A transactional outbox or CDC from the primary DB into Kafka, keyed by product ID.
  • Step 2 — Embedding workers: Batch requests to the embedding service, skip unchanged content using a hash, and cache embeddings by content hash.
  • Step 3 — Idempotent upsert: Version-guarded upserts into the vector DB with metadata filters, plus retry with backoff and a DLQ.
  • Step 4 — Multi-region: Replicate the event stream (or have each region consume it) and keep a regional index per region so queries stay local. Fail traffic over at the DNS or gateway level.
  • Step 5 — Evolve safely: Blue/green index builds for model changes, replay for recovery, and sampled recall checks against ground truth.

Treat the index as rebuildable and the event log as the source for rebuilding it.

💡

Key Takeaway

When freshness is measured in minutes, not milliseconds, decouple indexing from the write path with a durable stream and idempotent consumers. You get low write latency, spike absorption, and independent failure domains, and freshness becomes a lag metric you can alert on. Reach for synchronous or hybrid paths only when the requirement is genuinely sub-second visibility.
