Challenge

Maya targets sub-50ms reads: index-only scans or another approach?

Maya, a backend developer, runs a globally distributed user-profile service. The profiles table is very wide (hundreds of columns plus large JSON blobs), yet 80% of reads need only three small fields (user_id, display_name, avatar_url), looked up by username or email. Traffic peaks at about 8k reads/s and 1k writes/s on a sharded SQL database with PostgreSQL-style MVCC and autovacuum. Profiling shows these lookups fetch full rows and touch heap pages, causing high tail latency and wasted I/O. Routing of username and email lookups to the owning shard is handled separately, so the remaining cost is per-shard heap I/O, and the three fields change far less often than they are read. She must consistently achieve under 50 ms at peak while keeping the system stable and easy to maintain.

A
Create compact covering indexes (using INCLUDE) on username and email that carry the three needed columns, enabling index-only scans per shard; tune visibility maps and autovacuum, use partial indexes to limit size, and monitor write amplification.

B
Build an asynchronously refreshed denormalized read table (or materialized view) holding only the three hot fields per user, fed by CDC or background workers, and route reads there, accepting eventual consistency.
✗ Not Best
C
Stream profile updates into a columnar OLAP database such as ClickHouse and serve reads from it, using near-real-time or batch ETL and accepting higher latency and occasional staleness.
✗ Not Best
D
Put a global in-memory cache such as Redis in front of reads, keyed by username or email, loading from the primary table on misses, with short TTLs and invalidation on writes.

Answer & In-Depth Explanation

🏆 Best Answer — A: Covering Indexes (Index-Only Scans)

Profiling points to a clear root cause: queries need three tiny columns but pay for a full-row heap fetch on a wide table with large JSON. The most effective fix is the one that removes the heap access. A covering index with INCLUDE lets the database answer entirely from a small, cache-friendly index through an index-only scan. Here's why it stands out:

  • Removes the actual bottleneck: An index-only scan reads a small index entry instead of a heap page of a wide row. The large JSON blobs stay out of the hot path entirely, cutting I/O and shrinking p99 variance.
  • Small, cacheable working set: A covering index on username (and another on email) holding only three small columns stays compact enough to remain in shared buffers or the OS cache, making latency predictable at peak.
  • Same transaction, same consistency: The database maintains the index in the same transaction as each write, so there is no pipeline, no lag, no staleness, and nothing new to operate.
  • Low operational surface: It is a native schema change (CREATE INDEX CONCURRENTLY), reversible by dropping the index, and easy to verify with EXPLAIN (ANALYZE, BUFFERS) showing an Index Only Scan with near-zero heap fetches.
  • Controls the cost side: Partial indexes (for example, active users only) keep the index small, and including only rarely changing columns limits write amplification.

A solid rollout builds the indexes CONCURRENTLY shard by shard, confirms Index Only Scan plans with Heap Fetches near zero, sets aggressive per-table autovacuum, and tracks p99 latency, heap fetches, index size, and write latency. If heap fetches stay high or writes suffer, add a narrow read table or cache as a second step.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

📋

B — Denormalized Read Table

A narrow three-column table would also avoid the wide row, but it solves a problem the database can already solve in place. It adds a CDC or worker pipeline, eventual consistency (a user changes an avatar and still sees the old one), backfill and drift-detection work, and it still needs its own indexes on username and email. A covering index gives most of the benefit with none of the lag. Caveat: if the profile table is so write-hot that index-only scans cannot hold up (constant visibility-map churn), a separate narrow table becomes attractive.

📊

C — Columnar OLAP Store

Columnar engines such as ClickHouse are optimized for scans and aggregations over many rows, not for point lookups at thousands of queries per second under 50 ms. ETL adds staleness, and an OLAP system adds an entire new operational platform. It is the wrong tool for this access pattern.

⚡

D — Global Redis Cache

A cache can cut latency and may be a good second layer, but it does not fix the underlying inefficiency: every miss still pays the heap fetch, and tail latency returns during cold starts or invalidation storms. Keying by both username and email needs indirection (or duplicate keys) and invalidating both when either changes, and a global cache adds cross-region consistency and operational complexity.

⚡

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Covering Indexes

A small subset of columns is read repeatedly by well-defined lookup keys, those columns change rarely, and vacuum can keep the visibility map healthy.

📌

B — Denormalized Read Table

The hot subset is volatile or needs a different storage or replication shape (for example, regional replicas), or write rates make index-only scans ineffective.

📌

C — Columnar OLAP Store

Analytical aggregation across many rows (reporting, funnels, trends), not user-facing point lookups.

📌

D — Global Redis Cache

Highly skewed hot keys with repeated reads where short staleness is acceptable, typically layered on top of an already efficient database path.

⚠️ Common Mistakes to Avoid

  • Ignoring the visibility map: An index-only scan silently degrades into heap fetches when pages are not all-visible. Watch the Heap Fetches count and tune autovacuum.
  • Including too many or volatile columns: Every INCLUDE column makes the index bigger and every update to it costlier. Include only small, rarely changing fields.
  • Query and index mismatch: Using WHERE email = ? against an index on lower(email), or omitting a partial-index predicate, means the index is never used.
  • Building the index with a blocking lock: Use CREATE INDEX CONCURRENTLY, one shard at a time, and watch replication lag and I/O during the build.
  • Not verifying the plan: Assuming the planner will choose the index. Confirm Index Only Scan with EXPLAIN (ANALYZE, BUFFERS) on production-like data.
  • Forgetting shard routing: A perfectly covered index still loses to scatter-gather across shards when the lookup key is not the shard key.

🌍 Real-World Best Practice

In practice, teams fix the access path first and add layers only where measurements show a remaining gap. A typical sequence looks like this:

  • Step 0 — Profile first: Use pg_stat_statements and EXPLAIN (ANALYZE, BUFFERS) to confirm heap reads and shared-buffer misses, and break p99 down by shard.
  • Step 1 — Covering indexes: Add INCLUDE indexes for the username and email lookups, built concurrently, and replace the old plain indexes once plans switch.
  • Step 2 — Vacuum and visibility map tuning: Set aggressive per-table autovacuum thresholds and move frequently updated columns out of the hot table.
  • Step 3 — Routing: Make sure every username or email lookup goes to exactly one shard, for example through a directory table.
  • Step 4 — Cache hot keys if still needed: A short-TTL cache or small in-process cache for the hottest profiles, layered on an already efficient path.
  • Step 5 — Narrow read model only if proven necessary: For example, when write churn defeats index-only scans or regional replicas need a smaller copy.

Fix the access path first, then add layers only where the data says you still need them.

💡

Key Takeaway

When most reads need only a few small columns from a wide table, make the index answer the query. Covering indexes enable index-only scans that skip the heap, keep full consistency, and add little operational burden, provided vacuum keeps the visibility map healthy and lookups are routed to a single shard. Layer caching or a narrow read model only if profiling shows a remaining gap.
