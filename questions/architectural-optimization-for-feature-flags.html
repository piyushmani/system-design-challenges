Architectural Optimization for Feature Flags

Alex, a backend engineer, is assigned to architect a feature flag management system for a heavily used application built from many services. Flag checks sit on the hot path of nearly every request (often several per request), so the design must process them effectively with as little latency impact as possible and must not make flag-backend availability a dependency of request serving. Product teams want flag changes to take effect within seconds, and a given user should see consistent variants across services. He needs to choose the best architecture.

A
Create a centralized feature flag evaluation service to maintain uniform flag checks across the entire system.
✗ Not Best
B
Select a decentralized design allowing each service to handle its own feature flag evaluations on its own.
✗ Not Best
C
Go with an asynchronous architecture that caches flag checks locally within each service, minimizing reliance on external components.
✓ Best Answer
D
Use a third-party feature flag service to handle both the evaluation logic and any scalability issues.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — C: Local Evaluation with Asynchronously Cached Flag Rules

The key idea is to separate the control plane from the data plane. Flag definitions are changed and distributed centrally, but every check is evaluated in-process against a locally cached ruleset that is kept fresh asynchronously (streaming, with polling as a fallback). A flag check then costs microseconds with no network call, and request serving no longer depends on the flag backend being up. Note that what is cached is the rules (flag configuration), evaluated locally per request, not the individual evaluation results. Here's why it stands out:

  • Microsecond latency: Evaluation is an in-memory rule match instead of a network round trip, and the cost does not multiply when a request checks several flags.
  • Resilient by design: If the flag backend is down or slow, services keep evaluating against the last known good snapshot. On startup they can fall back to a persisted snapshot or to safe defaults.
  • Backend load scales with instances, not traffic: The flag backend serves a long-lived stream or a periodic poll per service instance, not one call per request.
  • Consistent rollouts without coordination: Deterministic bucketing, such as hash(flagKey + userId) mod 100, gives every service the same answer for the same user as long as they run the same ruleset version.
  • Matches industry practice: LaunchDarkly and Unleash server-side SDKs evaluate locally from a streamed or polled ruleset, and OpenFeature offers a vendor-neutral API in front of such providers. This is why option D is usually implemented as option C.

A robust design includes a versioned ruleset, streaming updates with a polling fallback, a persisted last-known-good snapshot, deterministic bucketing, per-flag safe defaults, and metrics for evaluation counts and propagation delay. Treat flags as short-lived and remove them once a rollout is complete.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🏢

A — Centralized Evaluation Service

It gives uniform results and a single place to audit, but every check becomes a network call on the hot path. Latency adds up with several flags per request, the service must scale with request volume, and a slowdown or outage cascades into every dependent service. Caveat: a thin evaluation endpoint is the right answer for clients that cannot hold rules (browsers, mobile), returning precomputed results that can be cached at the edge.

🧩

B — Decentralized Per-Service Evaluation

If each service owns its own flag logic and configuration there is no shared source of truth. The same user can get different variants in different services, audit and governance are weak, and flags drift over time. Latency is excellent, but consistency, auditability and operability are lost. Note that option C also evaluates locally, but from a shared, centrally managed, versioned ruleset.

☁️

D — Third-Party Feature Flag Service

It buys features (UI, targeting, audit trail, experimentation) and offloads the control plane, but it is a vendor and cost decision rather than an architecture. If checks are evaluated remotely per request it recreates option A's latency and availability coupling, and its SDKs usually evaluate locally anyway, which is option C. It also brings lock-in (reduced by OpenFeature), usage-based pricing and data-residency questions for user attributes.

⚡

C — Local Evaluation with Asynchronously Cached Flag Rules ✓

Go with an asynchronous architecture that caches flag checks locally within each service, minimizing reliance on external components.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Centralized Evaluation Service

A thin client-facing endpoint for browsers and mobile apps, or a small system with few checks per request where simplicity matters more than latency. Cache results at the edge.

📌

B — Decentralized Per-Service

Single-service applications, or flags that are truly service-local (internal operational toggles). Not suitable for cross-service rollouts.

📌

C — Local Evaluation, Cached Rules

The default for high-traffic, multi-service systems with many flag checks per request, where latency and availability matter.

📌

D — Third-Party Service

Teams that want a managed control plane (UI, targeting, experimentation, audit) and accept the vendor cost. Choose one whose SDK evaluates locally.

⚠️ Common Mistakes to Avoid

  • Caching results instead of rules: Caching per-user results for long periods hides rule changes and bloats memory. Cache the ruleset and evaluate per request, or keep result caches very short-lived.
  • No safe defaults: If the backend is unreachable at startup, an unsafe default can switch on a half-finished feature. Define the default per flag and persist a last-known-good snapshot.
  • Treating the kill switch as instant: Propagation takes time. Measure it, set a target, and keep a second mitigation (such as a circuit breaker) for critical failures.
  • Non-deterministic bucketing: Random assignment per request makes users flicker between variants. Hash a stable user id together with the flag key.
  • Shipping targeting rules to clients: Raw rules and segments in a browser or mobile app leak business logic and user attributes. Send only evaluated results.
  • Never removing flags: Flags that live for years become untested branches and hidden configuration. Add owners and expiry dates.

🌍 Real-World Best Practice

In practice the build-versus-buy question applies to the control plane. Teams keep evaluation local either way:

  • Step 0 — Define requirements: Latency budget, propagation target (for example under 10 seconds), consistency needs, client types (server, web, mobile) and audit or compliance rules.
  • Step 1 — Local evaluation: Embed an SDK (or an OpenFeature-compatible provider) in each service that evaluates cached rules in memory.
  • Step 2 — Asynchronous updates: Streaming as the primary channel, polling as a fallback, a persisted last-known-good snapshot and explicit default values.
  • Step 3 — Choose the control plane: A managed vendor, an open-source system or an in-house service, with approvals, an audit log and per-environment configuration.
  • Step 4 — Client and edge flags: Evaluate server-side or at the edge and send only the resulting variants to browsers and mobile apps.
  • Step 5 — Hygiene: Give every flag an owner and an expiry date, remove stale flags and test both code paths.

Keep the hot path local and the control plane central.

💡

Key Takeaway

Make flag checks local and in-memory, and make flag changes central and asynchronous. This keeps latency near zero and removes the flag backend from the request path, at the cost of a short, measurable propagation delay that must be accepted and monitored.
