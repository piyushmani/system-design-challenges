Asha's storage engine decision: LSM vs B-tree for a global, high-ingest event store

Asha is architecting a multi-tenant, global event store used by many internal services. It ingests about 200,000 small-event writes per second, must serve point reads with p99 under 30 ms, supports infrequent analytical range scans, and needs TTL expiration. The team wants cost-effective SSD storage, deep observability into IO and compaction, and strong consistency within a region (cross-region replication may be asynchronous). She must choose a storage-engine architecture (LSM-tree, B-tree or hybrid) with a replication and compaction strategy that balances scalability, availability, latency, consistency and operational overhead.

A
Run an LSM-tree engine (RocksDB-style) per partition with a memtable, write-ahead log, Bloom filters and background compaction. Replicate shards with leader-based Raft inside the region for strong regional consistency, throttle compaction IO and expose rich metrics to control tail latency, and keep secondary indexes in the LSM or in index tables updated with the primary write.
✓ Best Answer
B
Use a B-tree engine (InnoDB-style) per partition with MVCC, in-place updates and fsync-on-commit, replicate synchronously among regional primaries for cross-region strong consistency, rely on page caching for reads and run range scans directly on the B-tree files.
✗ Not Best
C
Build a hybrid: ingest into an LSM hot tier, then periodically compact and convert older records into a colder B-tree or columnar format for lower storage cost and faster large scans. Serve point reads from the hot tier and fall back to the cold tier for history, running conversion asynchronously.
✗ Not Best
D
Persist raw events in a distributed append-only log (such as Kafka) and build a separate read index per partition (B-tree or LSM) fed by consumers, with either synchronous index updates for read-after-write consistency or asynchronous updates for throughput at the cost of eventual read consistency.

Answer & In-Depth Explanation

🏆 Best Answer — A: LSM-Tree with Regional Raft

The workload is the textbook case for a log-structured merge (LSM) tree: a very high rate of small writes, mostly point reads, rare scans and time-based expiry. LSM engines turn random writes into sequential appends (log plus memtable flush), which is what sustains hundreds of thousands of writes per second on commodity SSDs, while Bloom filters and a block cache keep point reads fast. Layering Raft inside each region gives strong regional consistency and automatic failover without forcing cross-region synchronous latency onto every write. Here's why it stands out:

  • The write path fits the load: Writes append to a log and update an in-memory memtable, so a write costs roughly one sequential IO. Spread across partitions, 200,000 writes per second is a few thousand per partition, well within an LSM node's reach.
  • Point reads stay within the p99 target: Bloom filters skip most SSTables that cannot hold the key, and a block cache plus partitioned indexes keep hot data in memory, so a point read usually touches memory and at most one or two SSTable blocks.
  • TTL is cheap: With time-ordered keys and time-window, FIFO-style or TTL-filtered compaction, expired data is dropped by deleting whole SSTables or during compaction instead of issuing row-by-row deletes.
  • Consistency matches the requirement: Raft per partition within the region provides linearizable writes and automatic leader failover. Cross-region replication can be asynchronous (follower regions or change streams), which keeps write latency independent of inter-region distance.
  • Operability is explicit: LSM engines expose the knobs and metrics operators need (pending compaction bytes, write stalls, read amplification, Bloom filter and block cache hit rates) plus IO rate limiters to protect tail latency.

A well-tuned deployment uses time-windowed or tiered compaction, Bloom filters (around 10 bits per key), a compaction rate limiter, write-stall and pending-compaction alerts, group-committed Raft appends and asynchronous cross-region replication with lag metrics. Load-test with realistic key distributions and TTL churn; if range-scan demand grows, add a downstream columnar copy (the hybrid) rather than changing the core engine.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🌲

B — B-Tree Engine with Cross-Region Sync

B-trees excel at point reads and range scans, but this option fights the workload at 200,000 small writes per second: in-place page updates cause random IO, page splits and double-write or WAL overhead, and per-commit fsync caps throughput unless heavily group-committed. TTL expiry becomes row-by-row deletes that bloat pages and require purge or vacuum. Synchronous replication across regions also contradicts the stated allowance for asynchronous inter-region replication and adds tens to hundreds of milliseconds to every write. Caveat: a strong choice for read-dominated, update-in-place OLTP with heavy range queries.

🧊

C — LSM Hot Tier + B-Tree/Columnar Cold Tier

A hybrid is a legitimate evolution, but it adds a second storage format, a conversion pipeline and a tiered read path (hot first, then cold) with consistency windows during migration, all of which add failure modes and operational load. The scenario asks only for infrequent range scans, so the benefit does not yet justify the complexity. Caveat: becomes attractive when historical data dominates storage cost or analytical scans become a first-class workload.

📜

D — Kafka Log + Separate Read Index

A log is great for durable ingest and replay, but it is not a point-lookup store, so every read depends on a second system that must be built, scaled and kept in sync. Synchronous index updates couple write latency to the index (and cap throughput), while asynchronous updates give up the read-after-write consistency the scenario asks for within a region. The index itself still has to be an LSM or B-tree, so the core engine decision is simply deferred. Caveat: a good complement when many downstream consumers need replayable streams.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — LSM + Regional Raft

Write-heavy, small-record workloads with mostly point reads, TTL and strong regional consistency, such as event stores, time-series, messaging and metadata services.

📌

B — B-Tree + Sync Replication

Read-dominated or update-in-place OLTP workloads with heavy range queries and moderate write rates (orders, accounts, inventory), where predictable read latency matters most.

📌

C — Hybrid LSM + Cold Tier

Data volumes where cold history dominates cost, or analytical scans become important, so a columnar or compact cold tier pays back its added complexity.

📌

D — Kafka + Read Index

Many downstream consumers need replayable, ordered event streams (stream processing, CDC, auditing) alongside, not instead of, an indexed serving store.

⚠️ Common Mistakes to Avoid

  • Ignoring write amplification: Leveled compaction on a firehose can saturate IO and burn through SSD endurance. Estimate bytes written to disk per user byte and size hardware accordingly.
  • Letting compaction debt build: When pending compaction exceeds the engine's limits, it throttles or stops writes. Alert on pending bytes and L0 file counts, and rate-limit compaction to protect reads.
  • Using row-level deletes for TTL: Tombstones slow reads and delay space reclamation. Use time-ordered keys with time-window or FIFO compaction, or a TTL filter, so whole files expire.
  • Under-sizing Bloom filters and caches: Point reads then touch many SSTables and spike p99. Provision about 10 bits per key and a block cache sized to the hot set.
  • Running two durable logs blindly: A Raft log plus an engine WAL doubles fsync cost. Decide which log is authoritative, group-commit, and test crash recovery.
  • Mixing analytics scans into the serving path: Large scans evict cache and compete with compaction. Offload them to a replica, a snapshot or a downstream columnar store.

🌍 Real-World Best Practice

Storage engine choice is driven by measured IO patterns, not preference. A typical sequence:

  • Step 0 — Characterize the workload: Measure event size, write rate per partition, key distribution (time-ordered vs. random), read/write ratio, TTL churn and scan frequency.
  • Step 1 — Choose the engine from the dominant IO pattern: Write-heavy with point reads and TTL points to an LSM; update-in-place with heavy scans points to a B-tree.
  • Step 2 — Pick compaction for the key shape: Universal or time-window compaction for time-ordered events with TTL; leveled for read-heavy, update-heavy data.
  • Step 3 — Replicate with the weakest guarantee that meets the SLA: Raft inside the region for strong consistency, asynchronous replication across regions with lag alerts.
  • Step 4 — Load-test the tail: Run sustained writes with TTL churn and watch p99 reads during compaction, write stalls and node recovery.
  • Step 5 — Add tiers only when data proves the need: Add a columnar or cold tier when scan demand or storage cost justifies it.

Choose the simplest engine that matches the dominant IO pattern, then instrument it heavily.

💡

Key Takeaway

For high-ingest, small-event, point-read workloads with TTL, choose an LSM-tree engine with regional Raft replication and tune compaction for the key shape. Accept the range-scan and write-amplification trade-offs, monitor compaction debt, and add a cold or columnar tier only when scan demand or storage cost justifies the extra complexity.
