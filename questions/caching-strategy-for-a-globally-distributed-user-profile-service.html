Caching Strategy for a Globally Distributed User-Profile Service

Aiden is designing caching for a globally distributed user-profile service that handles hundreds of millions of reads per day and must keep tail read latency below 50 ms in every region. Profile updates are infrequent, but they must reach most clients within seconds, and the UI sometimes needs the writer to see their own change immediately. Profile data is user-specific and partly private. The stack uses Redis for caching and a primary relational database as the source of truth. He must pick a design that balances consistency, latency, availability, scalability, and operational overhead.

A
Single global Redis primary in one region with cache-aside, routing all reads and writes to it for strict consistency and a single source of truth.
✗ Not Best
B
Regional Redis clusters with asynchronous primary-to-replica replication, reads served locally, no explicit invalidation, relying on async replication and TTL expiry for freshness.
✗ Not Best
C
Regional Redis caches with cache-aside plus an ordered change log: each database write publishes an event to a durable broker (e.g., Kafka), and regional services consume it to update or invalidate local entries, with short TTLs and versioned keys as a safety net.
✓ Best Answer
D
CDN edge cache with long TTLs for most profile reads, synchronously calling the CDN purge API on writes, with the origin database serving misses.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — C: Regional Caches Fed by an Ordered Change Log

The requirements pull in opposite directions: local reads under 50 ms everywhere and updates visible within seconds. The way to get both is to keep reads local and make freshness an explicit, event-driven pipeline: every committed write emits an ordered change event that each region applies to its own cache, while TTLs and versions bound the damage if an event is delayed or lost. Here's why it stands out:

  • Local reads, global freshness: Reads hit the regional cache in a few milliseconds, and the change log typically delivers invalidations or updates to all regions within sub-second to a few seconds, which meets the propagation target.
  • Explicit invalidation: Unlike TTL-only designs, staleness is bounded by event delivery time rather than by the TTL, and the TTL becomes just a backstop.
  • Ordering and safety: Events carry a monotonically increasing version (or commit position), and caches apply a change only if it is newer than what they hold, so out-of-order or duplicate events cannot roll data back.
  • Resilient and decoupled: A durable broker buffers events during regional outages and lets a region catch up by replaying from its offset, and a cache outage falls back to the database without blocking writes.
  • Scales independently: Each region scales its own cache and consumers, and the source database is not hit by cross-region cache traffic.

Use invalidate-on-event (or versioned update), short TTLs with jitter, a version check on every cache write, stampede protection on misses, and per-region lag alerts. For the writing user's next read, either update the local cache on write or carry a version token.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🌍

A — Single Global Redis Primary

A central primary gives one version of the truth, but every distant read pays a cross-region round trip (often 100 ms or more for far-apart regions), which breaks the 50 ms tail target. It is also a single point of failure and a throughput bottleneck for hundreds of millions of reads. Caveat: acceptable when users and services sit in one region or latency is not critical.

🔄

B — Regional Replicas with Async Replication and No Invalidation

Local replicas give fast reads, but this design has no mechanism to tell caches about database changes: freshness depends on replication and TTL expiry. Redis replication copies cache state and knows nothing about database writes, and a TTL long enough to be efficient is too long for seconds-level freshness. Cross-region replication links are also a source of lag and failure. Caveat: reasonable only if staleness of minutes is acceptable.

🛰️

D — CDN Edge Cache with Purge on Write

CDNs excel at public, cacheable content. Profiles are user-specific and partly private, which demands careful cache keys and auth handling at the edge. Purge APIs are rate-limited, eventually consistent across the network, and can fail, so the write path either blocks on a third party or leaves stale edges until the long TTL expires, violating seconds-level freshness for some users. Caveat: good for public profile fragments such as avatars or public pages, layered in front of option C.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Single Global Redis

Single-region deployments or low-traffic internal tools where simplicity matters more than latency.

📌

B — Regional Replicas, No Invalidation

Data where minutes of staleness are acceptable, such as rarely edited public attributes, and where operational simplicity matters most.

📌

C — Regional Caches + Change Log

Global read-heavy services with strict tail latency, seconds-level freshness, and a source-of-truth database, especially when a durable event backbone already exists.

📌

D — CDN with Purge

Public, widely shared content (avatars, public pages, static assets) where purge-on-change is acceptable and private data is excluded.

🧑‍💻 Version-Guarded Cache Update from the Change Log

Regional consumers apply change events idempotently and only when they carry a newer version, so duplicates or reordered events can never roll data back. The writer's own region also updates its cache on write:

⚠️ Common Mistakes to Avoid

  • Dual write without an outbox: Updating the database and publishing separately loses events on a crash. Use the outbox pattern or CDC.
  • Applying events without versions: Out-of-order or duplicate events overwrite newer data. Compare versions and apply only newer ones, atomically (for example with a Lua script or compare-and-set).
  • Delete-then-refill races: A reader can repopulate the cache with an old row right after an invalidation. Version checks, short TTLs, and leases mitigate this.
  • Invalidating without stampede protection: Many regions and requests miss at once and hit the database. Use single-flight and jittered TTLs.
  • Ignoring the writer's own next read: Users see their old profile for several seconds. Update the local cache on write or use a version token.
  • Not monitoring propagation lag: Silent consumer lag means stale data for hours. Alert on event lag per region and run periodic reconciliation.

🌍 Real-World Best Practice

Global systems treat cache freshness as a pipeline with measurable lag, not a hope. A typical rollout:

  • Step 0 — Set the SLOs: p99 read latency per region, a propagation target (for example 99% of updates visible within 5 seconds), and read-your-writes expectations.
  • Step 1 — Start with cache-aside per region: Regional Redis with TTL and jitter, plus stampede protection.
  • Step 2 — Add reliable change events: Outbox or CDC from the primary into a durable log, with a monotonic version per profile.
  • Step 3 — Apply events safely: Regional consumers apply or invalidate with version checks, idempotently, and report lag.
  • Step 4 — Handle the writer: Write through to the local cache or return version tokens so the UI reflects the change immediately.
  • Step 5 — Layer carefully: Add a CDN only for public, non-personalized assets, and rehearse region failure, event backlog, and a full cache flush.

Measure propagation lag end to end and alert on it like any other SLO.

💡

Key Takeaway

To get local-speed reads and seconds-level freshness across regions, keep caches regional and drive them from an ordered, durable change stream with versioned writes, using TTLs only as a safety net. Avoid designs that rely on TTL alone, on one central cache, or on a third-party purge in the write path.
