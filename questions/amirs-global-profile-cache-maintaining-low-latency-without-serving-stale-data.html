Challenge

Amir's global profile cache: maintaining low latency without serving stale data

Amir, a backend engineer at a globally distributed social app, serves extremely frequent profile reads (display names, bios, avatars, minor settings) with a P95 target of about 50 ms worldwide. Profile updates are rare (under 1% of read volume) but must propagate within seconds. Today every app server queries one Redis cluster in a primary region, which produces high latency for distant users and a large blast radius when that region has problems. He needs a caching architecture that keeps reads fast, survives regional outages and limits stale data after updates, without excessive operational complexity.

A
Keep the single global Redis cluster as the only primary with a cache-aside pattern: app servers worldwide read from and warm it, synchronously invalidate the key on update, and use a long TTL to reduce database load.
✗ Not Best
B
Move to a multi-master, write-through cache: on update, write synchronously to both the primary database and the cache layer, which handles its own cross-region replication, and serve all reads from the replicated cache to get strong consistency globally.
✗ Not Best
C
Add local caches in each region (regional Redis clusters or in-memory near-caches) using cache-aside for reads. On every profile update, publish an invalidation or update event to a reliable broker (Kafka or Redis Streams) that every region consumes to refresh or evict its keys, using versioned cache entries and a short TTL fallback to prevent prolonged stale reads.
✓ Best Answer
D
Put profile JSON responses behind a global CDN or edge cache with edge workers serving payloads directly, call the CDN purge API on updates, and rely on long TTLs and the CDN's built-in edge replication to cut origin load.

Answer & In-Depth Explanation

🏆 Best Answer — C: Regional Caches with Event-Driven Invalidation

Two problems must be solved at once: distance (reads must be served close to the user) and coherence (every regional copy must learn about a change quickly). Regional caches fix distance, and a reliable, ordered invalidation stream fixes coherence. Because updates are under 1% of reads, the stream is low-volume and cheap, while versioned entries and a short TTL make the design robust to lost, duplicated or reordered messages. Here's why it stands out:

  • Local reads meet the latency target: A hit in an in-process (L1) or regional Redis (L2) cache is typically sub-millisecond to a few milliseconds, leaving ample room under a 50 ms P95 even with a database fallback on a miss.
  • Smaller blast radius: Each region can keep serving cached profiles when the primary region or the broker is degraded, because reads no longer depend on a single remote cluster. Regional failures stay regional.
  • Bounded staleness by design: Events typically arrive in well under a second, so updates become visible within seconds. If an event is lost or delayed, the short TTL (for example 30 to 60 seconds) caps how long a stale copy can live.
  • Safe against reordering and duplicates: Entries carry a monotonically increasing version from the database row. Consumers apply an event only if it is newer than what the cache holds, so out-of-order or replayed events do no harm.
  • Cheap at this read/write ratio: With writes under 1% of reads, event volume is tiny compared with read traffic, so the pub/sub or stream cost is negligible next to the latency and resilience gains.

A robust implementation combines a transactional outbox, versioned entries, short TTLs with jitter, single-flight loading to avoid stampedes, and read-your-writes for the editor (update the local cache synchronously and return the version). Track invalidation lag (commit time to eviction time per region), hit rate, stale-read rate and consumer lag; if invalidation lag creeps toward the TTL, fix the pipeline before lengthening any TTL.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🌍

A — Single Global Redis (Cache-Aside)

This keeps the exact architecture that created the problem: every distant user still pays an intercontinental round trip on every read, the primary region remains a single point of failure with a large blast radius, and a long TTL directly lengthens how long stale data can persist if an invalidation is missed. It is simple, but it fails both the latency and the resilience goals. Caveat: fine for single-region products.

✍️

B — Multi-Master Write-Through

Writing synchronously to both the database and a cache is a dual-write: if one succeeds and the other fails, they diverge, and failures leave stale or missing entries. Cross-region cache replication (for example active-active Redis) is generally asynchronous, so the claim of 'strong consistency globally' does not hold, and concurrent updates in different regions need conflict resolution. It also makes writes wait on the slowest cache region. Caveat: write-through within a single region is a useful local optimization.

🛰️

D — Global CDN / Edge Cache

A CDN gives excellent global latency, but with long TTLs the staleness window is only as short as the purge is reliable: a missed or slow purge leaves stale profiles at the edge for the full TTL, and purge propagation times vary by provider. Profile data with per-user settings may also be private, which makes shared edge caching unsafe unless responses are carefully keyed and authorized. Caveat: an excellent complement for public, immutable assets such as content-addressed avatar images, with short TTLs for public profile fields.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Single Global Redis

Single-region or low-traffic applications where all users are near the cache and a regional outage is acceptable.

📌

B — Multi-Master Write-Through

A single region (or tightly clustered regions) where write-through simplifies local read-after-write, paired with a message-based fix for cross-region propagation.

📌

C — Regional Caches + Events

Read-heavy, rarely updated data served worldwide, with a seconds-level freshness target and resilience requirements per region.

📌

D — CDN with Purge

Public, cacheable content (static assets, content-addressed images, public profile fields) with short TTLs or immutable URLs.

⚠️ Common Mistakes to Avoid

  • Publishing events after commit without an outbox: A crash between commit and publish loses the invalidation. Use a transactional outbox or CDC so events are never lost.
  • Applying events without versions: Out-of-order or replayed events can overwrite newer data with older data. Compare versions and apply only newer ones.
  • Refilling from a lagging replica: An invalidated key refilled with an old row recreates the stale value. Enforce a minimum version on refill or read from the primary.
  • Synchronized TTLs and cold starts: Identical TTLs expire together and stampede the database. Add jitter and single-flight loading.
  • Treating TTL as the primary freshness mechanism: TTL is the backstop; the event stream provides freshness. Monitor invalidation lag.
  • Caching private fields in shared layers: Settings tied to a user must not be served from shared CDN or public caches without keying by identity.

🌍 Real-World Best Practice

Global caching is built in layers, and teams measure staleness explicitly. A typical sequence:

  • Step 0 — Define the staleness budget: Agree on how many seconds an update may take to appear, and which fields are public, private or user-specific.
  • Step 1 — Regional caches: Deploy cache-aside Redis in each region (plus a small in-process L1 with a very short TTL for the hottest keys).
  • Step 2 — Reliable invalidation: Emit events from a transactional outbox or CDC, publish them to a cross-region stream, and have each region consume and apply them by version.
  • Step 3 — Harden against edge cases: Add jittered TTLs, single-flight loading, refill-version checks and a read-your-writes path for the editor.
  • Step 4 — Offload assets to the edge: Serve avatars and other immutable assets from a CDN using content-addressed URLs that never need purging.
  • Step 5 — Measure and drill: Track invalidation lag, hit rate and stale-read rate, and test regional failover and broker outages.

Keep reads local, send small version-stamped events everywhere, and let short TTLs cover the gaps.

💡

Key Takeaway

Serve profiles from regional caches so reads are local, propagate changes through a reliable, versioned invalidation stream, and keep a short TTL as the safety net. This meets the latency target, limits the blast radius of any one region and bounds staleness to seconds, without the pitfalls of dual-writes or long-lived edge copies.
