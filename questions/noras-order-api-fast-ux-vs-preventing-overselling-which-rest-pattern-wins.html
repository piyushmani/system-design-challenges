Challenge

Nora's Order API: Fast UX vs. Preventing Overselling; Which REST Pattern Wins?

Nora is designing the public REST endpoint for order placement in a global e-commerce backend. Requirements: a perceived checkout response under 200 ms, 50,000 order requests per second at peak, no overselling (cancellations must be extremely rare), high availability across regions, and strong observability. Some eventual consistency is acceptable for downstream records, but customers need an immediate, reliable confirmation that their item is secured. She must choose the API and backend workflow that best balances latency, availability, and correctness.

A
Utilize a synchronous strong-consistency pathway: the API handler executes a transactional write directly to a single primary SQL database utilizing serializable isolation, reducing inventory within the same transaction. The request is blocked until the database commit is successful, at which point it returns the final order confirmation to the client.
✗ Not Best
B
Adopt a purely asynchronous accept-and-process model: the API validates the incoming request, immediately returns a 202 Accepted status after placing a job in a durable queue, and instructs the client to poll a /status endpoint (or subscribe to a push notification) for final confirmation once background workers have processed the order and adjusted the inventory.
✗ Not Best
C
Execute a fast atomic reservation in a distributed cache coupled with an asynchronous persistent commit: the API performs an atomic reservation using a rapid distributed cache (e.g., a Redis Lua script or Redis Streams decrement) to guarantee stock reservation, returning success swiftly. A background worker then processes a reliable queue to save the order in the database and handle any failures; reconciliation jobs and metrics guarantee both durability and visibility.
✓ Best Answer
D
Implement a write-ahead client-store paired with batch inventory adjustments: the API appends the order to a region-specific append-only store and immediately signals success. Inventory adjustments occur subsequently via periodic batch processes that resolve any conflicts; instances of overselling are managed through cancellation and compensation workflows following the batch runs.
✗ Not Best

Answer & In-Depth Explanation

🏆 Best Answer — C: Atomic Cache Reservation + Asynchronous Durable Commit

The requirement that separates good from bad here is subtle: customers need an immediate guarantee that stock is secured, yet the system must absorb 50k requests per second within 200 ms. The part that must be synchronous is only the reservation (the scarce-resource decision). Persisting the full order, payment, and downstream records can be asynchronous. An atomic check-and-decrement in a fast in-memory store makes that decision in about a millisecond without ever going below zero, and a reliable queue plus idempotent workers moves the order into the database afterwards. Here's why it stands out:

  • Correctness at the point that matters: A Redis Lua script (or equivalent atomic operation) checks stock and decrements in one indivisible step, executed serially per key. Two buyers can never both take the last unit, so overselling is prevented by construction, not by later cleanup.
  • Latency and throughput: The synchronous path is a single in-memory round trip, typically low single-digit milliseconds, well inside the 200 ms budget. Stock is sharded by SKU (and region), so 50k requests per second spreads across many shards.
  • Immediate, meaningful confirmation: The customer gets an order id with status RESERVED, which is a real promise backed by decremented stock. Final confirmation (payment, fulfillment) follows asynchronously.
  • Spike absorption and decoupling: The queue or stream smooths bursts so the database sees a steady write rate, and an outage of the database or downstream services delays persistence without rejecting customers.
  • Visibility and self-healing: Idempotency keys, a dead-letter queue, and a reconciliation job comparing cache counters with the database ledger make failures visible and repairable. Metrics on reservation rate, stream lag, release rate, and drift give operators early warning.

A robust implementation has an atomic reserve-and-enqueue script, idempotency keys on the API, an idempotent persistence worker (unique constraint on order id), time-boxed holds with automatic release, a dead-letter path, and continuous reconciliation between the cache and the database ledger.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🧱

A — Synchronous Serializable Write to One Primary

This is the most obviously correct design and the least scalable. Popular SKUs become hot rows where serializable transactions conflict and retry, one primary caps write throughput far below 50k per second at peak, and users in distant regions pay cross-region round trips, which threatens the 200 ms target. The primary is also a single point of failure for availability. Caveat: for modest volumes, or when correctness outweighs latency (for example a small, regional ticketing system), this is the simplest right answer.

📬

B — Pure Accept-and-Process (202 + Polling)

It is excellent at absorbing load, but it does not secure the item at accept time. The customer learns later whether stock existed, which means rejections or cancellations after the user believed the order was placed, directly contradicting the 'immediate and reliable confirmation' requirement. Polling or push adds UX complexity as well. Caveat: a good fit when stock is effectively unlimited or backorders are acceptable. Combined with a synchronous reservation step, it becomes option C.

🧾

D — Append-Only Store + Batch Inventory Adjustment

It is fast and available, but it accepts overselling by design: inventory is only reconciled in periodic batches, so under heavy demand many orders are confirmed against stock that does not exist. The compensation and cancellation workflows that follow harm customer trust and create support cost, which the requirements explicitly say must be rare. Caveat: acceptable where the cost of oversell is small or stock is replenishable (digital goods, made-to-order items).

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Serializable Write to Primary

Moderate traffic, a single region or close users, and correctness matters more than latency. The simplest option when scale does not demand more.

📌

B — 202 Accepted + Polling

Long-running or non-contended work where the client does not need an immediate decision, or stock is effectively unlimited.

📌

C — Atomic Cache Reservation + Async Commit

Scarce, contended inventory at high request rates where customers need an immediate guarantee. Requires careful durability, expiry, and reconciliation design.

📌

D — Append-Only + Batch Adjust

Oversell is cheap or impossible to matter (digital goods, backorders, made-to-order), and throughput and availability dominate.

⚠️ Common Mistakes to Avoid

  • Check-then-decrement as two calls: A read followed by a write races under concurrency. Use one atomic script or conditional operation.
  • Decrementing stock and enqueueing the order separately: A crash between the two loses an order or leaks stock. Do both in one atomic step, or use a transactional outbox.
  • No idempotency key: Client retries after a timeout create duplicate orders and double reservations. Return the original result for a repeated key.
  • Holds that never expire or release twice: Leaked holds make items look sold out, and double releases make stock appear. Use TTLs and a release ledger that makes release idempotent.
  • Treating the cache as the source of truth: Redis failover can lose data. Keep a durable ledger in the database and reconcile continuously.
  • One global counter for a global catalog: Cross-region synchronization brings back the latency you tried to avoid. Partition stock by region and rebalance.

🌍 Real-World Best Practice

Large retailers treat inventory as a contended, partitioned resource and separate the cheap decision (reserve) from the expensive work (commit). A typical design evolves like this:

  • Step 0 — Classify SKUs: Most SKUs have plenty of stock and low contention. A small set of hot, scarce SKUs needs the strictest handling, so spend complexity there.
  • Step 1 — Reserve atomically: Atomic check-and-decrement with an idempotency key, sharded by SKU and region, with the order intent written in the same operation.
  • Step 2 — Persist reliably: A consumer group writes the order and a stock-ledger entry to the database idempotently, then acknowledges. Failures retry, then dead-letter.
  • Step 3 — Hold, then finalize or release: Payment authorization runs after reservation. On success the hold becomes a sale, on failure or timeout the stock is released exactly once.
  • Step 4 — Allocate across regions: Give each region a stock quota and rebalance asynchronously, so reservations stay local and available during regional failures.
  • Step 5 — Reconcile and observe: Compare cache counters with the ledger continuously, alert on drift, and track reservation latency, stream lag, and release rates.

The database remains the source of truth for money and history, while the fast store owns only the short-lived reservation decision.

💡

Key Takeaway

Make only the scarce-resource decision synchronous and atomic, and push everything else behind a durable queue. An atomic cache reservation gives fast, honest confirmations and prevents overselling, while idempotent workers, expiring holds, and reconciliation cover durability. Be explicit about the durability limits of your reservation store and choose a stronger one for the scarcest inventory.
