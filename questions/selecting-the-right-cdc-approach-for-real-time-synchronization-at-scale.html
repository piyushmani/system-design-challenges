Challenge

Selecting the right CDC approach for real-time synchronization at scale

Alex, a senior engineer, must distribute every modification from a busy OLTP PostgreSQL database to several downstream consumers: a search index, a real-time analytics stream, a cache-invalidation service, and numerous microservices. The pipeline needs sub-second end-to-end latency, tens of thousands of operations per second, fault tolerance with recovery, ordered updates per entity, and the ability to handle schema changes. He must choose a Change Data Capture strategy that balances scalability, availability, latency, consistency, operational overhead, and observability. What is the most appropriate approach?

Answer & In-Depth Explanation

🏆 Best Answer — A: Log-Based CDC with a Partitioned Streaming Platform

Log-based CDC reads PostgreSQL's write-ahead log (WAL) through a logical replication slot, so it sees every committed change, whether it came from the application, a batch job, a migration, or ad-hoc SQL, without adding queries or extra writes to the OLTP path. Publishing those changes to a partitioned log such as Kafka, keyed by the entity's primary key, gives per-entity ordering, durable replay, and independent consumer groups for the search index, analytics, cache, and microservices. Here's why it stands out:

  • Complete, commit-ordered capture: The WAL is the database's own record of committed changes, so inserts, updates and deletes are captured in commit order with no triggers, no polling queries, and no application changes. Nothing that bypasses the application layer is missed.
  • Low latency, low source overhead: Changes are decoded from the log stream rather than queried, so they typically reach Kafka in tens to a few hundred milliseconds without extra write amplification on the OLTP path. That fits comfortably inside a sub-second budget.
  • Per-entity ordering that scales: Events keyed by primary key land in one partition and stay ordered, while partitions let consumers scale horizontally. Each downstream system has its own consumer group and offsets, so a slow search indexer never blocks cache invalidation.
  • Built-in recovery and replay: The replication slot retains unconfirmed WAL, the connector resumes from its last confirmed LSN after a crash (at-least-once), and Kafka retention lets new consumers or rebuilt indexes replay history. The connector also manages the initial snapshot-then-stream handover.
  • Schema evolution and observability: Change events carry schemas registered in a schema registry with compatibility rules (BACKWARD or FULL), so additive DDL does not break consumers. Connector lag, slot lag in bytes (pg_replication_slots), consumer-group lag, and dead-letter counts give end-to-end visibility.

A production-grade setup pairs log-based CDC with a schema registry and compatibility policy, idempotent consumers that use the source LSN as a version, dead-letter handling, and replay tooling. Track commit-to-sink latency, retained WAL per slot, consumer lag, and DLQ rate, and rehearse a failover and a full replay before go-live.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

📤

B — Transactional Outbox

The outbox is an excellent pattern: it solves the dual-write problem by committing the event with the state change. But as the primary strategy here it falls short. It only captures what the application chooses to write, so batch jobs, admin SQL and other writers bypass it, and every writer needs code changes. It adds write amplification, storage and cleanup to an already busy OLTP database, and a polling reader that scans by auto-increment id can skip rows that commit out of order. Caveat: when consumers need curated domain events (such as OrderPlaced) rather than raw row changes, an outbox read through CDC is the right tool, and it composes with option A.

🔗

C — Synchronous Dual-Write Before Commit

Calling downstream systems inside the transaction is not atomic. If a call succeeds but the commit fails, consumers see phantom events; if the commit succeeds but a call fails, events are lost. It also couples OLTP latency and availability to every downstream system (availability multiplies across four or more dependencies) and holds locks and connections open during network calls. Strict cross-service consistency cannot be achieved this way without distributed transactions, so this is an anti-pattern for the stated requirements.

📸

D — Snapshot and Diff

Periodic snapshot comparison puts heavy read load on the OLTP database, and its cost scales with table size rather than change rate. Latency is bounded below by the interval plus diff time (seconds at best), intermediate states are lost (A to B to C between snapshots looks like A to C), and detecting deletes requires full comparison. It cannot meet sub-second latency at tens of thousands of operations per second. It is fine for low-volume, non-critical sync or as a periodic reconciliation audit.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Log-Based CDC + Streaming

Many downstream consumers need every committed change with low latency, per-entity ordering, replay, and schema-evolution support, and you can operate Kafka and Kafka Connect (or use a managed equivalent).

📌

B — Transactional Outbox

Services must publish curated domain events (OrderPlaced, PaymentCaptured) atomically with state changes, and every write path goes through application code you control. Most powerful when the outbox is read via CDC.

📌

C — Synchronous Dual-Write

Rarely appropriate. Only for a single, highly reliable downstream where you explicitly accept coupled latency and the possibility of inconsistency, and where an outbox or CDC is not yet available.

📌

D — Snapshot and Diff

Small or slow-changing datasets, batch-oriented consumers that tolerate minutes of delay, or periodic reconciliation to verify that a streaming pipeline has not drifted.

⚠️ Common Mistakes to Avoid

  • Ignoring replication slot lag: A stalled connector makes PostgreSQL retain WAL until the disk fills and takes the primary down. Cap retention with max_slot_wal_keep_size, alert early, and have a drop-and-resnapshot runbook.
  • Assuming exactly-once delivery: Restarts and rebalances replay events. Consumers that increment counters or append blindly will double-apply. Use idempotent upserts with an external version such as the LSN.
  • Expecting global ordering: Ordering holds per partition key only. Cross-table or cross-entity invariants need transaction metadata or consumers that tolerate interleaving.
  • Publishing raw table changes as a public contract: Every internal column rename becomes a breaking change for consumers. Put an outbox or a mapping layer in front of anything that crosses a team boundary.
  • Forgetting REPLICA IDENTITY and TOAST behavior: Updates and deletes on tables without a primary key, or without FULL identity when before-images are needed, produce incomplete events. Unchanged large TOAST columns arrive as placeholders and must not overwrite the sink.
  • Skipping failover and snapshot rehearsals: On PostgreSQL versions before 17, a failover can lose the logical slot, and re-snapshotting a huge table under load is slow. Practice both before an incident forces you to.

🌍 Real-World Best Practice

In practice, teams treat CDC as a platform and combine patterns rather than choosing one dogmatically. A typical rollout looks like this:

  • Step 0 — Check prerequisites: Set wal_level=logical, size max_replication_slots, make sure every table has a primary key, choose REPLICA IDENTITY (FULL only where consumers need before-images), and size WAL disk for the worst-case connector outage.
  • Step 1 — Stand up Debezium on Kafka Connect: Run the initial snapshot then stream, key events by primary key, serialize with Avro or Protobuf against a schema registry, and enable heartbeats.
  • Step 2 — Build idempotent, independently scaled consumers: One consumer group per downstream system, the source LSN (or a row version) as the external version in each sink, offsets committed only after the sink acknowledges, and a dead-letter topic with replay tooling.
  • Step 3 — Harden failure modes: Alert on slot lag and retained WAL, connector status, and consumer lag. Write a failover runbook (slot synchronization on PostgreSQL 17+, or re-snapshot) and load-test backpressure.
  • Step 4 — Add an outbox for business events: Where services need stable domain events instead of table-shaped changes, add an outbox table and Debezium's outbox event router so contracts stay decoupled from internal schema.
  • Step 5 — Evolve schemas safely: Use expand/contract migrations, additive changes first, tolerant-reader consumers, and compatibility checks in CI.

Use CDC to distribute data and an outbox to publish domain contracts; they complement each other.

💡

Key Takeaway

When many downstream systems need every committed change, ordered per entity, with low latency and replay, read the database's own commit log and publish it to a partitioned, durable stream. Log-based CDC removes dual writes and polling, but it demands idempotent consumers, replication-slot monitoring, and a schema-compatibility policy.
