Nina Selecting a Scalable Token Strategy: Evaluating the Trade-offs

Nina, a platform architect at a SaaS provider, runs a public API behind regional gateways in three regions that handles about 5 million requests per minute (roughly 83,000 per second). Today it uses self-contained JWT access tokens with long-lived refresh tokens. After a breach involving compromised refresh tokens and a new 99.99% availability target, she must redesign the token architecture. The constraints are minimal per-request latency at the gateway, fast invalidation of compromised sessions, no global single point of failure, and manageable operating cost.

A
Keep signed, self-contained JWT access tokens with a short lifetime (5–15 minutes); extend sessions with rotating refresh tokens held server-side in a highly scalable store and invalidated if compromised; verify only signature and expiry at the gateway; keep a central revocation list only for refresh tokens and specifically flagged high-risk sessions.
✓ Best Answer
B
Switch to opaque access tokens stored in a central, strongly consistent database, with synchronous validation against it on every API request (and short-term caching of results) for definitive revocation.
✗ Not Best
C
Keep JWTs but add a session_id claim, and have the gateway look it up in a globally replicated, strongly consistent session database on every request, treating that store as the final authority.
✗ Not Best
D
Keep long-lived JWTs and add asynchronous revocation: broadcast revocations through a global pub/sub to update regional in-memory caches, relying on token expiry and periodic syncs when a revocation is delayed.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — A: Short-Lived JWTs + Rotating Refresh Tokens

The constraints push toward keeping the hot path stateless and moving statefulness to the cold path. Short-lived, signed JWTs let every gateway authorize requests locally with no network call, which protects latency and availability at roughly 83,000 requests per second. Control over sessions is then exercised at the refresh step, where state is cheap because it happens once per token lifetime rather than once per request, using rotating, server-side refresh tokens with reuse detection. Here's why it stands out:

  • Zero network calls per request: The gateway verifies signature, expiry, issuer and audience against cached public keys (JWKS). Latency is microseconds of CPU, there is no per-request dependency, and an outage of the auth service does not stop already-authenticated traffic.
  • Bounded blast radius: A stolen access token is useful for at most its lifetime (5–15 minutes). A stolen refresh token is caught by rotation with reuse detection: if an old refresh token appears again, the whole token family is revoked and the user must re-authenticate.
  • State only where it is cheap: Refresh traffic is a tiny fraction of API traffic (one refresh per token lifetime versus thousands of requests), so a multi-region, highly available store can hold refresh-token state without becoming a bottleneck or a global single point of failure.
  • Targeted fast revocation: For confirmed compromises, push the session ID to a small deny-list at the gateways. Entries only need to live for the remaining access-token lifetime, so the list stays tiny, and if a push is missed the worst case is still bounded by token expiry.
  • Aligned with current guidance: The OAuth 2.0 security best current practice (RFC 9700) recommends short-lived access tokens and either sender-constrained refresh tokens or rotation with reuse detection.

A well-designed token system includes short access-token TTLs, refresh-token rotation with family revocation, sender-constraining (DPoP or mutual TLS) where feasible, a tiny TTL-bounded deny-list for incident response, and asymmetric key rotation. Track refresh-reuse detections, validation failures, JWKS cache age and time-to-revoke in drills; if time-to-revoke exceeds your policy, shorten the TTL rather than adding per-request lookups.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🗄️

B — Opaque Tokens + Central Validation

Opaque tokens give definitive, instant revocation, but every request now depends on a central database. At roughly 83,000 requests per second the lookup latency and the cost of a strongly consistent store are significant, and the store becomes a global single point of failure for all API traffic, which contradicts the 99.99% and no-SPOF goals. Caching validation results brings back a revocation delay equal to the cache TTL, which undermines the reason for choosing opaque tokens. Caveat: opaque tokens with introspection suit lower-volume APIs, or privileged tokens (such as admin consoles) where instant revocation is mandatory.

🌐

C — JWT + Global Session Lookup

This pays for a per-request lookup and keeps JWTs, and it puts a strongly consistent, globally replicated store on the hot path, which means cross-region quorum latency or CAP-style availability trade-offs on every call. The session store becomes the final authority, so it is again a global dependency for every request. Caveat: reasonable for a small set of high-risk operations (changing payout details, for example) where a step-up session check on those routes alone is affordable.

📡

D — Long-Lived JWTs + Async Revocation

Revocation here is best-effort: pub/sub delivery can be delayed or lost, a gateway that restarts or is partitioned loses its in-memory list, and the fallback is the token's expiry, which is long by design. A stolen long-lived token stays valid for hours or days wherever the message did not arrive, and the cache must remember every revocation for the full token lifetime. Caveat: pub/sub revocation is a good complement to short-lived tokens (it is the deny-list in option A), but not a substitute for them.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Short JWT + Rotating Refresh

High-volume public APIs across regions that need low latency, high availability and bounded exposure. The default for most large-scale SaaS APIs.

📌

B — Opaque + Central Validation

Lower-volume or high-sensitivity APIs where instant, definitive revocation matters more than latency and availability, such as admin consoles, usually with a local introspection cache.

📌

C — JWT + Global Session Lookup

Selected high-risk routes (payouts, credential changes) that deserve a step-up session check, in addition to stateless validation everywhere else.

📌

D — Long JWT + Async Revocation

As a complement to short-lived tokens for faster incident response (the deny-list in option A), not as a replacement for short expiry.

⚠️ Common Mistakes to Avoid

  • Long-lived access tokens: Lifetimes of hours or days turn every theft into a long-running incident and make revocation unreliable. Keep them to minutes.
  • Refresh tokens without rotation or reuse detection: A stolen refresh token can be replayed silently for months. Use one-time-use rotation with family revocation, plus absolute and idle lifetimes.
  • Storing refresh tokens in plain text: Store only a hash (as you would for a password), so a database leak does not hand out working tokens.
  • Weak JWT validation: Accepting alg: none, skipping aud or iss checks, or letting the token choose its own key. Pin algorithms and validate every standard claim.
  • Mishandling rotation races: Mobile retries and parallel tabs produce legitimate reuse. Use a brief grace window and scope the response to the family.
  • Unbounded deny-lists: Entries that never expire grow forever. Expire each entry after the maximum access-token lifetime.

🌍 Real-World Best Practice

In practice, token architecture is about choosing where state lives. A typical sequence looks like this:

  • Step 0 — Define the threat and the SLO: Decide the maximum acceptable exposure after a compromise (for example 5 minutes for access tokens, immediate for refresh tokens) and the availability budget for authentication.
  • Step 1 — Shorten and sign: Issue short-lived access tokens (5–15 minutes) with asymmetric keys, kid rotation and a cached JWKS at every gateway.
  • Step 2 — Rotate refresh tokens: Use one-time-use refresh tokens stored hashed, grouped into families with reuse detection, and enforce absolute and idle session lifetimes server-side.
  • Step 3 — Sender-constrain where possible: Bind tokens to the client with DPoP or mutual TLS so a stolen token is unusable elsewhere.
  • Step 4 — Add an incident deny-list: Distribute a small list of revoked session IDs to the gateways by push, with entries expiring after the maximum access-token lifetime. Fail toward token expiry, not toward an outage.
  • Step 5 — Drill and monitor: Measure time-to-revoke in game days, and alert on refresh-token reuse, auth latency and JWKS cache age.

Keep the per-request path stateless, and spend state on the rare refresh path.

💡

Key Takeaway

Make requests stateless and sessions stateful. Short-lived signed JWTs keep the gateway fast and independent, while rotating refresh tokens with reuse detection, sender-constraining and a tiny deny-list give you control where it is cheap. If instant revocation is needed for a few high-risk actions, add targeted checks on those routes rather than on every request.
