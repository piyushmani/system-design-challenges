Index-Only Scans Read Performance Write Impact
Challenge

Can we achieve true index-only reads without compromising write performance?

Maya, a senior backend developer on a payment analytics team, runs a PostgreSQL OLTP database holding hundreds of millions of transaction rows. A low-latency API returns the 50 most recent transactions per customer (transaction_id, created_at, amount_cents, status). The existing index on (customer_id, created_at DESC) locates the rows quickly, but every row still triggers a heap fetch for amount_cents and status, causing random I/O and p95 latency spikes. She needs these reads to run as index-only scans while keeping strong consistency, manageable write overhead, and simple observability.

A
Add a covering index with amount_cents and status so all required columns are in the index (e.g., CREATE INDEX ... ON transactions(customer_id, created_at DESC) INCLUDE (amount_cents, status)). Track index size and write latency, adjust the fillfactor, and implement monitoring for index bloat and write amplification.
✓ Best Answer
B
Apply denormalization by duplicating amount_cents and status into a specialized, lightweight 'recent_transactions' table, kept in sync within the same transaction so reads target a slim table. This duplicates data but preserves strong consistency through transactional updates.
✗ Not Best
C
Direct these API calls to an asynchronous read replica or a distinct read-optimized OLAP database capable of different indexing or columnar storage. This accepts eventual consistency in exchange for reduced read latency and easier maintenance of large indexes on the replica.
✗ Not Best
D
Construct a materialized view holding the latest N transactions per customer, refreshing it synchronously with triggers or on a periodic basis. This speeds up reads but complicates writes, introducing either latency (for synchronous updates) or staleness (for asynchronous updates).
✗ Not Best

Answer & In-Depth Explanation

🏆 Best Answer — A: Covering Index (INCLUDE)

The problem is precisely a heap-fetch problem: the index already finds the right rows in the right order, and the only missing piece is the payload columns. A covering index (INCLUDE columns, PostgreSQL 11+) puts those columns in the index leaf pages, so the planner can choose an Index Only Scan and skip the heap entirely. It is the smallest change that fixes the stated bottleneck while keeping everything inside one MVCC engine, which is why it is the strongest answer here:

  • Removes the actual bottleneck: The 50 rows for one customer sit contiguously in the index, so the read becomes one sequential index range read instead of up to 50 random heap page reads. This is what flattens the p95 tail.
  • Strong consistency for free: The index is maintained inside the same transaction and MVCC rules as the table. There is no second copy to reconcile, no lag, and no trigger or pipeline to fail.
  • Smallest, safest change: One DDL statement (CREATE INDEX CONCURRENTLY), no application changes, no dual writes. If it does not help, DROP INDEX CONCURRENTLY reverts it.
  • Bounded and visible write cost: Each insert adds one wider index entry. The cost shows up directly in pg_stat_user_indexes, index size, WAL volume, and write latency, so it is easy to observe and budget.
  • Why INCLUDE and not a wider key: Non-key columns are stored only in leaf pages, not in internal pages, and do not affect ordering or uniqueness. The index tree stays shallower and smaller than (customer_id, created_at, amount_cents, status) would be.

Ship it with CREATE INDEX CONCURRENTLY, drop the old narrower index once the plan is verified (its key is a prefix of the new one, so keeping both just doubles write cost), tune autovacuum so the visibility map keeps pace, and alert on Heap Fetches, index size, and p95 write latency. If Heap Fetches stays high after vacuum tuning, revisit the design before reaching for a second data store.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🗂️

B — Slim recent_transactions Table

Same-transaction duplication does keep reads strongly consistent, but it is a hand-built covering index with extra steps. You still need an index on the slim table, you double every insert and update, and you must write and operate the logic that prunes each customer down to the latest N rows. The slim table also needs its own vacuum and visibility-map health to get true index-only reads. Caveat: it becomes reasonable when you must cap rows per customer or the base table has a very wide row that makes even index entries impractical.

🪞

C — Async Replica / OLAP Store

This gives up strong consistency, which the scenario explicitly requires: a customer who just paid would not see the payment. It also does not remove the underlying problem. A physical replica needs the same covering index (indexes are replicated, not independent), and index-only scans on a standby still depend on the primary's visibility map. Moving to an OLAP or columnar store adds an ETL pipeline and a new failure domain for a point-lookup workload that columnar engines are not built for.

🧱

D — Materialized View of Latest N

PostgreSQL materialized views have no incremental refresh: REFRESH MATERIALIZED VIEW recomputes the whole query, which is untenable at this table size. Maintaining 'latest N per customer' with triggers is custom code on the hottest write path, adds latency to every insert, and is easy to get wrong under concurrency. Periodic refresh means stale reads, which violates the consistency requirement.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Covering Index

A well-defined, stable query shape where the index already finds rows efficiently and the only cost is the heap fetch, with strong consistency required and mostly append-only data.

📌

B — Slim Table

You need to cap rows per entity (latest N only), the base rows are very wide, or the hot subset is tiny relative to the full table and worth isolating physically.

📌

C — Async Replica / OLAP Store

Analytical, dashboard, or reporting reads that tolerate staleness and need columnar scans or different indexing, not user-facing read-your-writes API calls.

📌

D — Materialized View

Expensive aggregate or join results that are acceptable to refresh periodically, on data sets small enough that a full refresh is cheap.

⚠️ Common Mistakes to Avoid

  • Forgetting a selected column: Leaving transaction_id (or any selected column) out of the index silently keeps the heap fetch. Compare the SELECT list against key plus INCLUDE columns.
  • Putting payload columns in the key: (customer_id, created_at, amount_cents, status) bloats internal pages and ties the sort order to columns that should not influence it. Use INCLUDE for payload.
  • Ignoring the visibility map: A new index that still shows large Heap Fetches usually means autovacuum is not keeping up on the freshest pages. Check EXPLAIN (ANALYZE, BUFFERS), not just the plan node name.
  • Not accounting for HOT updates: Including a frequently updated column quietly turns cheap in-page updates into heap plus index writes. Measure n_tup_hot_upd before and after.
  • Building the index without CONCURRENTLY: A plain CREATE INDEX blocks writes for the whole build on a huge table.
  • Keeping the old redundant index: The old (customer_id, created_at DESC) index is now a prefix of the new one. Keeping both doubles the maintenance cost for no benefit.

🌍 Real-World Best Practice

A principal-level rollout treats this as a measured experiment, not a DDL one-liner:

  • Step 0 — Confirm the diagnosis: Run EXPLAIN (ANALYZE, BUFFERS) on the real query. Confirm an Index Scan with many heap buffer reads for the top-50, and capture the baseline p95.
  • Step 1 — Build the covering index: CREATE INDEX CONCURRENTLY ... INCLUDE (transaction_id, amount_cents, status) in a low-traffic window, watching replication lag and I/O during the build.
  • Step 2 — Tune vacuum: Lower autovacuum_vacuum_scale_factor and autovacuum_vacuum_insert_scale_factor (PG 13+) for this table so recent pages get marked all-visible quickly.
  • Step 3 — Verify and drop the old index: Confirm Index Only Scan with near-zero Heap Fetches, compare p95 and write latency, then drop the redundant narrower index.
  • Step 4 — Monitor continuously: Track index size, n_tup_hot_upd ratio, dead tuples, WAL rate, and Heap Fetches per query via pg_stat_statements and pg_stat_user_*.
  • Step 5 — Scale the table structure only if needed: If vacuum and index size become unmanageable, partition by time so old partitions become all-visible and static, keeping the hot partition small.

Fix the heap fetch with the least machinery first, and add pipelines only when measurements prove the single-node design is exhausted.

💡

Key Takeaway

When the index already finds the right rows and the cost is the heap fetch, the right fix is to make the index cover the query, not to copy data elsewhere. Include every selected column (including transaction_id), keep the visibility map healthy with autovacuum tuning, and watch write amplification if the included columns change often.
