Diego's quorum decision: keeping user profiles fresh and fast

Diego, a backend architect, is building a global user-profile service used by millions. Profiles are small (a few KB), and reads outnumber writes about 100 to 1. Requirements: users must see their own updates immediately (read-after-write), global read latency should stay under 50 ms, the system must survive the loss of an entire region, and operational overhead should stay manageable. Using quorum-based replication across regions, he must choose the approach that best balances consistency, latency, availability and cost.

A
Place 3 replicas in different regions and require a majority quorum for both reads and writes (N=3, W=2, R=2), guaranteeing every successful read sees the latest write at the cost of the higher latency of querying two replicas.
✗ Not Best
B
Deploy 5 replicas globally (N=5) with majority-quorum writes (W=3) but single-node reads (R=1) from the nearest replica, relying on background anti-entropy and read repair to limit staleness while keeping read latency minimal.
✗ Not Best
C
Use leader-based replication per partition (Raft-style): writes commit on majority acknowledgment, the leader serves linearizable reads via leases or read-index so local reads are very fast, followers may optionally serve stale reads, a majority vote elects a new leader after failure, and replicas are placed across regions to tolerate the loss of a single region.
✓ Best Answer
D
Use fully asynchronous replication with CRDTs and W=1, R=1, relying on conflict-free merges for maximum availability and lowest latency, avoiding majority quorums in favor of eventual convergence.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — C: Leader-Based Consensus with Fast Local Reads

Diego's requirements are really three different guarantees: safe, ordered writes (rare, so they can afford a cross-region quorum), fresh reads for the writing user (read-your-writes, not global linearizability for everyone) and fast reads for everyone (the 100x majority). A leader-based consensus group handles the first cleanly, and its leases, read-index and follower-read mechanisms provide the other two without paying a cross-region round trip on every read. Because a profile belongs to a single user, leaders can be homed in the user's nearest region, which makes both writes and linearizable reads local for most traffic. Here's why it stands out:

  • Write safety with region-loss tolerance: A write commits on a majority of replicas spread over at least 3 regions, so losing a whole region still leaves a majority, and a new leader is elected automatically without data loss or split-brain.
  • Reads are cheap where it counts: The leader (or leaseholder) can answer linearizable reads from local state without contacting other replicas (leases) or after one lightweight heartbeat check (read-index). With the leader placed near the user's home region, reads stay well under 50 ms.
  • Read-your-writes is explicit rather than probabilistic: The write returns a commit index or timestamp. A later read from a nearby follower is served only if that follower has applied at least that index; otherwise it waits briefly or forwards to the leader. Compare this with R=1 quorums, where freshness is hope, not a guarantee.
  • Tunable staleness for the 100x majority: Reads of other users' profiles can use follower or non-voting replicas in any region with bounded staleness, delivering local latency with no effect on write quorums.
  • Lower operational risk than hand-rolled quorums: Consensus libraries and databases (etcd, CockroachDB, Spanner, TiKV and similar) already implement election, log repair, membership change and snapshotting, so the team does not maintain read-repair or anti-entropy for correctness.

A practical configuration is 3 or 5 voting replicas across at least 3 regions, per-partition leaders homed near each user group, non-voting learner replicas in additional regions for local follower reads, and a session token (commit index or timestamp) that the client sends on subsequent reads. Monitor commit latency, leader distribution, follower apply lag and the fraction of reads that fall back to the leader; if too many fall back, add learners or re-home leaders.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🗳️

A — Majority Quorum Reads and Writes (N=3, W=2, R=2)

R + W > N does guarantee that a read overlaps the latest successful write, and losing one region still leaves two replicas, so correctness is fine. The problem is latency: every read must wait for the second-fastest replica, which is usually in another region, and inter-region round trips commonly exceed 50 ms for distant pairs. That penalizes the 100x read majority to protect the rare write. Overlap also does not equal linearizability in leaderless systems (concurrent writes, sloppy quorums, partial failures). Caveat: acceptable if all three regions are close together or if reads are rare.

⚡

B — Write Quorum 3 of 5, Read One (W=3, R=1)

With N=5, W=3 and R=1, R + W = 4, which does not exceed N, so a read can hit a replica that missed the latest write. Anti-entropy and read repair only reduce staleness over time; they do not provide the immediate read-after-write the requirement states. It trades the one hard consistency requirement for latency. Caveat: a fine setup where bounded staleness is acceptable, or when combined with session tokens that route a user's reads to a fresh replica.

🌱

D — Async CRDTs (W=1, R=1)

CRDTs give excellent availability and converge without coordination, but with W=1 and R=1 a user who writes in one region and reads from another can miss their own update until replication catches up, which violates the stated read-after-write need. Many profile fields (display name, bio) are last-writer-wins registers rather than natural CRDT merges, so concurrent edits can silently drop data. Caveat: excellent for commutative data (counters, sets, presence) and collaborative editing.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — N=3, W=2, R=2

Small clusters where replicas are close together (same continent or metro), reads are not the dominant cost, and the simplicity of a leaderless quorum is attractive.

📌

B — N=5, W=3, R=1

Workloads that tolerate bounded staleness (feeds, counters, recommendations), or setups that pair R=1 with session routing so a user's reads hit an up-to-date replica.

📌

C — Leader-Based Consensus

Globally distributed, read-heavy data with per-user ownership, a read-your-writes requirement, strict latency targets and a need for automatic regional failover.

📌

D — Async CRDTs

Commutative, collaboration-style data (counters, sets, presence, collaborative text) where concurrent updates must always merge and availability beats immediate freshness.

⚠️ Common Mistakes to Avoid

  • Assuming R + W > N means linearizable: It guarantees overlap, not a single global order. Concurrent writes, sloppy quorums and clock-based conflict resolution can still return surprising results.
  • Ignoring physical latency: A quorum across continents costs a real round trip. Compute commit and read latency from actual inter-region RTTs before choosing N, W and R.
  • Using R=1 and expecting freshness: Read repair and anti-entropy converge eventually; they do not give read-after-write. Use session tokens or quorum reads for the writing user.
  • Poor region placement: Placing replicas so that one region holds a majority makes that region a single point of failure. Spread voters so no single region holds a majority.
  • Forcing every read to be linearizable: The 100:1 read majority rarely needs it. Serve bounded-stale follower reads and reserve strong reads for the writing user.
  • Not monitoring lag and fallbacks: Follower apply lag and the share of reads that fall back to the leader reveal when placement or capacity is wrong.

🌍 Real-World Best Practice

In production, teams match the consistency level to the access pattern instead of applying one setting to everything. A typical sequence:

  • Step 0 — Classify reads: Separate 'read my own writes' (must be fresh) from 'read someone else's profile' (staleness-tolerant).
  • Step 1 — Establish a consensus core: Use 3 or 5 voting replicas across 3+ regions so a region failure keeps a majority, and home leaders near users.
  • Step 2 — Add local read capacity: Place non-voting learners in extra regions and serve bounded-stale follower reads for the majority of traffic.
  • Step 3 — Provide read-your-writes tokens: Return a commit index or timestamp on writes; route follow-up reads accordingly or pin the user to their home region for a short window.
  • Step 4 — Cache in front: Layer a regional cache with short TTL and version-based invalidation for the hottest profiles.
  • Step 5 — Rehearse failure: Test region loss, leader failover time and replica catch-up, and watch p99 read and write latency.

Pay for strong consistency only where users can notice it.

💡

Key Takeaway

Use leader-based consensus with replicas spread over at least three regions for safe writes and region-failure tolerance, then deliver speed with leader leases, follower reads and read-your-writes tokens. Raw R=1 quorums and async CRDTs sacrifice the read-after-write requirement, while R=2 across regions sacrifices the 50 ms read target.
