Challenge

Preventing Duplicate Charges in a Globally Distributed Payment API

Maya is building a payment API used by mobile apps worldwide. Because of unstable networks and timeouts, clients frequently retry POST /charge. The design must prevent duplicate charges, keep latency low in every region, scale to thousands of requests per second, stay resilient during partial network partitions, and give clear observability into retries and failures. She must choose the idempotency strategy that best balances availability, latency, consistency and operational overhead.

A
Centralize all idempotency checks in a single global relational database. Maintain a table with a unique constraint on the combination of customer_id and idempotency_key. For each request, open a transaction to check or insert the key, either returning the previous result or processing the charge, relying entirely on the database for strict consistency.
✗ Not Best
B
Require clients to provide idempotency keys and store them in a partitioned, persistent key-value store (such as region-local DynamoDB, Redis, or Cassandra). Use atomic conditional writes (like PutIfAbsent) to register an 'in-progress' state or the final outcome. For duplicate requests, return the cached result, utilizing TTLs for cleanup and region-based routing to keep latency low.
✓ Best Answer
C
Guarantee global exactly-once processing by directing all charge requests through a consensus protocol layer (like Paxos or Raft) to establish a single authoritative sequence. Each request is added to a log and executed strictly in order, with replicas following the sequence to ensure uniqueness.
✗ Not Best
D
Design the API to be synchronous only up to the point of queuing: acknowledge requests immediately while placing messages into a persistent, at-least-once message broker. Asynchronous consumers then deduplicate requests by validating business state and process charges, issuing refunds or reconciling accounts if duplicates are identified post-processing, thereby keeping the user-facing API highly responsive.

Answer & In-Depth Explanation

🏆 Best Answer — B: Idempotency Keys with Atomic Conditional Writes

Networks deliver requests at least once, so true end-to-end exactly-once processing is not achievable. What you can guarantee is an exactly-once effect: a client-supplied idempotency key is claimed with an atomic conditional write before any money moves, the outcome is stored, and every retry gets the stored response. Doing this in a region-local, partitioned key-value store keeps latency low and availability high, with no cross-region coordination on the hot path. Here's why it stands out:

  • Dedup at the layer that actually owns the side effect: A client-generated key plus an atomic PutIfAbsent means exactly one attempt wins the right to charge. Every other attempt, concurrent or later, sees the existing record and cannot start a second charge.
  • The in-progress state closes the concurrent-retry race: When a client retries while the first attempt is still running, the second request finds an IN_PROGRESS record and receives a conflict (or waits) instead of charging again. Finished records store the full response, so a replay returns the identical status and body.
  • Low latency and high availability: A regional key-value store answers in single-digit milliseconds, scales horizontally by partition key, and keeps working in the region during a partition. No global quorum sits on the request path.
  • Operationally cheap: TTL-based cleanup is built into stores like DynamoDB and Redis, and there is no global lock service to run. Each record naturally carries attempt count, timestamps and state, which feed metrics such as duplicate rate, in-progress conflicts and fingerprint mismatches.
  • Industry-standard contract: Stripe's API, AWS guidance on safe retries and an IETF draft for an Idempotency-Key header all use client-supplied keys with stored results, so client SDKs and developers already understand the pattern.

A well-designed API includes client-generated keys scoped per customer, request fingerprinting, an IN_PROGRESS lease with safe takeover, replay of the stored response including status code, a processor-level idempotency key, a unique constraint on the ledger, a TTL beyond the retry horizon, and home-region routing. Track duplicate-request rate, in-progress conflicts, fingerprint mismatches, reconciliation backlog and, above all, duplicate charges reaching the processor (it should be zero). Any non-zero value means a gap in the chain of guards.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🌐

A — Single Global Relational Database

A unique constraint is simple and strictly consistent, but every request in every region pays a cross-region round trip to one primary, and a regional outage or partition makes the charge API unavailable. Holding a transaction open while calling the payment processor is also dangerous (locks, connection exhaustion). Caveat: in a single-region system, or when each region owns its own customers' data, a relational unique constraint is an excellent choice and is still the ideal ledger-level backstop inside option B.

🏛️

C — Global Consensus for Every Charge

Paxos or Raft gives a linearizable log, but every charge pays cross-region commit latency, the leader limits throughput, and the system loses availability without a quorum. It also does not deliver the promised exactly-once result, because the call to an external processor is outside the consensus group, so you need idempotent effects anyway. It is heavy machinery for a deduplication problem.

📬

D — Acknowledge First, Deduplicate and Refund Later

Acknowledging before the charge is processed means the app cannot tell the user whether the payment succeeded or was declined, and payments need a synchronous outcome. Duplicates are charged first and refunded afterwards, which means fees, visible double debits, chargebacks, support load and regulatory exposure. Asynchronous processing is fine for receipts, ledger projections and webhooks, but not as the deduplication mechanism.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Global Relational DB

Single-region or low-volume systems with a relational ledger where simplicity and strict constraints matter more than cross-region latency.

📌

B — Regional KV + Conditional Writes

Multi-region, high-throughput APIs with unreliable clients and external side effects. The standard design for payments and order creation.

📌

C — Global Consensus

Rare cases needing a globally linearizable sequence for other reasons (for example global unique allocation) at a low request rate.

📌

D — Async Ack + Refunds

Non-financial side effects such as emails or notifications, where duplicates are cheap to compensate. Not suitable for charging money.

⚠️ Common Mistakes to Avoid

  • Server-generated keys: If the server invents the key, a retried request cannot present it. Keys must come from the client (or be derived deterministically from the business intent).
  • Check-then-insert races: Reading the key and then writing it lets two concurrent requests both pass the check. Use a single atomic conditional write.
  • No in-progress state: Without it, two simultaneous retries both see 'not found' and both charge. Record IN_PROGRESS first, with a lease.
  • Not replaying the original response: Returning a generic 'already processed' error forces clients to guess the outcome. Store and return the original status code and body.
  • Ignoring the request fingerprint: The same key with a different payload must be rejected, otherwise a bug or attack silently returns the result of a different charge.
  • Volatile or non-replicated key storage: A cache without persistence or replication loses keys on failover or restart, which silently re-enables duplicates.

🌍 Real-World Best Practice

Payment teams enumerate failure modes first and then build a chain of guards so no single layer has to be perfect:

  • Step 0 — Map the failure modes: Client timeouts, lost responses, concurrent retries, regional failover, processor timeouts and crashes between steps.
  • Step 1 — Define the key contract: An Idempotency-Key header, scoping per customer, a documented TTL, clear error codes (conflict for in-progress, unprocessable for payload mismatch), and client guidance to retry with the same key and exponential backoff.
  • Step 2 — Atomic claim and replay: A conditional write in a regional store with a request fingerprint, an owner token and a short lease.
  • Step 3 — Propagate the guard downward: Send a derived idempotency key to the payment processor and put a unique constraint on the ledger's charge ID.
  • Step 4 — Reconcile unknowns: A background job resolves timed-out or stuck records by querying the processor, and webhooks act as a second source of truth.
  • Step 5 — Multi-region and chaos testing: Home-region routing, a failover runbook, and tests that kill the process after the processor call, fire parallel duplicates, and partition regions.

Treat idempotency as a chain of guards (API record, processor key, ledger constraint), not a single check.

💡

Key Takeaway

Retries are inevitable, so make the effect idempotent: clients send a key, the server claims it with an atomic conditional write, records an in-progress state, and replays stored results for every retry. Keep the store regional for latency and availability, pin each customer to a home region, and back the API record with a processor-level key and a ledger unique constraint. If your system is single-region, a relational unique constraint may be all you need.
