Olivia’s Deadlock Dilemma: Balancing Scale and Correctness

Olivia is a backend engineer at an online retailer where the Orders and Inventory microservices use separate PostgreSQL databases, and inventory itself is sharded across multiple instances. A single order often touches several inventory rows on different shards. During peak traffic, concurrent orders update overlapping rows in different orders, causing deadlocks and long lock waits that surface as errors and latency spikes, and a few hot SKUs account for most of the contention. She needs an architectural fix that removes the deadlocks while preserving scalability, availability, performance and data integrity.

A
Take a coarse global lock per order using a centralized distributed lock (ZooKeeper or Redis Redlock), so overlapping orders run serially across the microservices.
✗ Not Best
B
Use optimistic concurrency control: add row versions or CAS operations, read before writing, and retry on conflict with exponential backoff while tracking conflict rates, keeping the existing data layout.
✗ Not Best
C
Redesign data ownership: partition customers or products so an order touches one partition (or a small, strictly ordered set), use local single-shard transactions or a per-partition leader, and handle cross-partition operations with asynchronous workflows and compensations.
✓ Best Answer
D
Run distributed transactions (XA or two-phase commit) across both databases, letting a transaction manager coordinate updates and enforce strict consistency.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — C: Data Ownership + Local Transactions

A deadlock needs transactions that hold locks on several resources, acquired in different orders, across a boundary where nobody can see the whole picture. The most effective fix is to remove that situation rather than manage it: redesign data ownership so each order's critical updates happen inside one partition (or a small, strictly ordered set), keep transactions local and short, and use sagas with compensations for the rare cross-partition case. Here's why it stands out:

  • Removes the root cause: A single-partition transaction holds locks inside one database, where PostgreSQL's own deadlock detector resolves any cycle. Cross-shard lock cycles, which no single database can detect and which only show up as timeouts, disappear because no transaction holds locks across shards.
  • Short, local transactions scale: Lock hold time shrinks to one statement or a few milliseconds, so contention and queueing under peak load drop sharply. Throughput grows with the number of partitions, and each partition can fail or be tuned independently.
  • Fits the microservice boundaries: Orders and Inventory already have separate databases, so an order that spans both is a cross-service workflow anyway. Reservation, confirmation and compensation is the natural model for it, and it avoids tying two services together with XA.
  • Deterministic ordering for the rest: When an order does need several partitions, always reserve in a global order (sorted by partition, then SKU). Because a saga holds no locks while it waits for the next step, even unlucky interleavings cannot form a cycle.
  • Compatible with the tactical fixes: Inside a partition, one conditional statement (UPDATE ... SET qty = qty - n WHERE sku = ? AND qty >= n) gives an atomic decrement with a very short lock, and optimistic checks can protect the few places that need read-modify-write. Ownership redesign makes those tools sufficient.

A well-designed approach includes a partition key that matches access patterns, single-statement conditional updates, deterministic ordering for multi-partition work, idempotent reservations with TTLs, and monitoring of lock waits, deadlock counts and conflict rates. Measure deadlocks per minute and p99 lock-wait before and after each step; if they do not fall, the contention is on hot rows rather than on lock ordering.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🔒

A — Global Distributed Lock

A coarse global lock turns the busiest path into a serial queue: throughput collapses to roughly one order at a time per lock scope, and the lock service becomes a single point of failure. Lock expiry and process pauses can still let two holders overlap unless you add fencing tokens, and the safety of Redis Redlock is contested. It also does nothing about lock ordering inside each database. Caveat: a narrowly scoped lock (per SKU, short TTL, with fencing) can be a reasonable stopgap for rare, low-volume critical sections, but not as a per-order global lock.

🔁

B — Optimistic Concurrency Control

OCC removes held locks, so classic deadlocks go away, and it is a quick win that preserves the schema. But it gives no atomicity across shards (an order that updates three rows on three shards still needs a coordination story), and under hot-row contention conflicts and retries multiply: at flash-sale rates the retry load can reduce throughput further. Caveat: OCC works very well when conflicts are rare. Track the conflict rate, and move any row whose conflict rate stays high to single-writer ownership.

⛓️

D — Distributed Transactions (XA / 2PC)

2PC makes the problem worse: locks are held through the prepare and commit round trips, so hold times grow by network latency, and a coordinator crash can leave participants blocked with locks held. Availability becomes the product of all participants' availability, and throughput falls under contention. PostgreSQL supports prepared transactions, but they are rarely used for high-throughput OLTP across services. Caveat: acceptable for low-volume administrative operations that truly need atomicity across two databases.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Global Distributed Lock

Rare, low-volume critical sections (a nightly job or an admin operation) where scoped locks with fencing tokens are acceptable. Not for per-order hot paths.

📌

B — Optimistic Concurrency

Read-mostly or low-conflict data (profiles, settings, low-traffic SKUs) where conflicts are rare and retries are cheap; also a cheap first step before a redesign.

📌

C — Data Ownership + Sagas

High-contention, high-volume domains (inventory, balances, seats) where access naturally partitions by an entity key and cross-entity operations can be eventually consistent.

📌

D — Distributed Transactions (2PC)

Low-volume operations that truly need atomic updates across two databases (a one-off migration or an admin correction) and can tolerate blocking.

⚠️ Common Mistakes to Avoid

  • Inconsistent lock ordering: Transactions that touch the same rows in different orders form cycles. Sort keys (partition, then SKU) before locking and keep one canonical order across services.
  • Calling other services inside a transaction: A network call while holding row locks stretches lock time from milliseconds to seconds. Commit first and then call, or use a saga.
  • Treating deadlocks as retryable noise: Retrying hides a design flaw and adds load. Track deadlocks per minute as an SLI and fix the cause.
  • Retry storms without jitter: Many transactions retrying in lockstep collide again. Use exponential backoff with jitter and bounded attempts.
  • Long or missing timeouts: Without lock_timeout, one slow transaction can queue everything behind it. Fail fast and surface a clear error.
  • Ignoring hot rows: Even perfect ordering cannot fix a single row that everyone updates. Bucket the stock or serialize writes through a queue.

🌍 Real-World Best Practice

In practice, teams move from cheap, reversible fixes to structural ones, and they measure before choosing. A typical sequence looks like this:

  • Step 0 — Find the real cycle: Enable log_lock_waits, review deadlock_timeout, inspect pg_locks and pg_stat_activity, and capture which statements and row orders form the cycle. Cross-shard waits show up as timeouts, so trace them end to end.
  • Step 1 — Quick wins: Keep transactions short, never call other services inside a transaction, acquire rows in a consistent order (sort by SKU ID), and set lock_timeout and statement_timeout so waits fail fast instead of piling up.
  • Step 2 — Atomic single-statement updates: Replace read-then-write with a conditional UPDATE ... WHERE qty >= n (or SELECT ... FOR UPDATE SKIP LOCKED for work queues) to shrink lock windows.
  • Step 3 — OCC for low-conflict paths: Add version columns where read-modify-write is unavoidable, with bounded retries, backoff with jitter and a conflict-rate metric.
  • Step 4 — Redesign ownership: Partition so most orders touch one partition, use an ordered reservation saga for the rest, and split very hot SKUs into buckets.
  • Step 5 — Keep global coordination rare: Reserve distributed locks and 2PC for low-volume operations, and monitor deadlock counts, lock-wait p99 and compensation rates continuously.

Fix lock ordering and transaction length first, then change who owns the data.

💡

Key Takeaway

Don't manage deadlocks, design them out. Make each order's critical updates local to one partition with short transactions, and use ordered, idempotent reservations with compensation for the rest. Use OCC and conditional updates as tactical tools, and keep global locks and two-phase commit out of the hot path.
