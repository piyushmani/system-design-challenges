Hash vs Tree: Selecting the index for a high-throughput feed service

Sofia leads the team building a worldwide user activity feed. The service must absorb millions of writes per second, serve point reads in under 10 ms (a user's latest events), support range queries (top-K within a period, events within a time window), and rebalance easily as nodes are added. It must also stay highly available, observable, and resilient to node failures. Most reads and range queries are scoped to a single user's feed, while a smaller share are cross-user or global analytics queries. She must choose between hash partitioning, an ordered (tree) index, or a mix of the two.

A
A purely hash-partitioned key-value store: consistent hashing by userID, an in-memory hash table per node with disk snapshots, O(1) point reads and easy rebalancing via virtual nodes, but range queries must scan keys across the relevant nodes.
✗ Not Best
B
A purely ordered/range-sharded store: contiguous (for example, time-prefixed) key ranges with a distributed ordered index or B-tree so range queries touch few shards, with strict leader-based consistency per shard for exact rankings and ordered scans.
✗ Not Best
C
A hybrid: consistent hashing distributes data evenly for balanced writes, with an ordered index (LSM or B-tree) inside each shard for efficient local range queries. Point lookups go straight to the hashed shard, range queries fan out to the shards covering the range, and per-shard replication plus background rebalancing use routing metadata and virtual nodes.
✓ Best Answer
D
A two-tier design: an in-memory hash cache for fast point reads in front of an asynchronously updated distributed ordered (tree) store, with writes applied synchronously to the cache and a write-ahead log and a background process updating the ordered index, so range results are eventually consistent.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — C: Hash Partitioning + Ordered Index per Shard

The workload has two access patterns that pull in opposite directions: massive, evenly spread writes and point lookups favor hash partitioning, while ordered scans by time favor an ordered index. The hybrid gets both by splitting the two jobs: hash the partition key (userID, optionally with a time bucket) to spread load and make rebalancing a matter of moving virtual nodes, then keep events sorted by time inside each partition with an LSM-tree (or B-tree). A user's latest events become a single-shard, reverse-ordered range read, which is both a point-lookup-latency operation and a range query. Here's why it stands out:

  • Write scalability: Hashing spreads writes uniformly across shards, avoiding the 'newest range' hotspot that time-ordered sharding creates. LSM-trees turn random writes into sequential appends (commit log plus memtable, flushed to sorted files), which is why they are the usual choice for millions of writes per second.
  • Fast point and per-user range reads: With partition key = userID and clustering key = event time (descending), 'latest N events for user X' is one shard and one contiguous scan. Bloom filters, block caches, and SSDs commonly keep this in single-digit milliseconds, though that depends on compaction health and cache hit rate.
  • Rebalancing: Consistent hashing with virtual nodes moves only a small fraction of data when nodes join or leave, and it can run in the background using routing metadata, which keeps the cluster available during scaling.
  • Availability: Per-shard replication (typically a replication factor of 3 with quorum or leader-based writes) tolerates node loss without a global coordinator or a single hot range leader.
  • Why not a pure ordered store? Range sharding by time sends every new write to the most recent range, so one shard's leader becomes the cluster's write ceiling. Splitting hot ranges mitigates this, but only after the hotspot forms.
  • Proven at scale: Cassandra/ScyllaDB (partition key plus clustering columns), DynamoDB (partition key plus sort key), and Discord's published message-storage design (partition by channel and time bucket, ordered by a time-sortable ID) all use this hash-then-order structure.

A robust design uses (userID, time bucket) as the partition key, event time as a descending clustering key, replication factor 3 with quorum or leader-based writes, and virtual nodes with background streaming for rebalancing. Track per-partition size, hot-key skew, compaction backlog, and p99 point and range latency; if most queries turn out to be global rather than per-user, add a secondary index or analytics store instead of forcing the primary feed to answer them.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🔑

A — Pure Hash-Partitioned Store

Hashing gives O(1) point reads and the easiest rebalancing, but it destroys key order, so any time-window or top-K query becomes a scan of every candidate key. Holding all data in per-node in-memory hash tables with periodic disk snapshots also ties capacity to RAM and risks losing recent writes between snapshots unless a write-ahead log is added. Caveat: if the feed only needed 'get by exact key' and never ordered or range access, a hash store would be the simplest and fastest option.

📏

B — Pure Range-Sharded Store

Contiguous time-prefixed keys make range scans cheap, but all new writes land on the newest range, so one shard absorbs the entire write stream (a classic hotspot). Strict leader-based consistency on each shard adds write latency and makes that hot leader an even bigger bottleneck. Rebalancing by splitting ranges is reactive and heavier than moving virtual nodes. Caveat: range sharding works well when the key is not monotonically increasing (for example, prefixed by tenant or user), which is essentially the hybrid design by another name.

🧱

D — Hash Cache + Async Ordered Store

Two tiers mean two sources of truth: the cache and the ordered store can disagree, range results lag behind point reads, and the write path must keep the cache, the log, and the index in step. A cache also does not remove the need for the underlying store to handle millions of writes per second, and cold starts or misses fall back to a slower tier at the worst moment. Caveat: a cache is a fine addition on top of the hybrid design for very hot users, as long as the durable store remains the source of truth.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Pure Hash Store

Pure key-value access by exact key (sessions, tokens, counters) with no ordered or range access, and data that fits the memory budget or an on-disk hash-based engine.

📌

B — Pure Range-Sharded Store

Workloads dominated by ordered scans across a global key space where writes are already spread by the key itself (for example, keys prefixed by tenant), with a mature range-split and load-based rebalancing story.

📌

C — Hash + Ordered per Shard

High-volume, per-entity time-series or event data with both point lookups and per-entity range scans: activity feeds, messages, IoT telemetry, audit logs.

📌

D — Cache + Async Ordered Store

Extremely read-heavy hot subsets, where a cache sits on top of a durable ordered store and the team can tolerate and monitor cache and index divergence.

⚠️ Common Mistakes to Avoid

  • Partitioning by raw timestamp: Using the timestamp as the partition key recreates the hot-newest-range problem inside a hashed system. Hash a stable entity (userID) and use time only as a clustering key or a bucket.
  • Unbounded partitions: A heavy user's partition grows forever, hurting compaction and repair. Add a time bucket (day or hour) and, for reads that cross buckets, query buckets newest-first.
  • Scatter-gather on the hot path: Making the common feed read fan out to many shards inflates p99 latency. Make sure the common query is single-partition.
  • Ignoring compaction: A compaction backlog causes read amplification and latency spikes. Alert on pending compactions and files touched per read.
  • No virtual nodes or routing metadata: Plain modulo hashing reshuffles most data when nodes change. Use consistent hashing with virtual nodes and a versioned routing table.
  • Skipping skew monitoring: Averages hide hot users. Track per-partition write rate and size, and the top-N hottest keys.

🌍 Real-World Best Practice

In practice, teams model the queries first, then choose the key structure. A typical sequence looks like this:

  • Step 0 — List the queries: Write down every read pattern (latest N per user, time window per user, global top-K) with its latency target and frequency. The key design follows from them.
  • Step 1 — Choose the partition key: Hash a key that spreads writes and keeps the common read in one place (userID, plus a time bucket for heavy users).
  • Step 2 — Choose the clustering order: Sort by event time descending inside the partition so 'latest N' is a short forward scan.
  • Step 3 — Replication and consistency: Use replication factor 3 across zones; choose quorum or leader-based writes and local reads for the feed, since a feed tolerates slight staleness.
  • Step 4 — Rollups for global queries: Stream events into a separate store (time-series or OLAP) for cross-user top-K and analytics.
  • Step 5 — Cache hot users: Add a small cache for the hottest feeds only after measuring hit rate and tail latency.

Let the query patterns, not the data structure's reputation, pick the index.

💡

Key Takeaway

Use hashing to distribute and ordering to scan: hash-partition by user (plus a time bucket) to balance writes and rebalancing, and keep an LSM-tree or B-tree ordered by time inside each shard so feed reads and per-user range queries stay on one shard. Treat global cross-user range queries as a separate scatter-gather or rollup problem.
