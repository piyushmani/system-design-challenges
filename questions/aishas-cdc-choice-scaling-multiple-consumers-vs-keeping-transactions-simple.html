Aisha's CDC Choice: Scaling Multiple Consumers vs. Keeping Transactions Simple

Aisha, a senior backend developer at a fast-growing SaaS company, runs a single primary PostgreSQL cluster for OLTP. Several downstream systems (analytics, search, caches, a data lake) need near-real-time updates, with freshness from sub-second to a few seconds. Teams must be able to scale consumers independently, and SRE requires strong observability and the ability to recover or rewind offsets. The application's transactions should stay simple: no extra network calls or coordinators in the commit path. She must pick the CDC strategy that best balances availability, latency, update consistency, operational ease, and scalability.

A
Leverage WAL-based logical decoding CDC tools (like Debezium) to route database changes from Postgres into a persistent pub/sub system (e.g., Kafka). Maintain raw change topics per table, utilize a schema registry, leverage compacted topics for current state representation, and use stream processing frameworks to transform and load data into downstream sinks. Ensure end-to-end once-or-idempotent delivery via Kafka transactions or idempotent sinks, while monitoring replication slots and consumer lag for observability.

Perform synchronous dual-writes within the application code: during each transaction, have the application write to Postgres and immediately publish an event to a message broker synchronously before completing. Use an application-level two-phase commit or distributed transaction coordinator to guarantee consistency between the database and event store.

Answer & In-Depth Explanation

🏆 Best Answer — A: WAL-Based CDC into a Durable Log (Debezium + Kafka)

Reading the Postgres write-ahead log through logical decoding and publishing every committed change to a durable, partitioned log satisfies all of Aisha's constraints at once. The database commit stays the single source of truth, so the application keeps simple local transactions, while the log gives every consumer its own independent, replayable view of the changes. Here's why it stands out:

  • Atomic by construction: The WAL only contains committed transactions, in commit order. There is no dual-write window where the database and the event stream disagree, and the application adds no code to the commit path.
  • Low latency without hammering the primary: Logical decoding streams changes as they commit, so end-to-end lag is typically sub-second to a few seconds. It does not run repeated queries against OLTP tables the way polling does.
  • Independent consumer scaling and replay: Each consumer group tracks its own offsets in Kafka. Analytics, search, cache, and lake sinks scale, fail, and catch up separately, and SRE can rewind offsets to rebuild a sink, which is exactly the recovery requirement.
  • Compacted topics and a schema registry: Compaction keeps the latest value per key, so a new consumer can bootstrap current state without replaying all history, and compatibility checks in the registry stop breaking schema changes before they reach consumers.
  • Captures what other approaches miss: Deletes, every intermediate update, and the old and new row images (with the right REPLICA IDENTITY) are all visible, so downstream state can be rebuilt faithfully.
  • Observable: Replication slot lag (pg_replication_slots, comparing pg_current_wal_lsn() with confirmed_flush_lsn), connector status, and consumer-group lag are first-class metrics that map directly to SRE alerts.

A production-ready setup combines per-table change topics, a schema registry with compatibility checks, idempotent sinks, and alerts on slot lag and consumer lag. For services that need domain events rather than raw row changes, pair CDC with the outbox pattern (Debezium tails the outbox table), so you publish stable business events instead of exposing table internals.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🔀

B — Synchronous Dual-Writes + 2PC

Writing to Postgres and a broker inside one request is the classic dual-write problem: if the commit succeeds and the publish fails (or the reverse), the two systems silently diverge. Closing that gap with two-phase commit or a distributed transaction coordinator couples the commit path to the broker's availability, adds latency to every transaction, and creates blocked in-doubt transactions when the coordinator fails. Kafka also does not participate in XA transactions, so an atomic commit across Postgres and Kafka is not available off the shelf. That is the opposite of 'keep transactions simple' and of high availability. Caveat: none of this is needed, because the outbox pattern or WAL-based CDC gives the same atomicity with a single local transaction.

⏱️

C — Polling updated_at / Version Columns

Polling is easy to start, but it is lossy and puts load on the OLTP database. It misses hard deletes entirely, collapses multiple updates between polls into one, and can skip rows because commit order differs from timestamp order (a long-running transaction commits an older updated_at after the poller has moved past it). Sub-second freshness means polling constantly, which adds index scans on hot tables, and independent offsets per consumer must be built by hand. Caveat: for a low-volume table with minutes-level freshness and soft deletes, polling is acceptable and cheaper to run.

📤

D — Polling Outbox Without a Durable Log

The outbox pattern is the right idea (events are written in the same local transaction as the data), but this version weakens it. A cron or polling publisher adds delay and polls the primary, deleting processed rows creates bloat and write contention on a hot table, and skipping a durable log means no replay and no independent consumer offsets: the publisher must fan out to every downstream itself, so each slow or failed consumer becomes the publisher's problem. Caveat: a polling outbox can work for one or two consumers at modest scale. The upgrade path is to keep the outbox table and let Debezium tail it into Kafka.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — WAL-Based CDC + Kafka

Multiple independent downstream consumers (search, cache, analytics, lake), freshness in seconds, a need to replay or rebuild sinks, and a team able to operate Kafka (or a managed equivalent) and Debezium.

📌

B — Dual-Writes + 2PC

Rarely. Only when both systems truly share a transaction manager that supports XA and throughput is small. Even then, an outbox is usually simpler and safer.

📌

C — Polling updated_at

Low-volume tables, minutes-level freshness, append-only or soft-delete data, and a single consumer where the simplicity of a query-based sync outweighs completeness.

📌

D — Polling Outbox (No Log)

A small number of consumers, moderate throughput, a team without Kafka expertise, and domain events that must be explicit. Often a stepping stone: keep the outbox table and replace the poller with log-based CDC later.

⚠️ Common Mistakes to Avoid

  • Ignoring slot lag: An unmonitored replication slot retains WAL indefinitely and can fill the disk, taking the primary down. Alert on retained WAL and cap it with max_slot_wal_keep_size.
  • Assuming exactly-once end to end: Kafka's transactional guarantees stop at Kafka. Every external sink needs idempotent upserts, keyed by primary key and protected against replayed or out-of-order events.
  • Publishing raw table changes as a public contract: Consumers couple to your table schema, and every migration becomes a breaking change. Use a schema registry with compatibility rules, and an outbox for domain events.
  • Skipping the failover test: After a Postgres promotion the logical slot may not exist on the new primary, leading to a lost position or a forced re-snapshot. Rehearse failover with the connector running.
  • Forgetting REPLICA IDENTITY and TOAST: With default settings, update and delete events may carry only the primary key as the old image, and unchanged large TOASTed columns can be absent from update events. Set REPLICA IDENTITY FULL where consumers need full rows, or design sinks to merge partial updates.
  • Weak initial snapshot plan: A new connector or sink needs a consistent snapshot plus a clean handoff to streaming. Use the connector's snapshot modes (including incremental snapshots) instead of ad-hoc exports that leave a gap.

🌍 Real-World Best Practice

In practice, teams roll CDC out in stages and prove the failure modes before the happy path. A typical sequence looks like this:

  • Step 0 — Define the contract: Decide which consumers need raw row changes and which need domain events, and what freshness each really requires. Not every consumer needs sub-second.
  • Step 1 — Prepare Postgres: Set wal_level=logical, size replication slots and max_slot_wal_keep_size, choose REPLICA IDENTITY per table, and use a dedicated replication user and publication.
  • Step 2 — Stand up one table and one consumer: Debezium to Kafka to a single idempotent sink, with a schema registry and dead-letter handling.
  • Step 3 — Add observability and runbooks: Slot lag, connector task status, consumer lag, an end-to-end freshness probe (a heartbeat table), and a documented offset-reset and re-snapshot procedure.
  • Step 4 — Rehearse failure: Connector crash, Kafka broker loss, Postgres failover, schema change, and a sink rebuild from rewound offsets.
  • Step 5 — Scale out consumers and add the outbox: Onboard search, cache, and lake sinks one at a time, and introduce an outbox table for events that should be stable business contracts.

Add consumers incrementally, and treat replication slot health as production-critical infrastructure.

💡

Key Takeaway

Keep the commit path simple and move the integration problem to the log. Reading the WAL gives atomic, ordered, low-latency change capture with no application changes, and a durable log gives every consumer independent scaling, replay, and observability. It demands real operational care (slot lag, failover, idempotent sinks), but the alternatives either lose data, load the primary, or put availability at risk.
