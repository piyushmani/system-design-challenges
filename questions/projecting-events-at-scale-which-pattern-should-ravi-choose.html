Challenge

Projecting events at scale: which pattern should Ravi choose?

Ravi, a senior backend developer, is building an order management platform on Event Sourcing. A durable, append-only event log (Kafka or a SQL table) is the source of truth. The system needs highly available, fast read models for APIs and dashboards, must support replays after bug fixes, and must handle tens of thousands of events per second at peak across thousands of aggregates. Many reads tolerate eventual consistency (a few seconds), but some critical business processes need strict per-aggregate ordering and low write latency. Which pattern should he use to project events into read models while balancing scalability, availability, consistency, replayability and observability?

A
Synchronous transactional projections: record the event and update the read model within the same database transaction. This ensures strict consistency with no lag, but couples write performance to read-model updates and hinders independent scaling.
✗ Not Best
B
A single-threaded asynchronous projector: write events to the log and use one consumer to sequentially process the entire stream to update read models. This is simple and guarantees global ordering, but severely bottlenecks throughput and makes replays sluggish.
✗ Not Best
C
Partitioned asynchronous projections using keyed shards and consumer groups: distribute the event stream by aggregate ID (e.g., Kafka partitions) so each worker processes a specific partition, maintaining per-aggregate order. Use idempotent handlers, checkpoints, and periodic snapshots for faster replays. Rely on eventual consistency, managing cross-aggregate rules via sagas or coordinators.
✓ Best Answer
D
Strongly consistent cross-system updates: leverage two-phase commit or distributed transactions to atomically save events and update read models across disparate systems. This achieves strict read consistency but drastically increases operational complexity and harms scalability.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — C: Partitioned Asynchronous Projections with Idempotent Handlers and Checkpoints

Event sourcing separates the decision (append an event) from the derived views (read models). Because read models can always be rebuilt from the log, they do not need to be updated atomically with the write. What they need is correct per-aggregate ordering, parallelism, safe reprocessing and visible lag, which is exactly what keyed partitions with idempotent projectors provide. Option C also leaves the write side free to meet its latency and ordering needs on its own. Here's why it stands out:

  • Ordering where it matters: keying by aggregate id sends every event of an aggregate to the same partition and therefore the same worker, in order. Global ordering across all aggregates is almost never a business requirement, so giving it up costs nothing.
  • Throughput scales with partitions: more partitions and workers means more parallel projection, so tens of thousands of events per second is routine. Each worker batches its writes to the read store.
  • Writes are decoupled from projections: the command side appends with an optimistic-concurrency check (expected stream version) and returns. A slow dashboard projection can no longer slow down order placement.
  • Effectively-once results with idempotent handlers: store the last processed offset or aggregate version in the same transaction as the read-model update. A crash and redelivery then re-applies nothing twice.
  • Replays are routine, not scary: to fix a projection bug, deploy projector v2 to build a new read model from the beginning in parallel, then switch traffic by alias and retire v1. Snapshots and compacted state make this faster for long histories.
  • Observable by nature: consumer lag per partition, projection freshness (event time to applied time), parked or poisoned events, and rebuild progress are all measurable and alertable.
  • Critical paths do not depend on read models: a command handler rebuilds the aggregate from its own stream (plus snapshot) for decisions. Where a user needs read-your-writes, return the new stream version and let the query wait until the projection reaches it (with a bounded timeout).

Key ingredients: aggregate-id partitioning, offset or version stored atomically with the read-model write, idempotent handlers, blue/green rebuilds by alias switch, event versioning and upcasting, sagas or process managers for cross-aggregate rules, and lag and freshness dashboards. Rehearse a full rebuild regularly so it is a routine operation.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🔗

A — Synchronous Transactional Projections

Updating the read model in the same transaction as the event append gives strict consistency and no lag, and it is simple. It works well as inline projection for a small number of critical read models that live in the same database as the event store. At the scale described, though, write latency now includes every projection's cost, one slow or locked read table slows all writes, readers cannot scale independently, and rebuilding requires locking or complex online migration. Caveat: use it selectively, for example for a small 'current order status' table, alongside option C for everything else.

🚶

B — Single-Threaded Asynchronous Projector

One consumer gives global ordering and trivial reasoning, but the requirement for global order is almost never real. Throughput is capped by one thread, lag becomes unbounded during peaks, a replay of the full history takes the longest possible time, and one poison event or slow query stalls every read model. Caveat: it is fine for small systems, prototypes, or a tiny read model that genuinely needs total order.

🧨

D — Two-Phase Commit Across Systems

Distributed transactions solve a problem event sourcing does not have. Read models are derived data that can be rebuilt, so atomically committing them with the event buys little. Meanwhile, 2PC blocks on a coordinator, makes availability the product of every participant's availability, lowers throughput, and is not supported across arbitrary combinations such as Kafka and a read database. Caveat: reserve distributed transactions for rare cases where two systems of record must change together, and even then prefer sagas.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Synchronous Transactional Projections

A few small, critical read models in the same database as the event store where immediate consistency is required and write volume is moderate.

📌

B — Single-Threaded Async Projector

Prototypes, low-volume systems, or a small read model that truly needs total ordering across the whole stream.

📌

C — Partitioned Async Projections

High-volume event-sourced systems with many aggregates, several read models, replay requirements, and a tolerance for seconds of read-model lag.

📌

D — 2PC / Distributed Transactions

Rare cases where two systems of record must change atomically and both support a transaction protocol; usually better replaced by a saga.

⚠️ Common Mistakes to Avoid

  • Checkpointing separately from the read-model write: a crash between them skips or double-applies events. Commit the offset in the same transaction as the data.
  • Non-idempotent handlers: at-least-once delivery then corrupts counts and totals. Use version checks or upserts keyed by event id.
  • Wrong partition key: keying by something other than the aggregate id breaks per-aggregate ordering. Key by aggregate id.
  • Side effects inside projections: replays resend emails and webhooks. Keep projectors pure and put actions in separate reactors.
  • Skipping poison events silently: the read model quietly diverges. Park the aggregate, alert, and fix the handler or data.
  • No schema-evolution strategy: a replay hits old event shapes and crashes. Version events and upcast on read.
  • Ignoring hot aggregates and rebalances: one very busy aggregate or a stop-the-world rebalance causes lag spikes. Monitor skew and use cooperative assignment.

🌍 Real-World Best Practice

Teams that run event-sourced systems at scale decide ordering and consistency per use case and make rebuilds a routine, automated operation. A typical path looks like this:

  • Step 0 — Choose the key and partition count: aggregate id is the default key. Size partitions for peak throughput and future growth, since changing them later reshuffles ordering.
  • Step 1 — Harden the write side: optimistic concurrency with an expected version, idempotent commands, and a way to publish events from the log (the store itself is the outbox, via tailing or change-data-capture).
  • Step 2 — Build projectors: one consumer group per read model, handlers that are idempotent, batched writes, and the checkpoint stored with the data.
  • Step 3 — Make rebuilds routine: projector versions write to new tables or indexes, catch up in parallel, then switch by alias; keep the old one briefly for rollback.
  • Step 4 — Define freshness SLOs and monitor them: lag per partition, end-to-end freshness, rate of parked events, and rebuild duration.
  • Step 5 — Coordinate across aggregates with process managers: long-running sagas react to events and issue commands, rather than expecting projections to enforce cross-aggregate rules.
  • Step 6 — Test the ugly cases: replay the full history, kill workers mid-batch, redeliver duplicates, introduce an event schema change, and inject a poison event.

Treat projections as disposable and rebuildable, and the system becomes easy to operate.

💡

Key Takeaway

Read models are derived, so they do not need to be atomic with the write. Partition the event stream by aggregate id, project asynchronously with idempotent handlers and atomic checkpoints, and make replays routine. Keep strict consistency on the command side where decisions are made, handle cross-aggregate rules with sagas, and use synchronous projections only for a few small, critical views.
