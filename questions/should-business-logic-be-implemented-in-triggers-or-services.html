Should Business Logic Be Implemented in Triggers or Services?

Priya, a backend developer, is building an order management system that must keep an order history audit trail whenever an order is modified. The database supports triggers and stored procedures, and the application server is Node.js. The team prioritizes low latency, high reliability, and a clean separation of concerns. The audit trail is a compliance requirement: every change must be captured, including changes made by migrations, admin scripts, and other services that write to the same database, and an audit row must never exist without its change (or the reverse). She must choose an implementation that scales without tight coupling or operational burden as business logic evolves.

A
Create a database trigger designed to automatically insert a log entry into the audit table upon any INSERT, UPDATE, or DELETE operation performed on the orders table.
✓ Best Answer
B
Incorporate all audit logic directly into the application layer, ensuring that every API endpoint responsible for modifying an order simultaneously writes the corresponding audit record within the same transaction.
✗ Not Best
C
Implement a stored procedure to handle all order modifications. This procedure will manage both the order update and the audit log insertion, requiring the application to route all mutations through it.
✗ Not Best
D
Emit order modification events from the application to a message broker, and deploy an independent worker service to consume these events and asynchronously update the audit table.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — A: Generic Database Audit Trigger

For a pure audit trail that must be complete and atomic, an AFTER row-level trigger is the strongest fit. It runs inside the same transaction as the change, so the audit row commits or rolls back with the order row, and it fires no matter which code path (API, migration, admin script) touched the table. The key discipline is to keep the trigger generic and free of business rules: it records what changed, and business logic stays in the Node.js service. Here's why it stands out:

  • Completeness by construction: The application cannot forget to log. Every INSERT, UPDATE, and DELETE on orders is captured, including writes that bypass the Node.js service, which is exactly what auditors care about.
  • Atomic and reliable: The audit insert shares the transaction with the change. There is no window where the order is updated but the history is missing, and no outbox, retry, or reconciliation job to maintain.
  • Low latency: The extra work is one local insert, with no network hop, broker, or second round trip. Capturing old and new row images as JSONB keeps the trigger tiny.
  • Good separation of concerns: Audit is a cross-cutting, data-layer concern. Node.js endpoints and business rules can change freely without touching audit code, and one generic trigger function can be attached to many tables.
  • Evolves cheaply: Because the trigger stores row snapshots rather than a hand-maintained column list, adding a column to orders does not require updating audit code in every endpoint.

A solid implementation uses a single generic trigger function, row snapshots (old and new as JSONB), actor and request context from session settings, an append-only audit table (grant the app role INSERT only), and time-based partitioning. If other systems also need to react to order changes, publish events separately (for example through an outbox) instead of overloading the audit mechanism.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🧱

B — Audit in the Application Layer (Same Transaction)

Writing the audit row from every endpoint, inside the same transaction, is atomic and explicit, and it makes the actor and the business reason easy to record. Its weakness is coverage: every endpoint, job, and future service must remember to do it, and anything that writes SQL directly (migrations, hotfix scripts, another service) leaves no trail. It also scatters a cross-cutting concern through the codebase, the opposite of strict separation. Caveat: if audit entries need rich business meaning (reason codes, approvals), or triggers are unavailable (some managed or multi-database setups), a central repository layer or ORM hook is a sound choice, and it is often used alongside a trigger.

🗄️

C — Stored Procedure for All Order Mutations

Routing every mutation through one procedure is atomic and central, but it moves the write API into the database. The Node.js service becomes tightly coupled to procedure signatures, business logic splits across two runtimes, and versioning and testing get harder. The audit is complete only if nothing ever writes to the table directly, which nothing enforces unless permissions are locked down. It also puts more CPU work on the one resource that is hardest to scale. Caveat: it can make sense in a database-centric architecture with strict DBA ownership and direct table access revoked.

📨

D — Async Events + Independent Worker

Emitting events from the app and letting a worker write the audit table decouples nicely, but it is the weakest option for a compliance-grade audit. Publishing after the database commit is a dual write: if the process crashes between commit and publish, the change exists with no history. The audit is also only eventually consistent, and it adds a broker, a worker, retries, deduplication, and monitoring. Caveat: with a transactional outbox it becomes reliable, and it is a good way to feed other systems (search, analytics, notifications), but that is more machinery than a plain audit trail needs.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Audit Trigger

Compliance-style audit where completeness matters, several writers touch the table, and the record needs old and new snapshots rather than business narratives.

📌

B — App-Layer Audit

Audit entries that carry business meaning (reason codes, approvals), a single well-controlled write path, or databases where triggers are restricted.

📌

C — Stored Procedure API

Database-centric systems with strict DBA ownership, direct table access revoked, and procedures treated as the versioned write API.

📌

D — Async Events + Worker

Downstream reactions (notifications, search, analytics) that tolerate delay, ideally fed by a transactional outbox. Not suitable as the primary legal audit record.

⚠️ Common Mistakes to Avoid

  • Putting business rules in the trigger: Pricing, validation, or notifications inside triggers create hidden behavior that is hard to test and reason about. Keep triggers to recording facts.
  • Losing the actor: Without session context, history rows say 'app_user' for everyone. Set user id and request id per transaction.
  • Using session-level settings behind a pooler: A session-level value can leak to the next request on a pooled connection and attribute changes to the wrong user. Use transaction-local settings.
  • Letting the app role edit audit rows: An audit trail the application can update or delete is not an audit trail. Grant INSERT only, or use an append-only role.
  • Unbounded audit growth: The audit table often outgrows the orders table. Partition by time, index by order id and timestamp, and archive old partitions.
  • Row-level triggers on huge batch jobs: A million-row update fires a million trigger calls. Use statement-level triggers with transition tables for bulk operations.

🌍 Real-World Best Practice

In practice, teams start from the list of writers to the table rather than from a pattern. A typical sequence looks like this:

  • Step 0 — Inventory the writers: List every path that writes to orders (API, jobs, migrations, other services, support scripts). If exactly one controlled path exists, the application-layer option gets stronger.
  • Step 1 — Add a generic audit trigger: One trigger function, old and new rows as JSONB, attached to orders and later to other audited tables.
  • Step 2 — Propagate actor and request context: Set user id and request id per transaction, so history rows say who changed what and from which request.
  • Step 3 — Lock it down: INSERT-only grants on the audit table, time-based partitioning, and a retention and archival policy.
  • Step 4 — Feed other systems separately: If notifications, search, or analytics must react to order changes, use a transactional outbox into a broker rather than the audit table.
  • Step 5 — Test the guarantees: Integration tests asserting audit rows for insert, update, delete, rollback, and bulk operations.

Keep audit in the data layer, keep business rules in the service, and keep the two from leaking into each other.

💡

Key Takeaway

Use triggers for what changed and services for why it changed. A generic, logic-free audit trigger gives complete, atomic, low-latency history that survives code churn, while business rules stay in Node.js where they are testable. If audit entries must carry business intent, add it through session context or pair the trigger with an application-level reason code.
