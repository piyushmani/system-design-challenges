Eliminating Overselling in Flash-Sale Inventory Updates

Maya is architecting the inventory backend for an international e-commerce app. Flash sales generate bursts of up to 100k requests per minute with enormous concurrent demand on a handful of popular SKUs. The current read-then-decrement code has a race condition that lets stock go below zero. The order confirmation (accepted or sold out) must be returned synchronously within 150 ms, the service must stay highly available within a region, and operators need clear metrics. Stock lives in a transactional relational database (a primary with a synchronous standby), and each order is for a small quantity of one SKU. She must pick the design that eliminates oversells with the best balance of latency, availability, scale and observability.

A
Per-SKU distributed locks (for example Redis Redlock): acquire the SKU lock, read quantity, decrement, unlock; if the lock is held, the request fails fast or waits.
✗ Not Best
B
Serializable transaction isolation for each stock reduction, so the database detects write conflicts and aborts or retries conflicting transactions.
✗ Not Best
C
Optimistic concurrency through one conditional atomic update, <code>UPDATE inventory SET stock = stock - ? WHERE sku = ? AND stock >= ?</code>. Zero rows updated means rejection (or a retry with backoff for transient errors); processing is idempotent and retries are metered.
✓ Best Answer
D
Route all writes to a SKU-keyed command queue (Redis Streams or Kafka keyed by item) processed by a single consumer per partition, confirming orders asynchronously and compensating on failure.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — C: Conditional Atomic Update

Overselling happens because the check and the decrement are two separate steps. The fix is to make them one: a single conditional UPDATE lets the database evaluate stock >= qty and subtract atomically under its row lock. There is no external lock service and no extra round trip, and the answer (1 row or 0 rows) is available synchronously inside the latency budget. Here's why it stands out:

  • Correct by construction: The row-level lock inside the database serializes concurrent updates to the same SKU, and the stock >= qty predicate guarantees the counter can never go negative.
  • Fits the latency budget: One statement, one round trip, and a lock held for microseconds. At 100k requests per minute (about 1,700 per second overall), a single primary handles this comfortably across many SKUs.
  • Synchronous, honest confirmation: The caller learns immediately whether the order succeeded or the item sold out, so the 150 ms confirmation requirement is met without compensating workflows.
  • Minimal moving parts: No Redlock cluster, no queue consumers, no isolation-level tuning. Availability is the database's own HA (synchronous standby, automatic failover), which the team already operates.
  • Easy to observe: Track successful decrements, sold-out rejections (zero-row results), transient retries, statement latency and row-lock wait time per SKU to spot hot items early.

A production-ready version wraps the decrement and an order or reservation insert (unique order ID) in one transaction, exposes metrics for rejections, retries and lock waits, and keeps a stock-bucket or admission-gate plan for the hottest SKUs. Load-test with a realistic skew (for example 80% of traffic on a few SKUs), not uniform traffic.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🔒

A — Distributed SKU Locks

Adds a network hop to lock, another to read, another to write and another to unlock, so latency and failure points multiply under a burst. Redlock-style locks are not safe for correctness (pauses and clock issues can let two holders proceed), and lock contention means failed or queued requests exactly when demand peaks. The database's own atomic update already provides what the lock is trying to simulate. Caveat: useful only when a critical section spans systems that cannot share a transaction.

🧱

B — Serializable Isolation

Correct, but it pays for generality: predicate tracking and conflict detection cause serialization failures under heavy contention, which means aborts and retry storms on exactly the hot rows that matter. It also keeps the original read-then-write code shape, so every caller must implement correct retries. Caveat: appropriate when a transaction spans many rows with complex invariants that cannot be expressed as one conditional statement.

📬

D — SKU-Keyed Command Queue

Single-consumer-per-partition ordering cleanly removes races and is a good pattern for very hot items, but asynchronous confirmation conflicts with the 150 ms synchronous requirement unless the queue path is fast enough, and compensation logic (cancellations, refunds, 'sorry, sold out' emails) is customer-visible complexity. Queue lag during bursts also hurts latency. Caveat: a strong choice when orders can be 'accepted pending confirmation' by design (for example ticketing waiting rooms).

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Distributed SKU Locks

Critical sections that span multiple systems that cannot share a transaction, with fencing tokens and a clear need that outweighs the added latency.

📌

B — Serializable Isolation

Multi-row transactions with complex invariants that cannot be written as a single conditional statement and that tolerate retries.

📌

C — Conditional Atomic Update

Counter-style invariants (stock, quotas, seats) in a transactional database where a synchronous decision is required.

📌

D — SKU-Keyed Command Queue

Extreme hot items, or designs where orders are accepted pending asynchronous confirmation and per-key ordering matters.

⚠️ Common Mistakes to Avoid

  • Retrying on zero rows: It means the stock predicate failed, so retrying only burns database capacity. Reject the order as sold out.
  • Reading stock first 'just to check': Any separate read reintroduces the race. Let the UPDATE be the check.
  • Decrementing outside the order transaction: A crash between the decrement and the order insert leaks stock. Do both in one transaction with a unique order ID.
  • Deciding on replicas: A replica may lag and approve orders for stock that is gone. Use the primary for decisions.
  • Unbounded retries on deadlocks and timeouts: Retry storms amplify load during a sale. Use a small retry budget with jittered backoff.
  • Testing with uniform traffic: Real flash sales are skewed to a few SKUs. Load-test with that skew to find row-lock ceilings.

🌍 Real-World Best Practice

In practice, teams fix the race at the database first and add scaling layers only where measured hot spots demand them. A typical sequence looks like this:

  • Step 0 — Reproduce and measure: Write a concurrency test that fires parallel orders at one SKU and asserts stock never drops below zero; capture baseline latency and lock waits.
  • Step 1 — Conditional atomic update: Replace read-then-write with a single conditional UPDATE and treat zero rows as sold out.
  • Step 2 — Idempotency: Insert the order ID (unique) in the same transaction so client retries and redeliveries cannot double-decrement.
  • Step 3 — Observability: Add metrics for decrements, rejections, retries, p99 latency and per-SKU lock waits, and alert on rising rejection or wait times.
  • Step 4 — Hot-SKU strategy: For flash-sale items, split stock into buckets or use an admission gate (rate limit or waiting room) in front of the database.
  • Step 5 — Optional async layers: Use queues for downstream work (payment, fulfillment, emails), not for the stock decision itself.

Make the stock decision atomic in the database, and scale around it only when measurements demand it.

💡

Key Takeaway

The race exists because check and decrement are separate. Collapse them into one conditional atomic statement and let the database's row lock do the serialization. It is the simplest design that satisfies correctness, a 150 ms synchronous answer and operational clarity; reach for bucketing, gates or queues only for proven hot SKUs.
