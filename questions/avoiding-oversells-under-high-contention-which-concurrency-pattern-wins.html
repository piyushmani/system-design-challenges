Avoiding oversells under high contention: which concurrency pattern wins?

Liam leads engineering for an international ticketing system. At peak, 10,000 reservation attempts per second hit highly sought-after events, creating extreme hot-key contention. The system must never oversell a seat, keep most responses under 100 ms, survive a data-center outage, and avoid heavy operational burden. The stack includes a relational database, Redis, and the ability to run stateful, key-sharded services (actor model). Which concurrency strategy best delivers correctness and scalability with the least operational pain?

A
Guarantee strong consistency via a relational database: execute every reservation inside a serializable transaction that locks the specific inventory rows. Trust the DB for correctness, scaling through read replicas and event partitioning across distinct database shards.
✗ Not Best
B
Utilize distributed locks in Redis (e.g., a per-seat Redlock pattern). Acquire the lock, reduce inventory in the database, and then release the lock. Handle contention with retries and short TTLs to minimize latency.
✗ Not Best
C
Implement a single-writer, sharded actor architecture: consistently hash each seat key to a designated owner process. The owner handles reservations sequentially in memory, writes commands to a persistent log, and flushes state asynchronously. Ensure failover via hot-standbys or replicas, scaling by adding more shards.
✓ Best Answer
D
Process reservations asynchronously for eventual consistency: ingest requests instantly into a distributed queue and use parallel consumers to adjust inventory. If overselling occurs, execute compensating actions to notify users. Favor availability and throughput over strict immediate consistency.
✗ Not Best

Answer & In-Depth Explanation

🏆 Best Answer — C: Single-Writer Sharded Actors with a Durable Command Log

Under heavy contention on a few hot keys, the winning idea is to remove contention rather than manage it. If exactly one process owns a key and processes its commands one at a time, there is nothing to lock, nothing to retry, and 'sold is never greater than capacity' is checked in a single place. In-memory sequential processing handles far more than 10k operations per second for one key, and a durable log plus fenced failover provides the fault tolerance. Here's why it stands out:

  • Correctness by construction: all operations for a seat (or event section) are serialized through one owner, so the check-and-decrement cannot race. Oversell is prevented by design, not by tuning timeouts.
  • Latency is a memory operation plus one log append: there are no lock round trips, no deadlocks and no aborted transactions. Batching log appends (group commit) keeps p99 well within 100 ms.
  • Throughput scales by adding shards: shard by event, section or seat block so no single owner is overloaded. This is the same single-writer principle that high-performance systems such as the LMAX architecture rely on.
  • Fault tolerance through the log: state is reconstructed by replaying the replicated command log from the last snapshot. A hot standby shortens recovery to seconds.
  • Fits the stack: actor frameworks (Akka, Orleans, Dapr actors, Proto.Actor) or a Kafka partition per key provide the ownership and routing. The relational database remains the system of record for confirmed purchases, fed by projection, instead of absorbing contention on the hot path.
  • Less operational pain than locks or serializable hot rows: no lock TTL tuning, no retry storms, no serialization-failure handling in application code.

Essentials: one owner per key, a quorum-replicated command log written before acknowledging, epoch-based fencing, idempotent request ids, snapshots for fast recovery, and admission control or a waiting room in front of the hottest sales. Verify the invariant continuously with a checker that asserts sold ≤ capacity under chaos.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🔐

A — Serializable Transactions with Row Locks

This is correct and simple to reason about, and for moderate load a single conditional UPDATE ... WHERE available >= 1 on a hot row is a respectable baseline. At 10k attempts per second on the same hot rows, however, requests queue behind row locks, each lock is held across application round trips and the commit (including synchronous replication for data-center tolerance), and serializable isolation adds aborts and retries (SQLSTATE 40001) that amplify load. Read replicas do nothing for the write path, and cross-shard events complicate things further. Caveat: it can be the right first implementation, with the actor model as the scale-up path.

🧷

B — Redis Distributed Locks (Redlock)

A lock with a TTL can expire while the holder is still working (a GC pause or network delay), letting a second client in; Redis failover can also lose a lock. The safety of Redlock under such pauses and clock jumps is widely disputed, and safe use requires a fencing token checked by the database, at which point the database, not the lock, is enforcing correctness. Each reservation also costs several round trips and retries under contention, causing a thundering herd. Caveat: locks are fine for efficiency (avoiding duplicate work), not for guarding an invariant such as 'never oversell'.

📬

D — Async Queue with Compensation

This fails the primary requirement outright: the design accepts overselling and fixes it afterwards, which means telling paying customers they lost a seat they were promised. Queues are a good fit for the work that happens after a reservation is decided (payment, email, projection), but not as the point where the decision is made. Caveat: a queue can still sit in front of the actor owners for buffering and admission control, as long as the owner makes the authoritative decision.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Serializable DB Transactions

Moderate contention, simpler stacks, and teams that want the database to be the single source of truth. A good first implementation using a conditional update on a hot row.

📌

B — Redis Redlock

Efficiency locking (avoiding duplicate work, rate-limiting a job) where an occasional double execution is harmless. Not for guarding hard invariants.

📌

C — Single-Writer Sharded Actors

Extreme hot-key contention with a strict invariant, a latency budget, and the capability to run stateful services with replicated logs and fenced failover.

📌

D — Async Queue + Compensation

Soft inventory where overselling is a tolerable business risk (for example overbooking with a clear policy), or for post-reservation processing rather than the decision itself.

⚠️ Common Mistakes to Avoid

  • Acknowledging before the log is durable: in-memory state with a lazy flush loses acknowledged reservations on a crash. Replicate the command log first.
  • No fencing on failover: a paused old owner and a new owner both accept writes. Use an epoch or lease token that the log verifies.
  • Hot shard from a poor shard key: sharding by event puts the busiest event on one node. Shard by section or seat block, or split inventory into counters.
  • No idempotency on requests: client retries consume two seats. Dedupe by request id inside the owner.
  • Unbounded mailboxes: under overload, queues grow until memory is exhausted. Apply admission control and bounded queues with load shedding.
  • Skipping failure drills: failover logic that has never been exercised under load fails in the real sale. Rehearse it.
  • Mixing slow work into the owner: payment calls inside the actor block all reservations on that key. Keep the owner's loop short and asynchronous.

🌍 Real-World Best Practice

Ticketing platforms handle hot sales by combining admission control with single-writer inventory. A typical design looks like this:

  • Step 0 — Admission control: a virtual waiting room or rate limiter keeps the arrival rate at the inventory service within what it can serve, and gives users a fair queue instead of errors.
  • Step 1 — Define hold semantics: reserve (hold with expiry), confirm after payment, release on expiry or failure. The seat state machine is the contract.
  • Step 2 — Choose the shard key: event, section or seat block, sized so that no single owner exceeds its capacity. General-admission inventory can be split into counters per shard.
  • Step 3 — Build the owner: in-memory state, idempotent request ids, epoch check, quorum log append, then reply.
  • Step 4 — Persist and project: snapshots for recovery, and an asynchronous projection into the relational database for orders, reporting and customer-facing history.
  • Step 5 — Drill failover: kill the owner mid-sale, partition it from the log, and confirm that fencing blocks the old owner and that no seat is sold twice.
  • Step 6 — Load test with skew: replay realistic hot-key distributions and run an invariant checker that verifies sold seats never exceed capacity.

Serialize on purpose, in one place, rather than coordinating everywhere.

💡

Key Takeaway

For hot keys with a hard 'never oversell' rule, assign each key a single owner, make its log durable and replicated before acknowledging, and fence ownership on failover. This removes lock contention instead of fighting it, scales by adding shards, and keeps latency low. Use database transactions for moderate load, treat Redis locks as an efficiency tool rather than a correctness guarantee, and never make overselling an accepted outcome.
