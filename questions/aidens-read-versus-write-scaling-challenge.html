Read vs Write Scaling Architecture Performance
Challenge

Aiden's read-versus-write scaling challenge

Aiden, a backend architect, is designing an e-commerce catalog platform. Traffic is about 95% reads, peaking at millions of QPS globally, and browsing and search must return with P95 latency under 100 ms. Writes are less frequent but include inventory adjustments and price changes that must be fully durable, and some flows (such as decrementing inventory at checkout) require strict accuracy. He needs an architecture that scales reads efficiently, keeps browse latency low, and guarantees correctness for the critical writes, while staying operationally manageable.

A
Retain a solitary primary SQL database for all write operations and provision numerous read replicas. Send all read traffic to the replicas and direct writes to the primary node. Depend on tracking replica lag and dynamically adjust the number and size of replicas to satisfy read requirements.
✗ Not Best
B
Horizontally partition the primary database (using hash or range sharding) such that each partition contains its own leader and replica nodes. Direct both read and write operations to the corresponding partition leader. Accommodate growth by provisioning additional partitions as system load increases.
✗ Not Best
C
Implement the CQRS (Command Query Responsibility Segregation) pattern: maintain a strongly consistent write model (such as a single primary or leader-per-critical-shard) for transactional operations (like checkout and inventory), and asynchronously push denormalized read models into specialized databases (e.g., search indexes, key-value stores, or read-optimized databases). Direct browse and search queries to these read models, while routing critical writes to the write model; support read-your-writes for transactional processes by querying the write model directly or utilizing short-lived caches.
✓ Best Answer
D
Deploy a globally distributed, strongly consistent database system (similar to Spanner) featuring synchronous cross-region replication, allowing every replica to process read queries with strict consistency. Tolerate increased write latency and higher operational expenses to achieve globally consistent read operations.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — C: CQRS with Specialized Read Models

The two halves of this workload have opposite needs. Browsing and search need massive fan-out, text and faceted queries, and global proximity, and they tolerate seconds of staleness. Checkout and inventory need serializable correctness on a tiny fraction of the traffic. CQRS gives each side its own model and store: a small, strongly consistent write model for commands, and denormalized read models (search index, key-value store, CDN-cached pages) fed asynchronously and scaled independently. It is the only option that scales reads by orders of magnitude without making every read pay for write-grade consistency:

  • Read scaling is decoupled from the database: Millions of QPS are served by search clusters, key-value stores, and CDN or edge caches, not by the transactional database. Read capacity grows by adding read-model nodes and cache tiers.
  • The right data structure per query: Browse needs precomputed, join-free documents. Search needs an inverted index with facets and ranking. A relational primary cannot serve either at this scale and latency.
  • Strict correctness where it counts: Inventory decrements and price validation execute against a single authoritative write model with transactions and constraints, so overselling is prevented at the source of truth.
  • Regional proximity for reads: Read models can be replicated to every region, giving low browse latency without forcing synchronous cross-region commits on writes.
  • Independent evolution and failure isolation: A slow projector or a search outage degrades freshness or search quality, not checkout. Read models can be rebuilt from the event log.

Keep the write model small and strict, build read models shaped like the queries, publish changes through an outbox to a durable log, and make checkout re-check price and stock at write time. Monitor projection lag, search freshness, and oversell or reservation-failure rates.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

📚

A — Single Primary + Many Replicas

Simple and often the right first step, but it hits limits at this scale: the primary must ship its log to every replica, so the replica count and lag are bounded by it. Millions of QPS would need a very large replica fleet, replicas still execute relational queries (poorly suited to full-text and faceted search), and replica lag causes stale or inconsistent reads without any of the isolation CQRS offers. It is the starting point, not the destination.

🧩

B — Sharded Primary (Leader per Shard)

Sharding scales writes and storage, but the bottleneck here is read volume and query type. Sending reads to shard leaders keeps expensive queries on the transactional path, cross-shard browse and search queries become scatter-gather, and rebalancing adds operational risk. The write side may need sharding eventually (leader-per-critical-shard is part of option C), but it does not solve read scaling or search.

🌍

D — Globally Strongly Consistent Database

Spanner-style systems offer remarkable guarantees, but paying for strict consistency on every browse read is the wrong trade. Strong reads and synchronous cross-region commits add latency and cost, and the 95% read traffic does not need them. Browse and search still need specialized indexes and caches to reach millions of QPS under 100 ms. It can serve as the write model for critical data, but as the single answer it over-buys consistency and under-delivers on search and read economics.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Primary + Replicas

Early and mid-scale systems where reads exceed one node but replicas can handle the load, queries are relational, and a few seconds of lag are acceptable.

📌

B — Sharded Leaders

Write throughput or data size exceeds a single node, and access patterns are keyed (tenant, user, SKU) so queries stay within one shard.

📌

C — CQRS

Very high read fan-out with specialized query needs (search, facets, personalization), a small set of strict transactional writes, and tolerance for seconds of read staleness.

📌

D — Global Strongly Consistent DB

Globally distributed transactional data (for example financial or inventory ledgers) where strict consistency across regions is a core requirement and the cost is justified.

⚠️ Common Mistakes to Avoid

  • Trusting browse data at checkout: Displayed stock and price are hints. The command must re-check against the write model, or you will oversell and mischarge.
  • Dual writes to the write model and read models: Writing to both from application code creates divergence on partial failures. Publish via a transactional outbox and CDC.
  • Non-idempotent or unordered projections: Replays and reordering overwrite newer data. Use versions and per-key ordering (key the stream by SKU).
  • Read-modify-write inventory logic: Reading stock, checking in the app, then writing back races under concurrency. Use a single conditional update.
  • No rebuild path: Read models will need to be rebuilt after bugs or schema changes. Keep the event log or snapshots and automate replay.
  • Adopting CQRS too early: For modest load, a primary with replicas and a CDN is far simpler. Introduce CQRS when measurements show it is needed.

🌍 Real-World Best Practice

Large catalogs (marketplaces, retailers, travel platforms) usually evolve toward this shape in stages:

  • Step 0 — Measure and classify: Separate browse, search, product-detail, cart, and checkout traffic. Note which operations need strict consistency (inventory, price at checkout) and which do not.
  • Step 1 — Cache aggressively: CDN and edge caching for product pages with short TTLs and event-driven invalidation often removes most read load.
  • Step 2 — Add a search and key-value read model: Project catalog data into a search engine and a KV or document store through an outbox and a log.
  • Step 3 — Keep the write model strict: Transactional inventory and pricing with constraints, reservations with expiry, and idempotent commands.
  • Step 4 — Make checkout authoritative: Re-read price and availability from the write model, and reserve before charging.
  • Step 5 — Operate the pipeline: Projection lag SLOs, replay and rebuild tooling, and reconciliation between write and read models.

Serve the many from caches and indexes, and protect the few critical writes with a strict, small core.

💡

Key Takeaway

When reads outnumber writes by 20 to 1 and the two have different consistency needs, separate them. Use CQRS to keep a strict, small write model for inventory and price and scale reads through denormalized, regionally replicated read models and caches. Re-validate critical data at checkout.
