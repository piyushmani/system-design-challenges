Choosing the Concurrency Pattern That Eliminates Overselling

Nora is building the inventory service for an international retailer. Thousands of orders per second arrive from many application nodes, and each order needs an atomic stock deduction so inventory never goes negative. Latency must stay low, availability high and monitoring simple. The data tier is a single primary relational database with read replicas, and the environment is exposed to node crashes and network partitions. Each order decrements one SKU by a known quantity, and no other rows need to be examined to decide. She must choose the most scalable, consistent and simple method for stock reduction.

A
<code>SELECT ... FOR UPDATE</code> inside a transaction on the primary: lock the inventory row, check the balance, decrement and commit (pessimistic row locking).
✗ Not Best
B
A distributed lock layer (for example Redlock on Redis) acquired per SKU across all application servers before reading and decrementing, serializing operations outside the relational database.
✗ Not Best
C
A single atomic conditional statement: <code>UPDATE inventory SET qty = qty - :amount WHERE id = :id AND qty >= :amount</code>, verifying that exactly one row was affected; otherwise abort (or retry transient failures). No separate lock service and no explicit pessimistic locks.
✓ Best Answer
D
Accept orders into a message queue and return success immediately; background workers check stock and decrement asynchronously, issuing compensating refunds or cancellations when stock is insufficient.
✗ Not Best

Answer & In-Depth Explanation

🏆 Best Answer — C: Single Conditional UPDATE

When the decision depends on one row and one predicate, the cheapest correct primitive is the one the database already guarantees: a single atomic statement. The row lock is taken, the condition is evaluated and the value is changed in one step, so there is no window between 'check' and 'decrement' for another order to slip into. Here's why it stands out:

  • No race window: Check and update are indivisible, so two orders competing for the last unit cannot both succeed: one sees one affected row, the other sees zero.
  • Shortest lock hold time: The row lock lives for one statement instead of spanning several round trips (as with SELECT ... FOR UPDATE), which matters most on hot rows receiving thousands of orders per second.
  • Immune to node crashes and partitions: A crashed or partitioned application node cannot corrupt stock: its transaction either committed atomically or the database rolls it back and releases the lock. There is no lease to expire.
  • Simplest to operate: No lock service to run, monitor or fail over. The database is the only authority, and its metrics (lock waits, rows affected, latency) are the monitoring surface.
  • Honest synchronous result: The affected-row count tells the caller immediately whether the order was fulfilled, so customers are never promised stock that does not exist.

Pair the statement with an idempotency key (unique order ID in the same transaction), retry only transient errors such as deadlocks or connection resets, and publish metrics for zero-row results, retries, latency and lock waits. Add a nightly reconciliation of orders against stock to detect drift from bugs or manual adjustments.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🔐

A — SELECT ... FOR UPDATE

Also correct, because the row lock prevents concurrent modification, but it needs at least two statements and a transaction that holds the lock across application round trips. At thousands of orders per second on hot rows, longer lock hold times increase queueing and deadlock risk, and any business logic added inside the transaction extends the hold further. Caveat: the right tool when the decision reads multiple rows or applies complex rules that cannot be expressed as a single conditional UPDATE.

🧷

B — Distributed Lock (Redlock)

Adds another system, more network hops and new failure modes to protect data that the database could already protect by itself. It is also unsafe as a correctness mechanism: a paused or partitioned client can resume after its lease expired and still write, and a plain database update has no fencing token to reject it. Caveat: fine for coordinating work across systems that do not share a database, ideally with fencing tokens.

📬

D — Queue With Optimistic Success

Excellent for absorbing bursts, but telling the customer 'success' before checking stock guarantees that some promises will be broken and then repaired with cancellations and refunds. It adds queue lag, ordering and exactly-once concerns for the workers, and it makes monitoring harder because order state is unknown for a while. Caveat: reasonable for backorder or pre-order models where 'accepted pending allocation' is a legitimate business state.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — SELECT ... FOR UPDATE

Decisions that read multiple rows or apply complex rules before writing, where transactions are short and contention is moderate.

📌

B — Distributed Lock (Redlock)

Coordinating work across systems without a shared transactional store, with fencing tokens and a clear cost-benefit.

📌

C — Single Conditional UPDATE

Single-row counters and quotas (stock, seats, credits) in a relational database where the answer is needed synchronously.

📌

D — Queue With Optimistic Success

Pre-order or backorder flows and burst smoothing where orders legitimately remain 'pending allocation' for a while.

⚠️ Common Mistakes to Avoid

  • Ignoring the affected-row count: The statement 'succeeds' even when zero rows change. Always branch on the count.
  • Read, compute in the application, write back: This reintroduces the race. Let the database do the arithmetic and the check.
  • Running the decision on a replica or through a lagging proxy: Writes must hit the primary, and so must reads used for decisions.
  • No idempotency key: A retry after a timeout decrements twice. Record the order ID transactionally.
  • Retrying the zero-row case: It is a legitimate sold-out result, and retrying wastes capacity.
  • Ignoring the replication mode after failover: Asynchronous replicas can miss committed decrements. Use synchronous or semi-synchronous commit for inventory.

🌍 Real-World Best Practice

In practice, the winning pattern is to push the invariant into the database and keep application code stateless. A typical sequence looks like this:

  • Step 0 — State the invariant: Stock must never be negative, and the decision for one order depends on one row.
  • Step 1 — One conditional statement: Express the check and the decrement together and branch on the affected-row count.
  • Step 2 — Make it idempotent: Store the order ID with the decrement in one transaction so retries and duplicate submissions are safe.
  • Step 3 — Protect the primary: Keep decisions on the primary with synchronous or semi-synchronous replication, and use replicas for display reads.
  • Step 4 — Monitor the database signals: Alert on lock wait time, zero-row rate, retry rate and p99 latency per SKU.
  • Step 5 — Scale selectively: Bucket or gate only the SKUs that measurements show are hot, and reserve queues for downstream work, not for the stock decision.

Let the database enforce the invariant, and keep everything else stateless.

💡

Key Takeaway

For single-row invariants, one conditional atomic UPDATE beats explicit locks and queues: no race window, minimal lock time, no extra infrastructure and a clear synchronous result. Choose SELECT ... FOR UPDATE only when the decision needs multiple rows or complex logic, and use queues for work that follows the stock decision, not for the decision itself.
