Data Tiering Storage Costs Performance
Challenge

Riley's data tiering dilemma: Hot performance or cold storage savings?

Riley, a senior backend engineer, is designing storage for an event platform ingesting 50,000 events per second. Data from the last 24 hours is read heavily (5–10 ms tail latency), data up to 30 days old is warm, and anything older (retained 2+ years) is a rarely touched cold archive. The design must minimize cold-storage cost, give 99.99% availability for hot reads, and provide read-after-write consistency for newly ingested events. Analytics jobs run bulk scans over warm and cold data and tolerate eventual consistency. Which hot/warm/cold architecture best balances cost, scalability, latency, and operational simplicity?

A
Write synchronously to hot, warm, and cold tiers using a distributed two-phase commit, and read by checking hot, then warm, then cold.
✗ Not Best
B
Write only to the hot tier plus lightweight metadata/catalog entries (lifecycle and location); migrate hot to warm to cold asynchronously by age or size policy; route reads through the catalog; keep migrations observable and retryable.
✓ Best Answer
C
Write only to hot with no background migration; move data to warm or cold lazily and synchronously when aged data is first accessed, or via batch jobs triggered by reads of old data.
✗ Not Best
D
Maintain a central per-record index of pointers and summaries across all tiers; write to the index and the hot tier, treat warm and cold as immutable archives reachable only through the index, and fetch cold data synchronously on demand.
✗ Not Best

Answer & In-Depth Explanation

🏆 Best Answer — B: Hot-First Writes + Catalog-Driven Async Migration

The requirements split cleanly by tier: recent data needs low latency and read-after-write consistency, so writes should land in one strongly consistent hot store, while old data needs cheap, durable, scan-friendly storage, so it should be moved in bulk and off the write path. Option B keeps the write path short, moves data with a background, retryable pipeline, and uses a small catalog (at segment or partition granularity, not per record) to route reads and analytics. Here's why it stands out:

  • Short, fast, consistent write path: Each event is acknowledged after one durable write to the hot tier, so the 50k events/s ingest path does not depend on warm or cold storage, and read-after-write holds because fresh reads are served from the same hot tier (leader or quorum reads).
  • Cost scales with data age: Only about 24 hours of data sits on expensive SSD or memory. As an illustration (assuming roughly 1 KB per event), ingest is about 4.3 TB per day, about 130 TB for 30 days, and about 3.1 PB over 2 years uncompressed, so nearly all volume should live as compressed, columnar objects in object storage.
  • Bulk movement beats per-event copies: Background jobs compact events into large, time-partitioned, columnar files (for example Parquet) and write them to warm or cold storage in big sequential batches, which is what analytics scans need and what object stores are cheap at.
  • The catalog keeps routing simple and migrations safe: A segment-level catalog (similar in role to Iceberg or Delta table metadata) records where each time range lives. Migration is copy, verify, atomically flip the catalog, wait a grace period, delete the source, so readers never see a gap and failed steps are simply retried.
  • Availability where it matters: Hot reads depend on the hot tier (plus time-based routing or a cached catalog for the last 24 hours), not on object storage or migration jobs. If the pipeline stalls, data just stays hot longer: cost rises, correctness does not suffer.
  • Analytics-friendly: Scans ask the catalog for partitions in a time range and read warm or cold files directly with engines such as Trino, Spark, or Athena, accepting eventual consistency.

A well-run pipeline includes versioned segment-level catalog entries, copy, verify (checksum and row count), commit, delayed delete, idempotent and leased mover jobs, lifecycle policies on object storage (colder storage classes for old data), and dashboards for migration lag, hot-tier utilization, and read-tier hit rates. Test with failure injection: kill the mover mid-copy, delay catalog commits, and verify no read ever returns missing or duplicate data.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

⏱️

A — Synchronous Writes to All Tiers (2PC)

Writing every event to three tiers synchronously, with 2PC, puts the slowest and least available system on the critical path: write latency is bounded by object storage, availability is the product of three systems, and a coordinator failure can block ingest at 50k events/s. It also stores fresh data in cold storage as many tiny objects (inefficient and costly per request) and defeats the point of tiering, which is to move data as it ages. Reading sequentially across tiers adds latency on misses. Caveat: a durable log (for example Kafka) as the single write target and replay source gives the safety this option is reaching for, without 2PC.

🐌

C — Lazy Migration on First Access

Waiting to move data until someone reads it inverts the cost model: aged data stays on expensive hot storage indefinitely if nobody reads it, which is exactly the common case for cold data, and the first reader pays for a synchronous migration inside the request path, producing unpredictable, high tail latency. Batch jobs 'triggered only when older data is read' give no cost bound and no schedule. Caveat: on-demand caching (promoting a recalled cold object into warm) is useful, but aging out must be proactive and policy-driven.

🧭

D — Central Per-Record Index

A pointer for every record is itself a big-data problem: at 50k events/s that is about 4.3 billion index entries per day and about 3 trillion over two years, which makes the index expensive, a scaling bottleneck, and a single point of failure on every read. Writing to both the index and the hot tier is a dual write with no atomicity, risking dangling or missing entries. Synchronously fetching cold data per targeted read gives high latency, and pre-aggregates in the index duplicate analytics work. Caveat: a small index over segments or partitions (which is what B's catalog is) is the efficient version of this idea, and secondary indexes (for example by user ID) can serve specific query patterns.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Sync Write to All Tiers

Very small data volumes with a strict need for immediate multi-tier durability, almost never at high ingest rates. A durable log is the better answer for the same goal.

📌

B — Hot-First + Async Catalog

High-ingest event and time-series workloads with clear age-based access patterns, cost sensitivity, and a need for fast, consistent reads on recent data.

📌

C — Lazy On-Access Migration

Rarely: small systems where operational simplicity outweighs cost and predictable latency. On-demand promotion (caching), not demotion, is the useful part.

📌

D — Per-Record Global Index

Workloads dominated by point lookups across old data (for example by entity ID), using a targeted secondary index over segments or keys rather than a global per-record index.

⚠️ Common Mistakes to Avoid

  • Moving data before it is safely copied: Deleting from hot before verifying warm or cold loses data on failure. Use copy, verify, commit, delayed delete.
  • Per-record cataloging: A catalog with one row per event becomes the biggest dataset you operate. Catalog segments or partitions instead.
  • Too many small files: Writing tiny objects to warm or cold storage makes scans slow and request costs high. Compact into large (hundreds of MB) columnar files.
  • No plan for late data: Events that arrive after their segment is sealed need a late-arrival window, delta segments, and compaction rules.
  • Unmonitored mover lag: A silent backlog fills the hot tier and causes an availability incident. Alert on lag and capacity.
  • Ignoring retrieval cost and latency of archive classes: Deep-archive tiers can take hours to restore and charge per retrieval. Match the storage class to real access patterns and keep 'cold but queryable' data in an infrequent-access class.

🌍 Real-World Best Practice

In practice, tiering is built on a durable ingest log, time-partitioned immutable segments, and a metadata layer, with lifecycle policy automation. A typical approach:

  • Step 0 — Define SLOs and access patterns: Query latency by age, freshness needs, retention, and consistency requirements per tier. Estimate volumes (events per second × size × retention) to size each tier.
  • Step 1 — Durable hot ingest: Acknowledge writes after a replicated, durable commit (a log or the hot store) and serve recent reads from the hot tier with leader or quorum reads for read-after-write.
  • Step 2 — Segment and compact: Roll data into time-partitioned, compressed columnar segments (for example hourly) with sorted keys and statistics for pruning.
  • Step 3 — Catalog and mover: Record segments in a transactional catalog and run an idempotent mover (copy, verify, commit, delayed delete) driven by age policy; monitor lag.
  • Step 4 — Warm and cold storage classes: Warm on cheaper block or standard object storage; cold on archive classes via lifecycle rules, with documented retrieval times for restores.
  • Step 5 — Analytics path: Query engines read segments through the catalog with partition pruning, with optional materialized aggregates for common dashboards.

Keep the write path short, move data in bulk by policy, and track location with a small catalog.

💡

Key Takeaway

Tier by age and access pattern: land every event in one fast, strongly consistent hot store, then asynchronously and idempotently compact and move segments to cheaper tiers while a segment-level catalog routes reads and analytics. Synchronous multi-tier writes, lazy on-read migration, and per-record global indexes each put cost or latency on the wrong path.
