REST API Read Latency Consistency
Challenge

Lina’s REST API design: low-latency reads vs strictly consistent writes

Lina, a software engineer, is building a User Preferences service for a mobile-first product. It must serve millions of reads per minute, accept simultaneous updates from web and mobile clients, and integrate with several downstream microservices (such as email and recommendations) that depend on current user preferences. Her main goals are strong observability, prevention of lost updates, high availability, low read latency, and acceptable write latency. She must choose a propagation mechanism and a RESTful API design. Which strategy gives the best balance of operational complexity, consistency, latency, availability, and scalability?

A
Synchronous writes to the master paired with synchronous downstream requests: process preference modifications via a unified API that synchronously updates the main database, followed by executing HTTP requests to all downstream microservices to refresh their state and caches before responding with a 200 OK. Direct all read traffic to the primary database to guarantee maximum freshness.
✗ Not Best
B
Event-based eventual consistency: the REST write operation replies with a 202 Accepted upon saving the modification and broadcasting an event to a message bus (like Kafka). Downstream applications subscribe to this bus and refresh their read models asynchronously. Client applications must be built to endure brief periods of stale data and use polling if they require instant verification.
✗ Not Best
C
Conditional updates utilizing ETags and If-Match combined with asynchronous cache clearing: employ standard REST principles with ETags and conditional PATCH/PUT headers to identify update conflicts and ensure idempotency. Save changes to the master database, dispatch lightweight update or invalidation events to the message bus for downstream caches and services, and handle read queries using replicas or read models and caches (configured with short TTLs) to ensure low latency.
✓ Best Answer
D
Client-initiated merging (using Last-Write-Wins or CRDTs): allow client applications to send partial updates without any conflict validation on the server side. The service combines these updates leveraging last-write-wins timestamps or CRDTs and instantly broadcasts the consolidated state to downstream consumers. Read requests are fulfilled by a highly available, eventually-consistent data store.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — C: ETag / If-Match Updates with Async Invalidation and Replica or Cache Reads

The requirements pull in three directions: no lost updates, very low read latency at massive scale, and high availability. Optimistic concurrency with HTTP conditional requests (ETag plus If-Match, returning 412 on conflict) solves lost updates at the API contract level, without locks or coupling. Writes go to the authoritative store, downstream services learn about changes through lightweight events instead of synchronous calls, and reads are served from replicas, read models, and short-TTL caches so millions of reads per minute never hit the primary. Here's why it stands out:

  • Lost-update protection by contract: The client sends the version it saw in If-Match. The server applies the change only if that version is still current (UPDATE ... WHERE version = ?); otherwise it returns 412 Precondition Failed. Requiring the header (428 Precondition Required if missing) makes the protection non-optional.
  • Low read latency at scale: Reads hit caches or replicas, and conditional GETs (If-None-Match returning 304) save bandwidth and battery on mobile networks. The primary only sees writes.
  • Availability and decoupling: Writes do not wait for email, recommendations, or any other consumer. The bus absorbs downstream outages, and the read side keeps working even when the primary is slow.
  • Consistency where it matters: The write decision is strongly consistent (one authoritative row plus a version), while derived views are eventually consistent. Events carry the version so consumers discard stale or out-of-order updates, which is precisely where eventual consistency is safe.
  • Observability: The 412 rate is a real measure of client conflicts, and event lag, replica lag, and cache hit ratio are direct SLIs. The version number in logs and events lets you trace one preference change end to end.

The contract is: GET returns a strong ETag; PUT/PATCH require If-Match (428 if absent, 412 on mismatch); the response carries the new ETag and body; every successful write emits PreferenceChanged{userId, version} through an outbox; consumers upsert only when the version is newer. Track 412 rate, event lag, replica lag, and cache hit ratio.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🔗

A — Synchronous Writes, Synchronous Fan-Out, Primary Reads

It maximizes freshness, but write latency becomes the sum of every downstream call and availability the product of all of them. A failure after the database commit leaves some systems updated and others not, with an ambiguous response. Routing every read to the primary cannot scale to millions per minute, and two concurrent writers still overwrite each other, so lost updates are not prevented.

📣

B — Event-Based Eventual Consistency with 202

Its propagation idea is sound (and option C uses it), but the API contract fails the stated requirement: with no conflict detection, concurrent web and mobile updates still cause lost updates. Returning 202 for a small preference change makes the client unable to confirm the result without polling, and read-your-writes becomes the client's problem.

🔀

D — Client-Initiated Merge (LWW or CRDT) Without Server Validation

Last-write-wins silently discards one of two concurrent updates (it causes lost updates) and depends on client clocks, which skew and can be tampered with. CRDTs genuinely merge, but they add metadata and complexity that small per-user preference documents do not need. With no server-side validation, integrity and observability weaken. This suits offline-first collaborative editing, not this service.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Sync Writes + Sync Fan-Out

Very small systems with one or two downstream consumers, low traffic, and a requirement that every consumer be updated before the user sees success.

📌

B — Eventual Consistency with 202

Write-heavy, fire-and-forget updates where concurrent edits to the same record are rare or harmless, and clients can tolerate polling for results.

📌

C — ETag/If-Match + Async Invalidation

Read-heavy resources that multiple clients can edit concurrently, with several downstream consumers and a need for lost-update protection, low read latency, and high availability.

📌

D — Client Merge (LWW / CRDT)

Offline-first or collaborative editing where clients must continue working while disconnected and merges are well defined (documents, shared lists), accepting the added complexity.

⚠️ Common Mistakes to Avoid

  • Using weak ETags with If-Match: If-Match requires strong comparison, so a weak validator (W/) never matches and every update fails or the check is skipped.
  • ETags that do not change on every update: Deriving them from a timestamp with second precision lets two quick writes share a tag. Use a version counter or a content hash.
  • Check-then-write in application code: Reading the version and then updating in two steps leaves a race. Put the version check into the UPDATE's WHERE clause so it is atomic.
  • Not requiring If-Match: If clients can omit the header, some will, and lost updates return. Enforce it with 428.
  • Publishing events outside the transaction, and consumers without version guards: Drift and out-of-order updates follow. Use an outbox and apply events only when they are newer.
  • No read-your-writes strategy: Users who read an older replica right after saving assume the app is broken. Return the fresh body and ETag, and pin the user's reads briefly.

🌍 Real-World Best Practice

In practice, teams model preferences as a small versioned document and let HTTP semantics carry the concurrency contract. A typical sequence looks like this:

  • Step 0 — Model the resource: Store one versioned preferences document per user (a version column), and decide whether conflicts are detected per document or per field.
  • Step 1 — Define the API contract: GET returns 200 plus a strong ETag; PUT/PATCH require If-Match (428 if missing, 412 on mismatch) and return the updated body and new ETag.
  • Step 2 — Implement the write path: Use a single atomic conditional update on the authoritative store, with the outbox insert in the same transaction.
  • Step 3 — Propagate changes: Relay the outbox to the bus, have consumers apply changes only if the version is newer, and invalidate caches by deleting the key, with a short TTL as a backstop.
  • Step 4 — Optimize reads: Use cache-aside plus read replicas and conditional GETs, and provide read-your-writes through a post-write token or a short primary-read window.
  • Step 5 — Observe and harden: Track the 412 ratio, cache hit rate, replica and consumer lag, and DLQ depth, and add contract tests that simulate two concurrent clients.

Let the HTTP contract carry concurrency, and let events carry propagation.

💡

Key Takeaway

Prevent lost updates with optimistic concurrency at the API (ETag plus If-Match), keep writes on one authoritative store, and propagate changes asynchronously with versioned events. Serve the heavy read load from caches and replicas. You accept brief staleness in derived views and gain safe concurrent writes, high availability, and low latency.
