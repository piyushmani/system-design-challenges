Architectural Decision: Managing NULL Values in a Distributed System

A software engineer at a growing e-commerce company must design a robust way to handle NULL values in the product catalog, where many optional attributes (weight, material, warranty period, energy rating) are unknown for a large share of products. The catalog is read by several consumers (storefront API, search index, recommendations, analytics) through CDC and events, and each needs different behavior for missing data. Critically, unknown must stay distinguishable from a real value such as 0 or an empty string: a missing weight is not a weight of zero. She needs an approach that protects data integrity across the whole system.

Answer & In-Depth Explanation

🏆 Best Answer — A: Keep NULL as Truth, Apply Defaults at Read (COALESCE)

In the system of record, NULL means 'unknown or not applicable', and that meaning is valuable. Applying defaults at the read boundary (queries, views, or API mappers) keeps the stored data honest while giving each consumer the behavior it needs. It is also the cheapest and most reversible option: no schema migration, no new infrastructure, and the policy can change without rewriting data. Here's why it stands out:

  • Preserves semantics: A missing weight stays NULL, not 0, so shipping calculators, filters, and analytics can tell 'unknown' from 'zero'. Writing a fabricated default destroys that information permanently.
  • Different consumers, different defaults: The storefront may show 'Not specified', search may omit the field, and analytics may exclude the row from averages. Defaults at read let each choose, while a stored default forces one answer on all.
  • Low cost and reversible: COALESCE is standard SQL, adds negligible overhead, and changing a default is a deploy, not a data migration.
  • Works with distributed pipelines: CDC events, search documents, and caches carry the honest NULL, and each downstream system applies its own policy at the edge, so no hidden normalization step becomes a point of failure or drift.
  • Pairs with constraints: Truly required attributes get NOT NULL and CHECK constraints, so NULL appears only where unknown is a legitimate state.

Combine strict write-time validation (required fields are NOT NULL, domain checks reject nonsense), NULL as the stored representation of unknown, and one explicit read-time policy per consumer. When a group of attributes is optional together (for example length, width, and height), model it as a separate table or a composite type so the all-or-none rule is enforced by the schema.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🧾

B — Schemaless NoSQL Store

Moving to a schemaless store does not remove missing data. It turns NULL into absent or null-valued fields and pushes the handling into every consumer, usually with weaker integrity guarantees (no NOT NULL, no CHECK, no foreign keys) and inconsistent conventions between documents. Changing the datastore to solve a NULL problem is a heavy, disproportionate decision. Caveat: when attribute sets genuinely vary by product category, a document model, or a relational table with a JSONB column for category-specific attributes, is a legitimate design, but for that reason rather than for NULL handling.

🧩

C — Normalize / Split Tables to Reduce NULLs

Moving optional attribute groups into child tables (a row exists only when data exists) is a sound relational technique and can make all-or-none rules enforceable. As a general NULL strategy it has limits: it adds joins and write complexity, it still needs defaults at read time for missing rows (a LEFT JOIN produces NULLs again), and the storage argument is weak, because modern databases store NULLs very cheaply (typically a bit in a row-header bitmap). Caveat: it is the right tool for attribute groups with real invariants, or for very wide, very sparse tables.

🧪

D — Preprocessing Cache That Fills Missing Values

Filling in values in a cache before data is persisted mixes responsibilities and fabricates data. It turns 'unknown' into a plausible-looking value, makes the cache a hidden dependency in the write path (a cache outage now affects data correctness), and gives no integrity guarantee. Caches should hold derived copies of the source of truth, not decide what the truth is. Caveat: enrichment from an authoritative source (for example, looking up manufacturer specs by SKU) is legitimate, but it belongs in an explicit, auditable ingestion step, not in a cache.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — COALESCE at Read

Optional attributes with a legitimate 'unknown' state, several consumers with different needs, and a wish for a reversible, low-cost policy. The default choice for catalogs.

📌

B — Schemaless NoSQL

Highly variable attribute sets per product type, where a document model (or a JSONB column) fits the data shape. Not a way to avoid NULLs.

📌

C — Normalize / Split Tables

Attribute groups that must be present together or absent together, very wide sparse tables, or optional sub-entities with their own lifecycle.

📌

D — Pre-Persist Cache Filling

Almost never for NULL handling. Use explicit enrichment pipelines with provenance if missing values must be filled from authoritative sources.

⚠️ Common Mistakes to Avoid

  • Storing sentinel defaults (0, empty string, 'N/A', -1): They look like data, pollute aggregates, and cannot be told apart from real values later. Store NULL when the value is unknown.
  • Using COALESCE ad hoc everywhere: Each team picks a different default, so the storefront and analytics disagree. Define the policy once in a view or mapper.
  • Coalescing inside aggregates and filters without thinking: AVG, COUNT(col), and index usage all change. Decide per metric whether unknown rows are excluded or defaulted.
  • Forgetting three-valued logic: NOT IN (subquery) returns nothing if the subquery yields a NULL, and col <> 5 excludes NULL rows. Use NOT EXISTS or IS DISTINCT FROM.
  • Letting NULL semantics diverge across systems: A JSON null, a missing field, and an empty string mean different things in search indexes, event schemas, and warehouses. Document the contract in the event schema.
  • Making everything nullable: Required business facts (price, SKU, currency) should be NOT NULL. Nullable-by-default schemas hide ingestion bugs.

🌍 Real-World Best Practice

In practice, senior engineers classify attributes before choosing a mechanism. A typical sequence looks like this:

  • Step 0 — Classify each attribute: Required, optional with a real 'unknown' state, or not applicable for some categories.
  • Step 1 — Constrain the base schema: NOT NULL, CHECK, and proper types for required facts, with no sentinel defaults in storage.
  • Step 2 — Put the default policy in one place: A view, read model, or API mapper per consumer, instead of scattered COALESCE calls.
  • Step 3 — Define the event contract: Specify how nullable fields appear in event schemas (explicit null versus omitted) and document it for every consumer.
  • Step 4 — Model all-or-none groups explicitly: Use separate tables or composite types when attributes must be present or absent together.
  • Step 5 — Monitor data quality: Track the percentage of NULLs per attribute and alert on sudden changes, which usually signal an ingestion bug.

Store the truth once, and decide how to present uncertainty at the edges.

💡

Key Takeaway

Treat NULL as information, not as a defect to be erased. Keep unknown values as NULL in the system of record, enforce NOT NULL and checks for what is truly required, and apply defaults at the read boundary with one explicit policy per consumer. Switching datastores, over-normalizing, or filling values in a cache either loses integrity or fabricates data.
