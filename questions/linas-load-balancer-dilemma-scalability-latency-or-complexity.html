Load Balancing Latency Architecture
Challenge

Lina's Load Balancer Dilemma: Scalability, Latency, or Complexity?

Lina leads backend engineering for a fast-growing web platform with traffic spikes up to 100k requests per second, running many microservices across multiple regions. Some endpoints are read-heavy and latency-sensitive. Others use session data (such as matchmaking state), but that state can be moved to an external store. She must choose a load-balancing strategy for both external ingress and service-to-service traffic that delivers low tail latency, supports autoscaling, gives strong observability, and leaves no single point of failure. The services are written in a few languages that all have mature HTTP/gRPC client libraries.

A
Deploy a centralized Layer 7 reverse proxy cluster (a small group of high-capacity NGINX or Envoy servers) to handle global routing, sticky session cookies, health monitoring, and TLS termination. Scale this gateway fleet horizontally behind a single DNS record.
✗ Not Best
B
Utilize DNS-based geolocation and latency routing (global DNS with latency or weighted records) directing traffic to regional load balancers that manage per-region session affinity. Maintain mostly stateful services behind these regional load balancers to preserve affinity and minimize cross-region network calls.
✗ Not Best
C
Design application services to be completely stateless by offloading session data to a distributed external store (such as a multi-AZ Redis cluster). Rely on client-side load balancing equipped with service discovery (via SDKs or sidecars) alongside local retries and health checks. Employ regional ingress load balancers for incoming external traffic, allowing clients to dynamically select optimal endpoints.
✓ Best Answer
D
Implement a service mesh (using sidecar proxies alongside every service instance) to manage Layer 7 load balancing, mTLS, circuit breaking, retries, and observability. Preserve necessary session affinity through cookie-based hashing at the sidecar level, requiring no modifications to the underlying application code.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — C: Stateless Services + Client-Side LB + Regional Ingress

The decisive fact is that session state can be externalized. Once any instance can serve any request, load balancing becomes a pure capacity and latency problem instead of an affinity problem, and the best tools (power-of-two-choices, latency-aware routing, instant autoscaling, regional failover) all open up. Option C removes the constraints that make the other options fragile. Here's why it stands out:

  • Stateless means autoscaling-friendly: Instances can be added, drained, or killed with no session loss, and new capacity absorbs load immediately instead of waiting for sticky sessions to expire.
  • Better tail latency: Client-side balancing uses per-request signals (EWMA latency, in-flight count, power-of-two-choices), skips an extra proxy hop, and avoids hot instances. Combined with outlier ejection, retry budgets, and careful hedging for idempotent reads, it cuts p99.
  • No central bottleneck: Each client holds the endpoint list from service discovery, so the east-west data plane is distributed and there is no proxy fleet to size for 100k requests per second. Managed regional ingress load balancers (multi-AZ) scale horizontally for north-south traffic.
  • Resilient by design: Health checks run at the ingress and in the clients, regional failover is driven by health-aware DNS or Anycast, and a multi-AZ session store keeps session data available when an instance dies.
  • Observable: Every client emits per-destination latency, error, and retry metrics, ingress produces access logs, and traces (for example OpenTelemetry) tie them together.

Standardize timeouts, retry budgets, outlier ejection, and load-aware balancing in one shared client (or one xDS configuration), keep ingress simple and managed, and watch p99 per hop. If uniform policy and mTLS justify the sidecar cost, a mesh is a reasonable evolution of this same design, as long as the services stay stateless.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🚪

A — Centralized L7 Proxy Cluster Behind One DNS Record

A small cluster of L7 proxies concentrates all traffic and all failure modes in one tier: it must be sized for the global peak, a bad configuration push affects every region, and cross-region users hairpin through it. Sticky session cookies defeat the purpose of externalizing state, because they create hot instances, slow rebalancing after scale-out, and lose sessions when an instance dies. A single DNS record gives no health-based or latency-aware routing. Caveat: a central gateway is excellent for north-south concerns (authentication, WAF, rate limiting) when it is regional and multi-AZ rather than one global tier.

🌍

B — Geo/Latency DNS + Regional Affinity + Stateful Services

DNS geo or latency routing is a good first tier, but this option pairs it with stateful services and affinity. DNS answers are cached by resolvers and clients, so failover takes seconds to minutes. Stateful instances cannot be freely autoscaled or drained, and affinity creates hot spots during spikes. It also says nothing about service-to-service balancing. Caveat: DNS-based geo routing remains the right outer layer for multi-region ingress. It just should not be the whole answer.

🕸️

D — Service Mesh with Cookie-Based Session Affinity

A service mesh is powerful (mTLS, retries, circuit breaking, uniform telemetry) and is a legitimate alternative, but this option leans on cookie-based hashing for affinity, which keeps the stateful constraints that autoscaling and failover want to remove. Sidecars add a proxy hop on each side of every call (typically sub-millisecond to a few milliseconds, plus CPU and memory per pod) that tail-sensitive paths feel, and the mesh control plane becomes another critical component to run. Caveat: when uniform mTLS and policy across many teams matter most, a mesh over stateless services without sticky routing is a strong choice. The best combination is option C's statelessness with a mesh or xDS as the delivery mechanism.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Central L7 Proxy Cluster

Small to medium single-region deployments and edge concerns (authentication, WAF, rate limiting), deployed as a multi-AZ managed gateway and not as one global proxy tier.

📌

B — Geo DNS + Stateful Regional LBs

As the outer routing layer for multi-region ingress, or for genuinely stateful, regionally pinned workloads (such as game servers) where affinity is inherent.

📌

C — Stateless + Client-Side LB

Multi-region microservices that are tail-latency sensitive and autoscaled, with externalizable state and teams able to share a client library or xDS configuration.

📌

D — Mesh with Sticky Affinity

Many teams and languages that need uniform mTLS, policy, and telemetry without code changes, and a platform team able to run a mesh. Best without sticky routing.

⚠️ Common Mistakes to Avoid

  • Round-robin only: Equal distribution ignores slow or overloaded instances. Prefer least-request or power-of-two-choices with EWMA latency.
  • Retry storms: Unbounded retries amplify an outage. Use retry budgets, jittered backoff, and per-try timeouts shorter than the overall deadline.
  • Hedging non-idempotent requests: Duplicate execution causes duplicate side effects. Hedge reads only.
  • Stale or fragile discovery: Clients that hard-fail when discovery is down, or never refresh endpoints. Cache the last known good list and combine it with health signals.
  • No outlier ejection: One bad instance keeps receiving traffic and dominates p99.
  • Treating the session store as just another dependency: It is tier-0. Make it multi-AZ with timeouts, a circuit breaker, and a defined fallback.
  • Ignoring locality: Cross-AZ and cross-region calls add latency and cost. Prefer zone-local endpoints with spillover.

🌍 Real-World Best Practice

Large platforms layer load balancing, and each layer solves a different problem:

  • Step 0 - Make services stateless: Move sessions to Redis or DynamoDB (multi-AZ) or into signed tokens, and keep only caches in process.
  • Step 1 - Global layer: Use Anycast or latency- and health-based DNS (for example Route 53 or Cloudflare) to steer users to the nearest healthy region, with short TTLs and health checks.
  • Step 2 - Regional ingress: Use managed L4/L7 load balancers (NLB or ALB) spread over multiple AZs for TLS termination, WAF, and coarse routing, with connection draining on scale-in.
  • Step 3 - East-west traffic: Use client-side balancing (gRPC with xDS, Envoy, or a shared library) with service discovery (Cloud Map, Consul, Kubernetes endpoints), locality awareness, power-of-two-choices, and outlier ejection.
  • Step 4 - Resilience: Enforce timeouts, retry budgets (for example at most about 10% extra load), circuit breakers, load shedding, and hedging only for idempotent reads.
  • Step 5 - Observe: Track golden signals per hop (rate, errors, p50 and p99), use distributed tracing, and run synthetic probes per region.

Use DNS for geography, managed load balancers for ingress, and smart clients for service-to-service calls.

💡

Key Takeaway

Remove affinity first, then balance for latency. Stateless services with externalized session state, regional ingress load balancers, and latency-aware client-side balancing with discovery and retry budgets give the best tail latency, elastic autoscaling, and no single point of failure. Use geo-DNS for regional steering, and a proxy or mesh only where policy needs justify the extra hop.
