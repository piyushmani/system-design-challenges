Inventory Management Deadlocks Concurrency
Challenge

Can Naomi eliminate inventory lock contention without overselling?

Naomi, a backend architect for a high-traffic e-commerce site, runs an inventory service that decrements stock inside database transactions using SELECT ... FOR UPDATE. At 10,000 updates per second across 100,000 SKUs, including a few extremely popular items, row-lock contention causes long tail latencies and occasional downtime. Business policy strictly forbids negative inventory (overselling). 'Add to cart' and 'place order' must stay fast (ideally under 100 ms) and users must get an instant reservation acknowledgement, although final confirmation may lag slightly. She needs an architecture that removes the database bottleneck while preserving correctness, availability, scalability, and observability. Which strategy should she adopt?

A
Maintain robust database transactions: vertically and horizontally scale the relational database (using read replicas and sharding based on SKU ranges) and stick with SELECT FOR UPDATE plus transactions for absolute consistency. Introduce connection pooling, edge-level queuing, and retry mechanisms with backoff to alleviate contention.
✗ Not Best
B
Transition to optimistic concurrency control: change write operations to version-based row updates (compare-and-swap / WHERE version = X), employing a limited retry loop with exponential backoff. Incorporate metrics and throttle highly popular SKUs based on a leaderboard to limit retries, while retaining the relational database as the primary source of truth.
✗ Not Best
C
Implement a distributed lock for each SKU utilizing Redis or ZooKeeper: obtain the lock during the request flow, execute the database update, and subsequently release the lock. Employ lock timeouts, lease renewals, and a clustered lock service to prevent single points of failure, while tracking lock latency and error rates.
✗ Not Best
D
Utilize sequential processing per key backed by an asynchronous durable log: route inventory modification intents to a partitioned messaging system (like Kafka or FIFO queues sharded by SKU) and handle each key serially using a dedicated consumer per partition. To achieve low latency for users, execute a rapid local reservation (using a cache or temporary database entry) and send the final stock reduction to the partitioned queue. Guarantee consumer idempotency, maintain a read model for current stock levels, and monitor consumer health and queue lag.

Answer & In-Depth Explanation

🏆 Best Answer — D: Per-SKU Serialized Processing via a Durable Log

The bottleneck is not the database's raw speed; it is many concurrent writers fighting over the same few rows. Funnel every change for a SKU through a single ordered lane (a log partition keyed by SKU) so one consumer applies them serially, with no lock waits and no retry storms. A fast atomic reservation at the edge gives the user an instant answer and enforces the never-oversell invariant, while the database is updated asynchronously and in batches. Here's why it stands out:

  • Contention removed by design: With one writer per SKU, nothing waits on a row lock. The consumer can also fold many reservations for the same SKU into a single net decrement, turning thousands of competing lock requests into a handful of sequential updates.
  • Fast, safe admission: An atomic conditional decrement (for example a Redis Lua script or a conditional insert) decides in about a millisecond whether stock exists. Only that atomic check can grant a reservation, so stock cannot go below zero, and the user gets an instant acknowledgement well within 100 ms.
  • Durable and replayable: Every intent is appended to a partitioned log (Kafka or FIFO queues). A consumer crash resumes from its offset, caches and read models can be rebuilt by replay, and you get a complete audit trail of stock movements.
  • Availability under stress: The user path no longer holds database locks, so a slow or briefly unavailable database delays confirmation instead of failing checkouts. The log absorbs flash-sale spikes, and partitions scale across the 100,000 SKUs.
  • Natural observability: Consumer lag per partition, reservation grant and reject rates, reservation age, and drift between counters and the ledger are all direct SLIs. Idempotency keys (order id plus SKU) make retries safe and traceable.

Model each reservation as a small state machine (RESERVED → CONFIRMED / RELEASED / EXPIRED) with TTLs, idempotency keys, and a periodic reconciliation job. Alert on consumer lag, drift between reservation counters and the ledger, and any oversell attempt (the target is zero).

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🔒

A — Scale the Database and Keep SELECT FOR UPDATE

Read replicas do nothing for write contention, and sharding by SKU range spreads different SKUs but leaves each hot SKU as one row on one shard, so the lock queue remains. Pooling, edge queues, and retries just move the waiting around and keep tail latency high. Caveat: at modest scale it is the simplest correct answer, and a cheap first fix is replacing read-then-write with one atomic UPDATE ... SET qty = qty - n WHERE sku = ? AND qty >= n in a short transaction.

🔁

B — Optimistic Concurrency (Compare-and-Swap)

CAS holds no lock while the application thinks and works well when conflicts are rare. On hot SKUs, though, most attempts lose the race and retry, which wastes database work, amplifies load, and starves some clients, so p99 latency worsens. Leaderboard-based throttling adds complexity and hurts user experience, and the database is still the single serialization point. It improves occasional conflicts, not hot-key contention.

🗝️

C — Distributed Locks (Redis / ZooKeeper)

A lock per SKU still serializes every hot-SKU request, now with extra network hops, and the database write still happens on each one. Lease-based locks can expire while a paused client is mid-operation, so correctness needs fencing tokens, and the lock service becomes a new availability dependency. You trade database lock contention for lock-service contention without removing the queue.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Scale DB + SELECT FOR UPDATE

Moderate write volume, low contention across SKUs, and a strong preference for operational simplicity. Usually combined with atomic conditional updates and short transactions.

📌

B — Optimistic Concurrency

Conflicts are rare (long-tail items, user-specific records) and retries are cheap. Not suited to flash sales or a handful of extremely hot rows.

📌

C — Distributed Locks

Coordinating work across systems that share no common transactional store, ideally for efficiency (avoiding duplicate work) rather than as the only guard for a hard correctness invariant.

📌

D — Per-SKU Log + Reservation

Very high write rates with hot keys, a hard no-oversell rule, a sub-100 ms user path, and tolerance for slightly delayed final confirmation. Worth the complexity once simpler fixes are exhausted.

⚠️ Common Mistakes to Avoid

  • Non-atomic reservation: Reading the counter and then writing it back in two steps creates a race that oversells exactly when traffic peaks. Use a single atomic operation (Lua script, conditional update).
  • Wrong order of operations: Publishing the intent before decrementing, or losing the intent after decrementing, breaks the invariant. Decrement first, publish with retries, and compensate on failure so errors fall toward under-selling, never over-selling.
  • No reservation TTL or release path: Abandoned carts and failed payments permanently hold stock. Expire reservations and release them through the saga.
  • Non-idempotent consumers: Redelivery after a rebalance double-decrements stock. Dedupe by command id (order id plus SKU) inside the same transaction as the update.
  • Wrong partition key: A random key loses per-SKU ordering, while a coarse key (such as category) creates hot partitions. Key by SKU and watch partition skew.
  • Treating the cache as the source of truth with no rebuild plan: A flush or failover then forces you to choose between overselling and a full outage. Keep the ledger authoritative and rebuild counters from it.

🌍 Real-World Best Practice

In practice, engineers fix the cheap things first and only add the log-based design when the hot-key problem is proven. A typical sequence looks like this:

  • Step 0 — Measure: Identify the hot SKUs, lock-wait time, and transaction duration. Confirm that the problem is row contention and not slow queries or connection exhaustion.
  • Step 1 — Cheap fixes: Replace read-modify-write with a single atomic conditional UPDATE ... WHERE qty >= n, keep transactions as short as possible, and move non-essential work out of the transaction.
  • Step 2 — Introduce reservations: Keep an atomic per-SKU counter (Redis Lua or similar) with reservation TTLs so users get instant answers without touching the database.
  • Step 3 — Add the durable log and per-SKU serial consumers: Partition by SKU, batch updates, dedupe by command id, and maintain a stock read model for browsing.
  • Step 4 — Handle hot SKUs explicitly: Use bucketed counters, or a virtual waiting room for flash sales, so one SKU cannot dominate a partition.
  • Step 5 — Reconcile and compensate: Run a saga for release and refund, rebuild counters from the ledger on a schedule, and alert on any drift.

Add moving parts only when measurement shows the simpler fix is exhausted.

💡

Key Takeaway

Contention on a hot row cannot be solved by scaling the database or by cleverer locking. Serialize writes per key behind a durable log and admit requests with a fast atomic reservation: users get an instant answer, stock never goes negative, and the database sees a few ordered, batched writes instead of thousands of competing ones.
