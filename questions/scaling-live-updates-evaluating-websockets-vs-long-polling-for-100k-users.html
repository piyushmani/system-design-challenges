Scaling Live Updates: Evaluating WebSockets vs. Long Polling for 100k+ Users

Liam, a senior backend engineer, is building a real-time collaborative dashboard for 100,000+ concurrent users across three regions. The system must deliver small event messages and presence updates with end-to-end latency of 200 ms or less, guarantee per-user message ordering, stay highly available so that a failure in one region does not disrupt the others, and be easy to observe. Web and mobile clients must be supported, and some legacy clients only support HTTP long polling. Which architecture for delivering updates and routing traffic between servers is the best fit?

A
Implement WebSockets utilizing load balancer sticky sessions to ensure every client remains linked to a specific application server. Maintain connection and subscription details in memory on each server, and employ server-to-server replication via RPC or peer connections to distribute messages across servers. Use long polling strictly as a fallback for clients incapable of establishing WebSocket connections.
✗ Not Best
B
Utilize WebSockets for active users while keeping application servers stateless, allowing sockets to terminate on any node and routing publish/subscribe messages through a highly available external broker like NATS, Kafka, or a Redis Cluster. Keep a compact, shared connection registry in a persistent store to associate user IDs with their respective hosting nodes, using the broker to distribute messages across regions and nodes. Include an HTTP long-polling fallback that accesses the same state and leverages the same message broker.
✗ Not Best
C
Avoid long-lived connections completely by deploying aggressive HTTP long polling across a dynamically scaled fleet of servers placed behind a global load balancer. Store the most recent state in a distributed cache and reply with state diffs. Decrease polling intervals in an effort to achieve the required latency, leaning on caching and horizontal auto-scaling to manage the traffic volume.
✗ Not Best
D
Implement a hybrid, region-centric architecture by using WebSockets inside each region alongside a local message bus to ensure low latency, while replicating events asynchronously across regions via an eventually consistent data stream. Route a user's write requests exclusively to their home region to ensure strict per-user message ordering, allowing read-only representations in other regions to remain eventually consistent. Supply a long-polling fallback for legacy clients.
✓ Best Answer
✅

Answer & In-Depth Explanation

🏆 Best Answer — D: Region-Centric WebSockets with Home-Region Ordering

Three requirements drive the design: a 200 ms budget (which rules out extra cross-region hops on the common path), per-user ordering (which needs one sequencer per user, not a global order), and regional fault isolation (which means each region must be able to run on its own). A region-centric design delivers all three: users connect to a nearby region over WebSockets, each user's events are sequenced in their home region, and other regions receive them through asynchronous replication. Here's why it stands out:

  • Local fan-out keeps latency low: Delivery to users in the same region is a WebSocket push through a local bus, typically a few tens of milliseconds and well inside 200 ms. Cross-region viewers pay inter-region latency once, not on every hop.
  • Per-user ordering is cheap and exact: All of a user's events pass through that user's home region, which assigns a monotonically increasing sequence number per user. Because the requirement is per-user (not global) ordering, no cross-region consensus is needed.
  • Failure isolation: Each region has its own gateways, bus, and connection state. If one region fails, the others keep serving their users; only users homed in the failed region need to be re-homed with a new epoch.
  • Stateless gateways inside each region: Any gateway can terminate any socket, and a regional bus (NATS, Redis Streams, Kafka) routes messages by subscription, so there is no sticky-session mesh to maintain and scaling out means adding nodes.
  • Legacy clients share the same path: Long-polling clients read from the same regional bus using a lastSeq cursor, so they receive the same ordered data with higher overhead and latency.
  • Operable and observable: Per-region metrics (connections, fan-out latency, bus lag, replication lag, reconnect rate) and event timestamps give end-to-end latency histograms and clear SLOs per region.

A practical recipe: stateless WebSocket gateways per region, a regional bus keyed by user, per-user sequence numbers plus epochs, asynchronous inter-region replication of the same stream, a cursor-based long-polling fallback, heartbeats, and backpressure. Monitor p99 publish-to-deliver latency, replication lag, sequence gaps, active connections, and reconnect rate by region.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

📌

A — Sticky WebSockets with Server-to-Server Replication

Sticky sessions and in-memory subscriptions make servers stateful: a crash loses subscription state, rebalancing is painful, and server-to-server replication forms a mesh whose fan-out cost grows roughly with the square of the server count. Deployments and autoscaling cause mass reconnects to specific nodes. It works for small clusters but does not scale gracefully to 100k users across regions. Caveat: stickiness itself is still useful for connection upgrade and long-poll affinity; the problem is putting state and routing logic inside the application servers.

🧰

B — Stateless WebSockets + Global Broker + Registry

This is a strong building-block design and is essentially what option D does inside each region. As described, however, it centers on one broker and one connection registry shared across regions, which couples regional failure domains and puts inter-region round trips on the fan-out path. It also does not say how per-user ordering is guaranteed across regions (a per-user Kafka partition key helps, but only within one cluster). Caveat: for a single-region deployment, B is arguably the simplest correct answer.

⏱️

C — Aggressive HTTP Long Polling

Long polling creates a new HTTP request and response cycle for each batch of events. At 100k users, shortening intervals multiplies request volume, TLS and header overhead, and server load, and still adds latency each time the poll is re-established. Ordering needs cursors and careful idempotency, and presence is awkward. It is a reasonable fallback, not a primary transport. Caveat: where proxies block WebSockets, long polling (or SSE) is a valid transport.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Sticky WebSockets

Small clusters in a single region where operational simplicity matters and the server count stays low.

📌

B — Stateless + Global Broker

Single-region or modest multi-region deployments where a shared broker is acceptable; also the building block used inside each region of the region-centric design.

📌

C — Aggressive Long Polling

Clients or networks that cannot use WebSockets or SSE, low-frequency updates, or as a fallback transport.

📌

D — Region-Centric

Large multi-region real-time systems with latency budgets, per-user ordering, and requirements for regional isolation.

⚠️ Common Mistakes to Avoid

  • Global ordering by accident: Forcing a total order across all users needs consensus or a single sequencer and destroys latency. The requirement is per-user ordering.
  • No sequence numbers or cursors: Without them, clients cannot dedupe or recover after a reconnect, and the long-polling fallback cannot resume.
  • Reconnect storms: Clients that reconnect immediately and in lockstep overload gateways after any blip. Use jittered exponential backoff and server-side admission control.
  • Unbounded per-connection buffers: A slow client can exhaust memory. Use bounded queues, coalesce or drop presence updates, and disconnect laggards so they resync.
  • Treating presence as strongly consistent: Presence is soft state. Use heartbeats and TTLs, and tolerate flapping.
  • Ignoring idle timeouts at proxies and load balancers: They close quiet sockets. Use ping/pong heartbeats and tune timeouts.

🌍 Real-World Best Practice

Real-time platforms keep each region self-sufficient and treat cross-region replication as an add-on for reach. A typical sequence looks like this:

  • Step 0 — Define budgets: Split the 200 ms into client-to-gateway, publish, bus, fan-out, and (when needed) replication, and set SLOs per region pair.
  • Step 1 — Terminate connections near users: Latency-based or geo DNS to the nearest region, with stateless gateways, heartbeats, and backpressure.
  • Step 2 — Regional bus keyed by user: Publish with key = userId so a partition preserves order, and assign per-user sequence numbers in the home region (the answer to this question).
  • Step 3 — Replicate asynchronously: Stream per-user ordered events to the other regions and apply them idempotently using (epoch, seq).
  • Step 4 — Support fallbacks: Long polling or SSE using the same cursors, and graceful degradation of presence updates under load.
  • Step 5 — Practice failure: Region evacuation drills, reconnect-storm tests, and load tests at two to three times the expected peak.

Optimize for locality first, then replicate for reach.

💡

Key Takeaway

Build each region as a self-contained real-time cell: stateless WebSocket gateways, a local bus, and per-user sequencing at the user's home region. Replicate asynchronously for cross-region reach and keep long polling as a cursor-based fallback. This satisfies the latency, ordering, and fault-isolation requirements together, as long as cross-region latency is measured against the 200 ms budget.
