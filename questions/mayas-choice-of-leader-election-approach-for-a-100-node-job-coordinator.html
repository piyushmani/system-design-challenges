Maya's Choice of Leader-Election Approach for a 100-Node Job Coordinator

Maya is a staff distributed systems engineer designing a mission-critical job coordination service intended to operate across up to 100 compute nodes distributed over multiple Availability Zones (AZs). The system architecture strictly requires that exactly one coordinator node acts as the active leader to sequence jobs, assign task partitions, and maintain unambiguous global task ordering. Key technical requirements include linearizable consistency for task assignments, automated leader failover completing within approximately 2 seconds during an AZ disruption, comprehensive observability into lease health, and minimal operational complexity for the platform team. Crucially, inter-AZ network connectivity exhibits occasional latency spikes, packet loss, and transient partitions. Maya must choose a leader-election approach that delivers uncompromising correctness without overwhelming cluster networking.

A
Embed a Raft consensus implementation directly within the application, allowing the nodes to form a Raft cluster without external dependencies.
✗ Not Best
B
Deploy a small, dedicated coordination cluster backed by Raft (like etcd or Consul) that is managed as a standalone operational service. Use its session/lease and watch APIs to handle leader election and store minimal metadata.
✓ Best Answer
C
Bypass leader election completely by designing a leaderless, multi-master architecture utilizing CRDTs or optimistic conflict resolution.
✗ Not Best
D
Implement a distributed lock mechanism on a general-purpose datastore, such as Redis (using Redlock) or rely on SQL row-locking to elect a leader.
✗ Not Best

Answer & In-Depth Explanation

🏆 Best Answer — B: Dedicated Coordination Cluster (etcd/Consul) via Leases and Streaming Watches

The fundamental distributed systems design principle here is the strict separation of consensus quorum size from application worker fleet scaling. Raft consensus scales poorly with cluster size: running Raft across 100 nodes requires a 51-node majority quorum for every single log entry and generates massive $O(N^2)$ cross-AZ heartbeat chatter, leading to heartbeat drops, election thrashing, and consensus deadlock under network jitter. By offloading leader election to a small, dedicated 3- or 5-node etcd or Consul cluster, consensus is constrained to a compact, highly optimized quorum. The 100 worker nodes compete for a short-lived lease (e.g., 2–3s TTL) using atomic Compare-And-Swap (CAS) transactions and monitor the leader key via streaming HTTP/2 gRPC Watches, enabling sub-2-second failover with near-zero network overhead.

  • Decoupling Consensus Quorum from Compute Fleet: Constraining Raft to a 3- or 5-node dedicated cluster limits quorum consensus to 2 or 3 votes, eliminating the exponential message overhead and heartbeat timeouts inherent in 100-node consensus.
  • Sub-2-Second Deterministic Failover via Streaming Watches: Standby nodes maintain an open gRPC Watch stream on the leader key. The instant the active leader's lease expires or its session heartbeat fails, etcd fires a key deletion event, triggering immediate standby election without polling.
  • Strong Linearizability and Split-Brain Prevention: etcd provides strict linearizable consistency backed by formal Raft consensus. Monotonically increasing revision numbers (fencing tokens) prevent split-brain zombies from issuing conflicting task assignments.
  • Minimal Worker Node Footprint: The 100 coordinator instances remain lightweight, running standard client libraries without maintaining local consensus state machines, WALs, or log compaction routines.
  • Production-Grade Telemetry: Standalone coordination engines provide turnkey Prometheus metrics for lease time-to-live, Raft proposal latencies, disk sync durations, and leader election churn.

Isolating consensus to a dedicated, battle-tested coordination cluster guarantees linearizable task ordering, rapid failover, and predictable networking while allowing the worker fleet to scale independently.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🕸️

A — Embedded Raft Across All 100 Application Nodes

Embedding Raft consensus across 100 nodes is a well-known distributed systems anti-pattern. Raft consensus requires a majority quorum (51 of 100 nodes) for every state transition and heartbeat round. In an environment with 100 nodes across multiple AZs experiencing unreliable network connectivity, heartbeat timeouts and lost election RPCs trigger continuous re-elections, consensus paralysis, and catastrophic network saturation.

🌀

C — Leaderless Multi-Master Architecture with CRDTs

A leaderless architecture utilizing Conflict-free Replicated Data Types (CRDTs) or optimistic concurrency is fundamentally incompatible with strict global task ordering and single-coordinator assignment. CRDTs provide eventual convergence for commutative data operations (like sets or counters), but cannot enforce linearizable, mutually exclusive decision-making or sequence interdependent tasks without consensus.

🔒

D — Distributed Locks via Redis (Redlock) or SQL Row-Locking

Redis Redlock and SQL row-locking fail the strict consistency and failover requirements. As formally proven by Martin Kleppmann, Redlock makes dangerous timing assumptions regarding wall clocks and network delays, making it unsafe for consensus under GC pauses and clock drift. Meanwhile, SQL row-locking with high-frequency polling introduces severe database connection contention and cannot reliably complete failover within 2 seconds without risking split-brain during AZ network splits.

⚡

B — Dedicated Coordination Cluster (etcd/Consul) via Leases and Streaming Watches ✓

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Embedded 100-Node Raft

Small, fixed 3-to-5 node clustered appliances or distributed databases (like TiKV or CockroachDB) where each consensus group is strictly capped at 3–5 replicas.

📌

B — Dedicated etcd/Consul Cluster

Clustered workloads with tens to hundreds of worker nodes requiring a single authoritative coordinator, sub-second failover, linearizable state, and minimal network overhead.

📌

C — Leaderless CRDTs

Collaborative text editing, shopping cart item counting, or distributed metrics aggregation where operations are commutative and global ordering is unnecessary.

📌

D — Redis Redlock / SQL Locks

Coarse-grained, non-critical background jobs (e.g., nightly batch invoice generation) where occasional lock contention or brief duplicate execution does not cause data corruption.

⚠️ Common Mistakes to Avoid

  • Omitting fencing tokens on task assignment: Believing a lease protects against split-brain without passing a monotonically increasing token (e.g., mod_revision) allows a partitioned leader to write after lease expiration during a GC pause.
  • Using polling instead of streaming Watches: Polling the leader key every 500 ms creates high query load on etcd; use long-lived HTTP/2 gRPC Watches for instantaneous push notifications.
  • Co-locating etcd on shared, throttled disks: etcd requires low fsync latency (< 10 ms p99) for its Raft write-ahead log; running on burstable EBS or shared storage causes election timeouts.
  • Setting lease TTL shorter than GC pause times: A JVM or Go runtime stop-the-world GC pause longer than the lease TTL triggers false leader ejections and rapid election flapping.
  • Ignoring lease keep-alive failure in the active leader: If the leader's background heartbeat fails due to network partition, the application must immediately abdicate and stop scheduling tasks.

🌍 Real-World Best Practice

Senior distributed systems engineers know that consensus does not scale horizontally: consensus algorithms are designed for 3, 5, or at most 7 nodes, never for 100 nodes.

  • Step 0 — Fixed Quorum Sizing: Deploy a 3-node or 5-node etcd cluster spread across three Availability Zones. This guarantees tolerance of 1 or 2 node/AZ failures while keeping consensus round-trips tight.
  • Step 1 — Ephemeral Leases with Background Keep-Alives: The leader creates a 2-second lease (client.Grant(ctx, 2)) and associates it with a leadership key (/service/leader) via an atomic transaction. A background goroutine issues heartbeats every 600 ms.
  • Step 2 — Push-Based Standby Waiting via gRPC Watch: All 99 standby nodes open a gRPC Watch on /service/leader. Standby nodes remain idle with zero CPU and negligible network usage until a DELETE event is received.
  • Step 3 — Fencing Tokens for Task Dispatch: Whenever the leader assigns a task to worker pools, it includes the etcd mod_revision as a monotonically increasing fencing token. Workers reject any task with a token lower than the highest seen token.
  • Step 4 — Fast Graceful Step-Down: On SIGTERM or planned deployment, the leader explicitly revokes its lease before process exit, allowing a standby node to claim leadership in under 50 ms.

By offloading the hard problem of consensus to an external 3-to-5 node cluster, the 100-node coordinator fleet stays simple, resilient, and blazingly fast to fail over.

💡

Key Takeaway

Never embed Raft consensus across 100 nodes. Separate consensus from compute: use a dedicated 3- or 5-node etcd cluster with leases and gRPC Watches for sub-2-second failover and linearizable task coordination.
