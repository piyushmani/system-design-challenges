Jordan's CDN Trade-off: Content Freshness vs. Scale

Jordan is the backend architect for a global e-commerce platform. Product pages are mostly cacheable, user-independent HTML (images, descriptions), but prices and inventory change and must show up within a few seconds. Traffic is spiky, and the origin cannot absorb heavy revalidation traffic. The team uses a multi-region CDN with edge caching. Jordan needs a strategy that balances low latency, a high cache hit rate, minimal origin load, and the ability to push urgent price and inventory updates quickly.

A
Assign lengthy TTLs (measured in hours) to all product pages and depend on URL versioning (deploying a new URL or fingerprint when content shifts). Bypassing runtime invalidation, link updates on the site occur when prices are modified.
✗ Not Best
B
Configure extremely brief global TTLs for product pages (e.g., 3-5 seconds) ensuring edges consistently fetch the latest content, without background revalidation or purging. This ensures data freshness but elevates traffic to the origin.
✗ Not Best
C
Apply moderate TTLs combined with cache-control directives that include stale-while-revalidate at the edges. Introduce an origin shield to aggregate revalidations, utilize conditional GETs (ETag/If-Modified-Since) to minimize payload size during revalidation, and execute selective instant invalidation via the CDN's surrogate-key or purge API for critical updates to price and inventory.
✓ Best Answer
D
Transmit every change in price and inventory to all CDN edge nodes through a push/replication channel, ensuring edges are synchronously updated upon write operations. Content is always served from the edge, which functions as the definitive store for current data.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — C: Moderate TTL + stale-while-revalidate + Origin Shield + Surrogate-Key Purge

The scenario contains a tension that no single TTL can resolve: pages should be served from the edge almost all the time, yet price and stock changes must appear within seconds, and the origin cannot handle revalidation storms. Option C resolves it with layers, each handling one failure mode: a moderate TTL with stale-while-revalidate keeps users on fast cached responses, an origin shield collapses many edge revalidations into one origin request, conditional GETs make that request cheap, and event-driven purge by surrogate key delivers urgent updates without waiting for TTL expiry. Here's why it stands out:

  • Users never wait for revalidation: With stale-while-revalidate, an edge serves the cached copy immediately and refreshes it in the background, so p99 latency stays at edge speed even when objects expire during spikes.
  • Origin load is bounded: Without a shield, origin requests per hot URL scale with the number of edge locations divided by the TTL. A shield (a single regional cache tier in front of the origin) turns hundreds of edge misses into roughly one, and request collapsing keeps concurrent misses from stampeding.
  • Revalidation is cheap: ETag or Last-Modified conditional requests let the origin answer 304 Not Modified after a lightweight version check, with no page render and no body transfer.
  • Urgent changes beat the TTL: A price or stock change emits an event that triggers a purge by surrogate key (for example product-123). Modern CDNs propagate purges in roughly sub-second to a few seconds, depending on vendor, which matches the freshness requirement.
  • Resilient to origin problems: stale-if-error lets edges keep serving a slightly old page if the origin is slow or down, which is usually better than a failed product page during a traffic spike.

A tuned setup defines cache keys carefully (strip tracking parameters, minimal Vary), uses surrogate keys that map to products and categories, runs a purge pipeline with batching and retries, and tracks hit ratio, origin offload, revalidation rate, and purge latency as first-class metrics.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🧷

A — Long TTLs + URL Versioning

Fingerprinted URLs are the right tool for immutable assets such as images, CSS, and JS. For product pages they fail: canonical URLs, bookmarks, search rankings, and inbound links need a stable address, and changing the URL on every price update is impractical. Hour-long TTLs with no invalidation also cannot meet the few-seconds freshness target for prices and stock. Caveat: use it for static assets alongside option C for the HTML and dynamic data.

⏱️

B — Very Short Global TTLs, No Revalidation or Purge

Freshness is easy, scale is not. With, say, 200 edge locations and a 5-second TTL, a single hot URL can generate about 40 origin requests per second just from expiry, multiplied across popular products. Without stale-while-revalidate, each expiry makes a user wait for the origin, so p99 latency spikes and concurrent misses cause a thundering herd, which the origin explicitly cannot handle. Caveat: short TTLs are acceptable for a few small dynamic endpoints when they are protected by a shield and stale-while-revalidate, which is precisely what option C adds.

📡

D — Synchronous Push to Every Edge

Making edges the system of record and updating hundreds of locations synchronously on every write couples write latency and availability to the slowest or failed POP. Mainstream CDNs do not offer synchronous global replication as a service, and consistency during partial failures becomes a hard distributed-systems problem. It also bloats edges with data that may never be requested. Caveat: edge key-value stores can hold small hot datasets with eventual replication, but that is a different guarantee from synchronous push.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Long TTL + URL Versioning

Immutable assets (images, CSS, JS, fonts) where each change ships under a new fingerprinted URL.

📌

B — Very Short TTLs

A tiny number of cheap-to-render dynamic endpoints with low traffic, where origin capacity is comfortably sufficient.

📌

C — SWR + Shield + Surrogate Purge

Mostly cacheable pages with a small volatile component, spiky traffic, a fragile origin, and a need for near-immediate updates on specific events.

📌

D — Synchronous Push to Edges

Rarely justified. Consider eventually consistent edge key-value stores for small hot configuration data, not synchronous replication of a catalog.

⚠️ Common Mistakes to Avoid

  • Trusting cached prices at checkout: A stale price shown for a few seconds is a UX issue, but charging it is a financial issue. Re-read authoritative data when adding to cart and paying.
  • Hard purge on every change: Evicting objects forces a synchronized wave of misses to the origin. Prefer soft purge and let the shield absorb revalidation.
  • Fragmented cache keys: Tracking parameters, unneeded Vary headers, or cookies in the key destroy hit rate. Normalize keys and strip irrelevant inputs.
  • No shield tier: Hundreds of POPs revalidating independently multiply origin load. Enable a shield or tiered cache.
  • Using stale-while-revalidate with no purge path: Users could see old prices for the whole SWR window. Combine it with event-driven purge for volatile data.
  • Unmonitored purge pipeline: Failed or delayed purges silently serve wrong data. Alert on purge latency and failures, and keep the TTL as a backstop.

🌍 Real-World Best Practice

CDN strategy is about classifying content by how often it changes and applying the cheapest mechanism that meets each class's freshness need. A typical setup looks like this:

  • Step 0 — Classify content: Immutable assets, slow-changing page content, and fast-changing data (price, stock) each get a different policy.
  • Step 1 — Cache static assets forever: Fingerprinted URLs with Cache-Control: public, max-age=31536000, immutable.
  • Step 2 — Cache HTML moderately: A short browser TTL, a longer shared-cache s-maxage, plus stale-while-revalidate and stale-if-error.
  • Step 3 — Add an origin shield and request collapsing: Reduce origin traffic to roughly one request per object per refresh.
  • Step 4 — Purge by surrogate key on change events: Price and inventory services emit events, a purge worker batches them and calls the CDN's soft-purge API.
  • Step 5 — Isolate volatile fields and verify at checkout: Serve price and stock from a tiny short-TTL endpoint if needed, and always re-validate authoritative values on the transactional path.

Measure hit ratio, origin offload, and purge propagation time before tuning TTLs.

💡

Key Takeaway

Don't pick a single TTL for a mixed-volatility page. Serve stale instantly, refresh in the background, collapse revalidations behind a shield, and purge precisely when something important changes. Keep the cache for speed and display, and keep authoritative price and stock checks on the transactional path.
