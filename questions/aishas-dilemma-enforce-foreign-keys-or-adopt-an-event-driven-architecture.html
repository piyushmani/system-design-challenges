Foreign Keys Event Driven Data Integrity
Challenge

Aisha's dilemma: enforce foreign keys or adopt an event-driven architecture?

Aisha, a backend architect, is building an orders and payments platform. In the existing monolith, orders.customer_id is a foreign key to customers.id and the database strictly enforces referential integrity. As the team moves to microservices, the Orders, Customers, and Payments services will each own their own database. She must choose a strategy for primary keys and cross-service foreign-key relationships that delivers excellent throughput, minimal latency when placing orders, autonomous deployments, robust availability during partial outages, and effective observability for tracing relationships across services. Which architectural strategy should she select?

A
Retain one shared relational database for all services, relying on the database to enforce PK/FK constraints (e.g., orders.customer_id as a foreign key to customers.id). This ensures strong consistency and straightforward transactional updates and deletions.
✗ Not Best
B
Assign globally unique identifiers (such as Snowflake or time-sorted UUIDs) to each entity, enforcing foreign key constraints solely within each service's individual database. Handle cross-service relationships through event-driven messaging: as Customer data changes, emit events; the Orders service subscribes to these and updates its own denormalized customer records or tracks eventual consistency links. Utilize consumer-side validation for reads, retries, and idempotent event handlers.
✓ Best Answer
C
Maintain isolated databases but implement distributed transactions (like two-phase commit) across the services to preserve strict referential integrity alongside data partitioning. Employ a transaction coordinator to execute commits or rollbacks for operations that span both the Order and Customer databases.
✗ Not Best
D
Allow every service to independently create random UUIDs for primary keys, completely abandoning foreign key semantics. Depend on periodic background reconciliation tasks to identify and remove orphaned payments or orders, and simply respond with a 404 error if a linked customer cannot be found during a read operation.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — B: Global IDs, Local FKs, and Event-Driven References

A database can only enforce a foreign key inside one database. Once each service owns its data, keep referential integrity within each service boundary and turn cross-service FKs into logical references using globally unique IDs. Keep those references correct through events and a small local copy of the reference data the service needs, validated at write time against that local copy so placing an order never makes a synchronous call to the Customers service. Here's why it stands out:

  • Autonomy and availability: Orders can accept orders while Customers is down or mid-deployment, because it validates against its own customer_ref table. There is no shared schema, so each team deploys and migrates independently.
  • Low latency, high throughput: Lookups and joins are local. There are no cross-network calls, distributed locks, or coordinators on the order-placement hot path.
  • Coordination-free identifiers: Snowflake IDs, UUIDv7, or ULIDs can be minted by any service without a central sequence. Because they are time-ordered, they also keep B-tree indexes compact, unlike random UUIDv4 values.
  • Integrity where it is enforceable: FK constraints stay inside each service database. Across services, integrity comes from consumer-side validation, idempotent and versioned event handlers, retries, and a dead-letter topic, with reconciliation only as a safety net.
  • Traceable relationships: Every event and request carries entity IDs plus correlation and causation IDs (W3C traceparent across HTTP and messaging). Event lag, orphan-reference rate, and DLQ depth become first-class metrics.

Define data ownership (Customers owns customer data), publish versioned events with a schema registry, enforce FKs within each service, validate cross-service references at write time against local reference data, and use sagas for multi-service business transactions. Monitor orphan rates and event lag from day one.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🗄️

A — Shared Database

A shared database keeps FKs and ACID transactions, and it is a reasonable stepping stone toward a modular monolith. But it defeats every stated goal: services are coupled through the schema (any migration becomes a cross-team change), they share connection pools, locks, and blast radius, and they cannot deploy or scale independently. It is a distributed monolith, not microservices.

🔐

C — Distributed Transactions (2PC)

Two-phase commit preserves strict integrity but is a blocking protocol. Locks are held across services, the coordinator is a single point of failure, latency grows with the number of participants, and one unavailable participant stalls everyone. Many modern brokers and NoSQL stores do not support XA at all. The standard alternative for multi-service business operations is a saga with compensations.

🎲

D — Random UUIDs, No FK Semantics, Reconcile Later

Independently generated UUIDs are fine, and that part is compatible with option B. The flaw is abandoning reference validation: orphans are discovered after the fact, users see 404s for integrity failures, and reconciliation becomes the only control instead of a safety net. Random UUIDv4 primary keys can also fragment clustered indexes. Option B keeps references validated at write time.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Shared Database

Early-stage products, a modular monolith, or a short migration phase where one team owns all the data and independent deployment is not yet required.

📌

B — Global IDs + Local FKs + Events

Independently deployed services with separate data stores, where write-time latency and availability matter and brief propagation delays between services are acceptable.

📌

C — Distributed Transactions (2PC)

Rare, tightly controlled cases (for example two databases in the same trust domain with XA support) where atomic cross-store commits are mandatory and the throughput cost is acceptable.

📌

D — Random UUIDs, No FKs

Loosely related data where orphans are harmless, such as best-effort telemetry or analytics references. Not suitable for orders and payments.

⚠️ Common Mistakes to Avoid

  • Dual-writing to the database and the broker: If either write fails, the services drift apart silently. Use a transactional outbox so the event is committed with the state change.
  • Copying the entire customer profile: Large replicas blur ownership, multiply privacy exposure, and recreate a distributed monolith. Replicate only the fields the consumer needs.
  • Non-idempotent, unordered event handlers: Redelivery and reordering corrupt local copies. Partition by entity id, carry a version, and ignore anything not newer.
  • Calling the Customers service synchronously on every order: That reintroduces the latency and availability coupling you set out to remove. Validate against local data instead.
  • Ignoring delete and privacy semantics: Cascading deletes no longer exist. Define tombstones, anonymization, and retention rules before the first deletion request arrives.
  • Choosing identifiers carelessly: Auto-increment integers collide on merges and leak volume, while random UUIDv4 primary keys fragment indexes. Prefer time-ordered globally unique IDs.

🌍 Real-World Best Practice

In practice, teams migrate incrementally with the strangler pattern rather than flipping everything at once. A typical sequence looks like this:

  • Step 0 — Draw the ownership map: Decide which service owns which entity and list every foreign key that crosses a service boundary.
  • Step 1 — Turn cross-boundary FKs into logical references: Keep the column and an index, drop the database constraint, and introduce globally unique IDs (UUIDv7, ULID, or Snowflake). Keep legacy integer ids as an alternate key during the transition.
  • Step 2 — Publish change events reliably: Add a transactional outbox to the owning service and publish versioned events to the broker, with schemas in a registry.
  • Step 3 — Build local reference data: Have consuming services upsert a minimal, version-guarded copy (for example customer_ref) from those events.
  • Step 4 — Validate at write time and handle the unknown: Check the logical FK against local data, and define behavior for references that have not arrived yet (park, retry, or a bounded verification call).
  • Step 5 — Add safety nets and observability: Run a periodic reconciliation job, track the orphan-reference rate and event lag, and propagate trace context across HTTP and messaging.

Use sagas for multi-service workflows (order, payment, fulfillment) and keep the reference-data pattern for lookups and validation.

💡

Key Takeaway

A foreign key is a single-database feature. When data ownership splits, keep FKs inside each service, replace cross-service FKs with globally unique logical references, and keep them correct through events, local reference data, and write-time validation. You trade instant global integrity for autonomy, availability, and low latency, and you recover the safety with idempotent handlers, outbox publishing, and monitoring.
