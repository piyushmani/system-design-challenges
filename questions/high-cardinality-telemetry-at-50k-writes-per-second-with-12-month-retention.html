High-Cardinality Telemetry at 50K Writes per Second with 12-Month Retention

Priya is architecting telemetry for a large network of smart meters. Traffic is about 50,000 writes per second with roughly 200,000 unique metric-and-tag combinations per minute (high cardinality that will keep growing). Data must be kept for 12 months. The SLO requires sub-100 ms queries on the last hour, while older data needs flexible ad-hoc querying. The design must also provide durable ingestion, the ability to reprocess data after pipeline bugs, cost-effective long-term storage, and costs that stay manageable as cardinality grows. Which architecture fits best?

A
Save time-series data directly into a distributed wide-column database (like Scylla or Cassandra). Structure rows using (metric_id, time_bucket) with a clustered write strategy, manage data lifecycle with TTLs, and create secondary indexes to handle tag filtering. Optimize compaction and consistency settings for each write operation.
✗ Not Best
B
Adopt a stream-first approach: capture raw events in a durable log (such as Kafka). Utilize stream processing frameworks (Materialize/ksql/Flink) to calculate real-time aggregations and maintain materialized views in an OLAP database tuned for rapid querying (like ClickHouse). Store raw events in object storage (e.g., S3) to support long-term analysis and data reprocessing.
✓ Best Answer
C
Depend on a managed time-series database (such as Timescale Cloud or InfluxDB Cloud) as the comprehensive solution for ingestion, querying, data retention, and downsampling. Trust the provider to handle scaling, replication, and complex query operations.
✗ Not Best
D
Implement a relational database (like Postgres) utilizing time-partitioned tables (hourly or daily), storing tags within a JSONB column indexed via GIN. Ensure strong consistency using synchronous replication, and run background processes to summarize older partitions into aggregate tables.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — B: Stream-First: Log, Real-Time Aggregation, OLAP and Raw Lake

Option B makes the immutable raw event log the source of truth and treats every queryable store as a derived, rebuildable view. That one decision satisfies the hardest requirements together: durable ingestion, reprocessing after bugs, cheap long-term storage, and cardinality that does not break the serving layer. Here's why it stands out:

  • Columnar OLAP tolerates high cardinality: engines like ClickHouse store rows sorted by (metric, series, time) and do not keep a per-series in-memory index the way inverted-index TSDBs do, so adding series grows storage roughly linearly instead of blowing up memory.
  • Fast recent queries: pre-aggregated views and a sort key matching the access pattern keep last-hour reads comfortably under 100 ms.
  • Reprocessing is a first-class operation: raw events live in object storage (Parquet), so fixing a unit-conversion or aggregation bug means replaying history into a new table and swapping it in, instead of hand-patching production data.
  • Durable and burst-safe ingestion: the log absorbs meter bursts and downstream outages, and consumers catch up from stored offsets.
  • Cost scales gently: hot data sits on fast disks for a couple of weeks, then tiers to object storage for the rest of the 12 months, while ad-hoc history queries read Parquet or the tiered table.
  • Sizing check: 50,000 writes per second is about 4.3 billion points per day and roughly 1.6 trillion per year. That is manageable for a compressed columnar store but impractical for a row store with secondary indexes.

Treat raw events as the ledger and everything else as a cache of it. Version your aggregation logic, keep Kafka retention long enough to cover your slowest recovery, and rehearse a full replay periodically so reprocessing is a drill, not a hope.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🧱

A — Wide-Column Store with Secondary Indexes

Cassandra and Scylla ingest 50,000 writes per second easily, but the hard requirements are on the query side. Secondary indexes on high-cardinality tags are a known anti-pattern, scan-heavy ad-hoc queries are not the model's strength, and rollups and downsampling must be built elsewhere. Reprocessing also needs raw data kept outside the database. Caveat: a good write-optimized serving store for known access patterns, but a poor single store for ad-hoc analytics.

☁️

C — Managed TSDB as the Whole Solution

A managed TSDB is the fastest way to start and can be right at lower cardinality. But cardinality is the stated pressure here: many TSDBs build per-series indexes held in memory, so cost and latency can climb steeply as series grow. Raw data lives only inside the vendor's store, which makes bug-fix reprocessing and portability harder, and trusting the provider hides pricing, limits and lock-in. Caveat: verify cardinality limits and pricing against projected series growth before committing.

🐘

D — Postgres with JSONB and GIN

At about 4.3 billion rows per day, a single relational primary cannot keep GIN-indexed JSONB tags up with the write rate: GIN has heavy write amplification, and tag-heavy filters bloat indexes as cardinality grows. Synchronous replication adds commit latency to every write. Twelve months is well over a trillion rows, so partition maintenance, vacuum and storage cost become the main workload. Caveat: works well for much smaller meter fleets.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Wide-Column + Secondary Indexes

Known, key-based access patterns (fetch one meter's latest readings) at very high write rates, with ad-hoc analytics handled elsewhere.

📌

B — Stream-First + OLAP + Lake

High and growing cardinality, long retention, a need to reprocess history, and a mix of real-time and ad-hoc analytics.

📌

C — Managed TSDB Only

Small to medium cardinality, a small team and fast time to market, where vendor limits and pricing have been verified and lock-in is acceptable.

📌

D — Postgres + JSONB + GIN

Modest fleets (millions, not trillions, of rows) with strong relational needs, where the simplicity of one database outweighs its scale limits.

⚠️ Common Mistakes to Avoid

  • Letting tags run free: request IDs, timestamps or free text in tags create unbounded series. Define an allow-list and a cardinality budget.
  • Row-at-a-time inserts into OLAP: this creates thousands of tiny parts and slows merges. Batch inserts or use async inserts.
  • Replaying into live aggregates: this double counts. Rebuild into a new table and swap, or use idempotent keys.
  • Short log retention: if Kafka retention is shorter than your recovery time, the raw lake becomes the only replay source. Know which one you depend on.
  • Sort key not matching the queries: an OLAP sort order that ignores the filter columns forces full scans. Design it from the real queries.
  • No pipeline observability: watch consumer lag, insert errors, series growth and part counts so problems surface before the SLO breaks.

🌍 Real-World Best Practice

A pragmatic rollout starts simple and adds stages only when measurements demand them:

  • Step 0 — Define the access patterns: list the dashboards, alerts and ad-hoc queries, plus the allowed tag keys and a cardinality budget.
  • Step 1 — Ingest to a durable log: partition by meter or metric, enforce a schema registry, and reject unbounded tag values.
  • Step 2 — Land raw data in object storage: write immutable Parquet partitioned by date. This is the system of record for replay.
  • Step 3 — Serve from OLAP: load into ClickHouse with a sort key aligned to the queries and materialized views for 1-minute and 1-hour rollups.
  • Step 4 — Tier and expire: move older parts to object storage and apply a TTL at 12 months.
  • Step 5 — Add stream processing only if needed: for windowed joins, anomaly detection or enrichment.
  • Step 6 — Rehearse reprocessing: replay into a shadow table, compare results, then swap.

Observability on the pipeline itself (consumer lag, insert latency, series growth) is part of the design.

💡

Key Takeaway

Keep an immutable raw log as the source of truth and build serving stores as rebuildable views. A columnar OLAP engine handles high-cardinality queries without per-series memory costs, and object storage keeps long retention and reprocessing cheap.
