Challenge

Balancing Inventory Accuracy and Read Speed in an Event-Driven Order Flow

Liam, a backend engineer, is designing the order-processing flow for a high-volume e-commerce platform that handles thousands of events per second. Product and checkout pages need low-latency inventory reads, the architecture must be event-driven (scalable, with event replay for analytics and recovery), and one business rule is non-negotiable: inventory must never be oversold. Stock for each SKU has a single authoritative owner (the inventory database), browse pages can tolerate a few seconds of staleness, but the purchasing user must see their own reservation immediately. The team also needs high availability and good observability without adopting exotic infrastructure. Which architecture should he choose?

A
A completely asynchronous event-sourced architecture: record each inventory modification as an event in Kafka, employing event-sourcing and CQRS to asynchronously generate materialized read models. Depend on compacted topics as the single source of truth, rebuilding read models from events as required. Tolerate eventual consistency for reads and rely on compensating transactions in case of overselling.
✗ Not Best
B
A synchronous, strongly consistent architecture: during checkout, make a synchronous call to the Inventory service to execute a serializable transaction (or two-phase commit) on a central inventory database, using distributed locks to prevent negative inventory balances. Only emit events once the transaction has successfully committed.
✗ Not Best
C
A hybrid approach using a transactional outbox and a read-your-writes cache: atomically commit inventory updates alongside an outbox record in the database. A background worker then publishes these outbox entries to Kafka for global events and materialized views. To serve customer reads, implement a local write-through/read-through Redis cache (or a session-based read-your-writes cache) to deliver near-real-time inventory data, preventing stale reads for the purchasing user. Ensure consumers are idempotent and process events in order when necessary.
✓ Best Answer
D
A decentralized architecture utilizing CRDT replication: represent inventory using conflict-free replicated counters distributed across services via peer-to-peer replication. Depend on the convergence properties of CRDTs to achieve eventual consistency, enabling each region to handle read requests locally with minimal latency and without the need for a central message broker.
✗ Not Best

Answer & In-Depth Explanation

🏆 Best Answer — C: Transactional Outbox + Read-Your-Writes Cache

The anti-oversell rule is an invariant (stock never goes below zero), and an invariant needs a single serialization point. Option C keeps that point in a transactional database using an atomic conditional decrement, and treats Kafka and the cache as downstream projections. The transactional outbox closes the gap between 'the database committed' and 'the event was published', so replay and analytics stay accurate, while the cache plus per-session read-your-writes delivers low-latency reads. Here's why it stands out:

  • Correctness lives in one place: UPDATE inventory SET available = available - :qty WHERE sku = :sku AND available >= :qty is atomic and cannot drive stock negative, even with many concurrent buyers. If zero rows are updated, the item is out of stock.
  • No lost or phantom events: The stock change and the outbox row commit in the same local transaction, so an event exists if and only if the change committed. This removes the crash window of 'commit, then publish' that makes direct dual writes unreliable.
  • Fast, honest reads: Product pages read a Redis projection (typically sub-millisecond to a few milliseconds) that may lag by seconds. The purchasing user's session carries the version of their last write, so a stale cache entry is bypassed and they never see their own reservation disappear.
  • Replay and analytics: Kafka receives every committed change as an ordered per-SKU stream (keyed by SKU), so read models, search indexes, and analytics can be rebuilt by replaying the topic without making Kafka the arbiter of stock.
  • Operationally proportionate: A relational database, an outbox relay (or Debezium CDC), Kafka, and Redis are all mainstream components. There are no distributed locks, no 2PC, and no custom convergence logic to maintain.

A solid implementation includes an atomic conditional decrement, a reservation with TTL, an outbox relay or CDC, idempotent consumers, and versioned cache writes. Monitor outbox lag, cache-versus-database drift, reservation expiry rate, and oversell count (which must stay at zero). If outbox lag grows, reads degrade gracefully but stock correctness is unaffected.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

📜

A — Event Sourcing + CQRS on Kafka

Event sourcing is excellent for audit and replay, but a log cannot reject a command by itself. To enforce stock never goes negative you still need a single writer per SKU that validates before appending. As written, the option accepts eventual consistency and fixes overselling with compensating transactions, which means customers are sold stock that does not exist and then apologized to. Using compacted topics as the sole source of truth also discards history (compaction keeps only the latest value per key), which undermines replay. Caveat: event sourcing with a validating command handler per SKU is a legitimate design when full history is the product requirement.

🔒

B — Synchronous Serializable Transactions + Locks

Strongly consistent, but at a high price. Serializable or 2PC transactions plus distributed locks on a central database put every checkout in one contention queue, couple checkout availability to the lock service and the database, and add tail latency exactly when traffic peaks. Emitting events only after commit also recreates the dual-write problem: a crash between commit and publish silently loses events. Option C achieves the same no-oversell guarantee with a single-row atomic update, no distributed locks, and a reliable event hand-off.

🌐

D — CRDT Replication

CRDT counters converge without coordination, which suits things like view counts. But non-negative stock is a global invariant that coordination-free replication cannot protect: two regions can each sell the last unit while partitioned, and a PN-counter will happily converge to -1. Bounded-counter or escrow designs exist, but they reintroduce coordination for the last units. Dropping the broker also removes the replayable log the requirements ask for.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Event Sourcing + CQRS

Audit-heavy domains (ledgers, financial positions) where full history is the product, with a validating command handler per aggregate that accepts or rejects before appending.

📌

B — Sync Serializable + Locks

Low-volume systems (back-office, B2B ordering) where one database comfortably handles the load and simplicity matters more than peak throughput.

📌

C — Outbox + Read-Your-Writes Cache

High-volume retail where stock must never go negative, reads vastly outnumber writes, and events need to drive search, analytics, and notifications.

📌

D — CRDT Replication

Counters that only grow or tolerate drift (likes, views, presence) across regions, where no global bound has to be enforced.

⚠️ Common Mistakes to Avoid

  • Dual writes without an outbox: Updating the database and publishing to Kafka as two independent steps. A crash between them loses or duplicates events. Write the event row in the same transaction.
  • Treating the cache as the stock authority: Decrementing a Redis counter and 'syncing later' reintroduces oversell on eviction or failover. The database decrement is the decision.
  • Unversioned cache writes: Two concurrent updates can write to the cache out of order and leave an older value in place. Store a version with each entry and only overwrite with a newer one, atomically (for example with a Lua script).
  • Non-idempotent consumers: The outbox relay delivers at-least-once, so a redelivered InventoryReserved event must not change a read model twice.
  • Losing per-SKU ordering: Several relay workers racing on one outbox, or a Kafka key that is not the SKU, can reorder events for a single product. Key by SKU and shard the relay, or use CDC.
  • Reservations that never expire: Abandoned carts hold stock forever. Give every reservation a TTL and a reaper that returns the units.

🌍 Real-World Best Practice

In practice, teams treat inventory as two different problems: an authoritative ledger for decisions and cheap projections for display. A typical rollout looks like this:

  • Step 0 — Define the invariant and the staleness budget: Which operations must be exact (reserve, release, commit) and which may be seconds stale (browse pages, search facets)?
  • Step 1 — Authoritative ledger: Atomic conditional decrement plus a reservation row with a TTL in the inventory database, with an idempotency key on every reserve request.
  • Step 2 — Outbox: Write the event row in the same transaction, then publish via a relay or Debezium CDC into Kafka keyed by SKU.
  • Step 3 — Projections: Idempotent consumers build Redis and search read models. Cache entries carry a version so an older write never overwrites a newer one.
  • Step 4 — Read-your-writes: Return the new version in the reserve response; the session sends it back on reads and the read path falls through to the database if the cache is behind.
  • Step 5 — Observability and reconciliation: Track outbox lag, consumer lag, and drift between ledger and projections, and run a periodic job that rebuilds a projection from the log.

Keep the decision path small and synchronous, and let everything else be asynchronous and replayable.

💡

Key Takeaway

Put the invariant where it can be enforced atomically, then derive everything else from events. A transactional outbox gives reliable replay without making the log responsible for correctness, and a versioned read-your-writes cache gives fast reads without risking oversell. If a hard no-oversell guarantee were not required, simpler eventually consistent designs would become viable.
