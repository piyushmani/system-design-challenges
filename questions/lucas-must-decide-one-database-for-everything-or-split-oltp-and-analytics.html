OLTP vs OLAP Database Split Analytics
Challenge

Lucas Must Decide: One Database for Everything or Split OLTP and Analytics?

Lucas is a backend developer on an e-commerce site whose row-oriented OLTP database handles 50k transactions per second at peak checkout. Product now wants near-real-time dashboards (conversion funnels, inventory heatmaps, user cohorts) with data freshness under 10 seconds. Today everything lives in the OLTP database, so analytical scans compete with checkout for CPU, I/O, and buffer cache. Lucas must keep transaction latency low, make analytics scalable and fast, and keep the pipeline fault-tolerant and observable. Dashboards may be eventually consistent inside the 10-second budget, but checkout itself must stay strongly consistent. He needs the best way to combine row-based and columnar storage and to move data between them.

A
Maintain a single row-oriented OLTP database to serve both transactional operations and analytical queries. Scale the system using read replicas and extensive indexing, and rely on query caching and materialized views within the same database to accelerate analytics while keeping data strongly consistent.
✗ Not Best
B
Separate OLTP and analytics workloads: retain the row-oriented database for core transactions and stream Change Data Capture (CDC) events (e.g., using Debezium and Kafka) into a columnar analytics database (like ClickHouse or BigQuery) for reporting dashboards. Develop idempotent consumers, implement a schema evolution strategy, and track offsets for observability, accepting eventual consistency for analytical reads.
✓ Best Answer
C
Configure the application to perform synchronous dual-writes for every transaction to both the row-based OLTP database and the columnar analytics store during the critical request path. This ensures dashboards are always strongly consistent, relying on distributed transactions or two-phase commits for reliable write operations.
✗ Not Best
D
Stick with the row-based OLTP database and execute a scheduled batch ETL process (running every 5 to 15 minutes or hourly) to extract and transform data into a columnar data warehouse. Leave the OLTP system unaltered and tolerate stale dashboard data in exchange for a simpler operational setup.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — B: OLTP + CDC Stream into a Columnar Store

Option B gives each workload the storage engine built for it: a row store for point reads, point writes, and ACID checkout, and a column store for scans and aggregations. They are joined by a log-based CDC stream that reads the database's write-ahead log, so nothing is added to the request path. It is the only option that satisfies both the sub-10-second freshness target and workload isolation. Here's why it stands out:

  • Workload isolation: Analytical scans never touch the OLTP buffer cache, locks, or CPU, so checkout latency no longer depends on dashboard load.
  • Right engine for the job: A columnar store reads only the columns a query needs, compresses well (often several-fold better than rows), and uses vectorized execution. Funnel and cohort aggregations over billions of rows typically return in sub-seconds to seconds, whereas a row store must read whole rows.
  • Freshness inside the budget: Log-based CDC typically adds hundreds of milliseconds, Kafka tens of milliseconds, and batched inserts one to two seconds, so end-to-end freshness of a few seconds is realistic against a 10-second target.
  • Zero impact on the write path: CDC reads the WAL or binlog asynchronously. There is no dual-write and no distributed transaction, so an analytics outage can never fail a checkout.
  • Replayable and observable: Kafka retains the change log, so a new consumer or a rebuilt dashboard table can replay from an offset. Consumer lag and end-to-end freshness (now minus source commit time) become first-class metrics.

A production setup uses log-based CDC (not polling), a schema registry, idempotent batched writers, dead-letter handling, a replication-slot lag alert, and an end-to-end freshness SLO measured as now() minus source commit time. If the SLO is breached, degrade the dashboard (show a stale banner), never the checkout.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🗄️

A — Single OLTP Database with Replicas and Materialized Views

One engine keeps things simple, but the engine is the problem. Analytical scans over wide rows read data the query never needs, and replicas still pay for it in I/O and cache. Replicas also apply the WAL, so a long-running analytical query can conflict with replay and cause replication lag (or cancelled queries), which makes the dashboards stale. Materialized views refreshed on a schedule are costly and rarely reach 10-second freshness at this write rate, and indexing everything taxes the 50k TPS write path. Caveat: for small datasets (millions of rows) and light dashboards, this is the simplest and often sufficient answer.

✌️

C — Synchronous Dual-Writes in the Request Path

Synchronous dual-writes put a second system into the checkout critical path: latency becomes the slower of the two stores and availability becomes the product of both. There is no practical atomic commit across a transactional database and a columnar analytics store (analytics engines do not take part in XA/2PC), so partial failures still happen: the OLTP commit succeeds, the analytics write fails, and the two silently diverge. Columnar stores also want large batches, not 50k single-row inserts per second. Caveat: if two stores truly must change together, use a transactional outbox rather than dual-writing from the request path.

⏱️

D — Scheduled Batch ETL (5-15 Minutes or Hourly)

Batch ETL is operationally simple and cheap, but it misses the 10-second freshness requirement by a factor of 30-90x (or more for hourly runs). Large extraction queries can also hit the OLTP database in bursts unless they run against a replica or use CDC. Caveat: if the business only needs hourly or daily reporting, batch ETL beats a streaming system on cost and operational effort. Here, the stated freshness requirement is what rules it out.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Single DB + Replicas/Views

Small datasets, light and infrequent dashboards, and a team that wants one system, or as an interim step while the pipeline is being built.

📌

B — CDC to Columnar

High-volume OLTP plus dashboards with seconds-level freshness, large history, and a team able to operate Kafka and a columnar store (or buy them managed).

📌

C — Synchronous Dual-Writes

Almost never. When two stores must change together, use the transactional outbox pattern instead of dual-writing in the request path.

📌

D — Scheduled Batch ETL

Daily or hourly reporting, finance close, or any case where freshness of many minutes is acceptable and simplicity matters more than latency.

⚠️ Common Mistakes to Avoid

  • Polling with updated_at queries instead of log-based CDC: Polling misses hard deletes, adds repeated load to the OLTP database, and loses intermediate row states under heavy write rates.
  • Unbounded replication slot: A stalled consumer makes PostgreSQL retain WAL until the disk fills and the primary goes down. Monitor slot lag and set max_slot_wal_keep_size.
  • Non-idempotent sinks: At-least-once delivery produces duplicate rows and wrong funnel counts. Dedupe on primary key plus a version or LSN (for example ReplacingMergeTree or a MERGE statement).
  • Ignoring updates and deletes: Columnar stores favor appends. Without tombstones or versioned rows, dashboards keep counting deleted or superseded orders.
  • Skipping schema evolution: An unannounced ALTER TABLE can break the connector or silently drop columns. Use a schema registry with compatibility checks.
  • Tiny inserts into the columnar store: One row per insert creates huge numbers of small parts and slows queries. Batch by size or time (for example 10k rows or 1 second).
  • Not measuring freshness: Consumer lag in messages is not freshness in seconds. Track now minus the source commit timestamp.

🌍 Real-World Best Practice

Teams that move from one database to a split architecture usually evolve in stages instead of flipping a switch:

  • Step 0 - Measure: Confirm with slow-query logs and replica lag that analytics contention really hurts checkout, and define the freshness SLO (for example p99 under 10 seconds).
  • Step 1 - Quick relief: Point dashboards at a dedicated read replica to isolate load while the pipeline is built.
  • Step 2 - Add CDC: Run Debezium against the WAL or binlog, publish one topic per table, and register schemas (Avro or Protobuf) in a schema registry.
  • Step 3 - Land in the columnar store: A batched sink (the ClickHouse Kafka engine or Kafka Connect, or the BigQuery Storage Write API) writes into a deduplicating table.
  • Step 4 - Model for dashboards: Build pre-aggregated rollups or materialized views for funnels and cohorts so common queries stay sub-second.
  • Step 5 - Operate: Alert on connector status, consumer lag, replication-slot lag, dead-letter depth, and freshness, and run periodic row-count or checksum reconciliation against the OLTP database.

Move analytics off the transaction path rather than onto it, and measure freshness end to end.

💡

Key Takeaway

Use OLTP for transactions and a columnar store for analytics, connected by log-based CDC. Keep analytics work off the request path, make consumers idempotent, and measure freshness end to end. Accept eventual consistency for dashboards, because strong consistency across two heterogeneous stores would cost checkout latency and availability.
