Decoupling Checkout: Nate's Strangler Fig Dilemma

Nate, a senior backend engineer on an e-commerce platform, is decoupling checkout and payment from a monolith (catalog, cart, checkout, payments, inventory) using the Strangler Fig pattern with zero downtime. The constraints are: checkout needs 99.99% availability, payment confirmations need a p95 latency under 200 ms, stock reductions must be strongly consistent to prevent overselling, and the transition must be gradual so other teams can keep deploying continuously. He must choose an architecture for routing, data ownership, and consistency during the shift. Which strategy best balances safety, operational simplicity, and these strict constraints?

A
Gradually direct traffic to a newly created Checkout service through the API gateway, segmenting by user groups. The new service maintains its own database with eventual consistency: it performs local writes and emits events for the monolith to consume, updating old read models. Asynchronous event consumers synchronize the monolith's state. This avoids distributed transactions but results in eventually consistent order and inventory data.
✗ Not Best
B
Deploy a reverse proxy to route users to the new Checkout service. Use dual writes to ensure both the monolith and the new service update their databases synchronously. This requires a two-phase commit (XA-style) spanning both databases for inventory and order modifications to guarantee strong consistency during the transition.
✗ Not Best
C
Implement an anti-corruption layer (ACL) ahead of the monolith. Construct the new Checkout as a standalone service possessing its own database. Use the monolith's outbox pattern and events for general domain synchronization to update the new service's read models (event-driven approach). For crucial operations needing strong consistency, such as payment capture and inventory reduction, the new service makes a synchronous, idempotent request via the ACL to the monolith or a designated source-of-truth service, using circuit breakers, timeouts, and retries. Use the API gateway and feature flags for gradual routing.
✓ Best Answer
D
Maintain one shared database for the monolith and the new Checkout service throughout the migration phase. Control routing using feature flags, allowing some requests to execute the new code while both systems access identical tables. Depend on database-level constraints and transactions within the shared database to ensure consistency, applying any schema modifications in-place.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — C: ACL + Outbox Events + Synchronous Idempotent Calls for Critical Writes

The four constraints do not apply equally to all data. Catalog, cart, and order-history data can tolerate seconds of staleness; stock decrement and payment capture cannot. Option C is the only design that treats these two classes differently: it uses asynchronous, event-driven synchronization (transactional outbox) for the general domain, and a narrow, synchronous, idempotent path to a single source of truth for the few operations that must be strongly consistent. It also keeps data ownership unambiguous (exactly one writer per piece of data at any moment), which is what makes the migration gradual and reversible. Here's why it stands out:

  • One writer per datum, no distributed transaction: Inventory stays owned by the monolith (or a designated inventory service). Strong consistency comes from having a single authority, not from coordinating two databases. Idempotency keys plus at-least-once delivery give an effectively-once outcome without holding locks across systems.
  • Availability math works: Serial dependencies multiply. Two 99.9% systems in a 2PC give at best about 99.8% (0.999 × 0.999), which already misses a 99.99% target. C limits synchronous coupling to two calls (stock, payment), each behind a circuit breaker with a defined degraded mode, and keeps everything else (read models, emails, analytics) off the critical path.
  • Latency stays controllable: The p95 budget is spent on a small, known set of hops with explicit per-hop timeouts and a bounded retry budget. Event consumers run asynchronously and cannot slow a payment confirmation.
  • The ACL protects the new domain model: It translates the monolith's legacy contracts and schema into the new Checkout model, so legacy concepts do not leak. Later, the monolith's inventory can be replaced by a real service behind the same ACL without touching Checkout.
  • Gradual and reversible rollout: The gateway plus feature flags allow routing by cohort (staff, 1%, 10%, 50%, 100%) with instant rollback by flipping a flag. The monolith's schema is not changed in place, so other teams keep deploying.

Sequence the work: (1) put the gateway and ACL in front of the monolith at 0% traffic, (2) run the new Checkout in shadow mode and compare results, (3) ramp by cohort with SLO-based automatic rollback, (4) move inventory and payment ownership out of the monolith and delete the synchronous hop. Track checkout success rate, p95 payment-confirmation latency, oversell count (target: 0), and outbox lag per cohort.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🌊

A — Eventual Consistency Only

Local writes plus events means the stock decrement exists in two places at different times. Two concurrent checkouts, one routed to each side, can both see stock = 1 and both succeed, which violates the strong-consistency requirement. It also leaves the monolith serving stale order and inventory data to other teams' features. Caveat: eventual consistency is exactly right for non-critical data (order history, recommendations, notifications), and C uses it there.

🔗

B — Dual Writes + Two-Phase Commit (XA)

Dual writes without a coordinator are unsafe (one write can succeed while the other fails). 2PC restores atomicity but blocks: locks are held across network round trips, a coordinator failure leaves in-doubt transactions, and transaction availability is the product of both systems' availability, which makes 99.99% and p95 under 200 ms hard to hold. XA is also often unsupported by managed cloud databases and NoSQL stores, and it ties the two teams' deployments together.

🗄️

D — Shared Database

A shared database gives easy strong consistency and is sometimes a deliberate, short-lived tactic. As the strategy for the whole migration it defeats the purpose: no data ownership, in-place schema changes can break the monolith and other teams (violating continuous deployment), and both codebases couple to one schema. You cannot scale or fault-isolate checkout independently, and you can never retire the monolith. It turns a migration into a permanent distributed monolith.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Eventual Consistency Only

Non-critical domains such as order history, recommendations, notifications, and analytics, where seconds of staleness are acceptable and no invariant (stock, balance) is at stake.

📌

B — Dual Writes + 2PC

Rarely. Low-volume internal back-office flows where both stores support XA, downtime tolerance is high, and the arrangement is short-lived.

📌

C — ACL + Outbox + Sync Critical Calls

Live, revenue-critical migrations with strict consistency on a few operations and strict availability and latency targets overall, and where other teams must keep shipping.

📌

D — Shared Database

A deliberate, time-boxed tactic to carve out a low-risk, mostly read-only module before data ownership is split, with a written exit plan.

⚠️ Common Mistakes to Avoid

  • Skipping idempotency keys: Retries on timeouts will double-reserve stock or double-capture payments. Every cross-system call needs a stable key that the callee de-duplicates on.
  • Dual write instead of outbox: Writing to the database and then publishing an event as two separate steps loses events on a crash. Write the event to an outbox table in the same local transaction and relay it.
  • Treating timeout as failure: Releasing stock or retrying payment after a timeout can duplicate effects. Query the outcome by idempotency key first.
  • Letting the ACL grow business logic: The ACL translates models and contracts only. Logic placed there becomes a second, hidden monolith.
  • Making decisions from event-fed read models: Use them for display, never for stock or payment checks.
  • No rollback path or SLO gates: A big-bang cutover removes the main safety property of the strangler pattern. Keep flags and automatic rollback on error-rate and latency regressions.

🌍 Real-World Best Practice

In practice, strangler migrations succeed by shrinking risk one capability at a time, not by choosing a clever pattern. A typical sequence looks like this:

  • Step 0 — Map seams and ownership: Identify aggregates (order, cart, stock, payment), assign one writer to each, and classify every data flow as strong or eventual.
  • Step 1 — Put a façade in front: Gateway or reverse proxy plus ACL in front of the monolith, with no behavior change and 0% traffic to new code.
  • Step 2 — Shadow and dark-launch: Mirror requests to the new Checkout without side effects and compare responses.
  • Step 3 — Ramp by cohort: Staff, 1%, 10%, 50%, 100%, with automatic rollback when SLOs breach.
  • Step 4 — Extract the owners: Move inventory and payment ownership into their own services and replace the monolith call behind the ACL.
  • Step 5 — Retire legacy: Remove old code paths and tables only after a soak period with the rollback flag still available.

Strangle one capability at a time, and always keep a rollback path.

💡

Key Takeaway

Use one writer per piece of data: events for what can be eventually consistent, and a narrow synchronous idempotent call for the few operations (stock, payment) that cannot. Avoid 2PC and shared databases; they buy short-term simplicity at the cost of availability or independence. The ACL, gateway, and flags are what make the migration gradual and reversible.
