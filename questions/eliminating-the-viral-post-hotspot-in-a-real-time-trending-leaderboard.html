Challenge

Eliminating the Viral-Post Hotspot in a Real-Time Trending Leaderboard

Maya works on a social platform with a real-time trending leaderboard. Traffic is extremely skewed: about 1% of posts generate 50% of engagement events (likes and comments). Those viral posts overload a few backend nodes and the leaderboard store, causing write latency spikes and timeouts. Today every event is written synchronously to a primary SQL database (for auditing) and to a single-region Redis sorted set. The leaderboard may lag by a second or two, but audit records must not be lost. Maya needs to remove the hotspot, keep reads fast, and stay observable and scalable. Which change should she make?

A
Retain the Redis sorted-set design but vertically scale the primary node (allocating more RAM or a larger VM) and introduce a strongly-consistent read-replica tier that features synchronous invalidation upon writes to guarantee read accuracy.
✗ Not Best
B
Shift leaderboard processing into the primary SQL database, enforcing row-level locking and serializable transactions for the highly active post rows. This allows the database to inherently ensure correct counts and ordering, combined with horizontal partitioning of leaderboards based on post_id ranges.
✗ Not Best
C
Implement request queuing at the gateway level alongside client-side throttling to manage updates for viral posts (rate-limiting comments/likes per second), while coalescing requests to bundle traffic spikes into fewer aggregate writes. Depend on client applications to retry requests using exponential backoff when encountering 429 status codes.
✗ Not Best
D
Separate data ingestion from materialization: record events in a durable append-only log (like Kafka), and leverage stateful, keyed stream processing to compute per-post aggregations. Materialize these results into a sharded read-optimized store (such as a materialized view or distributed cache). Mitigate extreme hot keys by routing them to specialized workers or fanning out the processing, and handle read queries from the distributed store to ensure low latency.
✓ Best Answer
✅

Answer & In-Depth Explanation

🏆 Best Answer — D: Decouple Ingestion with a Log and Keyed Stream Aggregation

The hotspot is caused by coupling the event rate to the write rate of two stores: every like is an individual synchronous write to the same few keys. Option D breaks that coupling. Events become cheap appends to a durable log, and a stream processor aggregates many events into few writes before the leaderboard store ever sees them. Here's why it stands out:

  • Write amplification collapses: instead of 100,000 individual increments per second on one hot post, a one-second window produces a single delta per post (or per salted sub-key), so the leaderboard store sees a small, steady write rate.
  • Hot keys are handled explicitly: detect heavy hitters and split a viral post across salted sub-keys (post_id plus a shard number) for partial aggregation, then combine, so no single worker or partition carries the whole load.
  • Auditing becomes cheaper and safer: the durable log is the audit trail, and the SQL database can be fed asynchronously in batches instead of taking a synchronous write per event.
  • Reads scale independently: the leaderboard is materialized into a sharded read-optimized store or cache, so reading top-N never competes with ingest.
  • Resilience and backpressure: bursts queue in the log instead of timing out user requests, and consumers catch up afterwards.

Measure end-to-end freshness (event time to leaderboard visibility), consumer lag, per-key skew and aggregation window sizes. Tune the window (for example 500 ms to 2 s) against the freshness SLO.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

📈

A — Scale Up Redis and Add Replicas

A bigger node raises the ceiling but does not remove the hotspot: one sorted-set key still lives on one shard, and Redis executes commands serially on a single thread. Vertical scaling is bounded and costly, and strongly consistent replicas with synchronous invalidation add latency to every write, making timeouts worse. It treats the symptom, not the skew. Caveat: useful as a quick stopgap while the real fix is built.

🔒

B — SQL Row Locks and Serializable Transactions

Serializable transactions with row-level locking turn the hot row into a lock queue: every viral-post event waits behind the previous one, which is the worst possible response to extreme skew. Partitioning by post_id range does not split a single hot row. Throughput falls, deadlocks and retries rise, and the audit database becomes the bottleneck for the live product. Exact accuracy for a trending list is unnecessary, and the cost is severe.

🚦

C — Gateway Throttling and Client Backoff

Rate limiting engagement events degrades the product: legitimate likes and comments are rejected, and counts become systematically wrong for exactly the most popular posts. Pushing retries onto clients with exponential backoff creates retry storms and tail latency. Coalescing is a sound idea (and is part of the best answer), but it must be done through durable aggregation, not by dropping or delaying user actions. Caveat: rate limiting is appropriate for abuse protection, not as the scaling mechanism.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Scale Up Redis + Sync Replicas

Moderate skew where the hottest key's rate fits within one shard's throughput, or as a short-term stopgap while a redesign is built.

📌

B — SQL Row Locks, Serializable

Low-volume systems where exact counts with relational guarantees matter more than scale, such as financial counters.

📌

C — Throttling + Client Backoff

Abuse and bot protection, and protecting backends from overload, as a safety net rather than the primary design.

📌

D — Log + Keyed Stream Aggregation

Heavily skewed, high-volume event streams that feed rankings, counters or dashboards and can tolerate seconds of lag.

⚠️ Common Mistakes to Avoid

  • Keying the log by post_id only: the viral post lands on one partition. Salt the key or partition randomly and aggregate downstream.
  • Windows that are too large: long windows cut load but hurt freshness. Tune against the SLO.
  • Counting duplicates: at-least-once delivery inflates counts. Deduplicate by event ID or by (user, post).
  • Merging salted sub-keys incorrectly: forgetting to combine partial counts before ranking produces a wrong top-N.
  • No heavy-hitter detection: salting everything wastes resources, salting nothing misses the hot keys. Detect dynamically (for example with a space-saving or count-min sketch).
  • Acknowledging before the durable append: confirm to users only after the log has replicated the event (acks=all with adequate in-sync replicas).

🌍 Real-World Best Practice

Teams facing viral skew combine aggregation, key splitting and decoupling, adding each only when the metrics demand it. A typical sequence:

  • Step 0 — Measure skew: find the top keys by event rate and confirm which tier (API, queue or store) saturates first.
  • Step 1 — Append to a log: acknowledge the user after a durable append; do not write SQL and Redis inline.
  • Step 2 — Aggregate by window: micro-batch per post (500 ms to 2 s) and write deltas instead of events.
  • Step 3 — Split hot keys: salt heavy hitters across N sub-keys, aggregate partially, then merge.
  • Step 4 — Materialize reads: sharded sorted sets or a cache keyed by trending window, refreshed from the aggregates.
  • Step 5 — Decouple audit: load SQL asynchronously in batches from the log.
  • Step 6 — Protect and observe: backpressure, dead-letter handling, and lag and freshness alerts.

Keep abuse protections (per-user rate limits) separate from the scaling design.

💡

Key Takeaway

Skew is solved by reducing and spreading writes, not by making one node bigger. Append events durably, aggregate in windows, split hot keys, and serve reads from a materialized view.
