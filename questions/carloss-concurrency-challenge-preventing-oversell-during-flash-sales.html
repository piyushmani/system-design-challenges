Carlos's Concurrency Challenge: Preventing oversell during flash sales

Carlos, a backend developer, owns the checkout service of an e-commerce platform. During flash sales, thousands of simultaneous purchase attempts hit the same few hot SKUs, and customers are occasionally charged for items that are actually out of stock. The stack is a stateless checkout API in front of a relational database that is the authoritative source of inventory. He must eliminate the race conditions at scale while keeping the system highly available and checkout latency low, weighing consistency, latency, scalability, observability, and fault tolerance.

A
Database-level locking: wrap the decrement in a serializable transaction or use SELECT ... FOR UPDATE on the SKU's inventory row.
✗ Not Best
B
A distributed lock (for example Redlock on Redis) per SKU around the database decrement.
✗ Not Best
C
A durable, partitioned command queue keyed by SKU (for example Kafka) with a single consumer per partition applying inventory decrements sequentially and publishing state-update events.
✓ Best Answer
D
Optimistic concurrency: a version column or compare-and-swap on the inventory row, with exponential-backoff retries on conflict.
✗ Not Best

Answer & In-Depth Explanation

🏆 Best Answer — C: Per-SKU Serialization via Partitioned Queue

Overselling is a contention problem on a handful of hot rows. Locks, retries, and lock services all make buyers compete for the same row, so their cost grows with the number of simultaneous buyers. The single-writer approach removes the competition: every command for a SKU goes into one ordered log and is applied by one consumer, so decrements are sequential by construction, with no lock waits, no retry storms, and a clean record of every decision. Here's why it stands out:

  • Correctness by construction: One writer per SKU means there is no concurrent read-modify-write, so the 'check stock, then decrement' race cannot occur, and stock cannot go below zero as long as the consumer checks before applying.
  • Throughput that does not collapse under contention: Buyers enqueue (cheap appends) instead of fighting for a row lock. The consumer applies decrements back to back, can batch them into one transaction or use an in-memory counter, and sustains thousands of operations per second per SKU.
  • Fail-fast and sold-out shedding: Once a SKU reaches zero, the API (via a cached sold-out flag) rejects further attempts without touching the queue or database, which protects the DB during the crush.
  • Fault tolerance and observability: The log is durable and replayable. If a consumer crashes, another instance resumes from the last offset, and consumer lag, accept/reject rates, and per-SKU decision history are directly observable.
  • Fixes the real bug (charging for nothing): The flow becomes reserve first, charge second. Customers are charged only after a successful reservation event, and failures release the hold through compensation.

A robust implementation partitions by SKU, uses idempotency keys, applies a conditional decrement in the database (WHERE available >= qty), issues time-limited reservations with compensation on payment failure, and publishes decision events. Track consumer lag, reject rate, reservation-expiry rate, and oversell count (which must be zero). If one SKU's lag keeps growing, add batching or stock slicing.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🔐

A — Database Locking

This is correct, and for moderate contention it is the simplest answer, especially in single-statement form: UPDATE inventory SET available = available - :qty WHERE sku = :sku AND available >= :qty. The problem is scale: thousands of transactions queue on one row lock, connections pile up, latency grows with queue depth, and serializable isolation adds abort-and-retry on top. If the transaction also wraps a payment call, the lock is held for hundreds of milliseconds and throughput collapses. The database also becomes the availability bottleneck for the whole checkout. Caveat: keep the atomic conditional update as the final guard even in the recommended design.

🧷

B — Distributed Lock (Redlock)

A lock service adds a network hop and a new failure domain to every purchase without removing the underlying contention, because the database still serializes the write. Redlock's safety is also debated: a client pause, clock drift, or network partition can leave two clients believing they hold the lock, so a correct design needs fencing tokens, which in turn require the database to enforce the check anyway. Caveat: lock leases suit coordination tasks (leader election, cron dedup), not the correctness of a money-and-stock invariant.

🔁

D — Optimistic Concurrency

Optimistic control shines when conflicts are rare. In a flash sale every buyer reads the same version, so one wins and the rest fail and retry, producing retry storms: wasted reads, backoff-induced latency, and starvation for unlucky clients. Throughput on a hot row can end up lower than with plain locking. Caveat: it is the right tool for low-contention, longer-lived edits such as a user editing a profile.

⚡

C — Per-SKU Serialization via Partitioned Queue ✓

A durable, partitioned command queue keyed by SKU (for example Kafka) with a single consumer per partition applying inventory decrements sequentially and publishing state-update events.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Database Locking

Moderate contention, simple checkout flows, a single database, and a team that wants the simplest correct solution. Use the single-statement conditional UPDATE and keep transactions short.

📌

B — Distributed Lock

Coordinating work that is not a data invariant (leader election, scheduled-job dedupe), with fencing tokens if a lock is ever used for correctness.

📌

C — Per-SKU Partitioned Queue

Extreme hot-SKU contention (flash sales, drops, ticketing) where durability, observability, and load shedding matter and asynchronous results are acceptable.

📌

D — Optimistic Concurrency

Low-contention, long-running edits (carts, profiles, documents) where conflicts are rare and retrying is cheap.

⚠️ Common Mistakes to Avoid

  • Charging before reserving: This is the original bug. Payment must follow a successful reservation, with a refund or compensation path.
  • Non-idempotent consumers: Redelivery after a crash would double-decrement. Dedupe by order ID in the same transaction as the decrement.
  • Committing the offset before the DB commit: A crash then loses the command. Commit offsets only after the transaction commits.
  • More than one consumer per SKU: Rebalances and consumer-group misconfiguration can break single-writer ordering. Use partition-keyed assignment and fencing.
  • Reservations that never expire: Abandoned carts leak stock. Use TTLs and a sweeper.
  • Hot partitions from poor keying: Keying by category or seller can overload one partition. Key by SKU and slice extreme SKUs.

🌍 Real-World Best Practice

Retailers usually combine several layers, from cheap to strict:

  • Step 0 — Fix the order of operations: Reserve stock before capturing payment. Never charge before the reservation is confirmed.
  • Step 1 — Make the database the last line of defense: A conditional atomic decrement (WHERE available >= qty) plus a CHECK (available >= 0) constraint. This alone may handle moderate load.
  • Step 2 — Shed load early: Cache a sold-out flag, use queue-based admission or a waiting room at sale start, and limit per-user purchase attempts.
  • Step 3 — Serialize hot SKUs: Partition commands by SKU with a single writer, and deliver results asynchronously to the client.
  • Step 4 — Reservations with TTL and compensation: Hold stock for a few minutes and release it on payment failure or abandonment through a saga.
  • Step 5 — Reconcile: Periodically reconcile inventory, reservations, and orders, and alert on any negative or mismatched stock.

Layer these in based on contention you can measure, not by default.

💡

Key Takeaway

Under extreme contention, stop making buyers compete. Funnel each SKU's commands through a single ordered writer, reserve before charging, and keep an atomic conditional update in the database as the last line of defense. Locks and retries scale with the number of contenders, whereas a queue scales with the amount of work. When contention is only moderate, a plain conditional UPDATE is often enough.
