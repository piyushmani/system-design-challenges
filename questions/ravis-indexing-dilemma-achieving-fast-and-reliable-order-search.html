Challenge

Ravi's indexing dilemma: achieving fast and reliable order search

Ravi, a senior backend developer, owns the order search service for a heavily trafficked e-commerce site. The system handles thousands of writes per second, and users expect sub-200 ms near-real-time search and filtering by customer ID, SKU, status, and date. Search currently runs on the primary PostgreSQL database using several composite indexes. Reads are degrading, write latency spikes whenever another index is added, and complex search queries occasionally cause production timeouts. Search results may trail the source of truth by a few seconds, but order creation and payment flows must stay fast and available. He needs an architecture for fast, scalable search that stays observable and resilient.

A
Keep a single PostgreSQL cluster: add more tailored composite and partial indexes, scale reads with replicas, switch to keyset pagination, and rely on the primary for strong consistency.
✗ Not Best
B
Write synchronously to Elasticsearch/OpenSearch inside the order write request so search always matches the database, and fail the whole write if the search node is unreachable.
✗ Not Best
C
Adopt a transactional outbox: commit each order and an outbox record together, stream events through Kafka, and let idempotent asynchronous consumers index into Elasticsearch, with retries, a dead-letter queue, and lag monitoring; search is eventually consistent.
✓ Best Answer
D
Migrate to a distributed SQL database (such as Spanner or CockroachDB) with global secondary indexes or strongly consistent materialized views, removing the need for a separate search component.
✗ Not Best

Answer & In-Depth Explanation

🏆 Best Answer — C: Transactional Outbox + Search Index

The core problem is that one database is serving two conflicting jobs: high-rate transactional writes and multi-dimensional search. Every extra index taxes every write, and heavy search queries compete with those writes for the same CPU, I/O, and buffer cache. The most effective strategy is to give search its own purpose-built read model and feed it reliably from the source of truth using the transactional outbox pattern with Kafka and Elasticsearch/OpenSearch. Here's why it stands out:

  • Decouples write cost from search cost: PostgreSQL keeps only the indexes needed for transactional access (primary key and a few lookups), so write latency stops growing with each new search pattern. Search-specific indexing work moves to a cluster that can be scaled and tuned independently.
  • Fits the query shape: Filtering by customer, SKU, status, and date range with sorting and pagination is a natural fit for a search engine. Supporting a new filter becomes a mapping change in the search index, not another B-tree on a hot OLTP table.
  • No dual-write inconsistency: The order row and the outbox row commit atomically in one local transaction, so an event exists if and only if the order does. A relay (Debezium CDC or a polling publisher) delivers it at-least-once, and consumers make that safe with idempotent versioned upserts.
  • Failure isolation: If Elasticsearch or the indexer is down, orders are still accepted. Events accumulate in Kafka and are replayed on recovery, so search gets staler instead of the write path failing.
  • Observable by design: Consumer lag, end-to-end index lag (commit time vs. indexed time), dead-letter queue depth, and outbox backlog are concrete SLIs you can alert on before users notice. The index can also be rebuilt from the database or the event log.

A production-grade implementation includes an outbox table with cleanup, a CDC or polling relay, idempotent versioned upserts, a dead-letter queue with replay tooling, index-lag SLOs, and an alias-based reindex procedure. Measure p95 search latency, index lag, and write latency before and after rollout.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

📇

A — More Indexes + Read Replicas

Keyset pagination and well-chosen partial indexes are good hygiene, and replicas do add read capacity. But the scenario's pain point is that indexes tax every write, so piling on more composite indexes makes write latency worse. Replicas still execute the same expensive multi-filter queries, and replication lag introduces its own staleness. Complex ad hoc filters will keep timing out on a B-tree-only design. Caveat: if write volume were moderate and query patterns few and stable, this is the cheapest option and often enough.

🔗

B — Synchronous Dual-Write

A database commit and a search-engine write cannot be made atomic: if the search write succeeds but the database commit fails (or the reverse), the two diverge anyway. Failing the whole order when the search node is down also ties checkout availability to the search cluster, and adds a network round trip to every write at thousands of writes per second. It delivers the worst of both worlds: higher write latency and no real consistency guarantee.

🌐

D — Distributed SQL

Spanner and CockroachDB offer strong consistency and horizontal scale, but this is a large migration for a problem that is mostly about workload separation. Global secondary indexes still make writes more expensive (often a distributed transaction per index), flexible multi-filter search and relevance ranking are not their strength, and cost and operational risk are high. Worth considering in a broader platform re-architecture, not as the first fix for search latency.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — More Indexes + Replicas

Write volume is moderate, query patterns are few and stable, and the data volume fits comfortably on one primary. Usually the cheapest first move when profiling shows missing index coverage.

📌

B — Synchronous Dual-Write

Rarely appropriate on a primary write path. Only for low-volume internal tools where an outage of the search system is acceptable, and even then an outbox is the safer choice.

📌

C — Outbox + Kafka + Search

High write throughput, rich multi-filter search, tight read latency, and a requirement that search problems must never affect order creation. Search can lag by seconds.

📌

D — Distributed SQL

The platform needs global scale and strong consistency across many tables, and the organization is prepared for a broad migration, not just a search fix.

⚠️ Common Mistakes to Avoid

  • Dual-writing from application code: Writing to the database and then to Kafka or Elasticsearch in separate steps loses events whenever the process crashes in between. Write the event to the outbox in the same transaction instead.
  • Non-idempotent or unversioned consumers: At-least-once delivery means duplicates and retries. Without idempotent upserts and an external version, an old event can overwrite a newer document.
  • Unbounded outbox table: Rows that are never cleaned up bloat the table and slow the relay. Delete or partition published rows, and alert on backlog size and age.
  • No end-to-end lag visibility: Consumer lag alone is not enough. Measure commit-to-indexed latency so you know how stale search really is.
  • Poison messages blocking a partition: One malformed event can stall a consumer forever. Use bounded retries, a dead-letter queue, and tooling to inspect and replay.
  • No reindex path: Mapping changes and bugs require rebuilding the index. Use index aliases and a backfill job so you can rebuild without downtime.

🌍 Real-World Best Practice

In practice, teams measure first and move search off the write path gradually. A typical sequence looks like this:

  • Step 0 — Measure first: Capture slow queries with pg_stat_statements and EXPLAIN (ANALYZE, BUFFERS), plus index usage and write latency. Dropping unused or redundant indexes alone can recover write headroom.
  • Step 1 — Quick wins on PostgreSQL: Switch to keyset pagination, add partial indexes for hot statuses, and set statement_timeout so runaway searches cannot hurt the primary.
  • Step 2 — Build the pipeline: Outbox table, CDC or polling relay, Kafka topic keyed by order ID, and an idempotent indexer with retries and a dead-letter queue.
  • Step 3 — Dual-run and validate: Shadow search traffic against both backends, compare results, and run a reconciliation job that compares counts and checksums.
  • Step 4 — Cut over search traffic: Keep by-ID reads on PostgreSQL, then remove search-only indexes from the primary to reclaim write capacity.
  • Step 5 — Operate it: Alert on index-lag SLO breaches, practice replay and reindex runbooks, and use index aliases for zero-downtime mapping changes.

Validate each step with data before moving the next piece of traffic.

💡

Key Takeaway

When one database serves both high-rate writes and multi-dimensional search, separate the read model from the write path and connect them with a reliable, idempotent pipeline. The transactional outbox gives atomicity without dual writes, Kafka provides durability and replay, and the search engine provides query flexibility. Accept bounded staleness for search, keep strongly consistent reads on PostgreSQL, and monitor index lag.
