Priya's Challenge at 200k RPS: Architecting Feature Flags for Speed and Safety

Priya is designing a global microservices platform handling 200k RPS across many regions. The product team needs to (a) progressively roll out features to a share of traffic (1% → 5% → 50%), (b) flip an emergency kill switch instantly, and (c) add no more than 5 ms of latency per request. Flags are evaluated synchronously on the request path and must be observable for metrics and auditing. The design must balance rollout accuracy, fault tolerance, availability, latency and telemetry.

A
Centralized authoritative flag service: every request synchronously calls a central, strongly consistent feature-flag API to fetch current rules. Decisions are perfectly consistent, but each request pays a network hop and depends on the latency and uptime of the central service.
✗ Not Best
B
Local caching with periodic updates: each service instance keeps a local cache of flags and polls the central repository every few seconds (for example 5 to 30 s). Evaluation is local, which cuts central load and per-request latency, but updates propagate slowly and rollouts can be inconsistent during ramps.
✗ Not Best
C
Push-based streaming with local deterministic evaluation: a control plane pushes flag updates to all instances over persistent connections (WebSockets, gRPC or SSE). Instances evaluate locally using deterministic bucketing (seeded hashes), keep versioned flags and an instant local kill switch, and log evaluations for observability.
✓ Best Answer
D
Embed feature flags in JWTs or session tokens at login: evaluate flags once during authentication and store the result in the token so downstream systems read it without lookups. This is very fast but limits flag changes to token refresh cycles, so active sessions cannot be toggled instantly.
✗ Not Best

Answer & In-Depth Explanation

🏆 Best Answer — C: Push-Based Updates with Local Deterministic Evaluation

Option C is the best fit. It separates the control plane (where flags are edited, audited and distributed) from the data plane (where flags are evaluated). Evaluation happens in-process against an in-memory snapshot, so it is effectively free, while a push channel delivers changes in well under a second. Here's why it stands out:

  • Latency far under budget: an in-memory lookup plus one hash takes microseconds, so the 5 ms budget is untouched even at 200k RPS. No network call sits on the request path.
  • Accurate, sticky percentage rollouts: deterministic bucketing computes hash(salt + flagKey + userId) mod 10000 and compares it with the rollout threshold. A user in the 1% group stays enabled at 5% and 50% because the threshold only grows, and every instance reaches the same decision without coordination.
  • Fast kill switch: a kill flag pushed over persistent connections typically reaches instances in tens to hundreds of milliseconds, instead of waiting for the next poll.
  • Resilient to control-plane outages: instances keep evaluating their last known good snapshot (persisted locally for cold starts), so the flag service is not a tier-0 dependency of request handling.
  • Versioned and auditable: every flag set has a monotonic version, so instances ignore stale or duplicate updates, and each evaluation can be counted against the version that produced it.
  • Cheap telemetry: evaluations are aggregated in memory and flushed in batches, giving exposure counts per flag and variant without a synchronous write per request.
  • Scalable distribution: regional relay proxies fan updates out to instances, so the central service does not hold every connection.

Use deterministic hashing with a per-flag salt, immutable versioned snapshots swapped atomically, push with a poll fallback and batched exposure telemetry. Measure flag propagation time (publish to applied), evaluation latency and snapshot age.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🌐

A — Central Authoritative Flag Service

Every request pays a network round trip, and at 200k RPS the flag service must serve the full request rate with its own tight latency. Even a hop of a millisecond or two plus tail latency consumes much of the 5 ms budget, and the service becomes a tier-0 dependency: if it is slow or down, every request is slow or must fall back to a default. It does give perfectly consistent decisions, but consistent rollout percentages do not require a central call. Caveat: a central call is fine for low-volume back-office paths where latency and availability matter less.

⏲️

B — Local Cache with Periodic Polling

This is simple and robust, and with deterministic hashing the percentage rollout is accurate. Its weakness is speed of change: with a poll interval of 5 to 30 seconds, a kill switch can take that long to reach every instance, and instances disagree while updates propagate. Polling from many instances also creates periodic load spikes unless it is jittered. Caveat: as the fallback layer under Option C polling is exactly right, but as the primary mechanism it fails the instant kill-switch requirement.

🎟️

D — Flags Embedded in JWT / Session Tokens

Flags frozen into a token at login stay stale until it is refreshed, so a kill switch cannot reach active sessions, and ramping from 5% to 50% only affects users who authenticate again. Tokens grow with every flag, expose rollout rules to clients, do not cover anonymous traffic, and revoking tokens at scale is hard. Caveat: coarse, long-lived entitlements such as a plan tier belong in tokens, but release flags and kill switches do not.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Central Flag Service

Low-volume admin tools or entitlement checks with a generous latency budget, where perfectly fresh, centrally logged decisions matter more than speed.

📌

B — Local Cache + Polling

Smaller systems, or as the fallback layer under a streaming design, where flags change rarely and tens of seconds of propagation delay is acceptable.

📌

C — Push + Local Evaluation

High-RPS, multi-region systems with tight latency budgets, progressive delivery and a need for a fast, reliable kill switch.

📌

D — Flags in Tokens

Coarse user-level entitlements that change rarely, such as plan tier or beta-program membership. Not for release flags or kill switches.

⚠️ Common Mistakes to Avoid

  • Random bucketing per request: users flip in and out of the feature between requests. Bucket deterministically by a stable id.
  • Reusing one salt for every flag: the same users end up in every experiment's early cohort, correlating results and risk.
  • Different hash implementations across services: the same user gets different answers from different languages. Share test vectors.
  • Push without a polling fallback or version checks: a dropped connection leaves instances stale indefinitely, and out-of-order messages can roll flags back.
  • Evaluating independently at every hop: one user journey sees the feature on in one service and off in another. Evaluate once and pass the decision along.
  • No fail-safe defaults: a missing or unparsable flag silently turns a risky feature on.
  • Synchronous per-request telemetry writes: the observability path then becomes the latency problem. Aggregate and flush in batches.

🌍 Real-World Best Practice

In practice, teams treat flags as a small distributed system with a data plane and a control plane. A typical sequence looks like this:

  • Step 0 — Classify flags: release flags, kill switches, experiments and permissions have different lifetimes and safety defaults.
  • Step 1 — Fix the bucketing spec: algorithm, salt per flag, a stable identifier (user id or device id) and basis points, with published test vectors.
  • Step 2 — Build the data plane: an SDK with an immutable snapshot, atomic swap, last known good copy on disk and fail-safe defaults.
  • Step 3 — Distribution: streaming (SSE or gRPC) through regional relays, with polling fallback and bootstrap from a CDN or object store.
  • Step 4 — Control plane: access control, approvals, an audit log, and gradual ramps with automated guardrails on error rate and latency.
  • Step 5 — Telemetry: batched exposure events, per-flag metrics and propagation-time dashboards.
  • Step 6 — Hygiene: flag expiry and cleanup, kill-switch drills, and chaos tests with the control plane unavailable.

Keep evaluation local and deterministic, and make distribution the only networked part.

💡

Key Takeaway

At 200k RPS, never put the flag decision behind a network call. Distribute versioned flag data to every instance, evaluate it locally with deterministic hashing, and combine push for speed with polling for safety. That gives microsecond decisions, sticky percentage rollouts and a kill switch that works in well under a second, even when the control plane is down.
