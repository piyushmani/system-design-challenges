Challenge

Balancing Read and Write Throughput in a Dual-Traffic-Pattern Platform

Sarah, a software engineer at a fast-growing social media platform, is tackling a dual-traffic-pattern problem: during peak hours, the system is hammered with write-heavy traffic (posts, comments, reactions, stories) while off-peak periods are dominated by read-heavy traffic (timeline browsing, search, profile views). The current single-database architecture is buckling under both patterns: during peak hours, the database struggles to keep up with write volume; during off-peak, read-heavy queries saturate its I/O capacity. Sarah needs to choose a scaling strategy that optimizes for both read and write throughput without over-engineering for one at the expense of the other.

A
Deploy a write-through cache layer to absorb write operations into memory while simultaneously serving cached data for faster reads.
✗ Not Best
B
Implement horizontal sharding to distribute write traffic across multiple independent database instances based on a partition key.
✗ Not Best
C
Introduce materialized views to precompute and persist the results of complex read queries, reducing query execution time for common access patterns.
✗ Not Best
D
Adopt a primary-replica (master-slave) database topology that routes all writes to a dedicated primary node while distributing read traffic across multiple read replicas.
✓ Best Answer
✅

Answer & In-Depth Explanation

🏆 Best Answer — D: Primary-Replica Topology

Adopting a primary-replica topology is the best first architectural move for Sarah, with one important scoping note: it fixes the read half of her problem directly, and only indirectly helps the write half. Off-peak, timeline, search and profile reads saturate the single database; replicas take that load without a schema change. At peak, reads never drop to zero, so moving them off the primary also frees its CPU and I/O for the write surge. But replicas do not add write capacity. Sarah must pair them with write-path work (batching, async queues for non-critical writes, connection pooling) and treat sharding as the escalation if the primary is still saturated after that. Here's why replicas lead:

  • Dedicated resources for reads: Read replicas can be configured with different resource allocations (more memory for buffer cache, query-tuned connection pooling) and serve as dedicated query endpoints without contending for the primary's I/O budget. This ensures that off-peak read traffic doesn't degrade performance.
  • Elastic read scaling: During off-peak read-heavy periods Sarah can add replicas to absorb the load, scaling horizontally and independently of write capacity. Replicas can lag during write surges, so route only staleness-tolerant reads to them and keep read-your-writes paths on the primary.
  • Minimal architectural disruption: Primary-replica is natively supported by every major database (PostgreSQL streaming replication, MySQL replication, MongoDB replica sets). It requires no schema changes, no application-level sharding logic, and no data model restructuring. Sarah can deploy it incrementally — add one replica, route read traffic, measure, add more.
  • Common foundation: Primary-replica is a standard first layer in the database architecture of large web platforms, before heavier patterns (sharding, CQRS) are justified. It often buys meaningful headroom, though how much depends on the read/write ratio and should be measured with load tests.
  • Write-path optimizations (what the peak actually needs): Batch inserts, move non-critical writes (notifications, analytics events, fan-out) onto a durable queue so they're applied at a controlled rate, and use connection pooling to prevent connection exhaustion. These are complementary to replicas, not optional extras.

Sarah should implement primary-replica with a connection-aware routing layer (e.g., ProxySQL, PgBouncer plus a read/write-splitting proxy, or application-level routing). Reads that tolerate slight staleness (timelines, profiles, search) go to replicas. Reads that require freshness (a user's own just-posted content) go to the primary with read-your-writes handling. Track the share of reads served by replicas and replication lag as first-class metrics.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

💾

A — Write-Through Cache

Write-through caching writes data to both cache and database simultaneously. This adds latency to every write (two write operations instead of one) — exactly the wrong trade-off during peak write hours. It also doesn't reduce database write load at all; every write still hits the DB. The read benefits are real (cache hits are fast), but a write-through cache is optimized for read-after-write consistency, not write throughput. For Sarah's peak write surges, this makes the write path slower while only helping reads that hit cached keys.

🔪

B — Horizontal Sharding

Sharding is the only option here that genuinely scales write throughput, so it's a serious candidate for Sarah's peak problem. But it brings heavy complexity: cross-shard queries (a timeline pulling posts from friends on different shards), rebalancing, routing logic, and distributed transactions, and it is hard to undo. It's the right move once load testing shows a single primary can't keep up even after write-path optimization and vertical headroom are exhausted. Until then, replicas plus write batching are cheaper and reversible.

📊

C — Materialized Views

Materialized views precompute expensive read queries, which dramatically speeds up specific read patterns (e.g., 'top posts this week', 'follower count'). But they only help reads — they do nothing for write throughput during peak hours. Materialized views must be periodically refreshed to stay current, and the refresh itself is an expensive operation that competes for database resources. They also don't reduce write load during peak hours. They're also rigid: each view is tailored to one query pattern, so new read patterns require new views. Materialized views are a powerful tactical optimization for known hot queries, but they're not a scaling architecture — they're a query-level optimization layered on top of one.

⚡

D — Primary-Replica Topology ✓

Adopt a primary-replica (master-slave) database topology that routes all writes to a dedicated primary node while distributing read traffic across multiple read replicas.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Write-Through Cache

Read-after-write consistency is critical (e.g., user profile updates that must be immediately visible) and write volume is moderate. Best used as a complement to primary-replica, not as a standalone scaling strategy.

📌

B — Horizontal Sharding

Load testing shows a single primary is saturated by writes even after batching, queuing and vertical scaling, or the dataset no longer fits one node. Works best when data partitions cleanly by a key (user ID, tenant, region) with few cross-shard queries.

📌

C — Materialized Views

Specific read queries are expensive (multi-table JOINs, aggregations, ranking algorithms) and their results can tolerate staleness. Ideal for dashboards, analytics, recommendation feeds, and trending content where precomputation is more efficient than real-time computation.

📌

D — Primary-Replica

Read volume is saturating a single database (CPU, I/O or connections), reads tolerate small staleness, and you want a low-risk first step. Pair it with write-path optimization if writes peak separately.

⚠️ Common Mistakes to Avoid

  • Sending all reads to the primary — After setting up replicas, engineers often forget to actually route read traffic. Use a connection proxy or application-level routing to ensure reads hit replicas by default. Monitor primary vs. replica query ratios.
  • Ignoring replication lag — Read replicas are asynchronously behind the primary. If a user posts content and immediately refreshes, they might not see their own post. Implement read-your-writes consistency by routing the authoring user's reads to the primary for a brief window after writes.
  • Sharding prematurely — Sharding is irreversible and dramatically increases operational complexity. Most platforms can serve a large number of users on primary-replica + caching alone. Don't shard until you've proven that single-primary write throughput is the bottleneck via load testing.
  • Caching writes instead of separating paths — Write-through and write-behind caches don't reduce database write load — they just add another write target. If write throughput is the problem, you need write path optimization (batching, async processing, event sourcing), not caching.
  • Assuming replicas can have different indexes: Physical (streaming) replicas are byte-for-byte copies, so they carry the same indexes as the primary. Different indexes require logical replication or a separate analytics instance. Over-indexing the primary also slows every write, so profile before adding indexes.
  • Not monitoring replica drift during peak writes — During write surges, replication lag can spike from milliseconds to seconds. If your application assumes near-real-time replica freshness, this creates subtle bugs. Set up alerts on replication lag and have a fallback strategy (route to primary) when lag exceeds thresholds.

🌍 Real-World Best Practice

In production social media platforms, senior engineers don't rely on a single scaling strategy. They layer complementary patterns to address different dimensions of the read/write scaling challenge:

  • Layer 1 — Primary-replica separation: Route writes to a primary, reads to replicas. This is the foundational layer that buys immediate headroom and is the biggest single architectural win.
  • Layer 2 — Read-through caching (Redis/Memcached): Cache hot read paths (timelines, trending content, user profiles) to intercept reads before they reach replicas. For skewed social-media access patterns this can remove a large share of replica load; the actual hit rate must be measured.
  • Layer 3 — Materialized views for analytics: Precompute expensive aggregations (engagement metrics, trending algorithms, recommendation scores) as materialized views refreshed on a schedule. These never hit the primary or real-time replicas.
  • Layer 4 — Sharding when a single primary saturates: If load tests show write volume still exceeds what one primary can absorb after batching, queuing and vertical scaling, shard by user ID or tenant. It is a last-resort change most platforms defer for as long as possible.

Sarah's first move should be deploying read replicas because it removes the read bottleneck with minimal risk, while she hardens the write path (batching, queues, pooling). Caching and materialized views come next for hot reads and analytics, and sharding only if peak writes still saturate the primary.

💡

Key Takeaway

Reads and writes peak at different times here, so the database has two separate saturation problems. Primary-replica is the cheapest, lowest-risk fix for the read side and gives the primary more room at peak, but only write-path optimization (and, if needed, sharding) raises write capacity.
