OLTP vs OLAP Dashboards Database Load
Challenge

Orders dashboard is overwhelming the OLTP database; what's the fix?

Owen, a backend engineer at an online retailer, works with a global OLTP database whose orders table holds about 1.2 billion rows and takes roughly 500 writes per second. Operations and product teams run ad-hoc reports and near-real-time dashboards (customer cohorts, time-window aggregates, funnel counts) directly against that table. These queries cause long scans that spike p99 latency and hurt checkout performance. Owen needs a solution that minimizes OLTP strain and speeds up dashboards, with a sensible balance of data freshness, availability, and operational overhead.

A
Add a broad composite index on the OLTP orders table covering the commonly used sort and filter columns (for example customer_id, product_category, status, created_at), and tune dashboard queries to use it, keeping all reads on the primary database.
✗ Not Best
B
Partition the OLTP orders table by customer shard or by day, using local per-partition indexes. Add daily materialized summary tables, generated by scheduled batch jobs, to serve the most common dashboard aggregations.
✗ Not Best
C
Redirect dashboard and analytical workloads to a dedicated columnar OLAP store (such as Pinot, Redshift, or ClickHouse). Feed it using change data capture (CDC) or a near-real-time ETL pipeline (for example a Kafka-based transformer), so the OLTP system handles only transactional work.
✓ Best Answer
D
Build an application-layer denormalized read model or cache that is updated synchronously inside the main write transaction (write-through), so dashboards read fully denormalized, strongly consistent data from a high-performance key-value store.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — C: Columnar OLAP Store Fed by CDC

The core problem is workload interference: analytical scans and transactional writes compete for the same CPU, I/O, and buffer cache. Owen can only remove that interference by moving analytics to a different engine. A columnar OLAP store is built for exactly these queries (aggregates over time windows, cohorts, funnels), and log-based CDC feeds it with very little load on the source. Checkout goes back to doing transactions, and dashboards get an engine designed for them. Here's why it stands out:

  • Real isolation: Heavy scans no longer touch the OLTP database, so checkout p99 stops depending on what the reporting teams run. Availability is also isolated: an OLAP outage does not affect purchases.
  • The right engine for the queries: Columnar storage reads only the columns a query needs, compresses well, and processes data in vectorized batches, so aggregates over billions of rows are typically far faster than on a row store.
  • CDC is cheap at this write rate: At about 500 writes per second, reading the database's transaction log adds little load, unlike polling queries, and it delivers changes in seconds.
  • Freshness is tunable: Seconds-level lag fits near-real-time dashboards. A durable stream in the middle buffers spikes and lets the pipeline catch up after downtime.
  • Supports ad-hoc analysis: Unlike pre-built summaries, the OLAP store can answer new questions without a new index or table for each one.
  • Observable by design: Pipeline lag, row-count reconciliation, and per-dashboard query latency give clear freshness and correctness signals.

A dependable setup includes log-based CDC with an initial snapshot, a durable stream buffer, an idempotent upsert sink, freshness SLOs with lag alerts, a reconciliation job, and pre-aggregated rollups for the busiest dashboards. Move dashboard credentials off the OLTP database once the new path is trusted.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

📇

A — Broad Composite Index on the OLTP Table

A wide index adds write amplification to every insert and update on a 1.2-billion-row table and consumes memory and storage. It only helps queries that match its leading columns, so ad-hoc cohort and funnel queries with varied filters still scan large ranges. And everything still runs on the primary, so analytics keep competing with checkout. Caveat: a narrow, targeted index for one known hot query can be a valid short-term fix.

🗓️

B — Partitioning Plus Daily Summary Tables

Partition pruning helps time-window queries, and summaries speed up fixed aggregations, but the heavy queries still run on the OLTP database. Daily batch summaries are not near-real-time and cannot answer new ad-hoc questions, and sharding by customer is a large migration. Caveat: partitioning is good hygiene for retention and archival, and daily summaries suit stable reports, so both complement option C.

🧾

D — Synchronous Write-Through Read Model

Updating a read model inside the checkout write path makes the critical path slower and couples checkout availability to the key-value store. A transaction spanning a relational database and a separate store is a dual write, not an atomic transaction. And a key-value store serves pre-shaped lookups, not ad-hoc aggregates, cohorts, or funnels. Caveat: a precomputed read model is a good fit for a small set of fixed, hot metrics, ideally fed asynchronously (for example from CDC) instead of inside the transaction.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Broad Composite Index

A single known, repeated query on a moderately sized table where the extra write cost is acceptable and no separate analytics platform is warranted.

📌

B — Partitioning + Daily Summaries

Stable, fixed daily or weekly reports, plus data lifecycle management (retention, archival) on large tables. Complements, but does not replace, an analytics store.

📌

C — Columnar OLAP via CDC

Large datasets with ad-hoc and near-real-time analytical queries that must not affect transactional performance, and a team that can operate a data pipeline.

📌

D — Synchronous Write-Through Read Model

A few fixed, hot lookups that must be strongly consistent with the write, at modest scale, where adding latency to the write path is acceptable.

⚠️ Common Mistakes to Avoid

  • Ignoring updates and deletes: Treating the OLAP table as append-only leaves stale statuses and inflated counts. Use versioned upserts keyed by order id.
  • Skipping the initial snapshot plan: Starting CDC without a consistent snapshot, or without handling the overlap between snapshot and stream, creates gaps or duplicates.
  • No reconciliation: Silent divergence is common in pipelines. Compare counts or checksums per time window and alert on drift.
  • Polling the source with queries: Query-based extraction recreates the load problem. Prefer log-based CDC.
  • Forgetting schema evolution: A new or renamed column can break the pipeline. Use a schema registry or compatibility rules and test changes.
  • Sending sensitive data unprotected: The analytical copy needs the same access controls and PII handling as the source.

🌍 Real-World Best Practice

In practice, teams relieve the pressure quickly and then move analytics to its own platform. A typical sequence looks like this:

  • Step 0 — Find the offenders: Use slow-query logs and statement statistics to identify which dashboards and reports cause the scans and when they run.
  • Step 1 — Immediate relief: Point dashboards at a read replica with statement timeouts and resource limits, so checkout is protected while the real fix is built.
  • Step 2 — Stand up CDC to an OLAP store: Snapshot the table, stream changes through a durable log, and upsert into a columnar store with a versioned key.
  • Step 3 — Pre-aggregate the hot paths: Add rollups or materialized views in the OLAP store for the busiest dashboards.
  • Step 4 — Tidy the OLTP side: Partition and archive old orders to keep the transactional table lean, and remove dashboard access from the primary.
  • Step 5 — Operate the pipeline: Define a freshness SLO, alert on lag, reconcile counts regularly, and manage schema changes deliberately.

Separate transactional and analytical workloads, and treat the analytical copy as a product with its own SLOs.

💡

Key Takeaway

Indexes and summaries cannot fix workload interference because the heavy queries still run on the checkout database. Move analytics to a columnar OLAP store fed by CDC, accept seconds of lag, handle updates with versioned upserts, and reconcile regularly. Checkout gets its p99 back and dashboards get an engine built for them.
