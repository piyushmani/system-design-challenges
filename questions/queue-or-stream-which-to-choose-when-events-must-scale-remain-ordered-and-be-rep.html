Queues vs Streams Replayability Event Processing
Challenge

Queue or stream: which to choose when events must scale, remain ordered, and be replayable?

Lena, a senior backend engineer, is building an event pipeline for personalization and payments. It must handle about 1 million events per second, enforce strict per-user ordering, allow replay of historical events for bug fixes and model retraining, deliver sub-second end-to-end latency to most consumers, and stay fault tolerant and observable across two data centers. She must choose the foundational messaging architecture: a traditional message queue, an append-only distributed log, a hybrid, or something else.

A
Use a conventional message queue system (such as SQS or RabbitMQ) with many small queues and competing consumers. Spread users across the queues to keep per-user ordering, and rely on acknowledgment and retry mechanisms for durability.
✗ Not Best
B
Use a partitioned distributed log (such as Kafka or Pulsar) with topics partitioned by user ID, retention that supports historical reprocessing, and a stream-processing framework (such as Flink or Kafka Streams) for stateful, idempotent or exactly-once processing. Add cross-datacenter replication and monitor consumer lag and offsets closely.
✓ Best Answer
C
Build a hybrid: write events to a durable stream for replay and audit, while pushing time-critical work into a queue (or a dedicated job service) for low-latency background processing. Keep a sync connector between the two, and use the stream only for reprocessing.
✗ Not Best
D
Skip specialized messaging platforms: append events to a relational database table and run worker pools that poll the table (or use LISTEN/NOTIFY) to process them. Rely on database transactions for durability and locking to enforce ordering.
✗ Not Best

Answer & In-Depth Explanation

🏆 Best Answer — B: Partitioned Distributed Log

Three of Lena's requirements point straight at a log: replay (events must remain after they are consumed), per-user ordering at huge scale (partition by user ID), and sub-second latency with many independent consumers (consumer groups read the same data at their own pace). A queue deletes messages on acknowledgment, so replay is not a native capability, and giving each of millions of users an ordered lane out of queues is awkward. A partitioned log gives ordering, durability, and replay in one structure. Here's why it stands out:

  • Per-user ordering by construction: Events keyed by user ID land on one partition and are read in offset order. No extra coordination is needed, and unrelated users are processed in parallel.
  • Replay is a first-class feature: The log retains events for a configured period (or indefinitely with tiered storage). A bug fix or model retrain starts a new consumer group from an earlier offset or timestamp without touching production consumers.
  • Throughput scales with partitions: At 1 KB per event, 1 million events per second is roughly 1 GB/s of ingress before replication. A log spreads that across many partitions and brokers, with sequential disk writes that suit this load.
  • Many consumers, one write: Personalization, payments, analytics, and audit each consume independently with their own offsets, so adding a consumer does not slow producers.
  • Sub-second latency is achievable: Consumers tail the log in near real time, and stream processors keep state locally, so end-to-end latency is typically well under a second when consumers keep up.
  • Operational visibility: Consumer lag per partition, offset progress, and under-replicated partitions are standard, directly actionable health signals.

A production setup uses an idempotent producer with full acknowledgment, replication with a minimum in-sync replica count, idempotent or transactional sinks, offset commits after results are durable, and cross-datacenter replication with a tested failover runbook. Alert on consumer lag, under-replicated partitions, and replication delay between sites.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

📮

A — Conventional Message Queue

Queues remove a message once it is acknowledged, so historical replay is not native. Keeping per-user order with competing consumers requires routing users into many small queues or ordered message groups, which adds operational complexity, and managed queues have per-queue or per-group throughput limits that make 1 million events per second hard. Caveat: queues are excellent for task distribution and work offloading. Note that log-style features in some brokers (for example, RabbitMQ Streams) move toward option B's model.

🔀

C — Hybrid Stream + Queue

A log consumer can already deliver sub-second latency, so the queue is unneeded extra moving parts. Splitting events across two systems introduces dual-write and synchronization problems, and the queue path loses strict per-user ordering because of competing consumers. Payments, which need ordering most, would have to stay on the stream anyway. Caveat: hybrids are reasonable for specific job workloads (for example, sending emails with retries and delays) driven by events from the log.

🗄️

D — Relational Database as the Event Bus

An append-only table gives durability and replay, but at 1 million inserts per second it concentrates write load, index maintenance, and polling on one database system. Ordering enforced by locking limits parallelism, and LISTEN/NOTIFY is not a durable delivery mechanism. Caveat: writing events to a table inside a business transaction (the transactional outbox pattern) is a good way to feed the log, but the table should not be the backbone.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Conventional Queue

Task and job distribution where each message is processed once by any worker, replay is not needed, and strict global per-key order is not required.

📌

B — Partitioned Log + Stream Processing

High-volume event streams that need per-key ordering, replay, and multiple independent consumers, such as payments, personalization, analytics, and audit.

📌

C — Hybrid Stream + Queue

A log as the source of truth, with specific task-style consumers (email sending, retries with delays) that fit a job queue's semantics.

📌

D — Relational DB as Event Bus

Low-volume systems where adding messaging infrastructure is not justified and transactional consistency with business data matters more than throughput.

⚠️ Common Mistakes to Avoid

  • Keying by the wrong field: Keying by event id or random values spreads one user's events across partitions and destroys per-user order. Key by user ID.
  • Committing offsets before processing completes: A crash then loses events. Commit after results are durable, and make processing idempotent.
  • Assuming exactly-once end to end: External databases and APIs still see duplicates unless the sink is idempotent or transactional.
  • Too few partitions at the start: Increasing later changes key placement and can reorder events during the switch. Provision with headroom.
  • Ignoring consumer lag: Sub-second latency depends on consumers keeping up. Alert on lag per partition, not only in total.
  • No dead-letter plan: A poison message can block a partition indefinitely, and silently skipping it can corrupt payment state. Define handling per event type.

🌍 Real-World Best Practice

In practice, teams use a log as the system of record for events and layer other tools around it. A typical sequence looks like this:

  • Step 0 — Define the ordering key: Confirm that per-user order is what correctness needs, and check key skew to estimate the hottest partitions.
  • Step 1 — Size the log: Estimate throughput from event size and rate, choose partition count with headroom, and set replication and minimum in-sync replicas for durability.
  • Step 2 — Make producers safe: Enable idempotent production and full acknowledgments, and use a transactional outbox when events originate from database changes.
  • Step 3 — Make consumers idempotent: Use event ids and either transactional sinks or deduplication, and commit offsets only after results are durable.
  • Step 4 — Plan replay: Set retention to match recovery and retraining needs, and replay into a separate consumer group and a separate or versioned sink.
  • Step 5 — Handle failure domains: Replicate across data centers, rehearse failover, and add dead-letter handling and lag alerts. Add queues only for task-style work driven off the log.

Choose the log first, then add queues only where task semantics (retries, delays) are the actual need.

💡

Key Takeaway

When events must be ordered per key, replayable, and consumed by many systems at huge scale, use a partitioned log keyed by user ID with idempotent producers and consumers. Add stream processing for state, replicate across data centers, and treat queues as a complement for task-style work, not as the backbone.
