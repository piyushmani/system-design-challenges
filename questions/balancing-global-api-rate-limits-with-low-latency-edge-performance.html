Challenge

Balancing global API rate limits with low-latency edge performance

Asha, a backend engineer, must design rate limiting for a public REST API used globally by mobile apps and external servers. The requirements pull in different directions: under 10 ms of edge overhead, high availability during regional outages, protection against both short bursts (per-second) and sustained abuse (per-day), and full metrics and audit logs for rejected requests. She needs the architecture that best balances consistency, scalability, and latency.

A
A single centralized strict rate-limiter: direct all requests to a lone Redis cluster leader executing rigorous token-bucket validations (via atomic Lua scripts), ensuring limits are globally consistent and strictly enforced from a central authority.
✗ Not Best
B
Completely decentralized eventual counters: each edge proxy maintains independent local in-memory counters and occasionally synchronizes with a central database. Limits are enforced based on local data; occasional reconciliation calculates global usage and applies subsequent throttling.
✗ Not Best
C
A hierarchical hybrid rate-limiting system: perform short-window, low-latency validations at the edge using a local token-bucket/cache (rapid, slightly lenient), while enforcing long-window/global limits in a sharded Redis cluster via atomic Lua scripts. Utilize consistent hashing for key sharding, replicate data cross-region for failover support, and send metrics/events to a centralized stream for auditing and analysis.
✓ Best Answer
D
Stateless client-side tokens: generate signed rate-limit tokens (similar to JWTs) from the authentication service, encoding limits and expiration times. Clients present these tokens, and proxies verify the signatures to make acceptance decisions without reaching out to central databases, bypassing server-side counters.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — C: Hierarchical Hybrid Limiter

The requirements describe two different time scales, and a single mechanism cannot serve both. Per-second burst protection must be decided in microseconds at the edge, so it cannot depend on a network call. Per-day quotas are coarse, so they tolerate small errors and batched coordination. A hierarchical hybrid gives each requirement the mechanism it needs: a local token bucket for bursts, a sharded Redis tier for long-window and global limits, and an asynchronous event stream for audit. That is why it satisfies all four requirements at once:

  • Fast path stays local: A token-bucket check in process memory costs microseconds, comfortably inside the 10 ms budget. The common request never waits on a cross-region round trip.
  • Bounded, tunable inaccuracy: Local enforcement is 'slightly lenient', but the worst-case overshoot is bounded by roughly number of edges x local burst. Leasing quota slices to each edge in batches keeps that error small and explicit.
  • Right tool for long windows: A day-level counter changes slowly relative to request rate, so atomic Lua scripts on a Redis cluster sharded by consistent hashing handle it easily, and batched updates cut Redis load by orders of magnitude.
  • Failure isolation: If Redis is slow or a region is down, edges degrade to local limits (a policy choice) instead of failing the API. Cross-region replication or per-region budgets let other regions continue to enforce.
  • Observability off the hot path: Reject events (and sampled accepts) go to a stream asynchronously, so audit logging and metrics add no request latency.

Key limits by API key or authenticated identity (not only IP), return standard 429 responses with Retry-After and RateLimit-* headers, and publish reject events to a stream for audit. Alert on Redis latency, lease refill failures, and the gap between local and global usage.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🏛️

A — Single Centralized Limiter

Perfect consistency, but every request pays a network round trip to one leader. For global clients that is tens to hundreds of milliseconds, far beyond the 10 ms budget, and the leader is a single point of failure and a hot spot. A regional outage or leader failover would either block traffic or force an unplanned fail-open. Strictness the product does not need is bought at the cost of the two requirements it does.

🌐

B — Fully Decentralized Eventual Counters

Fast and available, but with no coordination bound: with N edges each enforcing a local limit, a client spread across edges can consume up to roughly N times the intended quota before reconciliation catches up. Per-day limits become unreliable, and 'apply throttling after reconciliation' reacts too late to sustained abuse. It is the right idea for the burst tier, but incomplete as the whole design.

🎫

D — Stateless Signed Rate-Limit Tokens

A signed token can encode a policy (limit and expiry), but it cannot encode usage, which changes on every request. Enforcement therefore depends on the client honoring its own limits, which abusive clients will not. Revoking or tightening a limit mid-token requires short expiries and re-issuance. It is useful for carrying tier information to the edge, but it cannot replace server-side counters.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Central Strict Limiter

A single-region deployment, low request rates, and a need for exact enforcement (for example expensive operations or billing-sensitive quotas), where an extra round trip is acceptable.

📌

B — Decentralized Eventual

Soft protection where approximate limits are fine and availability matters more than accuracy, such as basic per-instance load shedding.

📌

C — Hierarchical Hybrid

Global public APIs that need microsecond burst protection, accurate-enough daily quotas, regional resilience, and audit trails.

📌

D — Signed Client Tokens

Carrying a client's tier or entitlements to the edge (for example plan limits), alongside server-side counters that do the actual enforcement.

⚠️ Common Mistakes to Avoid

  • Not bounding the overshoot: 'Slightly lenient' becomes N times the limit when edges and bursts grow. Compute edges x burst and set lease sizes accordingly.
  • Calling Redis on every request: That recreates the central bottleneck. Lease quota in batches and keep the hot path local.
  • Wrong failure policy: Failing closed for the whole API when Redis blips turns a limiter incident into a full outage, while failing open everywhere removes protection for sensitive routes.
  • Non-atomic counter logic: Doing GET, compare, then SET from the app creates races. Use a single Lua script (or INCRBY with expiry) so check and update are atomic.
  • Keys that spread across Redis Cluster slots: A Lua script touching multiple keys must use keys in the same hash slot (hash tags), or it will fail.
  • Synchronous audit logging: Writing reject logs inline adds latency exactly when the system is under attack. Emit events asynchronously and sample accepted requests.

🌍 Real-World Best Practice

Production systems (for example Envoy's local plus global rate limit filters, or the edge limiters of large API gateways) tend to converge on this layered shape:

  • Step 0 — Define the policy: List limits by identity and route, time windows, and the allowed overshoot. Decide fail-open vs fail-closed for each route class.
  • Step 1 — Local token bucket at the edge: Per-key bucket in memory for the per-second burst limit, with a short rejection cache for keys that are already over limit.
  • Step 2 — Leased global quota: Edges request batches of quota from a regional Redis cluster through an atomic Lua script, so Redis sees one call per batch instead of per request.
  • Step 3 — Shard and replicate: Use consistent hashing (or Redis Cluster slots) for keys, with replicas per region for failover.
  • Step 4 — Stream audit and metrics: Emit reject events and sampled accept events to Kafka or a managed stream, then build dashboards and abuse detection downstream.
  • Step 5 — Test failure modes: Run game days for Redis latency, region loss, and clock skew, and verify the chosen fail-open or fail-closed behavior.

Treat rate limiting as a degradable control plane: it must never become the reason the API is down.

💡

Key Takeaway

Split the problem by time scale: enforce short windows locally for microsecond latency, enforce long windows centrally where small coordination cost is acceptable, and stream audit data asynchronously. Accept a bounded, documented overshoot instead of paying global-consensus latency on every request.
