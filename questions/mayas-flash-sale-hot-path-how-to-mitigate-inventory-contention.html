Maya’s Flash-Sale Hot Path: How to Mitigate Inventory Contention?

Maya, a backend engineer at an e-commerce company, owns a flash-sale API that receives tens of thousands of simultaneous buy requests for the same SKU. Today every request decrements stock inside the main SQL database using a transaction, which causes heavy row-lock contention, rising latency, and timeouts at peak. The team needs an architecture that handles massive concurrency while keeping stock counts accurate (no overselling), stays highly available during the surge, and keeps read operations fast for user-facing pages. Which concurrency strategy should she pick?

A
Maintain centralized locking via Redis (using SETNX and expiration) for stock reduction, ensuring only a single process modifies a SKU at any moment. This approach forces updates to be serial and guarantees strong consistency for the inventory.
✗ Not Best
B
Transition to pessimistic database locking by executing SELECT FOR UPDATE within a transaction targeting the inventory record in the primary SQL database. This serializes access at the row level, trusting the database to maintain accuracy.
✗ Not Best
C
Implement optimistic concurrency control by keeping a version number (or utilizing CAS) on every inventory row, allowing simultaneous requests to try reducing the count. In case of a version mismatch, retry up to a set limit, and fail rapidly if the maximum retries are surpassed.
✗ Not Best
D
Implement an asynchronous partitioned command log (like a Kafka topic partitioned by SKU) and handle stock reductions using a single consumer instance per partition, ensuring a single writer per key. Producers log the reduction commands, while the consumer processes them sequentially into a materialized view or database, utilizing idempotent commands and an optimized read model for user pages.

✅

Answer & In-Depth Explanation

🏆 Best Answer — D: Single-Writer Partitioned Command Log

The root problem is not the database's raw speed; it is that tens of thousands of requests are fighting over one hot row. Locks, retries, and distributed mutexes all keep that contention and merely change where it is paid. A partitioned command log with one writer per SKU removes the contention instead: requests become cheap ordered appends, and a single consumer applies them sequentially, so no two writers ever race on the same stock count. Here's why it stands out:

  • Contention disappears by design: Partitioning by SKU routes every command for that SKU to one partition and one consumer. The consumer decrements stock serially (often in memory, with the durable log behind it), so there is no lock wait, no version conflict, and no retry storm. A single in-memory consumer can typically apply tens of thousands of simple decrements per second, far more than a contended SQL row sustains.
  • Exact stock, no overselling: Because exactly one writer owns each SKU, the 'stock is sufficient' check and the decrement are one sequential step. Once stock reaches zero, the consumer rejects the rest immediately and can publish a sold-out flag.
  • Absorbs the surge: Producers only append to a replicated log (for example acks=all with min.insync.replicas=2), which stays fast while the consumer drains at its own pace. The database is no longer in the request path, so a slow database delays confirmations instead of making the buy button unavailable.
  • Idempotent and replayable: Each command carries a unique request id (order id or idempotency key). The consumer dedupes on it, so producer retries, at-least-once delivery, and consumer restarts never double-decrement. After a crash the consumer rebuilds state from its last checkpoint plus the log.
  • Fast reads through a separate read model: The consumer (or a downstream projector) publishes remaining stock to a cache or materialized view. Product pages read that, never the contended write path. A second or two of display staleness is fine because the authoritative accept/reject decision is made by the consumer.
  • Well-established pattern: This is CQRS plus the single-writer principle, the same idea behind LMAX's single-threaded business logic and many Kafka-based order and inventory systems.

A production-grade version has: partition key = SKU, idempotency keys on every command, acks=all producers, a sold-out fast path at the edge, reservation TTLs, and a read model for product pages. Monitor per-partition consumer lag, accepted versus rejected ratio, and reserved-versus-paid reconciliation; if lag grows unbounded for a hot SKU, split its stock into buckets.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🔒

A — Redis Distributed Lock

A lock serializes access but does not remove contention: tens of thousands of requests still queue or spin on one key, and each now also pays a network round trip to Redis. Worse, a SETNX plus expiry lock is not a safe mutual-exclusion primitive. If the holder pauses (GC, network delay) past the TTL, a second holder enters and stock can be double-decremented unless fencing tokens are added. The 'strong consistency' claim also fails if the Redis primary fails over before replicating. Caveat: a single atomic Redis DECR or Lua script (no lock at all) is a legitimate, simple gate for a stock counter, but that is a different design from the lock described here.

🧱

B — Pessimistic Row Locking (SELECT FOR UPDATE)

This is essentially the current design with an explicit lock. Every buyer waits in line on the same row lock, transactions hold database connections while waiting, and the connection pool saturates, which is exactly the timeouts Maya sees. It guarantees correctness, but at the cost of throughput and availability under a surge. Caveat: it is perfectly fine for low-contention inventory (many SKUs, few concurrent buyers per SKU).

🔁

C — Optimistic Concurrency (Version / CAS)

Optimistic control shines when conflicts are rare. With tens of thousands of writers on one row, nearly every attempt conflicts: only one wins per round, so total attempts can grow toward O(N²) and the retries create a retry storm that raises latency and still starves some users. Capping retries makes it fail fast, but customers then get errors even while stock remains. Caveat: a single conditional statement such as UPDATE ... SET stock = stock - 1 WHERE stock > 0 avoids read-modify-write retries and is a good improvement for moderate contention.

⚡

D — Single-Writer Partitioned Command Log ✓

Implement an asynchronous partitioned command log (like a Kafka topic partitioned by SKU) and handle stock reductions using a single consumer instance per partition, ensuring a single writer per key.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Redis Lock

Coordinating infrequent, low-contention critical sections where occasional lock expiry is tolerable or fenced by the downstream system. Not for correctness-critical hot counters.

📌

B — SELECT FOR UPDATE

Low-to-moderate contention inventory (many SKUs, few concurrent buyers each) where simplicity and strict transactional guarantees matter most.

📌

C — Optimistic CAS

Workloads where conflicts are rare (for example, user profile edits), so retries are uncommon and cheap.

📌

D — Single-Writer Log

Extreme write contention on a small set of hot keys (flash sales, ticketing, limited drops) where exact counts and surge tolerance matter more than synchronous confirmation.

⚠️ Common Mistakes to Avoid

  • Commands that are not idempotent: Delivery is at-least-once, so duplicates will happen. Without an idempotency key and a dedupe window, a retry double-decrements stock.
  • Wrong partition key: Keying by order id or user id spreads one SKU across partitions and brings the race back. The key must be the SKU (or the bucket id).
  • Mismatched offset and state commits: Committing the offset before the state change is durable loses commands on a crash; committing after, without dedupe, duplicates them. Persist state and the processed id together, or checkpoint with the offset.
  • Stock that is never released: Abandoned carts and failed payments pin stock forever. Use reservation TTLs and an explicit release command.
  • Deciding from the read model: The cache is for display only. The consumer is the single authority for accept or reject.
  • Ignoring hot-partition limits: One SKU is one partition. Watch consumer lag per partition and be ready to split stock into buckets.

🌍 Real-World Best Practice

In practice, flash-sale systems shed load in layers long before stock is touched, and only then serialize the small amount of surviving traffic. A typical sequence looks like this:

  • Step 0 — Shape demand first: Use a waiting room or queue, rate limiting, bot protection, and per-user purchase limits so the backend sees a fraction of raw traffic. Load-test the hot SKU and record lock wait time and pool saturation.
  • Step 1 — Sold-out fast path: Once stock hits zero, publish a flag to the CDN or cache so remaining requests are rejected without touching the backend.
  • Step 2 — Single writer per SKU: Route purchase commands through a partitioned log keyed by SKU, with idempotent consumers (the answer to this question).
  • Step 3 — Stock bucketing for extreme SKUs: Split one SKU's stock across several buckets, each with its own partition, when a single consumer becomes the ceiling.
  • Step 4 — Reservations and payment: Treat the decrement as a reservation with a TTL; release it through the same log on payment failure or expiry.
  • Step 5 — Reconcile: Periodically compare log-derived stock, database stock, and paid orders, and alert on drift.

Protect the system with admission control first, then guarantee correctness with a single writer.

💡

Key Takeaway

When thousands of requests compete for one hot key, locks and retries only move the contention around. Serialize writes through a single owner per key (a partitioned log with one consumer per SKU), make commands idempotent, and serve reads from a separate read model. In exchange for asynchronous confirmation you get exact stock and a system that stays up during the surge.
