Asha's Real-Time Semantic Search: Syncing vs. Streaming the Vectors

Asha, a backend engineer, owns semantic search for a multi-tenant product catalog with thousands of item writes per second. Each item has metadata in a relational database and a vector embedding in a vector database used for approximate nearest neighbor (ANN) search. The requirements are search latency under 100 ms, near-real-time visibility of new and updated items, and predictable failure handling. The vector database excels at ANN queries but has slow bulk writes during spikes and weak transactional guarantees. She must design the write and indexing strategy.

A
Fully synchronous writes: generate the embedding in the request, then write metadata and vector atomically (transaction or 2PC), and return success only after both stores acknowledge.
✗ Not Best
B
Append a single event to a durable log (Kafka) while synchronously updating relational metadata, then use asynchronous workers or a stream processor to compute embeddings and upsert into the vector DB with versioned timestamps, and handle read-after-write with a small recent-writes cache or metadata timestamp checks at query time.
✓ Best Answer
C
Per-tenant isolation: separate vector clusters per tenant, with synchronous writes to the tenant's metadata DB and vector cluster, scaling by adding clusters for new tenants.
✗ Not Best
D
Persist only metadata on write, and run embedding and vector indexing in periodic batch jobs (nightly or hourly). Serve queries from the last batch, computing embeddings on the fly for modified records or falling back to metadata-only results.

Answer & In-Depth Explanation

🏆 Best Answer — B: Log-Based Async Indexing with Versioned Upserts

The two stores have different strengths. The relational database is the durable source of truth, while the vector index is a derived, rebuildable view that is slow to write in bursts. The right design makes the source-of-truth write fast and durable, then propagates to the index through a buffered, replayable pipeline. Here's why it stands out:

  • Write latency is decoupled from the slow vector DB: The request path commits metadata (and an event) and returns. Embedding generation and vector upserts, the slow parts, happen off the request path.
  • Spikes are absorbed by the log: Kafka buffers bursts, and workers batch upserts at a rate the vector DB can sustain. Backpressure shows up as consumer lag, not request failures.
  • Predictable failure handling: Failed embeddings or upserts are retried with backoff, and poison messages go to a dead-letter topic. Nothing is lost, because the log and relational DB are durable, and the index can be rebuilt by replay.
  • Correct under weak vector-DB guarantees: Versioned (or timestamped) idempotent upserts mean duplicates and out-of-order delivery cannot overwrite newer data with older data.
  • Near-real-time with read-your-writes: Typical pipeline lag is seconds. For items changed within that window, the query layer checks versions against the relational DB and merges them in from a small shared recent-writes set (matched lexically until their vectors are indexed), so users see their own changes immediately.

A production-ready version has an outbox or CDC source, partitioning by item ID, idempotent versioned upserts, a dead-letter queue, and a freshness SLO (for example 'p99 index lag under 5 seconds'). Monitor consumer lag, embedding latency, upsert error rate, and recent-writes overlay hit rate.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🔒

A — Fully Synchronous Dual-Store Write

There is no real distributed transaction across a relational database and most vector databases, and 2PC would couple request latency and availability to the slowest component. Embedding inference in the request path adds tens to hundreds of milliseconds, and during write spikes the vector DB's slow bulk writes turn into user-facing timeouts. Caveat: synchronous indexing can be acceptable for very low write volume where simplicity wins.

🏢

C — Per-Tenant Vector Clusters

Isolation is a legitimate requirement for some tenants, but separate clusters per tenant do not fix the write-path problem: writes are still synchronous and still hit slow bulk-write behavior. Operational cost grows with tenant count (many small, underused clusters, upgrades, backups, monitoring), and skewed tenants still need capacity planning. Namespaces or partitions with enforced tenant filters are usually the better default, with dedicated clusters reserved for large or regulated tenants.

🕒

D — Hourly or Nightly Batch Indexing

Batch indexing is simple and cheap, but it cannot meet near-real-time visibility: new items would be invisible for up to a batch interval. The fallback of computing embeddings on read adds inference latency to the search path and can break the 100 ms target. Large batches also create exactly the write spikes the vector DB handles poorly. Caveat: batch jobs are still useful for periodic full re-indexing and model migrations.

⚡

B — Log-Based Async Indexing with Versioned Upserts ✓

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Synchronous Dual-Store Write

Low write volume, relaxed latency targets, and a vector store that supports the needed transactional behavior.

📌

B — Log + Async Versioned Upserts

High write rates, bursty traffic, near-real-time search, and a vector DB with weak write guarantees (this scenario).

📌

C — Per-Tenant Clusters

A few large or regulated tenants that need hard isolation, data residency, or dedicated capacity.

📌

D — Batch Indexing

Mostly static catalogs where hours-old search results are acceptable, or as a complement for periodic full re-indexing.

⚠️ Common Mistakes to Avoid

  • Dual-writing to the DB and Kafka without an outbox: A crash between the two silently drops index updates. Make the event part of the same transaction.
  • Unversioned upserts: Retries and out-of-order messages can overwrite newer vectors with older ones. Always carry a version and upsert only if it is newer.
  • Ignoring deletes: Removed items keep appearing in search results. Propagate tombstones and verify against metadata at query time.
  • Unbounded retries on poison messages: A single bad document blocks a partition. Retry with a limit, then dead-letter it.
  • No tenant filter enforcement: A missing filter in an ANN query leaks data across tenants. Enforce it in a shared query layer, not per caller.
  • Per-node recent-write caches: Another API node will not see the entry. Use a shared cache or version checks against the DB.

🌍 Real-World Best Practice

In practice, search teams treat the vector index as a derived view of the source of truth. A typical sequence:

  • Step 0 — Define freshness and failure goals: Agree on index-lag SLOs, what users should see right after a write, and what happens when embedding or indexing is degraded.
  • Step 1 — Make the source write atomic with an event: Use an outbox or CDC so the item row and its change event commit together.
  • Step 2 — Build the indexing pipeline: Use Kafka partitioned by item ID, workers that batch embedding calls and upserts, retries with backoff, and a dead-letter topic.
  • Step 3 — Guard upserts with versions: Reject writes older than the stored version so replays and duplicates are harmless.
  • Step 4 — Add the read-your-writes overlay: Merge recently written items (from a shared short-TTL store) into results, enforce the tenant filter, and re-rank.
  • Step 5 — Plan rebuilds: Support full replay into a new index for model upgrades, corruption, or disaster recovery, and reconcile periodically by comparing versions between the DB and the index.

Keep the relational DB authoritative and treat the vector index as rebuildable.

💡

Key Takeaway

Decouple slow embedding and vector writes from the request path: commit metadata and an event atomically, index asynchronously through a durable log with versioned upserts, and overlay recent writes at query time for read-after-write.
