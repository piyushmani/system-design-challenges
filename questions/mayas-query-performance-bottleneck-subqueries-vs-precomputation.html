Maya’s Query Performance Bottleneck: Subqueries vs. Precomputation

Maya, a backend engineer on a payments system, owns a real-time dashboard endpoint that must return per-customer metrics (transaction count over 30 days, top 3 merchants, rolling spend percentiles) in under 200 ms. Today it runs one large SQL statement with nested subqueries and several CTEs over very large transaction tables. At peak, database CPU spikes, p99 latency degrades and requests time out. Profiling shows the cost comes from the volume of data aggregated on every request, not from a missing index, the same metrics are requested repeatedly by dashboards that refresh, transactions are essentially append-only, and the product can tolerate seconds to a minute of staleness if it is disclosed. She must pick the production strategy that best balances latency, scalability, consistency and operational overhead.

A
Retain the single complex SQL query (with its subqueries and CTEs) and vertically scale the database by increasing the instance size and introducing read replicas to handle read operations. Trust the database query optimizer to manage CTEs and subqueries dynamically for each request to provide real-time results.
✗ Not Best
B
Restructure the monolithic SQL into numerous smaller CTEs and temporary tables that run per-request, forcing the database to materialize partial results during execution. Incorporate query hints and performance tunings to encourage inlining or parallel processing where feasible.
✗ Not Best
C
Pre-calculate and store denormalized summary metrics (using materialized views or dedicated summary tables) that are updated asynchronously (via CDC or background tasks). Serve dashboard requests directly from the summary table, falling back to on-the-fly queries only for missing or cold data. Track staleness and clearly communicate eventual consistency levels.
✓ Best Answer
D
Extract the intensive joins and aggregations from the database and move them to the application layer or a specialized analytics microservice. This service would fetch raw data as needed, calculate the results in memory, and synchronously return them to the API.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — C: Precomputed Summaries Fed by CDC

The endpoint is slow because every request re-aggregates up to 30 days of raw transactions. No rewrite of that query changes the amount of data it must read. Option C moves the work from read time to write time: each transaction updates a small summary once, and each dashboard request becomes a handful of key lookups. Latency stops depending on table size and traffic stops multiplying database CPU. Here's why it stands out:

  • Constant-cost reads: A request reads about 30 daily buckets by primary key (customer, day) and merges them in memory, which is typically a few milliseconds, versus scanning and aggregating a month of rows. p99 becomes predictable and independent of table size.
  • Scales with writes, not reads: Each transaction is aggregated once, no matter how many times dashboards refresh. The CPU surge disappears and the source database is shielded from analytical load.
  • Mergeable design handles the hard metrics: Per customer per day, store the count, spend sum, a per-merchant spend map (or top-K sketch) and a percentile sketch (t-digest or DDSketch). A rolling 30-day window is the merge of 30 buckets. Percentiles cannot be derived from sums or averages, so sketches (or histograms) are essential.
  • CDC is non-invasive and replayable: Log-based change data capture (for example Debezium) reads the commit log, so there are no triggers on the hot payments tables and no dual writes. The summary can be rebuilt by replaying the stream, and idempotent upserts make retries safe.
  • Honest freshness: Every summary carries an as_of watermark that is returned to the client. For stricter freshness, add today's small delta from a live query or in-stream state. A rate-limited fallback covers cold or missing customers.

Define the freshness SLO and which metrics are exact versus approximate, make aggregation idempotent (dedupe by transaction ID and version), reconcile summaries against the source nightly, and alert on CDC lag. Guard the fallback query with a rate limiter and circuit breaker so a cold-cache storm cannot recreate the original outage.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

📈

A — Bigger Instance + Replicas + Trust the Optimizer

Scaling up and out does not change the work per request. Each request still scans and aggregates a month of data, so you just pay linearly more to run the same expensive query, and replicas add replication lag. The optimizer cannot turn an aggregate over 30 days into an index lookup. (In Postgres 12+ a CTE referenced once is inlined, but one referenced several times is still materialized on every execution.) Caveat: useful as a stopgap while the summaries are being built, and always fix a genuinely missing index first.

🧩

B — More CTEs, Temp Tables and Hints per Request

Per-request temp tables and extra materialization step increase the work done: temp-table creation writes to the catalog and storage, and at thousands of requests per second the I/O and CPU amplification is severe. Query hints are brittle and tend to break with data skew, upgrades or plan changes. This reshapes the plan but not the amount of data processed. Caveat: refactoring can give a 2–10× gain, which is worth applying to the fallback path.

🧮

D — Aggregate in the Application or Analytics Microservice

Pulling raw rows over the network shifts the cost to serialization, network and application memory, while the database still performs the same scans to produce those rows. Synchronous per-request computation keeps the p99 problem and adds network overhead, and the app has no access to the database's indexes or join algorithms. Caveat: an analytics service is a good idea when it owns precomputed or columnar data, which is effectively option C.

⚡

C — Precomputed Summaries Fed by CDC ✓

Pre-calculate and store denormalized summary metrics (using materialized views or dedicated summary tables) that are updated asynchronously (via CDC or background tasks). Serve dashboard requests dire

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Scale Up + Replicas

A temporary stopgap while a longer-term fix is built, or when the query is already efficient and the load is simply a bit higher than capacity.

📌

B — More CTEs / Temp Tables

One-off or low-frequency reports where readability or plan stability matters more than throughput.

📌

C — Precomputed Summaries

Repeated, latency-sensitive metrics over large append-mostly data where bounded staleness is acceptable, as in this dashboard.

📌

D — App-Layer Aggregation

Small result sets or logic that cannot be expressed in SQL, ideally over already-aggregated or columnar data rather than raw tables.

⚠️ Common Mistakes to Avoid

  • Skipping profiling: If the real problem is a missing index or a bad plan, precomputation adds a pipeline for nothing. Confirm with EXPLAIN ANALYZE first.
  • Averaging percentiles: You cannot get a rolling P95 from stored averages or per-day percentiles. Store mergeable sketches or histograms.
  • Relying on full-refresh materialized views: Refreshing recomputes everything, which is slow and heavy at this scale. Maintain summaries incrementally.
  • Ignoring reversals and late events: Refunds, chargebacks and out-of-order events make summaries drift. Model them as correction events and reconcile nightly.
  • Unbounded fallback to the source query: A cold start sends every request back to the slow path and recreates the outage. Use a rate limiter, a circuit breaker and stale responses.
  • Hiding staleness: If clients cannot see as_of, they cannot decide whether the number is fresh enough. Return it and alert on lag.

🌍 Real-World Best Practice

Performance work on a slow endpoint should start with evidence, but when the evidence points at aggregation volume, teams move to incremental precomputation. A typical path:

  • Step 0 — Profile: EXPLAIN (ANALYZE, BUFFERS) and pg_stat_statements to confirm the cost is aggregation volume and not a missing index. Take cheap wins first.
  • Step 1 — Define metric contracts: Freshness SLO, which metrics are exact, and the acceptable error for approximate percentiles.
  • Step 2 — Design the summary schema: Customer × day buckets with count, sum, merchant spend map and percentile sketch, keyed by (customer_id, day).
  • Step 3 — Feed it through CDC: Source database → Kafka → stream aggregator → idempotent upsert, deduplicating by transaction ID and handling refunds as corrections.
  • Step 4 — Serve and cache: Multi-get the 30 buckets, merge in memory, and optionally cache the merged result for a few seconds per customer when dashboards poll.
  • Step 5 — Protect and verify: Rate-limited fallback with a circuit breaker, nightly reconciliation against the source, lag alerts and a backfill tool for new metrics.

Measure first, then pay the aggregation cost once at write time instead of on every read.

💡

Key Takeaway

If a query is slow because it aggregates too much data on every request, rewriting it will not fix the fundamentals. Precompute mergeable summaries incrementally (CDC, daily buckets, sketches), serve reads as key lookups, disclose freshness with an as_of timestamp, and keep a guarded fallback for cold data.
