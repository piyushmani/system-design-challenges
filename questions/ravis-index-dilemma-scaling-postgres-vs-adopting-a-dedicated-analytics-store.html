Challenge

Ravi’s index dilemma: Scaling Postgres vs. adopting a dedicated analytics store

Ravi is building a multi-tenant analytics API that handles 5,000 write QPS and 1,000 read QPS across tenants. Reads filter by tenant_id, a time window, and several dimensions, then group and aggregate (counts and sums), sometimes with ordering and pagination. The targets are 200 ms read latency and roughly 5 seconds of data freshness. On a single PostgreSQL cluster, write latency is rising and planning and scan times for analytics queries are growing. He needs a strategy that meets latency and freshness while keeping operational complexity and cost manageable.

A
Keep everything in PostgreSQL and add narrow composite B-tree and covering (INCLUDE) indexes matched to the filter and sort columns on the tenant tables, relying on strong consistency and the primary for both reads and writes.
✗ Not Best
B
Shard by tenant and create many partial or per-tenant indexes (a partial index per tenant, or per-tenant schemas and tables), routing queries to the right shard to keep indexes small and selective, with strong read consistency within each shard.
✗ Not Best
C
Keep data in PostgreSQL but add near-real-time materialized views or pre-aggregated tables refreshed every few seconds by background jobs or triggers, accepting eventual consistency, and route reads to them.
✗ Not Best
D
Move analytics reads to a dedicated OLAP database (ClickHouse or a managed analytics service) fed by asynchronous CDC or streaming (such as Debezium), keep PostgreSQL for OLTP writes, and serve analytics from the OLAP cluster with eventual consistency.
✓ Best Answer
✅

Answer & In-Depth Explanation

🏆 Best Answer — D: Dedicated OLAP Store via CDC

The symptoms point to a workload mismatch, not a tuning problem. PostgreSQL is a row-oriented OLTP engine, and it is being asked to absorb 5,000 writes per second and run scan-and-aggregate queries over time windows on the same primary. Splitting the workloads (OLTP keeps the writes, a columnar OLAP engine serves the aggregates) fixes both pain points at once, and a 5-second freshness target is well within what CDC plus streaming ingestion can deliver. Here's why it stands out:

  • Columnar scans are the right tool: Aggregations over filtered time ranges read only the needed columns and benefit from compression and vectorized execution, often running orders of magnitude faster than row-store scans. Ordering the table by (tenant_id, time) means a query reads only that tenant's slice of data.
  • Isolates the workloads: Analytics queries stop competing with OLTP writes for CPU, I/O, buffer cache, and locks, so write latency improves without adding indexes that would slow writes further.
  • Freshness is achievable: Debezium reading the Postgres WAL, a Kafka topic, and batched inserts into ClickHouse typically land data within a second or a few seconds; a 5-second goal is realistic with tuned batch intervals (depends on volume and batch size).
  • Flexible dimensions: Because aggregation happens at query time over raw or lightly pre-aggregated data, new filters and group-bys need no new indexes or views, unlike pre-aggregation.
  • Why not materialized views in Postgres (Option C)? They keep the load on the primary and only help for the aggregates you precompute, and native REFRESH MATERIALIZED VIEW recomputes everything rather than updating incrementally.

A solid rollout includes a sort key that starts with tenant_id, time-based partitioning with TTL, idempotent or deduplicating ingestion, per-tenant quotas, and freshness monitoring (end-to-end lag from Postgres commit to queryable result). Before adopting a new system, check whether PostgreSQL-native steps (time partitioning, dropping unused indexes, a read replica) buy enough runway for your actual data volume.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

📇

A — Composite and Covering Indexes

Indexes help read paths but hurt the write path: every index adds write amplification, and with 5,000 writes per second and write latency already rising, more indexes make the root problem worse. Aggregating a time window still reads and groups many rows whatever the index shape, and covering indexes duplicate data. Indexing shines for selective queries; these queries aggregate large ranges. Caveat: a modest, targeted index plus time partitioning is the right first step for a small tenant base with limited data volume.

🧩

B — Tenant Sharding with Per-Tenant Indexes

Per-tenant partial indexes or schemas don't scale operationally: thousands of tenants produce thousands of indexes or tables, which slows planning, bloats the catalog, complicates migrations and vacuum, and turns onboarding into a DDL operation. Tenant sharding itself is legitimate (Citus, for instance, distributes tables by tenant_id), but it spreads the same row-store scan costs across more nodes at much higher operational cost and does not change the OLTP/OLAP mismatch. Large tenants also become hot shards.

🔄

C — Postgres Materialized Views / Pre-Aggregates

Pre-aggregation serves known dashboards quickly, but the query pattern includes various dimensions with filtering and grouping, so each new dimension combination needs another rollup and the number of rollups explodes. Refresh strategies are costly: full refreshes are heavy, and triggers or incremental maintenance (such as pg_ivm) add write overhead to a system whose writes are already slow. Everything stays on the primary, so reads and writes keep competing. Caveat: for a small, fixed set of dashboards, rollups can be enough and cheap.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Composite / Covering Indexes

Small to moderate data volumes, selective queries, and profiling that shows missing or ineffective indexes; the cheapest first step.

📌

B — Tenant Sharding + Per-Tenant Indexes

Very large multi-tenant OLTP workloads where tenants are isolated and mostly queried by point lookups and row-level operations (for example with Citus), not heavy aggregation.

📌

C — Materialized Views / Pre-Aggregates

A fixed, small set of dashboards or KPIs where query shapes are known in advance and a few seconds of staleness is fine.

📌

D — OLAP Store via CDC

High write rates with time-window aggregation across flexible dimensions, strict latency SLOs, and a team able to run (or buy) an analytics store.

⚠️ Common Mistakes to Avoid

  • Row-by-row inserts into the OLAP store: Columnar engines such as ClickHouse expect large batches. Thousands of tiny inserts create too many parts and hurt performance. Batch by size or time, or use async inserts.
  • Sort key without tenant_id first: Queries then scan other tenants' data and tenant-level performance isolation disappears.
  • Ignoring replication-slot lag: A stuck CDC consumer makes Postgres retain WAL and can take down the source database.
  • No plan for updates and deletes: CDC streams mutations, and append-only OLAP tables need dedupe or versioning to represent them correctly.
  • No per-tenant limits: One tenant's heavy query can consume the shared cluster. Apply quotas, timeouts, and concurrency caps.
  • Measuring freshness only at ingest: Track end-to-end lag from Postgres commit to queryable result, not just Kafka consumer lag.

🌍 Real-World Best Practice

Teams typically stage the move rather than jump, measuring at each stage:

  • Step 0 — Profile: Use EXPLAIN (ANALYZE, BUFFERS), pg_stat_statements, and write-latency breakdowns to confirm whether the primary is bound by index maintenance, I/O, or CPU.
  • Step 1 — Cheap Postgres wins: Drop unused indexes, partition by time, add a read replica for analytics, and tune autovacuum.
  • Step 2 — Separate the workloads: Stream changes through CDC into an OLAP store and shift the analytics API to read from it.
  • Step 3 — Model the OLAP tables: Order by (tenant_id, time), partition by month, use low-cardinality types, and add projections for common aggregates.
  • Step 4 — Protect the cluster: Per-tenant limits, query timeouts, and result caches.
  • Step 5 — Retire the old path: Remove heavy analytics indexes from OLTP once reads have moved, which also improves write latency.

Move to a dedicated analytics store when the aggregation workload, not just data size, is what hurts the OLTP system.

💡

Key Takeaway

When one database is asked to be both an OLTP write engine and an aggregation engine, stop tuning and separate the workloads. Feed a columnar OLAP store from the OLTP system through CDC or streaming, accept seconds of lag, and protect it with tenant-aware ordering, quotas, and end-to-end freshness monitoring.
