Challenge

Riya's multi-region trade-off: choosing between fast writes and strict consistency

Riya is the backend architect for a global web application serving users in the EU, US and APAC. The system stores user preferences that are read on almost every page load and updated less often (up to 10k writes/s at peak). Targets are 99.99% availability, user write latency under 150 ms, and manageable cost. Minor staleness is acceptable, but dropped updates and highly visible conflicting data are not. She must design how settings are replicated and served across regions so that availability and speed are maximized while conflicts are handled properly.

A
A single primary database situated in one region, enforcing synchronous cross-region replication (blocking until every region acknowledges). This ensures absolute strong consistency for every update.
✗ Not Best
B
An active-active multi-master topology allowing writes anywhere, leveraging a basic last-write-wins (LWW) timestamp rule to handle conflicts, supported by rapid asynchronous cross-region replication.
✗ Not Best
C
A local primary for each region (writes are processed locally) coupled with asynchronous replication to other locations. Utilize client-side session affinity for read-your-writes guarantees, alongside a lightweight reconciliation mechanism featuring versioned, idempotent updates and a background repair task for rare discrepancies.
✓ Best Answer
D
Adopt a globally distributed, strongly consistent database (like Spanner or CockroachDB in geo-distributed mode) that natively supports cross-region transactions and provides linearizable or serializable reads out of the box.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — C: Regional Primaries with Async Replication, Versioned Updates and Repair

The requirements describe a classic read-mostly, single-author, staleness-tolerant data set, and they say plainly which failures are unacceptable: lost updates and visible conflicts. Option C is the only design that meets the latency and availability targets and addresses those two failure modes. Writes commit in the user's own region, reads are served locally, and replication is asynchronous, while versioned, idempotent updates detect concurrent edits instead of silently overwriting them, and a background repair task closes any remaining gaps. Here's why it stands out:

  • Latency fits the budget: a local commit takes a few milliseconds to tens of milliseconds. A cross-continent round trip alone is roughly 80 to 100 ms between the US and EU and often 150 to 250 ms to APAC, which would consume or exceed the 150 ms write budget before any database work.
  • Availability does not multiply down: a write needs only its local region. 99.99% allows about 52 minutes of downtime per year, and a design that requires several regions to be up simultaneously cannot beat the weakest of them.
  • Reads are local and cheap: preferences are read on nearly every page load, so every region serves them from a local replica plus cache. Staleness is bounded by replication lag, typically sub-second to a few seconds.
  • Conflicts are rare and detectable: preferences are authored by one user, so true concurrent edits (two devices, or a user travelling) are uncommon. Carrying a version with each update turns them into detectable events, and field-level merging means edits to different settings do not conflict at all.
  • Read-your-writes without global consensus: session affinity, or a small version token held by the client (min_version), guarantees a user sees their own change even when the next request lands on a lagging replica.
  • Cost stays proportional: 10k writes/s shipped asynchronously is inexpensive compared with running globally synchronous consensus for every write.

A solid implementation has one version per entity (or field), idempotent update ids, HLC-based tie-breaks, a client version token for read-your-writes, and anti-entropy repair comparing replicas on a schedule. Optionally give each user a home region as the preferred writer, which reduces cross-region conflicts to near zero without blocking writes elsewhere.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🔒

A — Single Primary with Fully Synchronous Replication

Strong consistency is more than the requirements ask for, and it is bought with both of the constraints that matter. Every write waits for the slowest region, so APAC users alone can blow the 150 ms budget. Availability becomes the product of all regions (for example three regions at 99.95% each yield about 99.85%, below the 99.99% target), because a single unreachable region blocks every write. The single primary also becomes a regional single point of failure. Caveat: it is the right model for data that truly cannot diverge, such as balances.

⏱️

B — Active-Active with Basic Last-Write-Wins

The topology and speed are right, but the conflict rule violates a stated requirement. Basic LWW discards the losing write silently, and if timestamps come from wall clocks, clock skew decides the winner. At row granularity it also drops unrelated changes (a theme change overwritten by a language change made a moment earlier). That is precisely the 'dropped updates' outcome Riya cannot accept. Caveat: adding versioning, field-level merge and conflict logging to this design effectively turns it into option C.

🌐

D — Globally Distributed Strongly Consistent Database

Spanner or CockroachDB can reach the availability target and provide excellent correctness, but a cross-region write must reach a majority of replicas before it commits. With replicas on three continents, commit latency approaches or exceeds the 150 ms budget for some users, and running globally consensus-backed storage at 10k writes/s is materially more expensive. It buys linearizability that the requirements explicitly say is unnecessary for preferences. Caveat: it is a strong choice if the same platform also holds data that does need global transactions, or if regions are geographically closer together.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Single Primary + Full Sync

Small deployments in nearby regions with low write rates, or data that must never diverge and where higher write latency and lower availability are acceptable.

📌

B — Active-Active + Basic LWW

Data where a lost concurrent write is harmless (telemetry, last-seen timestamps, cache-like state) and simplicity matters more than preserving every edit.

📌

C — Regional Primaries + Async + Versioning

Read-heavy, single-author data (preferences, profiles, feature settings) that needs low latency everywhere, tolerates short staleness, and must not silently lose updates.

📌

D — Global Strongly Consistent DB

Data that needs cross-region transactions or linearizability (financial or entitlement data, global uniqueness), where regions are close enough that quorum latency is acceptable.

⚠️ Common Mistakes to Avoid

  • Row-level last-write-wins: one field's edit overwrites another's. Version and merge at the field level.
  • Trusting wall clocks: skew between regions decides winners. Use hybrid logical clocks or version counters.
  • No read-your-writes plan: users change a setting and see the old value on the next page. Use a client version token or region affinity.
  • Non-idempotent replication: a retried message applies twice and can reorder fields. Dedupe by update id and apply in version order.
  • No repair loop: a dropped replication message leaves replicas permanently different. Run anti-entropy comparisons and alert on drift.
  • Ignoring cross-field rules: independent field merges can combine into an invalid configuration. Keep rule-bound settings in one atomic document.

🌍 Real-World Best Practice

In practice teams classify the data first and then choose the cheapest model that meets its guarantees. A typical approach looks like this:

  • Step 0 — Classify: preferences tolerate staleness and rare conflicts; billing and entitlements do not. Only the first class uses this design.
  • Step 1 — Model the record: an entity with a version, per-field metadata (value, HLC, origin region) and an update id for idempotency.
  • Step 2 — Local primary per region: commit locally, return the new version, and give the client a min_version token.
  • Step 3 — Replicate asynchronously: a durable stream between regions with ordered, idempotent apply and lag metrics.
  • Step 4 — Serve reads locally: replica plus cache, with a fallback to the home region when the replica is behind the client's token.
  • Step 5 — Repair and verify: scheduled anti-entropy checks (checksums or Merkle trees), a conflict dashboard, and tests that cut inter-region links to confirm writes continue and state converges.

Spend consensus only where the business needs it.

💡

Key Takeaway

For read-heavy, single-author settings with tight latency and availability targets, commit locally, replicate asynchronously, and make updates versioned and idempotent so conflicts are detected rather than dropped. Add read-your-writes via a version token and a background repair job. Reserve synchronous or globally consensus-backed storage for the data that actually needs it.
