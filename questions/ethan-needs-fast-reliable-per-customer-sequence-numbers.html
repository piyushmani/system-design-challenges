Challenge

Ethan needs fast, reliable per-customer sequence numbers

Ethan is an infrastructure engineer building an order-processing and billing engine for a global SaaS enterprise. The platform must issue strictly ascending, monotonically increasing sequence numbers partitioned per individual customer (e.g., invoice_seq tied to a specific customer_id). The engine runs across hundreds of distributed stateless application worker nodes. Ethan must satisfy rigorous operational SLAs: assignment latency must remain strictly under 10ms (p99), aggregate throughput must comfortably exceed tens of thousands of allocations per second, availability must remain high without central lock bottlenecks, and duplicate sequence numbers are categorically prohibited. The business rules explicitly permit minor numeric gaps in the sequence following an unexpected application node failure or restart.

A
Centralized single-host allocator: Execute a dedicated leader process maintaining an in-memory counter for every customer.
✗ Not Best
B
Distributed locking for a shared counter: Employ Redis RedLock or SETNX to grab a customer-specific lock, fetch and increment a central counter.
✗ Not Best
C
Atomic database operations: Maintain a dedicated counter row for each customer within the primary relational database. Execute an atomic SELECT FOR UPDATE or UPDATE ... RETURNING.
✗ Not Best
D
Sharded range pre-allocation: Distribute customers among application server shard owners using lease-based assignment or consistent hashing. Each designated owner requests a block of sequence numbers from a centralized database or allocator service. The servers then dispense numbers from their local cache without requiring locks.
✓ Best Answer
✅

Answer & In-Depth Explanation

🏆 Best Answer — D: Sharded Range Pre-Allocation (Hi/Lo Block Allocation Pattern)

Generating monotonically increasing per-customer sequence numbers at tens of thousands of requests per second across hundreds of application nodes cannot rely on synchronous per-number database writes or distributed locks without violating the sub-10ms latency SLA. Sharded range pre-allocation (an evolution of the classic Hi/Lo algorithm) amortizes centralized coordination over large batches of allocations. By hashing or assigning customer affinity to shard nodes, each node claims a reserved numeric block (e.g., 100 sequence numbers) from the central backing store using a single atomic compare-and-swap or UPDATE ... RETURNING statement. Once claimed, the application node dispenses sequence numbers directly from its local in-memory counter (e.g., AtomicLong) in sub-microsecond time (<0.05ms) with zero network round-trips. Because the central allocator increments the global high-water mark atomically before granting a block, two nodes never receive overlapping ranges, guaranteeing absolute prevention of duplicates. When a node exhausts its block, it fetches the next block; if a node crashes, the unallocated numbers in its current in-memory block are simply discarded, creating minor numeric gaps—which the business requirements explicitly permit.

  • Sub-millisecond local allocation: Dispensing numbers directly from local memory variables bypasses network I/O, reducing p99 allocation latency from 15-50ms to less than 1ms.
  • Amortized database IOPS: Requesting blocks of size $N$ (e.g., $N=100$) reduces database write traffic by a factor of $100\times$, allowing a modest relational database or KV store to support 50,000+ allocations/sec.
  • Absolute duplicate immunity: The central allocation table uses atomic increments to grant non-overlapping intervals ($[1..100]$, $[101..200]$), making duplicate sequences mathematically impossible across the entire cluster.
  • Perfect tolerance for node failure: Discarding the remainder of an in-memory block upon process termination causes minor sequence gaps, perfectly aligning with business tolerance while avoiding complex two-phase rollback protocols.
  • Horizontal scalability via affinity: Using consistent hashing (e.g., Maglev or Ketama) to route customer requests to owning application instances maximizes cache hit rates and eliminates cross-worker block thrashing.

Decoupling high-frequency in-memory sequence assignment from low-frequency durable block allocation delivers sub-millisecond latency and massive throughput while maintaining unbreakable protection against duplicate identifiers.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🛑

A — Centralized Single-Host Allocator

Hosting all in-memory customer counters on a single dedicated leader process creates a fragile Single Point of Failure (SPOF) and an unscalable network bottleneck. Handling tens of thousands of network RPCs per second on a single host leads to thread starvation, and if the leader crashes, state synchronization or failover recovery risks losing counter state or causing prolonged cluster downtime.

🔒

B — Distributed Locking with Redis (RedLock / SETNX)

Acquiring a distributed lock via Redis RedLock or SETNX for every single sequence allocation incurs multiple network round-trips (lock acquisition, counter read, counter increment, lock release). Network jitter, lock contention under bursty customer load, and Redis master-replica async failover easily breach the 10ms p99 SLA and risk duplicate number generation upon split-brain re-elections.

⚠️

C — Atomic Database Operations (SELECT FOR UPDATE / RETURNING)

Executing a synchronous SQL UPDATE customer_sequences SET counter = counter + 1 WHERE customer_id = :id RETURNING counter for every sequence allocation serializes writes against the database transaction log (WAL). At tens of thousands of operations per second across hundreds of application workers, row lock contention and disk I/O saturation quickly drive p99 latencies past 50-100ms.

⚡

D — Sharded Range Pre-Allocation (Hi/Lo Block Allocation Pattern) ✓

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Single-Host Central Allocator

Low-scale internal developer tools or ephemeral lab environments where throughput is under 100 QPS and high availability is unnecessary.

📌

B — Distributed Locking with Redis

Coarse-grained distributed task coordination where locks are held for seconds and operations do not require low-latency monotonic numbering.

📌

C — Synchronous Atomic SQL Update

Low-volume enterprise invoicing (<10 orders per minute) where immediate continuous numbering without any gaps is legally enforced by strict local regulations.

📌

D — Sharded Range Pre-Allocation (Hi/Lo)

High-volume distributed billing, order processing, and telemetry ingestion platforms requiring sub-10ms latency, high throughput, and duplicate-free monotonic IDs.

🗺️ Hi/Lo Sharded Block Pre-Allocation Architecture

Application worker acquires a block of 100 sequence numbers from the central database in a single atomic update. Subsequent requests are dispensed locally from memory in sub-microsecond time with zero network overhead.

🧑‍💻 Thread-Safe In-Memory Range Sequence Allocator

Local high-performance allocator maintaining an active sequence block, dispensing via atomic primitives, and asynchronously replenishing blocks.

⚠️ Common Mistakes to Avoid

  • Allocating oversized blocks to inactive customers: Granting a block of 10,000 numbers to a customer who generates 1 invoice per month, causing giant numeric gaps when nodes cycle.
  • Synchronous blocking on block exhaustion: Failing to asynchronously pre-fetch the next block when the current block is nearly depleted, causing periodic 50ms latency spikes.
  • Non-thread-safe local counters: Using standard primitive integers without atomic operations (like Java AtomicLong or Go sync/atomic) for local block increments, leading to race conditions across worker threads.
  • Persisting local range state across restarts: Attempting to persist local unallocated blocks to local disk caches without distributed coordination, risking duplicate reuse across redeployments.

🌍 Real-World Best Practice

High-throughput identifier generation systems (such as Snowflake IDs, Flickr's ticket servers, and Hibernate's pooled-lo optimizer) universally use block pre-allocation. In production billing and invoice generation, database round-trips for every sequential number cannot scale under load.

  • Dynamic block sizing by customer tier: Allocate small blocks ($N=10$) for low-frequency retail customers and larger blocks ($N=500$) for enterprise accounts with massive batch invoice generation.
  • Asynchronous background block pre-fetching: When an in-memory block drops below 20% remaining capacity, trigger an asynchronous background worker to pre-allocate the next block, ensuring client threads never wait on network I/O.
  • Atomic SQL block allocation: Use an atomic reservation query: UPDATE customer_sequences SET last_allocated = last_allocated + :block_size WHERE customer_id = :cid RETURNING last_allocated - :block_size + 1 AS range_start, last_allocated AS range_end.
  • Graceful shutdown drain: Register a SIGTERM signal hook that attempts to update the database high-water mark backwards to trim unused numbers during controlled deployments.
  • Cryptographic audit logging: Pair each dispensed sequence number with an HMAC signature or UUID in the finalized order record to provide tamper-proof provenance during audits.

When ultra-low latency and high throughput are required for sequential identifiers, pre-allocate blocks durably and dispense locally in memory. It is the gold standard for distributed sequence generation.

💡

Key Takeaway

Never make a synchronous database or lock round-trip for every ID; pre-allocate ranges in blocks and dispense from memory to achieve sub-millisecond p99 latency.
