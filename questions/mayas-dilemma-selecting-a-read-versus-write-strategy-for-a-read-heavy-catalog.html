Read vs Write Optimization Caching Architecture
Challenge

Maya's dilemma: selecting a read-versus-write strategy for a read-heavy catalog

Maya is a backend architect for an international e-commerce catalog. The workload is heavily read-skewed: about 150k reads/second (product pages, personalization, search) against roughly 100 writes/second (product edits, inventory, price changes). Reads run intricate, denormalized queries (aggregations and joins) and need sub-100 ms p99 latency worldwide. Price and inventory writes must be strict to prevent overselling, while tags and descriptions tolerate brief UI delay. The team needs horizontal read scaling across regions, high availability, acceptable write latency and visible data staleness. Which primary strategy fits best?

A
Send reads to asynchronous database replicas (one primary, many followers) and add followers in each region. Rely on replication lag being eventually consistent, with no dedicated cache or separate read models.
✗ Not Best
B
Put a centralized write-through cache (for example a global Redis cluster) in front of the primary database. Every write updates both the DB and the cache synchronously, and all reads go to the cache, which is treated as the sole authoritative read source.
✗ Not Best
C
Use CQRS: a single authoritative write service handles transactional updates and appends events to a durable log. Build denormalized, regional read models (materialized views) asynchronously from those events and serve queries from them and local caches. Monitor lag and add compensations for critical writes.
✓ Best Answer
D
Keep a single SQL cluster but partition it by product ID across multiple primary shards. Route all reads and writes to the owning shard leader for strict consistency and scale reads and writes by adding shard leaders.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — C: CQRS with Event Log and Regional Read Models

Option C is the best fit. With roughly 1,500 reads for every write, the right move is to separate the two models: keep a small, strongly consistent write path and pre-compute the answers to the expensive read queries into regional materialized views fed from a durable event log. Here's why it stands out:

  • Moves expensive work to write time: joins and aggregations are computed once per change by projectors, not 150k times per second at read time. Read stores hold query-shaped documents, so most reads become key lookups.
  • Reads scale horizontally and regionally: each region consumes the event log into its own read store and cache, so users hit a nearby copy and the p99 target is not at the mercy of cross-ocean round trips.
  • The write path stays small and strict: 100 writes/s fits comfortably on one transactional store. Price and inventory are validated against this authoritative store, which prevents overselling without distributing the write path.
  • Staleness becomes observable: every event carries a commit timestamp and a version, so projection lag per region is a metric with an alert threshold. Replica lag in Option A exists too, but it is rarely measured per query.
  • Different consistency per field: tags and descriptions can be shown from the read model as is. For price and inventory, the cart and checkout re-validate against the write service, with compensation (reprice or cancel) as a rare fallback.
  • Resilient and rebuildable: a region that falls behind or loses its store can rebuild from the log, and regions keep serving reads while the write region is briefly unavailable.

Keep one authoritative write store, publish changes through an outbox to a durable log, build query-shaped read models per region, and track projection lag per region against a freshness SLO. Re-validate price and inventory at checkout.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🪞

A — Async Read Replicas

Replicas copy the normalized schema, so every replica still executes the expensive joins and aggregations. More replicas add capacity but do not make each query faster, and hitting a worldwide p99 of 100 ms on intricate queries is hard. Replication lag is unbounded unless someone monitors it, and there is nowhere to put search or personalized views. Caveat: replicas are a fine, simple fix for moderate read loads with simple queries, and they are still useful for reporting inside Option C.

⚡

B — Central Write-Through Cache as Sole Read Source

A cache is a performance layer, not a system of record. A single global cluster means distant regions pay cross-ocean latency, and an outage or mass eviction would take reads down or push them onto the database. Updating the DB and the cache synchronously is a dual write that can fail halfway, and a key-value cache cannot answer joins, aggregations or search unless the values are pre-computed, which is Option C's materialized-view idea without the durable log. Caveat: regional caches in front of read models are very useful, just not as the authority.

🧩

D — Shard by Product ID

Sharding scales writes and storage, but writes are only about 100/s here. The read queries aggregate and join across products (categories, search, personalization), so they turn into scatter-gather requests across shards, which raises latency. Shard leaders sit in specific places, so global read latency is not fixed, and cross-shard consistency and rebalancing add operational load. It solves a problem this workload does not have.

⚡

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Async Read Replicas

Moderate read load, simple queries that run fast on a normalized schema, one or few regions, and replica lag that users and business rules can tolerate.

📌

B — Central Write-Through Cache

As an accelerator in front of an authoritative store for hot keys, ideally regional and combined with Option C. Not as the sole source for reads.

📌

C — CQRS + Regional Read Models

Heavy read skew, complex or aggregated queries, multi-region low-latency requirements and mixed consistency needs across fields.

📌

D — Shard by Product ID

Write volume or data size exceeds one node and most queries naturally key by the shard key. Not for read-heavy workloads with cross-entity queries.

⚠️ Common Mistakes to Avoid

  • Using the read model for strict decisions: price at checkout and stock decrements must go to the authoritative store, never to a projection.
  • Events without versions: duplicates and out-of-order deliveries then overwrite newer data. Carry a version and ignore anything not newer.
  • Dual write instead of an outbox: committing to the DB and publishing separately can lose or duplicate events.
  • No lag metrics: staleness stays unknown until customers complain. Alert on per-region projection lag.
  • No rebuild plan: without replay tooling you cannot change a read model or recover a lost one.
  • CQRS everywhere: applying it to simple CRUD areas adds cost without benefit. Use it where the read and write shapes really differ.

🌍 Real-World Best Practice

In practice, teams find where the time goes and which fields really need strict consistency before splitting models. A typical sequence looks like this:

  • Step 0 — Profile and classify: identify the slowest read queries, and which fields need strict consistency (price, inventory) versus loose (tags, content).
  • Step 1 — CDN and cache for hot pages: edge caching with short TTLs and stale-while-revalidate removes a large share of load cheaply.
  • Step 2 — Outbox and event log: publish versioned ProductChanged events from the write store.
  • Step 3 — Regional read models: choose the store per query type, for example a document store for product pages, a search engine for search and a key-value store for personalization features.
  • Step 4 — Staleness SLOs: per-region lag metrics, alert thresholds and a documented degraded mode.
  • Step 5 — Authoritative checks: cart and checkout re-validate price and inventory against the write service or a strongly consistent inventory service.
  • Step 6 — Rebuild and backfill tooling: replay from the log and rebuild read models blue/green when schemas change.

Add the read-model layer where profiling shows joins and aggregations dominate, not by default.

💡

Key Takeaway

When reads outnumber writes by orders of magnitude and the queries are expensive, stop recomputing answers at read time. Keep a small authoritative write path, project changes into regional, query-shaped read models, and measure staleness explicitly. Re-check the few fields that must be exact (price and inventory) at the moment of purchase.
