Counting at Scale: Maintaining Fast Reads Without Sacrificing Correctness

Priya is a backend engineer for a social app where every like and comment is stored as an individual event row in a central OLTP table with tens of millions of rows and thousands of writes per second. The post detail screen must show counts with sub-50 ms reads. A few seconds of staleness is fine, but counts must be auditable and reconcilable against the event table, which remains the source of truth. A handful of viral posts receive thousands of events per second each, and users can also unlike or delete comments. Running COUNT(*) on the main table is slow and is hurting write throughput. Which strategy should she adopt?

A
Execute optimized SQL COUNT(*)/COUNT(id) queries on the primary database or its read replicas, implementing appropriate indexes or partitions, and caching the results with short TTLs. Perform these queries synchronously to guarantee the most current value is always retrieved from the database.
✗ Not Best
B
Include a counter column in the posts table and update it synchronously as part of the same database transaction that records the user event (a single-row atomic increment). Read operations will then fetch this authoritative value directly from the table to ensure strong consistency.
✗ Not Best
C
Publish write events (such as likes and comments) to a persistent event stream (using CDC or application-level events). Utilize a scalable stream consumer to aggregate these increments into a distributed key-value store (like Redis or Cassandra) or a materialized view. Serve read requests from this pre-aggregated store and schedule periodic reconciliation jobs to recount from the primary database, correcting any drift. Ensure consumers are idempotent and actively monitor consumer lag and reconciliation discrepancies.
✓ Best Answer
D
Employ approximate counting algorithms (such as HyperLogLog) or maintain data sketches to achieve extremely fast, memory-efficient counting. Serve these approximate counts to users to bypass querying the primary database entirely, thereby minimizing write contention.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — C: Event Stream to Pre-Aggregated Counters + Reconciliation

The event table already is the ledger, and the count is a derived read model. Option C treats it that way: increments flow through a durable stream into a store optimized for reads, and a reconciliation job proves the derived value against the ledger. It satisfies every requirement at once: sub-50 ms reads, seconds-level staleness, auditability, and no extra load or contention on the write path. Here's why it stands out:

  • Reads are O(1): A key lookup in Redis or Cassandra typically returns in about a millisecond, far inside the 50 ms budget and independent of how large the event table grows.
  • No write-path contention: Events are plain appends. There is no row lock on a hot post row, so viral posts do not serialize their writers (unlike a counter column).
  • Hot keys are absorbable: Consumers can batch increments, and one Redis shard handles on the order of 100k operations per second. An extremely hot counter can be sharded into N sub-counters and summed on read.
  • Auditable by construction: The count is a function of the events. A reconciliation job recounts from the event table up to a watermark, measures drift, logs it, alerts on it, and corrects it.
  • Fault-tolerant and replayable: The stream is durable. If the counter store is lost or corrupted, rebuild it by replaying events or recounting. Idempotent consumers keyed by event ID make redelivery harmless.
  • Observable: Consumer lag and drift are explicit metrics you can graph and alert on.

Make the counter a derived, rebuildable projection: a durable event log, idempotent batched consumers, watermark-based reconciliation, and alerts on consumer lag and drift. The event table remains the only source of truth.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🧮

A — Optimized COUNT(*) with Indexes and Short-TTL Caching

Even with indexes, partitions, and caching, COUNT(*) is O(n) in the rows that match the post. For a viral post with millions of likes, every cache miss scans millions of index entries, and the requirement for an 'always current' synchronous value conflicts with caching. Running it on replicas protects the primary but not the replicas. It cannot reliably hit 50 ms for hot posts. Caveat: for posts with a few thousand events, an indexed count with a TTL cache is perfectly fine, and it is a good fallback path for cache misses.

➕

B — Synchronous Counter Column in the Same Transaction

A counter column updated in the same transaction is simple and exactly consistent, but every like on a post runs UPDATE posts SET like_count = like_count + 1 against the same row. Row locks serialize those writers, so a viral post is capped by how fast one transaction at a time can commit, and lock waits spill into write latency. That is the very thing Priya is trying to protect. It also drags the hot post row into every write. Caveat: for moderate write rates per post it is a great choice: simple, transactional, and auditable. Sharded counter rows (N rows per post) extend its range.

🎯

D — Approximate Counting (HyperLogLog / Sketches)

HyperLogLog estimates the number of distinct elements, with roughly 1% error, and it cannot remove elements, so it cannot represent unlikes or deleted comments. A total comment count is not a distinct count at all. Approximate counts are also not auditable or reconcilable, which the requirements demand, and skipping the primary database entirely removes any way to verify correctness. Caveat: sketches are the right tool for unique-visitor and impression counts, where a small error is acceptable.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — COUNT(*) + TTL Cache

Small or cold datasets, admin and analytics queries, or as the cache-miss fallback path, with no extra infrastructure.

📌

B — Synchronous Counter Column

Moderate write rates per entity, a need for strong consistency, and a small team. Extend with sharded counter rows if specific rows heat up.

📌

C — Stream + Pre-Aggregated Store

High write volume, viral hot keys, strict read latency, and a requirement for auditable, rebuildable counts.

📌

D — Approximate Sketches

Unique visitors, impressions, and other cardinality estimates where small error is fine and removals do not matter.

⚠️ Common Mistakes to Avoid

  • Non-idempotent increments: At-least-once delivery turns every redelivery into a double count. Dedupe by event ID or apply the offset atomically with the counter.
  • Reconciling without a watermark: Comparing a live counter with a live COUNT(*) shows false drift from in-flight events. Compare at a recorded event sequence.
  • Ignoring toggles and deletes: Unlike and delete events must decrement exactly once. Enforce uniqueness on (user_id, post_id) in the source table.
  • Hot-key meltdown: One key for a viral post on one shard becomes the bottleneck. Batch increments, shard the counter, and add a short-TTL in-process cache.
  • No cold-start story: An evicted or missing counter that returns 0 shows wrong numbers. Fall back to a database count, backfill, and coalesce concurrent requests.
  • Treating the counter as the source of truth: Counters can drift. Never 'fix' one by hand-editing it without recounting from the events.
  • Not monitoring lag and drift: Without alerts, counts go stale or wrong silently.

🌍 Real-World Best Practice

Large social platforms layer several techniques depending on how hot a key is:

  • Step 0 - Classify counters: Exact and auditable (likes, comments, balances) versus approximate (impressions, unique viewers).
  • Step 1 - Cheap path first: For cold posts, a counter column or an indexed count plus cache is fine. Do not over-engineer.
  • Step 2 - Event stream: Emit events (or use CDC) keyed by post ID into Kafka or Kinesis so each post's events stay ordered within one partition.
  • Step 3 - Aggregating consumers: Apply increments idempotently (a Lua script that does SET NX on the event ID, then increments) into Redis, Cassandra counters, or a materialized view.
  • Step 4 - Protect hot keys: Shard the counter into N sub-keys and sum on read, or add a short-TTL in-process cache for viral posts.
  • Step 5 - Reconcile: Recount recently active posts up to a watermark on a schedule, auto-correct small drift, and alert on large drift.

Counts are a read model: cheap to serve and rebuildable from the ledger.

💡

Key Takeaway

Do not count on the read path and do not increment on the write path. Keep events as the ledger, derive counts with an idempotent stream aggregator into a fast key-value store, and prove them with watermark-based reconciliation. This gives sub-50 ms reads, seconds of staleness, auditability, and no new contention on the write path.
