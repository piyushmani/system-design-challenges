Speeding Up Complex SQL Built on Subqueries and CTEs

Sneha, a backend engineer, owns a reporting endpoint backed by a large SQL query with several nested and correlated subqueries and a chain of Common Table Expressions (CTEs). As the tables have grown, the query has gone from milliseconds to several seconds, and EXPLAIN shows the subqueries being evaluated over and over. The data changes often and users expect current results. What should Sneha try first?

A
Rewrite the subqueries as joins so the optimizer can plan the query as a single set-based operation.
✓ Best Answer
B
Create materialized views that precompute and store the subquery results.
✗ Not Best
C
Add an application-level cache that temporarily stores the subquery results.
✗ Not Best
D
Partition the underlying tables so the subqueries can run in parallel.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — A: Rewrite Subqueries as Joins

Rewriting correlated subqueries and opaque CTE chains as joins fixes the root cause, which is the shape of the query, instead of hiding it. Here's why it's the right first move:

  • **Eliminates row-by-row execution:** A correlated subquery in the SELECT or WHERE clause can run once per outer row, which is effectively an N+1 problem inside the database. A join (or a join against a pre-aggregated derived table) runs once as a set operation.
  • **Unlocks better join algorithms:** Once the query is written as joins, the planner can pick hash joins or merge joins, reorder tables, and push predicates down. None of that is possible while the logic is locked inside subqueries.
  • **Removes optimization fences:** Some engines materialize CTEs as written (PostgreSQL before version 12, or any CTE marked MATERIALIZED), which blocks predicate pushdown and index use. Inlining them or converting them to joins lets filters reach the base tables.
  • **No staleness, no new infrastructure:** Results stay fully up to date, there's nothing to refresh or invalidate, and the change is a single query rewrite that's easy to roll back.

Sneha should compare EXPLAIN ANALYZE output before and after, make sure the joins are backed by indexes on the join and filter columns, and watch for duplicated rows. Where a one-to-many join would multiply rows, aggregate first or use EXISTS/semi-joins.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🗂️

B — Materialized Views

Materialized views trade freshness for speed: results are only as current as the last REFRESH, and refreshing a complex view can be expensive and lock-heavy. With data that changes often and users expecting current results, that's a poor first step. It also leaves the inefficient query in place, just running on a schedule.

💾

C — Application Cache

Caching hides the slow query instead of fixing it. Every cache miss and expiry still runs the multi-second query, invalidation is tricky when the data changes often, and reporting queries with many parameter combinations get low hit rates.

🧩

D — Table Partitioning

Partitioning helps when queries can skip partitions based on a key such as date. It doesn't stop a correlated subquery from running once per row, and it adds significant schema and operational complexity. Running a badly shaped plan in parallel just spends more CPU on the same wasted work.

⚡

A — Rewrite Subqueries as Joins ✓

Rewrite the subqueries as joins so the optimizer can plan the query as a single set-based operation.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Rewrite as Joins

Queries with correlated subqueries, repeated subplans, or CTE chains that block optimization, where the data must be fresh. Always try this first.

📌

B — Materialized Views

Expensive aggregations over large, slowly changing data where results can be minutes or hours old: dashboards, daily reports, leaderboards.

📌

C — Application Cache

The same query with the same parameters requested repeatedly, where brief staleness is acceptable and the query has already been optimized.

📌

D — Table Partitioning

Very large tables (hundreds of millions of rows) where queries naturally filter on the partition key, such as date ranges on event or log tables.

⚠️ Common Mistakes to Avoid

  • **Assuming CTEs are always optimized away:** This depends on the engine and version, and some engines materialize CTEs and block predicate pushdown. Check the plan.
  • **Duplicate rows from join fan-out:** Replacing a scalar subquery with a join to a one-to-many table multiplies rows and inflates aggregates. Aggregate in a derived table first, or use EXISTS.
  • **Using NOT IN with nullable columns:** NOT IN returns no rows if the subquery produces a NULL. Use NOT EXISTS or an anti-join instead.
  • **Optimizing without measuring:** A rewrite that looks cleaner isn't always faster. Compare EXPLAIN ANALYZE output and timings on production-like data.
  • **Missing indexes on join keys:** A query rewritten with joins can still be slow if the join and filter columns aren't indexed.
  • **Reaching for materialized views first:** Precomputing a badly written query just moves the slowness into the refresh job.

🌍 Real-World Best Practice

Experienced engineers tune SQL in a set order, from cheap and safe to expensive and structural:

  • **Step 1 — Profile:** Run EXPLAIN ANALYZE to find repeated subplans, sequential scans, and row estimates that don't match reality.
  • **Step 2 — Rewrite:** Turn correlated subqueries into joins or semi-joins, inline CTEs, and aggregate before joining.
  • **Step 3 — Index:** Add indexes that support the new join and filter columns.
  • **Step 4 — Precompute:** Only if the query is still too slow and some staleness is acceptable, add materialized views or caching for the heaviest aggregates.

Rewriting the query is the highest-leverage, lowest-risk fix. Materialized views, caching, and partitioning are for later, once the query itself is efficient.

💡

Key Takeaway

Before adding infrastructure, fix the shape of the query. Turning per-row subqueries into set-based joins often speeds things up 10×–100×, with no staleness and nothing new to operate.
