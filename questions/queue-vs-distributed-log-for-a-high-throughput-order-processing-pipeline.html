Challenge

Queue vs. Distributed Log for a High-Throughput Order-Processing Pipeline

Diego, a senior backend engineer, is building the core order pipeline for a fast-growing e-commerce site. At peak it must handle about 100k events per second, preserve chronological order per order, keep end-to-end latency between sub-second and a few seconds for shipping, payments, and inventory, and let teams replay history for analytics and debugging. Several independent teams consume the same events, consumers must scale horizontally, consumer lag must be observable, and the system must survive an availability-zone failure. He must pick the messaging architecture (traditional queue, distributed log, hybrid, or in-memory stream) that best balances scalability, latency, ordering, consistency, replayability, and operational simplicity.

Traditional queues (SQS or RabbitMQ): one queue per downstream service, consumers acknowledge to delete messages, with dead-letter queues and FIFO queues where ordering is critical.

Answer & In-Depth Explanation

🏆 Best Answer — B: Distributed Partitioned Log (Kafka or Pulsar)

The requirements (100k events per second, per-order ordering, replay, several independent consumers, observable lag, zone resilience) describe a distributed, partitioned, replicated log. Partitioning by order ID gives ordering where it is needed and parallelism everywhere else, retention provides replay, and consumer groups let each downstream service progress independently. Here's why it stands out:

  • Ordering and scale together: Events with the same order ID land in one partition and stay ordered, while 100k events per second is spread across many partitions and brokers. Consumers scale up to the partition count.
  • Replay is built in: Events are retained by time or size instead of being deleted on acknowledgment, so analytics, debugging, and brand-new consumers can rewind to any offset.
  • Fan-out without extra copies: Shipping, payments, inventory, and analytics each read the same log with their own consumer group and offsets, instead of publishers writing to one queue per consumer.
  • Observability and resilience: Consumer lag per partition is a first-class metric, and replication across brokers in different zones (for example replication factor 3, min.insync.replicas=2, acks=all) tolerates a zone failure without losing acknowledged events.
  • Latency is fine: A well-tuned log typically delivers end-to-end latency from a few milliseconds to a few hundred, depending on batching and acknowledgment settings, comfortably inside the sub-second to few-seconds target, so no separate low-latency queue is needed.

A solid design uses order ID as the key, a transactional outbox from the order service to avoid dual-write inconsistencies, idempotent consumers with deduplication by event ID, a dead-letter topic for poison events, and alerts on consumer lag and under-replicated partitions.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

📬

A — Traditional Queues (SQS / RabbitMQ)

Queues excel at work distribution, but messages are deleted after acknowledgment, so there is no replay and a new consumer cannot read history. One queue per service forces publishers (or an SNS or exchange fan-out layer) to duplicate every event. FIFO queues preserve order within a message group but have per-queue throughput limits that make 100k events per second hard without heavy sharding. Caveat: queues are a great fit for task queues, delayed retries, and lower-volume workflows without replay needs.

🔀

C — Hybrid Queue + Stream

The hybrid duplicates infrastructure, adds a mirroring hop that can lag, reorder, or drop events, and creates two sources of truth for the same order history. A log already delivers low enough latency for checkout and payments, so the split solves a problem that does not exist here. Caveat: hybrids make sense when a legacy queue-based system exists and migrating it all at once is not feasible.

⚡

D — In-Memory Streams (Redis Streams)

Redis Streams are fast and simple, but retention is bounded by RAM, replication is asynchronous so acknowledged writes can be lost on failover, and long-horizon replay is costly or impractical. Sharding streams across a cluster and rebalancing consumers are largely manual. Caveat: a good fit for lightweight, short-retention pipelines where occasional loss is tolerable.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Traditional Queues

Task distribution, delayed retries, and workflows that do not need replay or per-key ordering at very high throughput; small teams that want fully managed simplicity.

📌

B — Distributed Log

High-throughput event backbones that need per-key ordering, replay, many independent consumers, and observable lag, such as order, payment, and inventory pipelines.

📌

C — Hybrid Queue + Stream

Migrations from an existing queue-based system, or specific command workflows that need queue semantics (priorities, per-message TTLs) alongside an analytics stream.

📌

D — Redis Streams

Low-latency, short-retention pipelines where data is reproducible and occasional loss on failover is acceptable.

⚠️ Common Mistakes to Avoid

  • Choosing the wrong key: Keying by customer or SKU when ordering is needed per order (or the reverse) breaks guarantees. Choose keys per consumer need.
  • Too few partitions: Partition count caps consumer parallelism and is painful to change later. Size for peak plus headroom.
  • Dual writes from the order service: Writing to the database and the log separately can diverge on a crash. Use the transactional outbox or CDC.
  • Assuming exactly-once covers side effects: Charging a card twice is still possible. Use idempotency keys and deduplicate at the sink.
  • Ignoring consumer lag and rebalances: Slow handlers cause long pauses and rebalance storms. Monitor lag, tune max.poll.interval.ms, and keep handlers fast.
  • Weak durability settings: acks=1 or a low replication factor can lose acknowledged events during a broker or zone failure. Use acks=all, replication factor 3, and min.insync.replicas=2.

🌍 Real-World Best Practice

Mature order platforms usually settle on a log as the backbone and keep queues for task-style work. A typical path:

  • Step 0 — Define the contract: Event schema, key (order ID), ordering and delivery guarantees, retention, and an idempotency strategy per consumer.
  • Step 1 — Size the cluster: Choose partitions for peak throughput and consumer parallelism, replication factor 3 across three zones, with rack awareness enabled.
  • Step 2 — Publish reliably: Use the outbox pattern or CDC so the order database and the log never diverge.
  • Step 3 — Build idempotent consumers: Deduplicate by event ID or sequence number, and use external idempotency keys for payments.
  • Step 4 — Add stream processing where needed: Enrichment, joins, and aggregations with a stream processor such as Kafka Streams or Flink.
  • Step 5 — Operate it: Alert on consumer lag, under-replicated partitions, and rebalance frequency, and rehearse broker failures, zone failures, and replay procedures.

Use queues for jobs and retries, and use the log as the source of truth for events.

💡

Key Takeaway

When you need per-key ordering, replay, and several independent consumers at high throughput, choose a partitioned, replicated log. Key by order ID, make consumers idempotent, and remember that ordering holds per partition and exactly-once ends at the platform boundary.
