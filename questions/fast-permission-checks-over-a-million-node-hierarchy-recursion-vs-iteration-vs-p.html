Fast Permission Checks over a Million-Node Hierarchy: Recursion vs Iteration vs Precomputation

Nora leads backend development for an access-control platform that resolves inherited permissions across an organizational hierarchy with millions of nodes. It handles about 2,000 authorization checks per second with a p95 latency below 50 ms. Permission and hierarchy changes are rare but must take effect within minutes. The hierarchy is deep (tens of levels at most) but can have very large fan-out near the top. Her team is weighing recursive traversals (DFS, recursive SQL or service-to-service calls) against iterative ones (explicit queues, worker loops, precomputed paths). Which design best balances scalability, read latency, availability and write complexity?

A
Execute a synchronous depth-first traversal via recursive calls across microservices (where each service queries its downstream dependencies and aggregates the outcome). This provides strict per-request consistency through real-time computation.
✗ Not Best
B
Conduct the traversal iteratively during the request via a local worker loop or an explicit application-level stack/queue (where a single service dynamically fetches children from the database using breadth-first or depth-first patterns), maintaining brief in-memory state on a per-request basis.
✗ Not Best
C
Leverage a recursive database query (using WITH RECURSIVE or specialized graph database traversals) to determine the entire reachable set in a single execution when requested, and deduce the permissions from that set for each request.
✗ Not Best
D
Pre-calculate and cache the transitive closure or materialized paths (or a denormalized permission read-model) within a high-speed, sharded key-value store, and update it asynchronously via event-driven background tasks or CDC. This makes reads nearly instantaneous lookups, while writes initiate incremental background updates and reconciliation processes.
✓ Best Answer
✅

Answer & In-Depth Explanation

🏆 Best Answer — D: Precomputed Closure in a Sharded Key-Value Store

This workload is the textbook case for moving work from the read path to the write path: reads are frequent and latency-critical, while writes are rare and may take minutes to propagate. Option D precomputes the hierarchy relationship (transitive closure or materialized ancestor paths) so an authorization check becomes a few key lookups instead of a traversal. Here's why it stands out:

  • Latency is independent of hierarchy size: a check reads one node's ancestor path and the relevant grants with a batched multi-get, typically a few milliseconds, instead of paying one round trip per level.
  • Read availability does not depend on live computation: the read path touches only a replicated key-value store, so a slow database or a struggling downstream service does not stall authorization.
  • Scales horizontally: 2,000 requests per second is modest for a sharded key-value store, and capacity grows linearly by adding shards and replicas.
  • Matches the staleness budget: within minutes is exactly what asynchronous CDC-driven updates provide, and the cost of that lag is paid only on rare writes.
  • Recursion disappears from the hot path: traversal happens once, in a background worker, where depth and cycles are easy to bound and where the work can be retried and rate limited.

Keep the relational hierarchy as the source of truth, treat the key-value closure as a rebuildable read model, and monitor propagation lag, check p95 and p99, cache hit rate and reconciliation drift. If lag approaches the minutes budget, alert before users notice.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🔁

A — Recursive Cross-Service DFS

Each level adds a network hop, so latency grows with depth and the p95 is dominated by the slowest call in the chain. Availability multiplies: if each service is 99.9% available, a ten-level chain is roughly 99%. Retries amplify load, cycles or very wide nodes can cause runaway call trees, and timeouts are hard to budget. Strict per-request consistency is real, but it is bought with the very latency SLO the scenario sets.

🔂

B — Iterative Per-Request Traversal

Replacing recursion with an explicit queue fixes stack-depth problems and keeps logic in one service, which is a genuine improvement. But the cost is still one database round trip per level (or per batch of children) on every request, so 2,000 checks per second multiplies into tens of thousands of queries per second against the primary. Tail latency depends on the hierarchy shape, and a wide node near the top can blow the 50 ms budget. Note that inheritance should be resolved by walking up the ancestors (short), not down through children (huge). Caveat: a good bounded fallback for cache misses.

🕸️

C — Recursive SQL or Graph Traversal

WITH RECURSIVE pushes the traversal into the database and removes network hops, but CPU cost and latency still scale with the size of the reachable set, and the work repeats on every request. At 2,000 requests per second the primary becomes the bottleneck, plans vary with data shape, and cycle protection adds overhead. Caveat: fine for admin tooling, audits and for building the read model, just not for the hot authorization path.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Recursive Cross-Service DFS

Tiny hierarchies, low traffic or prototypes where strict real-time consistency matters more than latency and the call graph is shallow.

📌

B — Iterative Per-Request Traversal

Moderate scale, or as the cache-miss fallback; simple to reason about and reasonable when depth is small and the database can absorb the load.

📌

C — Recursive SQL / Graph Query

Admin queries, audits, impact analysis (who can access this subtree) and building or verifying the read model.

📌

D — Precomputed Closure in KV

High-read, low-write authorization with large hierarchies, strict latency SLOs and tolerable propagation delay.

⚠️ Common Mistakes to Avoid

  • Materializing user x node: this explodes storage. Store ancestor paths and grants, and evaluate at check time.
  • Unbounded subtree rewrites: a single re-parent can trigger millions of updates. Batch, throttle and make updates resumable.
  • No reconciliation: missed CDC events silently create wrong permissions. Run periodic recompute-and-compare jobs.
  • Ignoring deny and revocation semantics: slow propagation of a removed permission is a security issue. Provide a fast revocation path.
  • Cold-cache stampedes after deploys: rebuilds under load hit the database. Warm gradually and rate limit fallbacks.
  • No versioning: without a version on decisions, callers cannot detect stale results.

🌍 Real-World Best Practice

Production authorization systems follow the read-optimized, precomputed approach, layered with safeguards. Google's Zanzibar, for example, uses a dedicated precomputed index for deeply nested groups. A typical sequence:

  • Step 0 — Measure: hierarchy depth, fan-out, read/write ratio and the real staleness tolerance.
  • Step 1 — Source of truth: keep the hierarchy and grants in a relational store with an outbox or CDC stream.
  • Step 2 — Build the read model: a worker computes ancestor paths and denormalized grants into the sharded key-value store.
  • Step 3 — Check path: multi-get ancestors and grants, evaluate allow and deny rules, and return the decision with a version.
  • Step 4 — Fallback: on a missing key, run a bounded iterative walk up to the root against the database and repair the entry.
  • Step 5 — Reconcile and observe: sample live checks against a slow, authoritative evaluator, and alert on mismatch rate and propagation lag.

Use a recursive query to build the model, not to serve it.

💡

Key Takeaway

When reads vastly outnumber writes and slight staleness is allowed, precompute at write time so reads are bounded lookups. Keep traversal logic in background workers and continuously verify the read model against the source of truth.
