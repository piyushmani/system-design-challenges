Maya's Pagination Dilemma: Choosing Between Cursor and Offset for a High-Scale Feed

Maya is building the backend for a /user/{id}/feed API in a social app. Feeds contain millions of items, users scroll deep into history, and the system sees heavy concurrent writes (new posts, edits and deletions). The feed is ordered by an immutable key such as creation time plus ID, and the data lives in a database that supports index range scans. The service needs predictable database cost, low tail latency, high availability and enough consistency that users do not see duplicates or skipped items while scrolling. She must choose a pagination approach and supporting architecture.

A
Keep it simple with SQL OFFSET/LIMIT on the primary database, scale reads with replicas, add slow-query alerts, and fall back to the primary when clients demand strong consistency.
✗ Not Best
B
Use keyset (cursor-based) pagination: an opaque cursor encodes a composite sort key (for example created_at DESC, id DESC) and stateless keyset queries fetch the next page. Reads go to replicas, with fallback to the primary for freshness-critical requests, and monitoring for missing-item rates and cursor drift.
✓ Best Answer
C
Build a per-feed in-memory ranking tier with Redis sorted sets (timestamp score with a tie-breaker), paginate with ZRANGE/ZREVRANGE for sub-millisecond reads, update the sets asynchronously from the write stream, and run background reconciliation jobs and metrics to repair mismatches.
✗ Not Best
D
Pre-generate static page snapshots for hot feeds (in a cache or object storage) and serve them by page index, refreshing them periodically or after a write threshold, falling back to dynamic queries for less active feeds, with page-hit and staleness metrics.

Answer & In-Depth Explanation

🏆 Best Answer — B: Keyset (Cursor) Pagination

Given deep scrolling, heavy concurrent writes and the requirement for no duplicates or gaps, keyset (cursor-based) pagination on an indexed, immutable sort key is the best fit. Each page is a short index range scan that starts right after the last seen item, so cost does not grow with scroll depth, and the cursor identifies a position in the sort order rather than a numeric offset that shifts when rows are inserted or deleted. Here's why it stands out:

  • Constant cost per page: A query such as WHERE (created_at, id) < (:c, :i) ORDER BY created_at DESC, id DESC LIMIT 20 seeks directly into the index. Page 1 and page 5,000 cost about the same, whereas OFFSET must read and discard every skipped row.
  • Stable under concurrent writes: Because the cursor is a key position, new posts inserted at the top and deletions above the cursor do not shift the window. Users do not see repeated items or skipped items caused by inserts.
  • Stateless and horizontally scalable: The cursor carries all required state, so any API instance and any replica can serve the next page. There is no server-side session or snapshot to keep alive or fail over.
  • Predictable tail latency: Bounded index scans keep query time and buffer usage predictable, which avoids the long scans that make OFFSET queries spike at deep pages.
  • Works with replicas and is observable: Reads can use replicas, with the primary as a fallback for freshness-critical calls. Metrics on page latency by depth, replica lag, empty-page rates and cursor errors make drift visible.

A solid implementation uses a composite index matching the ORDER BY (for example (user_id, created_at DESC, id DESC)), an opaque, versioned, signed cursor, a fetch of limit plus one row to compute has_more, soft-deleted rows filtered in the query, and metrics on latency by page depth, replica lag, duplicate and missing-item reports, and cursor decode errors.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

📉

A — OFFSET/LIMIT with Replicas

OFFSET forces the database to scan and discard all skipped rows, so cost grows linearly with depth and deep pages become slow and spiky. Under concurrent writes the offset window shifts, so users see duplicates or skipped items. Replicas add capacity but also add lag, and they do not change the per-query cost. Caveat: OFFSET is fine for small, mostly static datasets, admin tools and shallow, page-numbered lists.

⚡

C — Redis Sorted Sets per Feed

Sorted sets give very fast range reads, and this is a real pattern for precomputed feeds. But it adds a second source of truth that must be kept in sync with edits and deletes through asynchronous workers, so drift, ordering mismatches and repair jobs become your problem. Memory cost for millions of items per feed can be high, and Redis availability becomes part of the feed's availability. Caveat: for ranked, fan-out-on-write feeds, a cache tier in front of keyset pagination (for the first pages) can be a worthwhile optimization once the database path is solid.

🗂️

D — Materialized Page Snapshots

Page-index snapshots are cheap to serve, but they are inherently stale and fragile under writes: inserting one post shifts every later page, so either snapshots refresh constantly (cost) or users see overlaps and gaps between pages generated at different times. Storage and invalidation grow with the number of feeds and pages. Caveat: caching the first page or two of a very hot feed is effective, because most users never scroll deeper.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — OFFSET/LIMIT

Small or rarely changing datasets, admin tables and UIs that need numbered pages and random access at shallow depth.

📌

B — Keyset Cursor

Large, write-heavy, append-mostly feeds with infinite scroll and API clients (mobile, web) that need predictable cost at any depth.

📌

C — Redis Sorted Sets

Ranked or fan-out-on-write feeds where ordering is computed (scores, personalization) and sub-millisecond reads justify the cost of a derived store.

📌

D — Page Snapshots

Very hot, widely shared feeds or public timelines where the first pages are requested by many users and slight staleness is acceptable.

⚠️ Common Mistakes to Avoid

  • Ordering by a non-unique column: Sorting by created_at alone drops or repeats rows that share a timestamp. Add a unique tiebreaker such as the ID and use both in the cursor.
  • Sorting by a mutable field: An edit that changes the sort key moves the item between pages. Sort by an immutable key or snapshot the score.
  • Index does not match the ORDER BY: A mismatch forces a sort step and removes the performance benefit. Create the composite index in the same column order and direction.
  • Transparent cursors: Letting clients build or modify cursors locks you into the format and opens the door to tampering. Use opaque, versioned and signed cursors.
  • Ignoring replica lag: A page from a lagging replica can skip recent items or return deleted ones. Pass a freshness hint or use the primary for read-your-writes.
  • Computing has_more incorrectly: Guessing end-of-feed from a short page fails when items are filtered after the query. Fetch one extra row and filter inside the query.

🌍 Real-World Best Practice

In practice, large feeds (social, messaging, activity streams) paginate by position, not by number. A typical sequence looks like this:

  • Step 0 — Define the ordering: Choose an immutable sort key with a unique tiebreaker. Decide whether the feed is chronological or ranked, since ranked feeds need a snapshot or a score in the key.
  • Step 1 — Add a matching index: A composite index that mirrors the filter and ORDER BY exactly, so each page is a pure index range scan.
  • Step 2 — Implement opaque cursors: Encode the last key (plus a version and an optional freshness token), sign it, and treat it as opaque to clients so the format can evolve.
  • Step 3 — Route reads sensibly: Serve pages from replicas, use the primary for the first page after a write, and handle replica lag explicitly.
  • Step 4 — Cache the head of the feed: The first pages are the hottest. Cache them with short TTLs or invalidate on write, and keep keyset queries for everything deeper.
  • Step 5 — Monitor correctness, not just speed: Track latency by page depth, replica lag, duplicate or missing-item reports and empty-page rates, and repair feeds if drift is detected.

Paginate by position in the sort order, not by how many rows to skip.

💡

Key Takeaway

Use keyset (cursor) pagination on an indexed, immutable composite key. It gives constant per-page cost at any depth, stable results under concurrent writes, stateless scaling across replicas, and predictable tail latency. Add caching for the hottest pages if needed, but avoid OFFSET at depth and avoid maintaining a second derived feed store unless you need its ranking capabilities.
