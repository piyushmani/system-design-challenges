Safely Extracting the Orders Domain from a Monolith with the Strangler Fig Pattern

Asha, a senior backend developer, is extracting the Orders domain from a large e-commerce monolith using the Strangler Fig Pattern. The monolith owns all order writes and the primary Orders table. Read traffic is very high and latency-sensitive, some writes (inventory reduction, payment capture) require strict correctness, and production peaks at thousands of writes per second. Her goals are to (1) minimize user-visible downtime, (2) let the new Orders service own its schema and deployments, and (3) keep latency and availability acceptable. Which migration architecture best delivers independence, safety and manageable operational complexity?

A
Deploy a lightweight API gateway that directs all write operations to the existing monolith's database, while routing read queries to the new Orders microservice, which directly accesses the monolith's database. This shared-database strategy sidesteps initial data synchronization efforts and maintains the monolith as the source of truth for writes.
✗ Not Best
B
Provide the new Orders service with an independent database and utilize Change Data Capture (CDC) or the outbox pattern to stream write events from the monolith into a log like Kafka. The new service consumes these events to construct its own replica of the Orders data. Once validated, gradually transition write authority to the new service using an event-driven, eventually consistent approach.
✓ Best Answer
C
Execute synchronous dual-writes from the API layer to both the new Orders service database and the monolith DB. Use a transactional coordinator or a two-phase commit protocol to enforce strong consistency across both data stores throughout the migration process.
✗ Not Best
D
Maintain the monolith as the exclusive writer and design the new Orders service purely as a read-only materialized view that is refreshed by scheduled batch ETL jobs every few minutes. Direct client read requests to the new service for fast responses, keeping all write operations on the monolith until a complete cutover is feasible.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — B: Own Database via CDC/Outbox, Then Shift Write Authority

The Strangler Fig works by growing the new system alongside the old one and shifting traffic gradually, with the ability to back out at any step. Of the four options, only B gives the new service its own database (the autonomy goal) while keeping the monolith as the safe source of truth until the replica is proven. An outbox written in the same local transaction as the order, or CDC on the monolith's log, produces a reliable event stream without dual writes or distributed transactions. Reads move first, and write authority moves later, one cohort at a time. Here's why it stands out:

  • Real autonomy: The Orders service owns its schema, migrations and release cadence from the start. No shared tables means a monolith schema change cannot break it, and vice versa.
  • Reversible, low-risk migration: The monolith stays authoritative while the replica fills and is validated through shadow reads and diffing. Reads are cut over gradually with feature flags, and rollback is a routing change.
  • No distributed transaction: The outbox row commits atomically with the order in the monolith's own database, and a CDC tool such as Debezium publishes it. This avoids both the divergence of naive dual writes and the blocking behavior of two-phase commit.
  • Reads scale independently: The new service can use a read-optimized schema and its own caches and replicas, which directly serves the very high, latency-sensitive read traffic without loading the monolith's database.
  • Observable and rebuildable: Event-stream lag, per-event versions and mismatch counts show migration health, and replaying the log rebuilds the replica after a bug or schema change.

A well-designed migration includes a routing facade, an outbox with a versioned event contract, idempotent and version-checked consumers, shadow reads with automated diffing, cohort-based cutover with ownership fencing, reverse sync for legacy consumers, and rollback drills. Track replication lag p99, read mismatch rate, write error rate per cohort and rollback time. Do not retire the monolith's tables until mismatch has stayed at zero for a full business cycle.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

⛓️

A — Shared Database Behind a Gateway

It skips data synchronization, but the new service cannot evolve its schema independently, so goal (2) fails. Monolith schema changes can break the service, both compete for locks and capacity on the same database, and the coupling is hidden (a distributed monolith). Caveat: as a short-lived, read-only stepping stone, for example through database views while the real data extraction is prepared, it can be a pragmatic first step. It should not be the destination.

⚖️

C — Synchronous Dual-Writes with 2PC

Two-phase commit across two databases blocks participants when the coordinator fails, lowers availability and adds latency at thousands of writes per second, and many managed databases and ORMs do not support it well. Dual-writing from the API layer without 2PC is worse: a failure between writes leaves the stores permanently different. An outbox plus idempotent consumers, and sagas for business invariants, avoid both problems.

⏱️

D — Read-Only View via Batch ETL

Minutes-old data means users cannot see an order they just created, and the approach never moves writes, so the new service gains no schema autonomy where it matters. It is a reasonable first milestone for proving the read model, and a fine permanent design for staleness-tolerant views such as reporting or search, but it is not a migration architecture on its own.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — Shared Database

A short-lived, read-only stepping stone (for example via views) while preparing real data extraction, or when the team cannot yet operate an event platform.

📌

B — Own DB via CDC/Outbox

Extracting a core, high-traffic domain with strict write correctness, where independence and a safe, reversible rollout are required.

📌

C — Dual-Writes with 2PC

Rarely: both stores support XA transactions, write rates are low, and the coordinator's availability impact is acceptable. Usually avoid.

📌

D — Batch ETL Read View

Staleness-tolerant read models such as reporting or search, or as a first milestone to prove the read model before building streaming.

⚠️ Common Mistakes to Avoid

  • Attempting a big-bang cutover: The pattern's value is incremental risk. Move traffic by route or cohort so every step can be reversed quickly.
  • Dual-writing from application code without an outbox: A crash between the two writes leaves the systems different with no record of it. Write the event in the same local transaction as the data.
  • Exposing the monolith's table schema as the contract: Raw CDC couples consumers to internal columns. Publish explicit, versioned events through an outbox.
  • Non-idempotent or unordered consumers: Redelivery and reordering are normal. Partition by order ID and ignore events whose version is not newer than what is stored.
  • Two writers at once during handoff: Without ownership fencing and draining, concurrent writes in both systems cause lost updates. Flip one cohort at a time.
  • No shadow comparison or reconciliation: If you never compare old and new answers, you find divergence in production. Diff automatically and track mismatch rate.

🌍 Real-World Best Practice

Successful extractions are incremental and verified at every step. A typical sequence looks like this:

  • Step 0 — Map boundaries and data ownership: Identify the Orders aggregates and find every reader and writer of the Orders table using query logs and code search before promising independence.
  • Step 1 — Insert a routing facade: Put an API gateway or proxy in front of the monolith with no behavior change, so traffic can later be redirected per route or cohort.
  • Step 2 — Build the data pipeline: Outbox plus CDC into Kafka, a consistent backfill, the new service's read model, and shadow reads that compare old and new answers.
  • Step 3 — Cut over reads gradually: Feature-flag reads by cohort, keep the monolith as fallback, and watch mismatch and latency.
  • Step 4 — Move writes cohort by cohort: Ownership flag with fencing, reverse sync to the monolith, and sagas with idempotent commands for inventory and payment.
  • Step 5 — Decommission: Stop reverse sync, remove the monolith's Orders code and tables, and archive the data once mismatch has been zero for a full business cycle.

Move reads before writes, and move writes one small cohort at a time, always with a tested way back.

💡

Key Takeaway

Give the new service its own database, feed it from the monolith through an outbox or CDC event stream, validate with shadow reads, then move reads and finally writes in small, reversible steps with explicit ownership fencing. Avoid shared databases as a destination, avoid two-phase commit, and handle read-your-writes deliberately. A batch-refreshed read-only view is fine as a first milestone but not as the end state.
