BCNF vs Speed: Architecting a membership service for global auth checks

Ravi, a backend architect at a growing SaaS company, runs a membership service (users, accounts, organizations, roles, permissions, memberships) that is consulted on every API request for authorization. The OLTP database is BCNF-normalized to prevent anomalies, but auth checks need multi-table joins, which raises primary-DB load and latency. Requirements: sub-100 ms authorization checks, millions of users, cross-region high availability, and simple observability. Permission changes are infrequent compared with checks, and the product can accept a short, bounded propagation delay (seconds) for most changes, as long as revocations take effect quickly and are never silently lost. He must pick a schema and architecture that balances scalability, latency, and correctness, and keeps failures observable and recoverable.

A
Keep the BCNF schema in one strongly consistent primary database, using serializable isolation or distributed transactions (2PC) for correctness, scale reads with synchronous read replicas, and mitigate join cost with heavy indexing and query tuning.
✗ Not Best
B
Flatten everything into one read-optimized table (a row per user-and-organization pair combining role, membership, and user data), updated synchronously inside the write transactions so reads are single-row, fully consistent lookups.
✗ Not Best
C
Adopt event-driven CQRS: keep the BCNF model for writes, publish change events, and asynchronously build denormalized, region-specific materialized views (read models) for authorization reads, keeping writes auditable and simple.
✓ Best Answer
D
Keep BCNF but run scheduled batch jobs that precompute the join results into a distributed in-memory cache (such as Redis) every few seconds, serving auth checks from the cache and falling back to live joins only on a cache miss.
✗ Not Best
✅

Answer & In-Depth Explanation

🏆 Best Answer — C: Event-Driven CQRS with Denormalized Read Models

Ravi has two competing needs that a single schema cannot serve well: the write side needs normalization for correctness, auditability, and clean constraints, while the read side needs a pre-joined, key-addressable answer to 'can user U do action X in organization O?' in a few milliseconds, close to every region. CQRS separates the two models: BCNF remains the source of truth, and each change is published as an event that updates denormalized read models for authorization. Reads become single-key lookups against a local store, the primary database stops serving auth traffic, and the denormalized data is derived, so it can be rebuilt from the source of truth at any time. Here's why it stands out:

  • Latency: An authorization check becomes a key lookup such as (userId, orgId) to effective permissions plus a version, typically a millisecond or a few in a local store, comfortably inside the 100 ms budget even with network overhead.
  • Primary-DB offload: Auth traffic (the bulk of all requests) no longer touches the OLTP database, so writes, admin tools, and reporting keep predictable performance.
  • Correctness is preserved where it matters: Writes still go through the normalized model with its constraints and transactions. Denormalized views are derived data, so an anomaly in a view is repaired by replaying events, not by reconciling divergent copies.
  • Cross-region availability: Each region holds its own read model, so authorization keeps working during cross-region link problems, and a regional failure only affects that region's traffic.
  • Auditable and recoverable: The event stream is a built-in audit trail of who changed what and when, and projections can be rebuilt (replayed) after a bug or schema change, which directly answers the 'observable and recoverable' requirement.
  • Why not flatten inside the OLTP database? Changing a role's permissions touches every user-organization row that uses the role, so writes fan out and hold locks, and the flattened table reintroduces the anomalies BCNF exists to prevent.
  • Proven at scale: Google's Zanzibar authorization system (USENIX ATC 2019) is built around a globally replicated relationship store, precomputed indexes for group membership, and consistency tokens ('zookies'); event-fed, denormalized permission stores apply the same idea at smaller scale.

A mature setup has a transactional outbox or CDC, versioned, idempotent projections, per-region read models, lag and drift monitoring, a rebuild-from-source procedure, and fail-closed behavior. Measure p99 check latency, event-to-visible lag, projection error and dead-letter counts, and periodic read-model-versus-source verification; if lag cannot meet the revocation requirement, narrow the denormalized scope or add targeted synchronous checks for sensitive operations.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🔒

A — BCNF + Serializable/2PC + Sync Replicas

Serializable isolation and 2PC protect write correctness but do not make the joins cheaper; they add locking, coordination, and tail latency, and synchronous cross-region replicas slow every write and reduce availability when a link degrades. Indexing helps, but the primary still carries all auth traffic, so scaling is bounded by one write master. Caveat: for a modest user base in a single region, a well-indexed normalized schema plus a cache is perfectly adequate; add complexity only when measurements demand it.

📋

B — Single Flattened Table

Single-row lookups are fast and consistent, but the table duplicates data across every user-organization row, so a role or permission change fans out into many row updates inside the write transaction. That inflates write latency and lock contention, reintroduces the update anomalies BCNF was chosen to prevent, and does nothing for cross-region read latency because the table still lives in the primary. Caveat: a flattened, synchronously maintained table is reasonable when the fan-out is small and bounded, such as per-user attributes that rarely change.

⏱️

D — Batch Precompute + Redis, Fallback to Joins

Periodic batch precomputation is wasteful (recomputing everything to catch a few changes), gives an unpredictable staleness window, and delays revocation until the next batch. Falling back to real-time joins on a miss sends traffic to the primary exactly when the cache is cold or has failed, which is a stampede risk. Caveat: a change-driven cache (updated per event, with stampede protection) is essentially the CQRS design with a lighter store.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — BCNF + Serializable/2PC

Smaller systems in one region with modest read volume, where indexing and caching are enough and strong, immediate consistency matters more than scale.

📌

B — Flattened Table

Narrow, bounded fan-out cases (per-user attributes or small lookup tables) where synchronous denormalization within one database is simple and cheap.

📌

C — CQRS Read Models

Read-dominated authorization or entitlement checks at scale, with multi-region deployment, a need for audit trails, and tolerance for second-level propagation delay.

📌

D — Batch Precompute + Cache

Quick wins for moderately loaded systems where staleness of several seconds is acceptable and a stampede-safe cache can be added without a new event pipeline.

The write commits state and event together, each region's projector applies versioned events idempotently, and the hot-path check denies when the read model cannot be trusted:

⚠️ Common Mistakes to Avoid

  • Dual writes without an outbox: Updating the database and publishing an event as two steps can lose or duplicate events. Commit the event in the same transaction (outbox) or capture it via CDC.
  • Non-idempotent projectors: Redelivery corrupts the view. Store a per-entity version and ignore older or duplicate events.
  • Fail-open on a missing read model: A cold or lagging store should deny or consult the source of truth, not allow access.
  • No lag or drift monitoring: Without event-to-visible lag and periodic reconciliation, divergence is found by customers. Alert on lag percentiles and compare samples against the source.
  • Over-denormalizing: Caching every permutation bloats the store. Precompute effective permissions per (user, organization) and resolve rarely used paths on demand.
  • No rebuild plan: If projections cannot be rebuilt from the log or a snapshot, a bug becomes a long outage. Rehearse the replay.

🌍 Real-World Best Practice

In practice, teams start simple and separate read and write models only when measurements justify it:

  • Step 0 — Profile the joins: Check EXPLAIN ANALYZE, indexes, and join order. Fix missing indexes first; sometimes a covering index or a single materialized view in the primary solves it.
  • Step 1 — Define the read contract: Specify the exact query ('can U do X in O?'), the allowed staleness, and fail-open versus fail-closed behavior.
  • Step 2 — Outbox or CDC: Capture committed changes (a transactional outbox, or change data capture such as Debezium) into a durable log like Kafka.
  • Step 3 — Build projections: Idempotent consumers write per-region read models (key-value or document stores) keyed by user and organization.
  • Step 4 — Consistency tokens for sensitive paths: Return a version with each write and require reads for sensitive actions to be at least that fresh, as Zanzibar does with zookies.
  • Step 5 — Verify and rebuild: Run drift checks against the source of truth and keep a tested replay procedure.

Denormalize the reads, never the source of truth.

💡

Key Takeaway

Keep the normalized model as the system of record and serve authorization from event-driven, denormalized, per-region read models. You get millisecond checks, offloaded primaries, auditability, and replay-based recovery, in exchange for bounded propagation delay, which you control with outbox publishing, idempotent projections, lag alerts, version tokens for sensitive actions, and fail-closed defaults.
