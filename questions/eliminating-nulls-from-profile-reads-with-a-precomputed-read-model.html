Challenge

Eliminating NULLs from Profile Reads with a Precomputed Read Model

Maya manages the Profile Service in a heavily trafficked microservices architecture. Optional fields (bio, location, avatar_url, display_name) are updated continuously by user edits, analytical backfills, and third-party enrichment. Clients need a stable, definitive display_name (preferred name, then first/last name, then email handle) and must be able to tell whether a value was user-set or derived. Reads vastly outnumber writes, and nulls currently leak into mobile apps and public APIs. The solution must be fast, consistent across clients, observable, and scale to millions of reads per second. Which approach should she implement?

A
Maintain a single canonical relational database and embed COALESCE and DEFAULT logic directly into all SQL read queries (e.g., SELECT COALESCE(display_name, CONCAT(first_name, ' ', last_name), email_handle) AS display_name ...). Allow the database engine to resolve null values dynamically at query time, keeping the write operations straightforward.
✗ Not Best
B
Build a centralized normalization layer within the API. On every request, retrieve the raw profile data from the database or cache and execute the COALESCE and fallback logic directly in the application service code. Cache the fully resolved API responses with brief Time-To-Live (TTL) settings to mitigate load.
✗ Not Best
C
Shift the responsibility for COALESCE logic entirely to the client applications (mobile and web) by returning raw, nullable data from the Profile Service. Thoroughly document the fallback rules and supply presence flags so clients can determine how to handle missing data locally, keeping the backend simple and stateless.
✗ Not Best
D
Construct a denormalized read model leveraging Change Data Capture (CDC) and stream processing. Capture all enrichment events and profile modifications, funneling them through a stream processor that computes the COALESCE logic and outputs the resolved fields alongside presence metadata into a cache or materialized view optimized for reads. Serve all read requests directly from this pre-computed store.
✓ Best Answer
✅

Answer & In-Depth Explanation

🏆 Best Answer — D: CDC-Fed Denormalized Read Model with Precomputed Fallbacks

With reads vastly outnumbering writes, the fallback rule should be computed once per change, not once per read. A CDC-driven read model applies one authoritative resolver to every change, regardless of which writer produced it, and serves the resolved result from a store built for lookups. Here's why this option stands out:

  • Pays the cost at write time: The COALESCE chain runs once per profile change in a stream processor, so the read path becomes a key lookup. That is what makes millions of reads per second feasible.
  • Nulls cannot leak by construction: The API serves only the resolved, validated document. Clients never see raw nullable fields, so no client-side workarounds are needed.
  • Provenance is first-class: The processor emits metadata such as display_name_source = user | derived_first_last | derived_email_handle, directly satisfying the requirement to distinguish explicit from derived values.
  • All writers converge: User input, backfills, and enrichment jobs all change the source of truth; CDC observes every change, so no writer can bypass the rules or forget to apply them.
  • Decoupled and replayable: Reads do not load the OLTP database. If the fallback rules change, replay the change log to rebuild the read model, and measure freshness lag and null-rate directly on the output.

Treat the read model as a versioned, derived view: one resolver, ordered idempotent updates, provenance fields, lag and null-rate monitoring, and a documented rebuild path.

🔍 Why Not the Other Options?

Each alternative is a valid technique — but none addresses the core problem as directly:

🗄️

A — COALESCE in SQL Read Queries

Simple and correct at modest scale, but it makes the database the hot path for every read, recomputing the same fallback millions of times. The logic gets duplicated across queries, ORMs, and services (drift is inevitable). Provenance needs extra CASE expressions, and values enriched in other stores cannot be coalesced in a single query. Fine for a small system, not for millions of reads per second.

🧮

B — API-Layer Normalization with Short-TTL Cache

A strong incremental step: the logic lives in one service and caching reduces load. Weaknesses: every cache miss recomputes from raw data (stampedes at peak), the short TTL trades freshness against load, and any consumer that reads raw data directly bypasses the rules. It does not give a precomputed, replayable source of resolved values.

📱

C — Fallback Logic in Clients

This spreads the problem rather than solving it. iOS, Android, web, and third parties each implement the rules and will drift; old app versions cannot be updated, and any rule change needs a client release. It also leaves the public API returning nullable data, which is the defect being fixed.

🎯 When Would You Pick Each?

Every option is the right answer in a specific context:

📌

A — COALESCE in SQL

Small to medium scale, a single consumer, and simple fallback rules where DB load is not a concern.

📌

B — API Normalization + TTL Cache

A quick, low-risk centralization of rules when read volume is moderate and some staleness is fine. A good first step toward Option D.

📌

C — Client-Side Fallbacks

Purely presentational choices (e.g., placeholder icon or localized wording), never the canonical value contract.

📌

D — CDC Read Model

Read-heavy at very high scale, multiple writers, shared rules and provenance across many consumers, and a need for replayable derivation.

⚠️ Common Mistakes to Avoid

  • No ordering guard: An out-of-order event can overwrite newer data. Use per-key partitioning and version comparison.
  • Ignoring read-your-writes: Users who edit their name and still see the old one will think the system is broken. Handle user-initiated writes explicitly.
  • Treating blank strings as present: Empty or whitespace-only values defeat COALESCE. Normalize with trimming and NULLIF semantics in the resolver.
  • No fallback on read-model miss: A cold or evicted entry should compute on demand, not return nulls.
  • Unversioned resolver logic: Without versions you cannot tell which records need rebuilding after a rule change.
  • Exposing personal data via derived values: Email handles can reveal identity; sanitize.

🌍 Real-World Best Practice

Teams typically evolve toward the read model rather than starting there:

  • Step 0 — Define the contract: Which fields are guaranteed non-null, the fallback order, and the provenance values. Publish it as part of the API schema.
  • Step 1 — One shared resolver: A single library or service that implements the rules, with unit tests for edge cases (blank strings, whitespace, missing names).
  • Step 2 — Normalize at the API with caching: Quick win that removes client workarounds (Option B).
  • Step 3 — CDC and stream processing: Move resolution to the change stream and serve from a precomputed store when read volume or latency demands it.
  • Step 4 — Rebuild and reconcile: Backfill tooling, version tags on the resolver, and a periodic reconciliation job comparing the read model to source.
  • Step 5 — Monitor quality: Null-rate, fallback-rate by source, and replication lag as first-class dashboards.

Centralize the rule, precompute the result, and make the derivation visible.

💡

Key Takeaway

For read-dominated data that needs consistent fallback rules and provenance, compute the resolved view once on change and serve it from a read-optimized store. Start simpler if scale allows, but keep one authoritative resolver.
